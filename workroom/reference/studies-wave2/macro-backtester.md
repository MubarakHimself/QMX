# Sextant — macro-vintage backtester study

Repo: `reference/repos/Sextant` (also referenced as SEXTANT). Licence: **MIT** (Copyright 2026, raphaub-hub). No `.git` directory present in the clone (flat snapshot, no history to inspect) — consistent with the wave-1 catalog flag that this is a very new, single-author, unvetted repo. README footer reads "Built with Claude Code," i.e. it is itself an LLM-authored hobby project, not a maintained library with a track record. Treated as READ ONLY per instructions; nothing here was executed, installed, or run.

## In plain words

1. Sextant is a local Streamlit desktop app: a personal backtester, not a service or library to depend on.
2. Its one genuinely interesting piece is a FRED/ALFRED data provider with two fetch modes: "first" (ALFRED, point-in-time) and "latest" (FRED, revised).
3. In "first" mode it indexes each observation by `realtime_start` — the date the value actually became public — not by the economic reference period.
4. That single design choice is the whole look-ahead defense: downstream code never sees a macro print before the date it was actually released.
5. Everything downstream (normalizer, Parquet store, event-loop data handler) is date-indexed and slices strictly on `current_timestamp`, so the point-in-time discipline established at ingestion is preserved end-to-end.
6. The event loop itself (`MarketEvent → SignalEvent → OrderEvent → FillEvent`) is a textbook single-threaded bar loop; nothing new for QMF here.
7. The no-code "strategy builder" is a CLI wizard that assembles `Condition` objects (LEFT OP RIGHT, with AND logic, crossing operators, latch/persistence) and then code-generates a `.py` strategy file — it does not persist strategies as data (no JSON/YAML schema, no round-trip parse-back).
8. That code-generation choice is the opposite of what QMF's `qmf.spec` wants: QMF needs strategies to remain data (typed, inspectable, diffable) all the way through, not collapse into generated source.
9. Daily-only, no intraday, no live trading, no portfolio optimizer, no multi-timeframe — explicitly out of scope per its own README, and a real gap against QMX's forex/cTrader/prop-firm goals which need finer-than-daily granularity.
10. Verdict: skip the codebase as a dependency or transplant target; borrow exactly one mental model (realtime_start-indexed vintage data) and nothing else.

## Findings per repo

**Sextant** (single repo assigned).

- **FRED/ALFRED vintage adapter** — `app/databank/providers/fred_provider.py`. Two modes:
  - `mode="latest"` (`_fetch_fred_latest`, lines 174-227): calls FRED's own `/series/observations` with server-side `units` transform, indexes by the observation's reference date (`obs["date"]`). This is the "final revision, as if we always knew it" view — it is exactly the shape that produces look-ahead bias if used naively in a backtest.
  - `mode="first"` (`_fetch_alfred`, lines 73-172): calls the same endpoint but with `realtime_start=1776-07-04` / `realtime_end=9999-12-31` to pull **every vintage** of every observation, then does `groupby("obs_date").first()` after sorting by `realtime_start` to keep only the first-ever published value per reference date. Comment: "units intentionnellement absent : FRED refuse la combinaison realtime_start=all + units!=lin" — a real, useful gotcha (ALFRED rejects server-side transforms when pulling all vintages) — so it fetches raw levels and reimplements pc1/pch/ch1/chg (YoY%, period%, YoY-abs, period-abs) client-side, inferring the periodicity from the median gap between observation dates to choose the YoY lag window. **The critical line**: `df = df.set_index("realtime_start").sort_index()` then `df.index.name = "timestamp"` — the DataFrame that flows into the rest of the app is indexed by publication date, not reference date. Output schema is a plain OHLC DataFrame (`open/high/low/close`, all four equal to the same scalar value) so it can reuse the same Parquet/columns contract as price series.
  - Verdict: **sound, well-commented pattern, worth understanding — but thin.** It doesn't model revisions beyond "first vs latest" (no arbitrary as-of query, no revision count, no distinction between routine revision and benchmark/methodology revision), and it silently drops rows where `value` is `.`/empty/None with no logging of how many were dropped (contrast with the CSV normalizer, which does log dropped rows). No tests reference this file (`app/tests/` only covers events/indicators/portfolio/risk, not databank/fred_provider).

- **Point-in-time propagation through the engine** — `app/databank/normalizer.py` and `app/backtest/data/handler.py`. The normalizer enforces one non-negotiable invariant on everything that reaches storage: sorted, deduplicated `DatetimeIndex`, `close` mandatory, OHLC fallback-filled from `close`. It explicitly rejects intraday data ("Le moteur fonctionne en mode daily uniquement") and resamples weekly/monthly to business-day forward-fill. `DataBankHandler` (`app/backtest/data/handler.py` lines 34-217) then builds an **intersection grid** across all primary symbols so every symbol advances on the identical timestamp each bar, and companion/breadth series (which a macro series would be, if used as a strategy input rather than a tradeable) are reindexed onto that same primary calendar and forward-filled (`_load_companion`, lines 195-216), then cut with `df[df.index <= cutoff]` (`_get_companion_bar`, `get_latest_n_bars`). So a macro series ingested via ALFRED's `realtime_start` index, once forward-filled onto the trading calendar, is only ever visible to `on_bar()` up to and including the current bar's date — the no-look-ahead property established at ingestion survives the resample/align/lookup chain. This is the one piece worth studying closely: the discipline is applied consistently at every layer (fetch → normalize → store → lookup), not just at the API call.
  - Verdict: **solid engineering practice, straightforward to imitate conceptually.** The `<=cutoff` boundary check is duplicated three times (`get_latest_bar`, `get_latest_n_bars`, `_get_companion_bar`) rather than centralized, which is a maintainability smell but not a correctness bug as observed.

- **No-code strategy builder / "strategy as data"** — `app/strategy_builder.py` (1400+ lines). `Condition` (lines 109-183) is a plain `__init__`-based class (not even a dataclass) holding `left_type/left_name/left_period/op/right_type/right_value/...logic/lookback/persistence`, with a `human_readable()` renderer. The wizard (`run()`, `_build_conditions()`, etc., from line 1009) walks the user through picks and builds lists of `Condition` objects in memory, then `CodeGenerator.generate_multi()` (from line 467) turns those into **Python source text** written out as a new file under `strategies/`. There is no `to_dict`/`from_dict`, no JSON/YAML serialization of the condition list, no schema versioning — the `Condition` objects exist only transiently to drive string templating; the persisted artifact is generated `.py` source, not the structured description. This means Sextant cannot re-open a strategy in its own builder for editing (it isn't a round-trip), cannot validate a strategy without executing generated code, and cannot diff two strategies except as text diffs of generated Python.
  - Verdict: **useful as a negative example.** Its condition taxonomy (LEFT op RIGHT with typed sides: indicator / series_indicator / series / bar / value, plus `lookback` latch and `persistence` streak fields) is a reasonable enumeration of what a rule-based confluence condition needs to express, and is worth noting as prior art for enumerating condition "shapes" — but the mechanism (codegen to `.py`, not a durable typed schema) is exactly what `qmf.spec`'s typed Confluence schema should NOT do.

- **Event loop / engine** (`app/backtest/engine.py`, `app/backtest/core/events.py`) — standard `MarketEvent → SignalEvent → OrderEvent → FillEvent` dataclass pipeline with a full JSON event log for audit. `SignalEvent` carries an `indicator_snapshot: dict[str, float]` captured at signal time specifically "pour l'audit trail" / "permet de rejouer et vérifier la décision" (events.py lines 79-91) — a reasonable, cheap habit (snapshot the inputs that produced a decision, not just the decision) that generalizes past this specific event-loop shape.
  - Verdict: **competent but unremarkable**; this is the same event-driven backtest architecture as countless other repos (e.g. the classic QSTrader / Zipline lineage) and doesn't extend or improve on it in any way relevant to QMF's "no central backtest engine, per-Book callable components" architecture. QMF explicitly does not want a central engine like this at all.

## Mental models worth borrowing

| Idea | Where (file:lines) | Why for QMF | How QMF implements |
|---|---|---|---|
| Index macro observations by publication/realtime date (`realtime_start`), not by the economic reference period, as the sole no-look-ahead mechanism | `app/databank/providers/fred_provider.py:73-172` (`_fetch_alfred`) | QMF's `qmf.spec` Confluence conditions may reference macro releases (CPI, NFP, rate decisions) as Level/Trigger/Confirmation inputs; if such a component ever reads a macro series, it must only ever see values as of their true release timestamp, never the reference period | A macro-data adapter in QMF should fetch/store observations keyed by an explicit `release_timestamp` (or equivalent "as-of" field) distinct from `period_start`/`period_end`, and any as-of lookup helper must filter strictly `release_timestamp <= current_bar_timestamp` |
| ALFRED rejects server-side value transforms (`units != lin`) when pulling `realtime_start=all` — compute derived transforms (YoY%, MoM%, deltas) client-side after fetching raw levels | `app/databank/providers/fred_provider.py:86-97, 135-159` | Any QMF macro adapter hitting ALFRED/FRED directly will hit this exact API constraint; worth pre-empting rather than rediscovering via a failed 400 | Document the constraint in the adapter's docstring/tests; always fetch `lin` (raw level) when doing full-vintage pulls, and implement transforms as a pure function over the raw series so they can be unit-tested independently of the network call |
| Snapshot the exact inputs (indicator/feature values) that produced a decision, attached to the decision event itself, for later audit/replay | `app/backtest/core/events.py:73-91` (`SignalEvent.indicator_snapshot`) | Debugging a rejected trade or a prop-firm compliance review benefits from being able to reconstruct "what did the strategy actually see" without re-running the whole pipeline | Any QMF signal/decision record (e.g. a Confluence evaluation result) should carry a snapshot dict of the resolved input values at evaluation time, not just the boolean/enum outcome |
| Enumerate condition "sides" as a small closed set of typed shapes (bare indicator, indicator-on-a-companion-series, raw series value, OHLCV bar field, constant) plus temporal modifiers (latch/persistence) | `app/strategy_builder.py:109-183` (`Condition`) | This is a reasonable checklist of what a rule atom in a typed Confluence schema needs to be able to express; useful as a cross-check against qmf.spec's existing condition vocabulary, not as code to copy | Compare qmf.spec's condition/operand enum against this list when reviewing schema completeness; nothing to implement directly, it's a checklist exercise |

## What to avoid

- **Do not adopt Sextant's "strategy as generated Python source" pattern.** Its no-code builder assembles a structured `Condition` list in memory purely as an intermediate step to string-template a `.py` file; the structured representation is discarded, not persisted. This is the direct opposite of QMF's typed Confluence schema goal (strategies must remain inspectable, versionable, diffable data — not collapse into generated source that can only be understood by re-reading generated code).
- **Do not adopt the engine/event-loop architecture wholesale.** It is a single central `BacktestEngine` orchestrating one bar-by-bar loop across all components — exactly the "central backtest engine" shape QMF has explicitly decided against (callable components tested per-Book instead).
- **Do not treat this as a maintained dependency.** No `.git` history in the clone, single author, days old per the wave-1 catalog flag, README explicitly says "Built with Claude Code" (i.e., itself AI-scaffolded) and is a personal/hobby tool ("Use case: Personal use / research"). Fine as a source of mental models to read once; not something to pin as a dependency, fork, or trust for correctness without independent verification.
- **Do not copy the ALFRED look-ahead handling uncritically.** It only distinguishes "first published value" vs. "latest revision" — it has no concept of arbitrary as-of dates between those two poles, no handling of benchmark/methodology revisions vs. routine data revisions, and drops invalid observations (`"."`, empty, `None`) silently with no count/logging (unlike its own CSV normalizer, which does log drops). A QMF macro adapter should go further: support arbitrary as-of queries, and log/count any dropped or invalid observations for auditability.
- **Daily-only design.** Explicitly out of scope for intraday/tick data by its own README. Forex trading via cTrader for a prop-firm goal will need finer granularity than this codebase was ever built to handle — irrelevant as an execution-layer reference for QMX, useful only for the ingestion-layer idea above.
