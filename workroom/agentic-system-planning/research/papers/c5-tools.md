## 1. Tool-R0: Self-Evolving LLM Agents for Tool-Learning from Zero Data (arXiv 2602.21320)

**Core mechanism (faithful):** A self-play RL *training* method, not an agent architecture. A single base LLM (e.g., Qwen2.5-1.5B/3B) is split into two roles initialized from the same weights but trained with **separate parameters**: a **Generator** and a **Solver**. Each self-play iteration: (1) Generator is trained with GRPO to emit grounded, verifiable tool-calling tasks — a `<question>`, an `<available_tools>` JSON tool menu, and a gold `<tool_call_answer>` — conditioned on a sampled task specification `s=(domain, context-type, #tools, #calls)` to prevent mode collapse; reward = format validity + semantic coherence + a **difficulty/curriculum reward** shaped by the frozen Solver's answer uncertainty (band-pass: hard enough to teach, easy enough to verify); (2) the trained Generator is frozen and used to build a deduplicated, difficulty-ordered dataset; (3) the Solver is trained on that dataset with outcome-based (format + accuracy) reward. No human-authored tool-use data is used anywhere.

**Evidence quality:** Empirical, ablated, moderate scale (0.5B–3B models, 5 benchmarks: ToolAlpaca, Seal-Tools, NexusRaven, API-Bank, SNIPS; AST-match scoring). +22.99pp / 92.5% relative gain on Qwen2.5-1.5B; gains generalize across model scale/architecture. Solid ablations show parameter separation and the difficulty reward are both load-bearing (removing either causes real regression, e.g. −17.4pp for shared params). Single research group, single paper — not yet independently replicated.

**What QMA should borrow:** Nothing architectural. This is a *pre-deployment model-training recipe* for improving a base model's raw tool-call competence (schema adherence, argument grounding, multi-step composition) — it happens upstream of any runtime harness/kernel. The one transferable idea: their taxonomy of tool-call failures (structural: wrong tool/arg-count; semantic: wrong values; format: malformed JSON) is a useful failure-mode checklist for QMA's own tool-call validation/telemetry, regardless of whether the underlying model was trained this way.

**What to reject and why:** Treating this as a "tool lifecycle" paper in the proposal→sandbox→registry sense QMA needs — it isn't one. It says nothing about tool creation, versioning, permissions, or registries; "tools" here are ephemeral, synthetic, single-turn benchmark constructs invented by the Generator, not artifacts that persist or get promoted.

**Kernel implications:** None directly — it operates below the harness layer (weights, not runtime). Its only indirect signal: as base-model tool-calling competence improves (via recipes like this), harness-side scaffolding to compensate for weak tool-calling (retry loops, heavy prompt engineering, JSON-repair) becomes less necessary — a data point that *reduces* the case for a heavy kernel-mediated tool-calling correction layer, consistent with what paper 4 finds empirically at the harness level.

## 2. Tool-Making and Self-Evolving LLM Agents in Low-Latency Systems (arXiv 2607.08010)

**Core mechanism (faithful):** An industrial, deployed system (outbound dock alarm triage) that **compiles a repeated agentic sub-loop into a deterministic tool, offline, at build time**. Baseline: a hierarchical architecture (after Eluna) where a main agent walks a decision tree of ~44 SOP nodes, delegating each node to a CodeAct sub-agent that writes/executes code against a live MCP interface, iterating until it returns a verdict (true/false/no-data) — up to 100+ LLM turns per alarm, dominated by the sub-agent re-deriving the same MCP queries every time. The **tool-making pipeline** replaces this per-node loop with a single deterministic function via two grounding mechanisms fed to a tool-maker LLM: (a) a **data-collection trace** — the baseline CodeAct sub-agent run on 3 sampled labeled cases per node, capturing its query code, the live MCP schema/values it observed, and its graded verdict (supplies execution details the human-authored SOP text omits — field names, dtypes, null handling, boundary conventions); (b) a **test–repair loop** — the candidate tool is tested against the node's full labeled training set, a reflector LLM diagnoses failures, the tool-maker rewrites conditioned on the diagnosis, budget of 3 rounds, best-of-N by training pass-rate deployed. Each tool has a uniform signature `(warehouse, timestamp, context) → (verdict, observed value, threshold, explanation)`. At inference the tool-making pipeline runs offline with strong models (GLM-4.7); a separately fine-tuned small model (distilled via rejection-sampled trajectories, including with tools randomly disabled for robustness) calls the resulting tool library in production, with **fallback to the original CodeAct sub-agent on tool failure/missing data**. Before production promotion, candidates run in **shadow mode** (parallel to production, no effect on outcomes, discrepancies human-reviewed).

**Evidence quality:** Strong for an industry paper — real production deployment (>5,000 live alarms since launch), 8,011 train / 8,022 held-out eval cases across 44 nodes (temporal split), pass@1 as the metric, confidence intervals and significance tests reported, four tool-maker LLMs compared, and a genuinely useful negative-space finding: at the 94.5% pass@1 ceiling, remaining errors trace almost entirely to **SOP specification ambiguity**, not code-generation weakness (clarifying the spec + augmenting labeled data pushes an Opus run to 99.9%). This "spec is the bottleneck, not the codegen" result is one of the more load-bearing empirical claims in the whole cluster.

**What QMA should borrow:** This is the closest thing in the cluster to a validated **proposal → sandbox → tests → versioned registry** pipeline for tools:
- Build-time/offline compilation of a repeated agent sub-loop into a narrow, typed, deterministic tool — decoupled from runtime serving and from the agent's own fine-tuning (tools are "model-agnostic and regenerable independently").
- Grounding candidate generation in an *execution trace* (real tool calls against the live interface + graded verdict), not spec text alone — ablations show the trace and repair loop are each independently necessary (removing repair: −9.6pp; removing trace: −5.2pp).
- Mandatory test-repair against a held-out labeled set before promotion, with a fixed round budget and best-of-N selection.
- Shadow deployment + human review as the promotion gate before a tool reaches production, exactly the "review the diff/results before acceptance" pattern QMA's Cordis-leaning design already wants.
- A tool contract with a uniform signature and an explicit `no_data`/failure mode, plus a defined fallback path (to a slower, general sub-agent) when the tool doesn't apply or fails.
- The finding that spec quality dominates residual error rate argues for investing kernel/tooling effort in **spec clarification and edge-case capture**, not just in codegen loops.

**What to reject and why:** The setting is narrow (one SOP-shaped decision-tree domain; the paper itself flags this as an open generalization question) and human oversight remains load-bearing throughout ("we cannot yet guarantee every failure would be caught without human review"). Don't over-generalize the specific 3-round/3-sample budget numbers — they're tuned to this domain's cost/latency profile, not universal constants.

**Kernel implications:** **Demands a build-time/offline kernel hook distinct from the runtime hook.** QMA's plugin kernel needs (at minimum): (1) a way to record execution traces of a generic sandboxed sub-loop as training/grounding data for tool synthesis; (2) an offline tool-compilation phase that is explicitly decoupled from which model is deployed at runtime; (3) a test-repair harness that runs candidate tools against held-out cases before they enter the versioned registry; (4) a shadow-mode execution path (run new tool in parallel with existing behavior, log discrepancies, no side effects) as a first-class kernel primitive, not an ad hoc script; (5) a required fallback/escape hatch from a compiled tool back to a general sandboxed sub-agent when the tool returns "no data" or throws. This is a genuine, evidence-backed case *for* kernel-level machinery (not a simplification argument) — but the machinery it demands is a build/CI-time pipeline plus a shadow-deploy primitive, not a runtime plugin-dispatch layer.

## 3. AgentFactory: A Self-Evolving Framework Through Executable Subagent Accumulation and Reuse (arXiv 2603.18000)

**Core mechanism (faithful):** A **Meta-Agent orchestrator** built on three components: a unified **Skill System** with three tiers — (1) fixed **Meta Skills** for lifecycle ops (`create_subagent`, `run_subagent`, `modify_subagent`, `list_saved_subagents`, `view_subagent_code`, `get_skill_description`, `finish`); (2) fixed **Tool Skills**, static built-ins (`web_search`, `web_reading`, `browser_automation`, `shell_command`, the last with "built-in security checks that flag destructive operations"); (3) dynamic **Subagent Skills** — executable Python scripts the Meta-Agent writes to encapsulate a successful task-solving pattern, each accompanied by a standardized `SKILL.md` doc (functionality, parameters, usage). A **Workspace Manager** gives each task an isolated execution directory so in-progress subagent creation/modification can't corrupt the shared skill library or interfere with concurrent tasks; only on successful completion are results/improved subagents "promoted" from workspace to the persistent library. Three-phase lifecycle: **Install** (no matching subagent exists → Meta-Agent decomposes the task, writes new subagent(s) from scratch, saves them); **Self-Evolve** (a similar task arrives → retrieve via `list_saved_subagents`, run the candidate, if it fails or underperforms, analyze the failure and call `modify_subagent` to patch it, re-validate against the *current* task); **Deploy** (mature subagents are pure Python + `SKILL.md`, runnable standalone, or onboarded into an *entirely different* agent framework — LangChain, AutoGen, or Claude Code — purely by giving that other system a prompt explaining how to read the `SKILL.md` and invoke the script; no code-level integration required). Demonstrated cross-system: a subagent built inside AgentFactory was later invoked successfully from a Claude Code session with zero framework-level glue.

**Evidence quality:** Weak-to-moderate. Small scale — 30 hand-curated tasks (2 batches of 15, Batch 2 = parameterized variants of Batch 1 for transfer measurement), 2 backbone models (Claude Opus 4.6, Sonnet 4.6), one baseline comparison metric: **orchestrator output-token count per task** (not correctness/robustness/safety). The headline result (AgentFactory: 2,971–3,862 tokens/task on Batch 2 "w/ saved" vs. 6,893–7,022 for plain ReAct) is a real efficiency signal but a thin one — "all tasks completed without runtime errors" is asserted, not benchmarked against a held-out failure-inducing set. No statistical testing, no adversarial/OOD evaluation, no comparison to the tool-making paper's rigor (pass@1 on held-out labeled cases, shadow deployment).

**What QMA should borrow:** The **artifact format**, not the governance. A "mind" (QMA's deployable semi-profile) or a subagent it spawns, saved as **plain inspectable code + a standardized companion doc describing interface/usage**, is a genuinely good idea for portability and human auditability — it's literally why the cross-system reuse demo worked (an *unrelated* host framework onboarded the artifact purely via natural-language documentation, no shared runtime). Also worth keeping: the explicit distinction between fixed primitive skills (meta + tool) vs. dynamically accumulated skills, and per-task workspace isolation as the unit of safe mutation (nothing touches the shared registry until the task workspace succeeds).

**What to reject and why:** The promotion gate is thin and should **not** be copied as-is. "Persistence" in Phase 1 is just: "the Meta-Agent evaluates the subagent and decides which skills to save" — a single LLM's self-assessment, no held-out test set, no independent reviewer, no human-in-the-loop step described anywhere in the pipeline (contrast sharply with paper 2's labeled-eval-set + shadow-mode + human-review gate). The only stated safety mechanism for autonomously-generated, autonomously-executed code is `shell_command`'s built-in check for "destructive operations" — the paper's own Ethical Considerations section flags this as a real concern rather than a solved one. If QMA borrows the artifact format, it must bolt on a much stronger promotion gate (independent of the same Meta-Agent's self-judgment) before treating this as a template for tool/skill promotion.

**Kernel implications:** This argues for a **lighter** kernel coupling than a tight Cordis-style plugin-registration model might assume: since a subagent artifact here is *just* code + a doc string, and gets picked up by a completely different host framework purely through prompt-based onboarding, the "kernel hook" it actually needs is minimal — a workspace-isolation/sandboxing primitive for safe mutation, a promote-on-success step, and a discovery mechanism (`list_saved_subagents`-equivalent) — not a rich in-process plugin API. This is a mild but real counter-signal to over-investing in kernel-mediated plugin interfaces when a simpler "self-describing code artifact + natural-language onboarding" pattern demonstrably achieves cross-framework portability. It should not, however, be read as license to skip a real promotion/test gate — that's a governance gap in this paper, not evidence it's unnecessary (paper 2 shows the opposite in a production setting).

## 4. The Bitter Lesson of Tool Calling (arXiv 2608.06370) — located by title

**Core mechanism (faithful):** Not a tool-creation/lifecycle paper — a controlled empirical comparison of two **tool-calling interfaces** for already-existing tools: native **JSON tool calling** (model emits a structured JSON object per call via the provider's tool-calling API) vs. **programmatic tool calling (PTC)** (the model is given typed Python stub functions compiled 1:1 from the tool schemas, writes one Python script that imports and calls them — including loops/`asyncio.gather` for fan-out and intermediate variables for chaining — and the agent loop executes that single script in a shell subprocess in one inference turn; a "stop middleware" prevents any further model turns). Evaluated across 14 models (5 Anthropic, 9 OpenAI, spanning 20 months of releases) on a 309-entry BFCL v4 subset plus three targeted ablations: sequential chaining (2–20 hop chains), parallel fan-out (7–100 calls), and context rot (128 total schemas incl. decoys vs. filtered).

**Evidence quality:** The strongest empirical paper in the cluster for its specific claim — deterministic scorer (sidesteps a documented 20% LLM-judge misalignment issue in BFCL v4), 14 models, matched LLM-call counts between paradigms (fair latency comparison), confidence intervals reported, and it's honest about its own limits (echo-return stubs measure argument-serialization accuracy, not end-to-end correctness with real API side effects; some ablation cells are small, n=31–52). Headline results: PTC matches/exceeds JSON in 11/14 models overall; PTC's advantage on chaining *grows with chain length* (18.8pp absolute gap at ≥12 hops, because JSON pays one inference turn per hop and PTC pays one turn total); **JSON tool calling has a hard structural fan-out ceiling** — for Claude Sonnet 5 it starts dropping calls entirely between N=70 and N=72, while PTC holds 100% enumeration accuracy through N=100; under context-flooding (128 schemas) JSON degrades 2.3% on average while PTC *improves* 5.5% on average. The 3 models that underperform under PTC (GPT-4o, GPT-4.1, GPT-5.4-mini) all share one specific, isolated failure mode (`\n` escape sequences instead of real newlines breaking multiline scripts) — viability tracks **model generation, not model family or vendor**, and the gap is closing/reversed for frontier models (all 5 Anthropic models and the 3 newest GPT models match-or-beat baseline on every ablation).

**What QMA should borrow:** For any provider-unbiased sandbox/computer abstraction QMA designs, treat "expose tools as typed code stubs the model writes-and-executes against in one sandboxed call" as a first-class calling convention alongside (not necessarily instead of) structured JSON/MCP-style dispatch, especially wherever the workload involves chaining or fan-out — the latency and reliability wins there are large and structural, not marginal. Also worth keeping: their fan-out finding is architecture-specific (the JSON drop-off threshold is about how a given model serializes a parallel-call block, not a universal property) — so QMA shouldn't hardcode a universal fan-out limit, but should expect and design for one existing per-model/per-provider under JSON-style dispatch.

**What to reject and why:** Don't treat PTC as strictly dominant — it carries a real ~1.5× fixed input-token overhead on non-fan-out tasks (crossover ≈ N=26 calls), aggregation-type answers can be "correct" via parametric knowledge without actually invoking tools (a scoring artifact the paper itself calls out and controls for by reporting enumeration accuracy separately), and it fails outright on weaker/older models with a specific, currently-uncharacterized code-generation bug class. It is also from a single lab (PwC) evaluating against one benchmark family (BFCL v4) with acknowledged label-noise risk.

**Kernel implications — direct challenge to the Cordis-leaning kernel direction:** This is the one paper in the cluster that should be surfaced prominently rather than smoothed over. It provides real benchmark evidence that, for capable models, **a single sandboxed "execute this code against typed stubs" hook can outperform fine-grained, per-call kernel-mediated tool dispatch** — on accuracy, on latency (fewer inference round-trips), and specifically on the failure modes (fan-out ceilings, context rot from many registered tools) that a plugin-kernel architecture with one-call-at-a-time mediation is most exposed to. If QMA's kernel plans to mediate every tool invocation individually (JSON-schema-style, MCP-style), this paper is evidence that a **simpler alternative** — compile the plugin surface into typed stubs, let the model write one script, execute it once in a sandbox, parse structured stdout — may be both simpler to build and empirically stronger, at least for frontier-generation models, with the caveat that it silently degrades on older/weaker models in a way that's hard to detect without dedicated testing (the `\n`-escaping bug). This doesn't eliminate the need for a kernel (sandboxing, permissioning, and the tool-lifecycle machinery from paper 2 are still real requirements) — but it does argue the *calling convention* at the center of that kernel should be code-execution-first, with structured per-call dispatch as a fallback for weaker models or high-precision/low-fan-out cases, rather than the reverse.

## Cluster verdict

**Top borrowings for QMA:**
1. **Tool-compilation pipeline (paper 2)**: offline/build-time synthesis of a tool from (SOP-like spec + execution-grounding trace), mandatory test-repair against held-out cases, shadow-mode deployment, human review gate, explicit fallback-on-failure. This is the strongest evidenced template for QMA's proposal→sandbox→tests→registry requirement.
2. **Self-describing portable artifact format (paper 3)**: code + companion doc (`SKILL.md`-equivalent) as the unit of a saved subagent/skill, enabling cross-host reuse without shared runtime — but pair it with paper 2's promotion gate, not paper 3's (which is a single self-judging LLM with no held-out test set).
3. **Spec-quality-is-the-bottleneck (paper 2)**: invest kernel/tooling effort in capturing execution-grounding detail and edge cases in tool/skill specs, since that — not codegen ability — was the dominant residual error source at scale.
4. **Failure-mode taxonomy (paper 1)**: structural/semantic/format tool-call error categories, useful for QMA's own tool-call telemetry regardless of training approach.

**Direct challenge to our Cordis-leaning kernel direction (surfaced, not smoothed over):** Paper 4 (Bitter Lesson of Tool Calling) gives controlled multi-model benchmark evidence that a **single sandboxed code-execution call against typed tool stubs** matches-or-beats **structured per-call, kernel-mediated JSON tool dispatch** on accuracy, latency, and — critically — on exactly the failure modes (parallel fan-out ceilings, context rot from many tool schemas) a plugin-kernel with fine-grained per-call mediation is most vulnerable to, for current frontier models. This suggests QMA's kernel should treat "compile the plugin surface to typed stubs, execute one script in a sandbox per turn" as the default/primary calling convention rather than an alternative to fine-grained per-plugin-call dispatch — a real simplification pressure against a heavier one-call-at-a-time plugin-mediation kernel, tempered by the paper's own finding that this degrades unpredictably on older/weaker models (a real reason to keep JSON dispatch available as a fallback, not to discard kernel-level dispatch machinery entirely).
