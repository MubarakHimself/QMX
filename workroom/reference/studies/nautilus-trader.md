# NautilusTrader — deep study for QMF

**Clone studied:** `C:/Users/Mubarak/Desktop/QMX/reference/repos/nautilus_trader`
**Version in clone:** `v2.0.0rc3` (`version.json`) — the `develop` branch, Rust-native, post-Cython.

**Written:** 2026-08-17.

---

## In plain words

1. NautilusTrader is the closest thing in open source to what QMX wants to be: one engine that runs a strategy identically in a backtest and against a real broker.
2. The trick that makes that true is small and copyable. There is a box called the **kernel** that holds a clock, a memory of current state, a message switchboard, and four workers (data, risk, execution, portfolio accounting). The kernel never knows whether it is in a backtest.
3. What changes between backtest and live is only **which clock and which broker plug you push in**. A fake clock that you advance by hand, and a fake broker that fills your orders, versus a real clock and a real broker. Everything above that line is the same code (`crates/system/src/kernel.rs`, `crates/system/src/clock_factory.rs`).
4. This is not a slogan there. The fake broker is *literally the same kind of object* as a real broker adapter, and there is a third mode ("sandbox") that uses real live prices with fake fills, built from the same matching machinery (`crates/adapters/sandbox/src/execution.rs`).
5. A strategy is a class with `on_bar`, `on_quote`, `on_order_filled` methods. It never runs a loop. The framework calls it. That is the same shape QMF wants for Level/Trigger/Confirmation/Exit.
6. Indicators are written once, in "one bar at a time" form. You register an indicator against a chart, and the framework guarantees it is already updated before your `on_bar` runs. There is no separate "batch" version to drift out of sync.
7. Every piece of data carries **two timestamps**: when it happened at the venue, and when this system first knew it. The whole no-lookahead discipline rests on that one pair of fields. Nautilus even publishes the rule for bars: a bar's "known at" time must be the bar's *close*, or the backtest sees the future.
8. Orders that fail get a **stable reason code** — not a free-text error. And failures are sorted into exactly three buckets: "definitely never sent", "the venue definitely said no", and "we honestly do not know". The third bucket is never allowed to invent a rejection. That distinction is the single most valuable thing in the repository for QMX.
9. The whole thing is now **Rust**. About 1.1 million lines of it. The Python you write is a thin skin generated by PyO3 — 49 real Python files in the entire published package, and most of those are one-line re-exports (`python/nautilus_trader/`).
10. That matters for us in two ways. Good: the *shapes* are visible and well-documented, so we can copy the thinking. Bad: we cannot lift anything, both because of the licence and because it is Rust.
11. It is also mid-rewrite. The stable release is still `v1.231.0 **Beta**` (2026-08-02) after ten years, while `develop` is `2.0.0rc3` and has just *deleted* the entire v1 Python layer. Building QMX on it right now means inheriting somebody else's migration.
12. It has no cTrader adapter and no prop-firm rules. Its official adapters are crypto exchanges, Interactive Brokers, Databento, Betfair and Polymarket. Forex through cTrader is our own work regardless (`ADAPTERS.md`).
13. Honest scope for writing our own Python kernel with the same *ideas*: the skeleton (clock, bus, cache, engines, strategy base) is about 2,500 lines and a few weeks. The expensive parts are the order state machine, the simulated fill engine, multi-currency margin accounting, and startup reconciliation — call it 8,000–12,000 lines of careful Python and 3–6 months to production confidence for one venue.
14. Nautilus's own numbers say the same thing from the other side: for every line of production code in its execution engine there are roughly 1.3 lines of test code. That ratio, not the feature list, is what "production-grade" costs.
15. Net recommendation, unchanged from the earlier synthesis but now evidenced: **write QMF's kernel, borrow Nautilus's shapes, and copy its discipline about uncertainty and provenance rather than its architecture diagrams.**

## How it is built

### The kernel

`crates/system/src/kernel.rs` defines `NautilusKernel`, which owns — as shared single-threaded handles (`Rc<RefCell<_>>`) — the clock, the `Cache`, the `Portfolio`, the `DataEngine`, the `RiskEngine`, the `ExecutionEngine`, the `OrderEmulator`, and the `Trader`. Its own doc comment states plainly: *"the kernel is not a cross-thread synchronization boundary."*

The message bus is **not** a field on the kernel. It lives in thread-local storage (`crates/common/src/msgbus/mod.rs`, the `thread_local!` block). Components reach it through free functions. This is why "one node per process" is a documented hard rule (`docs/concepts/architecture.md`, "Processes and threads").

**Startup order** (`kernel.rs::start`, ~line 651, then `start_trader`, ~line 752):

1. optionally restore cache from the event store, open a new event-store run;
2. `start_engines()` — data, risk, execution engines start, and the engines start their clients;
3. `trader.initialize()` — components are registered and wired;
4. *(live only)* connect data clients → let instrument events populate the cache → connect execution clients → reconcile;
5. `start_trader()` — load saved actor/strategy state, start the order emulator, then start strategies; a partial start failure is immediately stopped and the state saved, and the error is raised.

Shutdown is deliberately split into `stop_trader()` (which may emit residual events like cancels, and the caller must keep pumping the loop) and `finalize_stop()` (save state, stop engines, cancel timers, seal the event-store run).

### The environment switch

`crates/system/src/clock_factory.rs` is the whole "backtest ≡ live" mechanism in 155 lines:

- `ClockFactory::for_environment(Environment::Backtest)` → produces `TestClock`s.
- `Environment::Live | Sandbox` → produces `LiveClock`s.
- The *primary* clock is memoized (kernel and trader share one); each component gets a **fresh** clock instance so timer callback registration stays isolated per component.

`Clock` (`crates/common/src/clock.rs`, line 49) is a small trait: `timestamp_ns()`, `set_time_alert(_ns)`, `set_timer(_ns)`, cancel. `TestClock` implements it by holding a `u64` you set; `LiveClock` by reading the system clock and scheduling on Tokio. Nothing above the trait knows which it has.

### The message bus

`crates/common/src/msgbus/` — three patterns: publish/subscribe on wildcard topics, point-to-point to named endpoints, request/response correlated by ID.

- Topics are strings under a `data` root, e.g. `data.quotes.BINANCE.BTCUSDT-PERP`, `data.book.deltas.XCME.ESZ24`.
- Requested/replayed/derived data is published under a **separate** root `data.pipeline.<kind>...` precisely because *"they do not claim the same live ordering and timing semantics as normal real-time publications"* (`docs/concepts/message_bus.md`).
- Matching is `*`/`?` glob with a greedy two-pointer algorithm (`msgbus/matching.rs`) — explicitly chosen over regex and over DP for cost reasons.
- **Messages are immutable after creation**, including their `params` maps. Component workflow state (cursors, counters, grouping) must live in component-owned context keyed by message ID, never written back onto the message. The rationale given is replay, debugging and audit.
- Two dispatch paths coexist: typed (`publish_quote` → handlers receive `&QuoteTick`, zero runtime type checks) and `Any`-based (for custom data and Python interop).

### Data path

`docs/concepts/architecture.md` traces "life of a quote tick": adapter parses → sends `DataEvent` on an MPSC channel → `DataEngine::process_data` → `handle_quote` → **`cache.add_quote(quote)` first** → *then* `publish_quote(topic, quote)` → subscribed strategies' `on_quote`.

**Cache-then-publish** is the invariant: after a successful cache insertion, a handler that asks `self.cache.quote(instrument_id)` sees the same object it was just handed. The doc is honest about the edge: a synchronous persistence error prevents in-memory insertion but the engine still publishes, and database-backed writes are asynchronous so a later DB error does not roll the cache back.

Bar aggregation (`crates/data/src/aggregation.rs`, 9,015 lines) implements `BarAggregator` with `update(price, size, ts_init)` and `update_bar(bar, volume, ts_init)` — time, tick, volume, value, imbalance, runs, and Renko variants, all incremental over a shared `BarBuilder`.

### Execution path

`docs/concepts/architecture.md` traces "life of an order": strategy → `RiskEngine` pre-trade checks → (`OrderDenied` and stop, or) `ExecutionEngine` routes → `ExecutionClient` → venue → events flow back through `ExecutionEngine` (which updates the cache) → message bus → strategy handler → portfolio update.

- `RiskEngine` (`crates/risk/src/engine/mod.rs`) checks precision, price positivity, quantity min/max/precision, notional, balance impact, reduce-only, trading state, and applies submission/modification rate limits. Roughly two dozen distinct `deny_order` call sites.
- Denials are typed. `crates/model/src/events/order/denied_reason.rs` defines `OrderDeniedReason` with a companion generated `OrderDeniedCode` enum. The contract in its doc comment: *"Only the leading code is canonical. Consumers must not recover classification or control flow from the diagnostic suffix."* Message forms are specified (`CODE`, `CODE: value`, `CODE: key=value, key=value`, `CODE: value; free text`).
- `crates/execution/src/order_emulator/` locally emulates order types a venue does not support, holding them against a local matching core and releasing a supported order when triggered. Emitted events: `OrderEmulated`, `OrderReleased`.

### Simulated venue = ordinary adapter

- `crates/execution/src/matching_engine/` (7.5k lines) is the `OrderMatchingEngine` — venue-agnostic.
- `crates/backtest/src/execution_client.rs` implements the shared `ExecutionClient` trait (`crates/common/src/clients/execution.rs`, line 55) on top of it.
- `crates/adapters/sandbox/src/execution.rs` implements the **same trait**, over the **same matching engine**, but driven by live market data.
- Therefore three environments (`Backtest`, `Sandbox`, `Live`) are three wirings of one kernel, not three programs.

Fidelity models are pluggable and named: `crates/execution/src/models/fill.rs`, `fee.rs`, `latency.rs` (`LatencyModel` trait with insert/update/delete/base latencies).

### Backtest driver

`crates/backtest/src/engine.rs::run_impl` (line 700) is the replay loop. Its ordering discipline is the interesting part:

1. Refuse to run if data was added but not sorted.
2. Set **all** component clocks to `start_ns`.
3. On first iteration: initialize accounts, load open orders, start the kernel, `start_trader()`, then **drain the data-command queue until empty** — so that aggregators created in `on_start` are subscribed before the first data point, *"else internal aggregation drops the first tick"*. Trading and execution commands stay queued.
4. Loop: peek the next datum from a min-heap merge of all streams (`crates/backtest/src/data_iterator.rs`, `BinaryHeap` keyed on `ts_init`, then priority, then insertion index); advance clocks to its `ts_init`, firing timers; deliver it to the exchange and to `DataEngine::process_data`; drain deferred command queues; settle venues; when the next timestamp differs, flush accumulated timer events and finalize the timestamp.
5. Logging is switched to a **static clock mode** so log timestamps come from simulated time.

`crates/backtest/src/result.rs` produces a `CanonicalBacktestResult`: a JSON document with a declared schema (`nautilus-backtest-result/v1`), sorted keys, sorted unordered arrays, **identities normalized** (client order IDs, venue order IDs, trade IDs, event IDs, position IDs replaced by class-prefixed ordinals), and a `blake3:` digest over the exact bytes. `from_slice` re-canonicalizes and refuses bytes that are not already canonical. `first_divergence()` reports the first differing field between two runs.

### Live driver

`crates/live/src/runner.rs` owns seven Tokio MPSC channel pairs (time events, system events, system commands, execution events, trading commands, data events, data commands) plus a shutdown signal. The `select!` is **`biased;`** — system and execution branches are polled ahead of data branches, and within each pair, events before commands. Senders live in thread-local storage; the event loop and every TLS consumer must be on one thread.

So: live is asynchronous at the edges (Tokio tasks for sockets, a logging worker, async DB writes) and **synchronous and single-threaded at the core**, exactly like the backtest. `docs/concepts/architecture.md` cites the LMAX single-threaded transaction-processing architecture as the reference.

### Reconciliation

`crates/execution/src/reconciliation/` — only the live execution engine reconciles, *"since backtesting controls both sides"*. Two cases: cached state exists (generate the missing events to close the gap), or no cached state (materialize everything the venue reports). Venue-sourced orders that no strategy claims get strategy ID `EXTERNAL` with tag `VENUE`; ones synthesized during position reconciliation get tag `RECONCILIATION`. A strategy declares `external_order_claims` per instrument to adopt them. `docs/concepts/reconciliation.md` also warns about **bounded history**: if the venue's history window starts *after* the fill that opened a position, adapters that declare their lower bound get a safe path and adapters that do not fall back to a lossy synthetic-event path.

### Cache and event store

`crates/common/src/cache/mod.rs` is 8,221 lines with 392 public methods — instruments, accounts, orders, positions, order lists, synthetic instruments, greeks, and bounded ring buffers of recent quotes/trades/bars, plus a `CacheIndex` of cross-references. Optional Redis/Postgres backing writes asynchronously.

`crates/event_store/` plus `docs/concepts/event_sourcing.md` add a stronger claim: *"The event store is the durable authority for state-affecting history. The cache is a write-through projection, not the source of truth."* Runs are sealed; entries carry a per-run `seq`; a snapshot anchor plus the run tail rebuilds the cache. Market data is explicitly *not* in the event store — it stays in the data catalog.

### Component lifecycle

`crates/common/src/component.rs` defines a finite state machine with stable states `PRE_INITIALIZED / READY / RUNNING / STOPPED / DEGRADED / FAULTED / DISPOSED` and *transitional* states `STARTING / STOPPING / RESUMING / RESETTING / DISPOSING / DEGRADING / FAULTING`. A callback that errors leaves the component parked in its transitional state — except `dispose`, whose failure moves it to `FAULTED` so it can still be retired.

Two traits are deliberately separated (`docs/concepts/architecture.md`, "Actor vs Component"): `Actor` = targeted message dispatch by ID; `Component` = lifecycle. A throttler is Actor-only, the `Trader` is Component-only, a `Strategy` is both.

### Strategy authoring

Python: subclass `Strategy` (a PyO3 class) and override `on_*` handlers. `python/nautilus_trader/trading/__init__.pyi` line 457 shows the surface — about 60 methods: state predicates, `clock` / `cache` / `portfolio` / `order_factory` / `log` accessors, `submit_order`, `modify_order`, `cancel_order(s)`, `close_position(s)`, `market_exit`, `publish_data`, `publish_signal`, `save`/`load`, and the three `register_indicator_for_*`.

Rules that carry over to QMF:

- `clock`, `cache`, `portfolio`, `order_factory` **raise until the strategy is registered with a trader** — so `__init__` may only set plain state; system work belongs in `on_start()`.
- Handlers dispatch most-specific first, then general (`on_order_accepted` → `on_order_event`).
- Data/order/position handlers fire **only while `RUNNING`**; messages in other states are logged and dropped. Request responses are exempt.
- Callbacks are synchronous on the event thread and must return promptly; long work must be offloaded (`docs/concepts/python.md`).

Indicators: `crates/indicators/src/indicator.rs` defines `Indicator` with `name()`, `has_inputs()`, `initialized()`, `handle_quote/trade/bar/delta/depth/book`, `reset()`. Roughly 44 indicators across `average/`, `momentum/`, `volatility/`, `ratio/`. Each keeps its own scalar state and updates in O(1) (`average/ema.rs` is the canonical shape: `has_inputs` seeds the first value, `count >= period` flips `initialized`).

`crates/common/src/actor/indicators.rs` holds the registry: indicators are keyed by `InstrumentId`, and for bars by `(InstrumentId, BarSpecification)`. The framework updates every registered indicator **before** the user's handler runs, and hydrates them from historical request responses before `on_historical_bars`.

### Venue adapters

Every adapter under `crates/adapters/<venue>/src/` follows one skeleton: `config.rs`, `factories.rs`, `data.rs`, `execution.rs`, `common/` (enums, symbol mapping, instrument parsing, credentials, wire models, parse), `http/` (client, error, models, parse, query), `websocket/` (client, auth, dispatch, handler, messages), `python/` (PyO3 exposure).

`docs/developer_guide/adapters.md` is the most transferable document in the repository. It states conformance as a **rule table** — foundations, runtime/lifecycle, execution/reconciliation, transport/streaming — and names a **shared baseline** piece per contract (`CommandFailure`, `OrderIdentity`/`OrderContext`, `FifoCache` for replay dedup, `OrderDeniedReason`, `TaskHandles`, `HttpClient`, `AuthTracker`, `SubscriptionState`, `RetryManager`). It permits exceptions with a condition: *"Name the venue behavior that forces the exception, keep it inside the adapter, and cover it with a test that fails if the venue stops requiring it."*

No cTrader adapter exists. `ADAPTERS.md` lists one *community* MetaTrader 5 connector; official adapters are Architect, Betfair, Binance, BitMEX, Bybit, Coinbase, Databento, Deribit, Derive, dYdX, Hyperliquid, Interactive Brokers, Kraken, Lighter, OKX, Polymarket, Tardis, plus blockchain and sandbox.

### Rust ↔ Python boundary

`docs/concepts/python.md` states the split cleanly:

| Layer | Owns |
|---|---|
| Python application | configuration, composition, user components, analysis |
| PyO3 bindings | type conversion, argument validation, exception translation, ownership-safe wrappers |
| Rust core | domain types, engines, nodes, cache, portfolio, bus, adapters, persistence |

Python `Cache` and `Portfolio` objects are wrappers over Rust-owned state — there is exactly one copy of the state. `LiveNode` offers `run()` (blocks the calling thread) and `run_async()` (hosted on a Python asyncio/uvloop/ASGI loop) driving the identical Rust lifecycle. PyO3 does not turn Python coroutines into Tokio tasks.

Two-timestamp provenance is a domain-type property, not a convention: every data type carries `ts_event` and `ts_init`, and `HasTsInit` (`crates/model/src/data/mod.rs`, line 363) is the trait the replay heap sorts on. Money, prices and quantities are fixed-precision types with a documented fail-fast policy: NaN, infinity, negative timestamps, overflow, and precision violations return `Err` or panic rather than propagate (`docs/concepts/architecture.md`, "Data integrity and fail-fast policy").

## Mental models worth borrowing

### 1. The environment is a factory, not a branch

**Where it lives:** `crates/system/src/clock_factory.rs` (155 lines), consumed by `crates/system/src/kernel.rs::new_with_dependencies`.

**The model:** there is no `if backtest:` anywhere in the kernel. There is a `ClockFactory` that returns `TestClock` or `LiveClock`, and a set of client adapters. The primary clock is memoized and shared by kernel and trader; every *component* gets a fresh clock so its timer callbacks stay isolated.

**Why it matters for QMF:** this is the concrete, 150-line answer to decision A3 in the synthesis ("is the simulator just another `BrokerAdapter`, so there is no backtest engine at all?"). It converts an aspiration into a dependency graph. It also gives us the free property that a strategy's timers behave identically in both modes.

**How QMF would implement it:** `qmf.runtime.Kernel` takes `clock_factory` and `brokers` as constructor arguments and never imports `qmf.sim`. `qmf.sim` provides `SimClock` and `SimBroker`; `qmf.broker.ctrader` provides the live pair. A CI test asserts `qmf.runtime` has no import edge to `qmf.sim`.

### 2. Cache-then-publish as a named invariant

**Where it lives:** `docs/concepts/architecture.md` ("Data flow: life of a quote tick"); `DataEngine::handle_quote` in `crates/data/src/engine/mod.rs`.

**The model:** the engine writes the datum into the shared cache *before* publishing it on the bus. So a handler that receives a bar and then asks the cache "what is the latest bar?" gets the one it is holding — never the previous one.

**Why it matters for QMF:** without this rule, a Confirmation component that reads a Level's cached zone gets a one-tick-stale view, and the bug is invisible in backtests with sparse data and fatal in live. It is one ordering decision that removes a whole class of "works in backtest" defects.

**How QMF would implement it:** make it a written invariant of `qmf.runtime` dispatch, and enforce it with a property test: for every published datum, assert the cache accessor returns it inside the very first subscriber's handler.

### 3. The simulator is an ordinary broker adapter — and "sandbox" proves it

**Where it lives:** the shared `ExecutionClient` trait at `crates/common/src/clients/execution.rs:55`, implemented by `crates/backtest/src/execution_client.rs` and by `crates/adapters/sandbox/src/execution.rs`, both over `crates/execution/src/matching_engine/`.

**The model:** a matching engine that is not owned by the backtest. Backtest = historical data + matching engine. Sandbox = live data + matching engine. Live = live data + venue. Three wirings, one core.

**Why it matters for QMF:** it upgrades "no central backtest engine" from a slogan to a testable claim, and it hands us a *third* mode we had not planned — paper trading on live cTrader prices — for free, which is exactly what a prop-firm challenge dry-run needs.

**How QMF would implement it:** write the `BrokerAdapter` port and the conformance suite first; make `SimBroker` implementation #1 so the suite has a subject before cTrader exists; then wire a `PaperBroker` = live cTrader data feed + `SimBroker` fills, as a distinct third `Environment` value.

### 4. Three evidence classes for every command outcome

**Where it lives:** `docs/developer_guide/adapters.md` §"Order command outcome policy" and §"Naming the evidence classes"; the shared `CommandFailure` type at `crates/live/src/execution/failure.rs`.

**The model:** every state-changing order command failure is classified as exactly one of `NotSent` (local evidence proves it never left), `VenueRejected` (a structured venue response explicitly rejected it), or `Ambiguous` (it may have arrived; nothing definitive). **An `Ambiguous` classification never emits a terminal event by itself.** Transport errors, timeouts, disconnects, retry exhaustion, HTTP 5xx, rate limits, missing acks, and post-transmission parse failures are all `Ambiguous`, not rejections. Batch commands are classified per child order.

**Why it matters for QMF:** this is the highest-value paragraph in the repository for a prop-firm operator. Converting a timeout into "rejected" is how an account ends up with a live position the system believes does not exist — and a prop-firm daily-loss breach is unappealable. The synthesis already proposed `outcome ∈ {ACCEPTED, REJECTED, DENIED_LOCALLY, UNKNOWN}`; Nautilus supplies the *rule* that makes it work, which is the prohibition on terminal events from the unknown branch.

**How QMF would implement it:** `qmf.broker` returns exactly those four outcomes; `UNKNOWN` is a type the BMS understands as "position may exist, size unknown, treat as worst case until reconciled"; the conformance suite includes a fault-injection case per transport failure mode asserting no terminal event is produced.

### 5. Stable denial codes with a non-canonical diagnostic tail

**Where it lives:** `crates/model/src/events/order/denied_reason.rs`.

**The model:** a closed enum of denial reasons. Each renders to a message whose **leading token is a stable SCREAMING_SNAKE code**, followed by typed diagnostic context. The contract is written into the doc comment: consumers may branch on the code, never on the suffix. A companion generated enum lists the codes without context, so docs and dashboards can iterate the closed set.

**Why it matters for QMF:** the BMS must produce denial reasons that an LLM agent can read, an operator UI can group, and a research fitness function can treat as a hard disqualifier — all without parsing English. And enumerable-without-instantiating is what lets us auto-generate the agent-facing documentation of "every way your order can be refused".

**How QMF would implement it:** `qmf.errors.DenialCode` as a `StrEnum`; `Denial(code, context: dict)` with `str()` rendering `CODE: k=v, k=v`; a test asserting every code appears in the agent-facing spec page.

### 6. Fresh clocks per component, one clock per kernel

**Where it lives:** `ClockFactory::clock()` (memoized) vs `ClockFactory::create_component_clock()` (fresh), `crates/system/src/clock_factory.rs`; the backtest's `collect_all_clocks()` / `set_all_clocks_time()` in `crates/backtest/src/engine.rs`.

**The model:** the *time* is global; the *timer registry* is per component. Advancing simulated time means walking every component's clock and firing its due callbacks in timestamp order into an accumulator, then flushing.

**Why it matters for QMF:** a Confluence with a "max bars between touch and trigger" rule needs timers. If timers are global, one strategy's cancelled timer can silently affect another; if they are per component, `reset()` on a strategy is total and a crashed strategy leaves no orphan callbacks.

**How QMF would implement it:** `Clock` protocol with `now_ns()`, `set_alert()`, `set_timer()`, `cancel()`; each registered component gets its own instance from the factory; `SimClock.advance_to(ts)` collects due events across all component clocks, sorts by `(ts, component_id, name)` for determinism, and dispatches.

### 7. `ts_init` on a bar must be the bar's close — stated as a data contract

**Where it lives:** `docs/concepts/backtesting/bar-execution.md`, the warning block at the top.

**The model:** the two-timestamp pair is not decorative. `ts_event` may be the open or the close depending on the source; `ts_init` — "when this system could first have known it" — **must** be the close, or the whole complete bar becomes visible before it formed. If the source stamps at the open, the ingest step must add the interval. Nautilus tells adapter authors to prefer a `bars_timestamp_on_close=True` setting where the venue offers one, and to verify on a small sample before running.

**Why it matters for QMF:** this is the *only* concrete instance in any surveyed project of the two-timestamp discipline being written as a rule with a failure mode attached. It is also precisely the trap `smartmoneyconcepts` fell into. Our `Provenance` type should carry the rule, not the docs.

**How QMF would implement it:** `Bar` construction refuses a `known_at` earlier than `ts_event + interval`; `qmf.data.ingest` adapters declare their source's stamping convention as a field, not as a comment; a registration-time property test replays each component over `bars[0:t]` and `bars[0:t+n]` and asserts equal labels at index `t`.

### 8. Canonical, identity-normalized, content-digested run results

**Where it lives:** `crates/backtest/src/result.rs` — `CanonicalBacktestResult`, `CANONICAL_SCHEMA = "nautilus-backtest-result/v1"`, `UNORDERED_ARRAY_KEYS`, `IdentityClass`, `digest()` returning `blake3:<64 hex>`, and `first_divergence()`.

**The model:** a run result is a JSON document with (a) a declared schema version, (b) sorted keys, (c) sorted "unordered" arrays, (d) all random identities — client order IDs, venue order IDs, trade IDs, event IDs, position IDs — replaced by class-prefixed ordinals, and (e) a content digest over the exact bytes. The reader re-canonicalizes and **rejects** bytes that were not already canonical. A divergence helper reports the first differing field.

**Why it matters for QMF:** the earlier synthesis wants results keyed by `(confluence_id, split_id, data_fingerprint, qmf_version, venue_model_id)`. This adds the missing half: a digest of the *result* itself, so "did this rerun reproduce?" is a byte comparison, and "what changed?" has a machine answer. It is also the cheapest possible regression test for the kernel — freeze one digest and any accidental change to ordering, timers, or fill logic is caught instantly.

**How QMF would implement it:** `qmf.metrics` emits a canonical JSON result with normalized identities and a `blake3:` digest; the experiment ledger stores the digest; CI runs one golden backtest and asserts the digest is unchanged.

### 9. Event store is the authority; the cache is a projection

**Where it lives:** `docs/concepts/event_sourcing.md`; `crates/event_store/`; the kernel's `restore_parent_cache` / `open` / snapshot-anchor calls at `crates/system/src/kernel.rs:651+`.

**The model:** the cache answers "what is true now"; the append-only event store answers "how did we get here". Runs are sealed, entries carry a per-run sequence, a snapshot anchor plus the run tail rebuilds the cache, and **market data deliberately stays out** — it lives in the catalog. Replay is a first-class start mode that skips engines, clients, trader startup and reconciliation.

**Why it matters for QMF:** the BMS needs durable state reconciled at startup (prop-firm daily loss is path-dependent and cannot be recomputed from positions alone), and the operator needs to explain to a prop firm exactly what happened. Two problems, one log.

**How QMF would implement it:** one append-only JSONL/parquet event log per run holding commands, fills, account states and BMS decisions; `qmf.bms` state derived from it at startup; a `replay` mode that rebuilds without touching the broker. Prices stay in `qmf.data.lake`.

### 10. Indicators registered against a (instrument, bar-spec) key, updated before your handler

**Where it lives:** `crates/common/src/actor/indicators.rs` (`indicators_for_bars: map[(InstrumentId, BarSpecification)]`); `crates/indicators/src/indicator.rs`; `docs/concepts/strategies.md` ("Registered indicators receive the bars from a request response before `on_historical_bars()` runs").

**The model:** the strategy declares `register_indicator_for_bars(bar_type, indicator)` in `on_start`, and thereafter never updates it. The framework updates every registered indicator for that exact key before the handler runs, and hydrates it from historical request responses. The strategy asks `indicators_initialized()` before acting.

**Why it matters for QMF:** it is the enforcement mechanism behind "write each calculation once, in incremental form". If the *framework* owns the update, a strategy author — human or LLM — physically cannot feed an indicator a future bar or forget to update it, and cannot accidentally use a batch variant.

**How QMF would implement it:** `qmf.indicators` keeps the `Indicator` protocol from the module map, and `qmf.runtime` owns a registry keyed by `(symbol, bar_spec)`. Components in a `Confluence` never call `handle_bar` themselves — they read `peek()`. `replay()` is the same registry driven by a `SimClock`.

### 11. A biased priority order in the live loop

**Where it lives:** `crates/live/src/runner.rs` — `tokio::select!` with `biased;`, ordering shutdown → time events → system events → system commands → execution events → execution commands → data events → data commands.

**The model:** when several inputs are ready at once, execution and system messages are handled before market data, and events before commands. Data can wait a microsecond; a fill or a shutdown cannot.

**Why it matters for QMF:** under a news spike the tick rate can starve the order-event path, and the BMS's daily-loss check depends on fills arriving promptly. Priority is a two-line decision with a large safety payoff, and it is invisible until it bites.

**How QMF would implement it:** `qmf.runtime`'s asyncio loop drains queues in a fixed priority order each pass — shutdown, timers, broker events, broker commands, data — rather than using a single merged queue.

### 12. Adapter conformance as a rule table plus a shared baseline, with earned exceptions

**Where it lives:** `docs/developer_guide/adapters.md` — the four conformance tables, the "Shared baseline" table mapping each contract to the shared type that implements it, and the exception rule.

**The model:** conformance is enumerated as rules with an "applies to" column; each contract names *the* shared implementation (retry manager, auth tracker, subscription state, FIFO replay-dedup cache, task handles, HTTP client); a local reimplementation is allowed but must prove the same contract; and any venue-forced exception must be named, contained inside the adapter, and covered by a test that fails when the venue stops requiring it.

**Why it matters for QMF:** QMX will have exactly two adapters for a long time (`SimBroker`, cTrader) and later a third (a crypto exchange). Two is precisely when a shared contract is cheapest to establish and most likely to be skipped. The exception rule is the part worth stealing verbatim in spirit: it converts "we had to hack it for this broker" from technical debt into a documented, self-expiring test.

**How QMF would implement it:** one `tests/conformance/` package parameterised over adapters; a short `ADAPTERS.md` rule table in QMX; and a convention that every broker-specific workaround ships with a test named for the broker behaviour that forces it.

### 13. Component finite state machine with a `DEGRADED` seat

**Where it lives:** `crates/common/src/component.rs`; the state diagram in `docs/concepts/architecture.md`.

**The model:** components are not "on/off". Stable states include `DEGRADED` ("may not meet its full specification") alongside `RUNNING`, `STOPPED` and `FAULTED`, and transitional states are explicit so a failing lifecycle callback parks the component visibly rather than silently half-started. `dispose` is special-cased so a failure still retires the component.

**Why it matters for QMF:** the BMS's `TradingState ∈ {ACTIVE, REDUCING, HALTED}` is the same idea one level up, and `REDUCING` is a `DEGRADED`. Having the pattern at component level too means "market data feed is stale but orders still work" has somewhere to live other than a boolean and a log line.

**How QMF would implement it:** one `ComponentState` enum in `qmf.runtime` with the same stable/transitional split; strategies and adapters both implement it; the operator UI reads it directly.

### 14. Name the heuristic, and cite its evidence

**Where it lives:** `docs/concepts/backtesting/bar-execution.md`, "OHLC price simulation".

**The model:** filling orders from bars requires inventing an intrabar path. Nautilus splits bar volume across four synthetic L1 updates, offers `bar_adaptive_high_low_ordering` (visit the extreme nearest the open first), links the exploratory EUR/USD analysis that motivated it — and then says outright: *"a deterministic heuristic, not a reconstruction of the actual trade sequence"*, whose accuracy *"depends on the market, interval, and data source"*.

**Why it matters for QMF:** this is the honest treatment of a fidelity assumption that silently decides every backtest where a stop and a target sit inside the same bar — which for a Level+Trigger+Exit strategy on M15 is most of them. It is the same posture the module map wants for `evidence_state` on components, applied to the simulator itself.

**How QMF would implement it:** `qmf.sim.FillModel` declares its intrabar path policy as a named, versioned choice recorded in every result; forex-first QMX should default to *tick* replay where we have it and mark bar-derived results with a lower fidelity grade in the result contract.

## What to avoid

**1. Do not adopt NautilusTrader as QMX's engine right now.**
Evidence: the clone is `v2.0.0rc3` while the latest published release is `v1.231.0 **Beta**` (2026-08-02). `MIGRATION_V2.md` states that after cutover v1 moves to a `develop_v1` branch for *"approximately three months of critical security backports"* and *"does not receive new feature or parity work"*. `RELEASES.md` for this very release removes the entire Cython package, all FFI outside two crates, `LiveNode.poll()`, the generic Python network clients, and renames the core strategy callbacks (`on_quote_tick` → `on_quote`, and dozens more). Building on this means inheriting a migration mid-flight. Add LGPL-3.0 on top and decision A1 in the synthesis (assume QMX may be licensed or served) settles it.

**2. Do not copy the god-object cache.**
`crates/common/src/cache/mod.rs` is 8,221 lines with **392 public methods**, plus a 9,833-line test file. It is the single point every engine, the portfolio, the risk engine and every strategy touches. It works because Rust's borrow checker and a single-threaded core make the aliasing tractable — Python has neither. QMF should split the cache by concern (market-data tail, execution state, instrument registry) with narrow read protocols per consumer.

**3. Do not import the thread-local global runtime pattern.**
The message bus, actor registry, component registry and channel senders all live in thread-local storage. The consequence is documented as a hard limitation: *"Running multiple `LiveNode` or `BacktestNode` instances concurrently in the same process is not supported"*, and *"For parallel execution or workload isolation, run each node in its own separate process"* (`docs/concepts/architecture.md`). For QMF that would forbid running a parameter sweep in-process. Pass the bus and registries explicitly as kernel-owned objects so N kernels can coexist; accept the small dispatch cost.

**4. Do not accept `Rc<UnsafeCell<dyn ...>>` re-entrancy as a model.**
The architecture doc's own warning: registry `get` returns shared `Rc<UnsafeCell<...>>` handles; the borrow guard applies only to lifecycle wrappers, not to raw registry access; typed actor accessors *"do not prevent two simultaneous guards for the same actor"*; *"Creating overlapping mutable references is undefined behavior"*; and same-actor re-entrant lookup is *"a constraint of the current dispatch model, not a safe aliasing guarantee."* That is a performance-driven escape hatch with a documented sharp edge. QMF has no performance reason to accept re-entrancy hazards.

**5. Do not ship indicators without warm-up metadata.**
`crates/indicators/src/indicator.rs` exposes only `has_inputs()` and `initialized()` — booleans. Grepping the crate finds no `warmup_bars` or stability classification anywhere; warm-up is discovered by feeding data until `initialized` flips, and composite indicators note in *comments* that "for slowing > 1, we need additional warmup" (`momentum/stochastics.rs`). The module map is right to make `warmup_bars` and `stability` **manifest fields** — a `Confluence` of five components cannot compute its own warm-up from five booleans.

**6. Do not let the strategy base class grow to sixty methods.**
The Python `Strategy` surface (`python/nautilus_trader/trading/__init__.pyi:457`) exposes `submit_order`, `submit_order_list`, `modify_order(s)`, `cancel_order(s)`, `cancel_all_orders`, `close_position(s)`, `market_exit`, plus lifecycle, plus indicator registration, plus publishing. That is right for a general framework with human authors. It is wrong for QMF, where the whole safety argument is that an LLM-authored component **cannot express a quantity or place an order**. Nautilus is the demonstration of what happens when you do not draw that line: sizing and risk are conventions inside the strategy, and `RiskEngine` can only check the result. Keep `qmf.spec` at one printed page.

**7. Do not mistake documented rigour for validated fidelity.**
Even here, bar-based execution is *"a plausible intrabar path"* on a *"deterministic heuristic"* whose motivating analysis *"does not establish a general accuracy rate"*. And `docs/concepts/architecture.md` concedes the single-threaded core *"helps maintain backtest-live parity, though live inputs and latency can still cause behavioral differences."* The best-engineered backtest in open source still says this. QMX's slippage-measurement loop (synthesis idea #4) is not a nice-to-have; it is the missing half.

**8. Do not expect any forex or prop-firm help from this repository.**
`ADAPTERS.md` lists no cTrader adapter, official or community — only a third-party MT5 connector. The forex-specific content is `crates/trading/src/sessions.rs` (four session windows with timezones) and `crates/model/src/instruments/cfd.rs` (a CFD instrument with margin, fees, lot size, notional and price bounds). Both are worth reading for field lists. Nothing models a daily-loss anchor, a ratcheting drawdown, or a challenge phase.

## Licence & maturity

**Licence: GNU LGPL-3.0.** `LICENSE` is the full LGPL v3 text; every source file carries the header *"Licensed under the GNU Lesser General Public License Version 3.0"*. Copyright Nautech Systems Pty Ltd, 2015–2026. There is also `CLA.md` (contributor licence agreement) and `TRADEMARK.md` restricting use of the name.

**What LGPL means for QMX in practice.** LGPL permits *linking* from a proprietary application, but §0 of the licence text is explicit that *"Defining a subclass of a class defined by the Library is deemed a mode of using an interface provided by the Library"* — which is how you write a Nautilus strategy. So a strategy that subclasses `Strategy` is a mere user of the library. The obligations attach to redistribution (you must allow the user to relink a modified library version), and copying source into QMF would make QMF a derivative work. **For QMX: design study only. Read it, name the shapes, cite the paths, write our own code. Do not copy code, do not translate functions line-for-line from Rust to Python, and do not vendor any of it.** Decision A1 in the synthesis (assume QMX may be sold, licensed, or served) makes this unambiguous.

**Maintenance: very actively maintained.** As of 2026-08-17 the `develop` branch's latest commit is dated **2026-08-17** — the same day. GitHub shows ~25.7k stars, ~3.4k forks, ~98 open issues, 20,663 commits on `develop`. The project aims at a bi-weekly release cadence with nightly snapshots, runs daily vulnerability scans, and has `SECURITY.md`, `CONTRIBUTING.md`, `AI_POLICY.md` and an unusually complete developer guide.

**Maturity: high engineering quality, unstable API surface.** Ten years in, the published release is still labelled *Beta* (`v1.231.0 Beta`, 2026-08-02), and `develop` is `2.0.0rc3` — a ground-up Rust rewrite that has just deleted the entire v1 Python layer. `RELEASES.md` for this release candidate lists dozens of breaking changes and renames. `ROADMAP.md` names priority #1 as *"Stabilize the Rust-native core"* and priority #3 as *"Improve code ergonomics… standardize naming conventions"*. Declared out of scope: UI dashboards, distributed backtesting, and any built-in optimisation or ML tooling.

**Verdict for QMX:** the reference implementation to study, not a dependency to adopt. Revisit only if (a) 2.0 goes stable and out of Beta, (b) a cTrader adapter appears, and (c) QMX's licensing posture changes — and all three would have to be true.

## What a from-scratch Python-only kernel would actually cost

Estimated honestly, for **one venue (cTrader forex CFD), one OMS type, market/limit/stop plus attached SL/TP, no order book, bars and quotes only**:

|---|---:|---:|---|
| Value types: nanosecond time, Decimal money/price/qty, identifiers | ~9k | 600–900 | Cheap. Get precision and fail-fast right once. |
| Domain model: instrument, bar/quote/trade, order, position, account, events | ~73k (14.6k orders alone) | 2,500–4,000 | The **order state machine** is the hidden cost: statuses, contingencies, trailing, GTD, reduce-only. |
| Clock (sim + live) + timers | ~4k | 400–600 | Straightforward once the factory pattern is settled. |
| Message bus (topics, wildcards, endpoints, correlation) | ~11k | 250–400 | Python needs none of the zero-cost dispatch machinery. |

| **Startup reconciliation** | ~2.7k prod / 8k tests | 800–1,200 | Largest risk-per-line item in the whole table. |

| **Total** | | **~13,000–19,000** | plus a comparable or larger volume of tests |

Three caveats that matter more than the numbers:

- **The skeleton is not the work.** Clock + bus + cache + engines + strategy base + a naive `SimBroker` is roughly 2,500 lines and two to four weeks. That produces something that *runs*. Everything after it — order state machine edge cases, partial fills, contingent order handling, margin, reconciliation — is the other 80% and the part that decides whether real money survives.
- **Test volume is the real cost signal.** In the crates sampled, test code runs 0.7×–1.6× production code (`crates/execution`: ~40k test lines against ~56k production; `crates/data`: ~25k against ~41k). QMF's kernel needs the same ratio in the execution and reconciliation paths and can be lighter elsewhere.
- **Scope discipline is the lever.** Nautilus's size is mostly breadth we do not need: 23 instrument classes, 20+ bar aggregators, 44 indicators, DeFi, options and greeks, order books to L3, 17 venue adapters, four persistence backends. Cut to one asset shape, one bar type, one venue and one account model and the kernel is genuinely a solo-operator project. Let scope creep back in and it is not.
