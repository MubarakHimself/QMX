# QMF V1 Operations Runbook

QMF V1 is design-only: the `qmf.*` libraries are a reusable toolbox rather than an application runtime, so QMF itself has no ratified start, stop, restart, deploy, migration, rollback, or live-connection command, and this document records the operational boundaries the libraries leave open. [DEC-0008] [DEC-0009] The **trading node** (`COMP-QMN`, code name `qmn`) is the application built on QMF that DOES carry ratified operations — one product with two modes `paper | live`, run entirely through the operations toolkit's `just node-…` recipes and the node's powers channel, because the operator ruled the node ships NO operator command line (DEC-0186, DEC-0211). The node's operational procedures are the trading-node sections of this runbook; its capability contract is [the trading-node component spec](../../components/trading-node.md) and its architecture decision is [ADR-0019](../../decisions/ADR-0019-trading-node.md). Nothing here grants implementation, credential, order, promotion, live-money, or destructive authority; that arrives only through the factory pipeline (DEC-0259).

## Permission boundary

This runbook grants no permission to initialize the project, deploy code, access credentials, connect to a broker, submit an order, promote an artifact, change a Book mode, flatten exposure, or operate live money. Project initialization remains with operator tooling, and promotion into the live zone remains human-only. [DEC-0005] [DEC-0041]

Agents may inspect documented contracts, run already-approved read-only validation, and preserve evidence. Agents may not infer an operational command from a recommendation, a GAP, a study, or an external provider's examples. [DEC-0003] [DEC-0004]

### The node's operations toolkit

Every node deployment and provisioning operation is a `just node-…` recipe in the repo's root justfile, with bodies in `qmn/deploy/justfile-recipes/`; the toolkit is the node's DevOps tooling, the layer the operator called "a very separate system, like how big tech teams work" — his posture on the DevOps lens as a whole, not a description of any one recipe — and is NEVER a trading control and never a product command line (DEC-0186, DEC-0211). No recipe places, cancels, amends, flattens, promotes or activates anything: the restriction is enforced by the transport, not by recipe text, because a recipe that needs live node state makes the same evidence read or powers call the desktop UI will make, under the powers channel's **ops principal**, for which every trading, protection, promotion, activation, settings, `resurrect`, attestation and countersign power is refused (DEC-0202, DEC-0234). `node-install`, `node-switch` and `node-rollback` are privileged host acts run through the declared sudo admin path and touch no door, and no recipe ever constructs a composition root or imports the Python API in a process other than the node's (DEC-0186).

**Check mode** is the node's dry-run boot, defined once (DEC-0201): it binds the doors, runs the config compile, the fingerprint and the seal, and every preflight gate that needs no venue and no credential; it SKIPS credential-presence, store-reachability, `chronyc waitsync` and venue connect, exits non-zero on any refusal, and NEVER opens a sequencer. `just node-switch` runs a check-mode boot against the new tree before the symlink flip; the soak gate additionally requires one boot under the real systemd unit with `LoadCredentialEncrypted` from a scratch credstore, because a CI runner cannot exercise systemd credentials.

**Two placement variants.** The node has two placement variants, one product with two placements and never a fork. The VPS variant is the ratified path today: everything in this runbook — the `just node-…` recipes above, the systemd units, the safe-point restart and the VPS-loss procedure — operates that variant (DEC-0262). The single-machine variant — the node co-located with the agentic system on one box, in scope with its design owed under GAP-0058 (open) — sets itself up out of the box, its backend installing its own dependencies and provisioning its own stores, with the desktop UI later fronting an installation page or walkthrough over that self-setup (DEC-0262). That self-setup installer is design-owed and not yet specified, so this runbook describes no procedure for it; until the one-shot architecture increment rules GAP-0058, operate the node through the VPS recipes above (DEC-0262).

### Operator acts run on the powers channel, not a command line

There is NO node command line: every operator ACT is a call on the node's unix-socket powers channel (`/run/qmn/powers.sock`, `SO_PEERCRED`), which the desktop UI will make later over an SSH tunnel and which the operations toolkit reaches only for the ops-principal subset (DEC-0202, DEC-0211, DEC-0234). The powers list is CLOSED — a capability not on it does not exist on the powers channel — and the peer credential is read from the transport and recorded beside the claimed signer; a call whose credential is neither declared principal is refused outright (DEC-0234).

Two principals are declared by uid, and NEITHER is the `qmx` service account (DEC-0234):

- The **operator principal** may call every power: `resurrect` from stand-down; `resume` and de-escalate, naming the KSA scope it reopens; `resolve_unknown` (operator-attested); flatten at any scope; manual kill-switch escalation; paper flip; paper-epoch reset; the promotion sign, and activation as its own second act; `config_version_activate`; `seat_reinstate` (the only exit from `quarantined`); `restore_drill_run` (the host-loss rehearsal trigger); `hub_publish`; `config_validate`; the `state_carry` declaration with its `carries-ledger` and `continues-performance` signatures; the `value-status` countersign (refused without the variable's evidence citation by `fp1`, one variable per call); the sealed period's one logged final look; a settings edit (which mints a new config version and schedules a restart at a safe point); the notify test; and a secrets `is_set` check (DEC-0202, DEC-0231).
- The **ops principal** — the identity the operations toolkit runs under — may call ONLY `notify_test`, `restore_drill_run`, `config_validate`, `hub_publish` and the evidence reads; every trading, protection, promotion, activation, settings, `resurrect`, attestation and countersign power is refused to it BY THE TRANSPORT, and the refusal is journaled (DEC-0234).

Preflight refuses to boot if any systemd unit on the host declares an operator-principal uid, so no automated unit ever runs as the operator (DEC-0187, DEC-0234). What the peer credential proves is an ACCOUNT, not a human — humanity beyond "no automated unit runs as the operator" is asserted by the signer and is a named residual risk (DEC-0202).

### systemd units and the timer ceremony

The node's units are checked in under `qmn/deploy/systemd/` so Skylos's IaC scan gates them (DEC-0201): the long-lived `qmn.service` (`Type=notify`, `WatchdogSec` set, `Restart=on-failure`) and four scheduled timer units — `qmn-news-calendar.timer`, `qmn-backup.timer`, `qmn-restore-sample.timer` (nightly) and `qmn-restore-full.timer` (monthly), each paired with its `.service` — five node units in all, under the fixed `User=qmx` service account with `ProtectSystem=strict` plus `ReadWritePaths=/var/lib/qmx` (DEC-0201, DEC-0227). `qmx-observability.service` is a SIXTH checked-in unit that is NOT one of the node's: it runs under a distinct non-`qmx` account with its own credentials and its own storage (DEC-0200). The host-loss restore rehearsal is a power, not a timer (DEC-0198).

A timer unit that writes journal records runs an ABBREVIATED boot ceremony (DEC-0187): it composes from **the config version the RUNNING node has sealed**, read from the node's boot-epoch record over the evidence channel — never from the config graph's `current` pointer, which may already have moved past a settings edit that takes effect only at the next boot epoch. It computes `composition_fp` over the same inputs as the node process so one deployment yields one value, mints its own boot epoch stamped with its unit role, and writes only under its own allocated `WriterId`. Where the node is NOT running, the timer composes from `current` and stamps `node-absent` on its own boot-epoch record. A timer that can neither read the running node's sealed version nor establish that the node is down REFUSES to write and alarms on the silent-degradation class (DEC-0187, DEC-0233).

### Start, stop, restart at a safe point

Start, stop and restart go through systemd and the operations toolkit, never an operator command line (DEC-0186, DEC-0211). The node starts by binding its doors first — the evidence channel, a preflight-status read model and the `resurrect` power — then writing a boot-attempt record, then running preflight, compose, fingerprint and seal (DEC-0187, DEC-0226).

Stop and restart happen only at a **safe point**, defined once (DEC-0189, DEC-0226): (a) the slice driver is between slices, (b) `suspend_new` is enforced on every stream, (c) every command has reached a terminal outcome OR has had an UNKNOWN minted for it, and (d) every sink has flushed with block-on-unpersistable honored. **Positions are never waited on.** Reaching the safe point is bounded by `registry:drain_window`, from which `TimeoutStopSec` is rendered; `WatchdogSec` is rendered from `registry:watchdog_interval`, so a config change and a unit file can never disagree (DEC-0189, DEC-0201). A drain breach is a typed refusal, not an indefinite hang.

The shutdown contract on SIGTERM enforces `suspend_new` on every stream, closes sessions with no command resubmission, mints an UNKNOWN for every command still without a terminal outcome (under trigger `disconnect`, after session close), then flushes every sink; it exits **0 for an operator stop and 75 for a requested restart**, and **never flattens** — standing intents survive as folds and are re-decided at the next boot (DEC-0189). If the flush itself cannot complete, the node stays up, alarms on the silent-degradation class, and refuses to exit clean (DEC-0189, DEC-0233).

A **requested restart** — a settings edit or a `just node-switch` — exits with the reserved code **75** (`RestartForceExitStatus=75`, `SuccessExitStatus=75` in the unit) so systemd restarts a clean drain rather than treating it as a failure, and it never advances the crash-loop counter (DEC-0189, DEC-0201).

### Stand-down-alive and resurrect

Node stand-down is an ALIVE lifecycle state, not a control action (DEC-0189, DEC-0218). It is entered automatically on a crash loop, a `halt` clock band, or a preflight failure, and the doors keep serving throughout — `resurrect`, the evidence channel and the preflight-status view stay available. It is left **ONLY by an operator `resurrect` act** through the powers channel, journaled as an AD-21 `control action` event under the declared `node_resurrect` subtype at global scope; no clocked clear, no reconnect, no reconciled verdict and no restart leaves it (DEC-0189, DEC-0218, DEC-0236).

In stand-down the sequencers refuse and journal **ENTRY intents only** — `place_order` and risk-increasing `amend_protection`, whatever their author — while **every risk-non-increasing act passes**: a Book-minted protective close, a declared force-flat trigger, an exit-logic-derived exit, a bot-proposed risk-non-increasing tighten, the standing-intent dispatcher, and every operator-signed protective command (flatten at any scope, `close_all`, `close_position`, `cancel_order`, risk-non-increasing `amend_protection`). Where the sessions have quiesced, a protective command is journaled as a standing protection intent before dispatch and satisfied on the next healthy session — never refused, never dropped: "reachable in stand-down" means ENACTABLE, not merely answerable (DEC-0189, DEC-0221).

### The soak week (the first-deploy warm-up rider)

Milestone 1 is the **soak**, and it IS the first-deploy warm-up rider in full — one full UNATTENDED week, on the demo account, with the live binding taken at its end and the soak acceptance checklist unchanged (DEC-0194, DEC-0212). It is the same week as the ratified roughly one-week warm-up/observation rider (DEC-0135) — one attribution, one rider — and it runs with the FULL live machinery: a real cTrader connection, the first-connection verification suite, reconciliation read-backs, standing intents, KSA, windows, SQS baseline minting, recording, backups, the restore drills, the doors, metrics and alerts, under full logging and monitoring (DEC-0194).

The soak runs the DEMO binding; **the live connection is opened for sensing and recording only** as soon as live credentials exist — no live binding, no command stream open — so the live-environment SQS baseline (keyed `(VenueId, environment, instrument)`) and the live-path rung baseline accumulate on the live environment while the machinery proves itself on the demo one (DEC-0194, DEC-0193). The live binding waits on its own baselines, so a late Spotware approval or KYC delays go-live and never the week (DEC-0194).

**VPS procurement gates the soak's START** — the bind-time check refuses a live binding without a rung baseline on this deployment tuple — while **Spotware app approval and live KYC gate go-live ONLY** (DEC-0260). Acceptance is machinery proof (the soak checklist with its fault-injection drills), NEVER profit: paper evidence can never authorize live money (DEC-0208). This runbook authorizes no live trading; the soak records the operator's stated precondition and the acceptance bar, not a grant (DEC-0041). The VPS is procured by the operator, and an existing Linux VPS may serve the first-deployment window; the binding minimum spec is whatever the node's own benchmark measures in the soak's first hours, so a procurement starting point — Ubuntu 24.04, about 4 vCPU, 8 GB RAM, about 100 GB SSD shared with the observability stack, sited near the broker's cTrader server — is recorded as engineering evidence only, never a ratified value (DEC-0261).

### VPS-loss runbook

A VPS-loss runbook is a required node artifact. Host loss surfaces as a **missing liveness-heartbeat ping** — the liveness heartbeat (formerly the dead-man's switch) holds zero authority and acted on nothing, so the first response is to **check the box** (the VPS and the network) before anything else — and once the host is confirmed gone the steps run in this exact order (DEC-0198, DEC-0217, DEC-0261):

1. **Procure** a new VPS (the provider is deployment configuration, never architecture).
2. **Bootstrap** uv and CPython, install `just` at its pinned version and the container runtime the observability stack needs, and clone at the pinned commit into the first per-commit tree.
3. **Provision** — run `just node-secrets-provision` to re-seal credentials into the new host's `systemd-creds` store, minting a fresh KEK.
4. **Re-authorize cTrader**, because the stored refresh token is spent — cTID re-authorization is required to obtain fresh tokens (DEC-0197).
5. **Restore** from the bucket with the **escrowed workstation-minted payload key** — the KEK protects only rotated session material and does NOT survive VPS death, so disaster recovery rests on the escrow, not on the host-key seal (DEC-0197, DEC-0217).
6. **Replay check** against a recorded day to confirm the restored node reproduces its decisions (DEC-0206).

The full-DR recovery time this sequence takes is MEASURED at the host-loss restore rehearsal, never declared; RPO is 24 h by construction (DEC-0198).

### Backup and the three restore drills

Backup is pushed BY THE VPS: `qmn-backup.timer` runs nightly, and the CT-14 primitives produce encrypted, versioned copies (key = the escrowed workstation-minted payload key) to an S3-compatible bucket, ciphertext only (DEC-0198, DEC-0217). A copy is always a PREFIX OF A REAL STREAM — only journal segments sealed at a committed sequence boundary are copied — so a restored room never holds a torn record (DEC-0198). The backed-up set is the immutable raw archive, every journal room, the registry room, and the evidence tier's `sealed-archive` role and research door, for every world; the processed room is rebuildable and excluded (DEC-0188, DEC-0198).

Three restore drills run, each journaled as `data quality`, each failure alarming on the silent-degradation class and never silently retried, each with its own unit so one timer never carries two cadences (DEC-0198, DEC-0233):

1. **Nightly sample restore** — `qmn-restore-sample.timer`, right after the backup: pull one file back and verify its fingerprint.
2. **Monthly full restore** — `qmn-restore-full.timer`: a full restore into a scratch directory, fingerprint-verified — an integrity test, and only that.
3. **Host-loss restore rehearsal** — NOT a timer, but the operator's `restore_drill_run` power (DEC-0202), run once before the live milestone and after every rebuild: restore from the bucket onto a clean host holding nothing but the escrowed payload key — the only drill that exercises key availability and the only one that can prove disaster recovery.

Two recovery-time numbers are recorded apart and never conflated (DEC-0198): the **integrity-restore** time measured at the monthly rehearsal (`registry:backup_recovery_time_objective_integrity`) and the **full-DR** time measured at the host-loss rehearsal (`registry:backup_recovery_time_objective_full_dr`), which includes VPS re-procurement, re-provisioning and key recovery. Both are MEASURED, never declared. No agent may run a destructive restore or cutover over the only copy or over live evidence.

## Venue first-connection and session procedures

The venue-adapter contract is ratified (DEC-0138); these procedures are ratified design, and implementation authorization arrives only through the factory pipeline, never from this runbook. When any step runs in production, its scheduling and consequences are application/node/risk territory, tracked in `tracker/trading-node-notes.md` (DEC-0142).

### First-connection verification suite (verify-or-refuse)

The capability surface is two artifacts: a **static capability declaration** (importable without credentials, marked `static` or `measured-at-connection`) wired at construction, and a per-`(VenueId, account)` **venue-observation profile** produced post-connect by the verification suite before the first command and before any evidence-bearing decode (DEC-0138). The suite is a named contract part and is **verify-or-refuse throughout** — a `measured-at-connection` capability is `unavailable dependency` until its profile exists:

| Verification | Rule | Refusal on failure |
|---|---|---|
| Spot-timestamp unit | Assert milliseconds by magnitude at first connection (the unit is undocumented, DEC-0135). | An unverified spot-timestamp unit refuses spot evidence. |
| Daily-boundary measurement | Derive the actual daily-bar boundary from the venue's own timestamps per broker; once measured and verified, mint it as a **venue-scoped market-hours calendar identity**, giving venue-native bars a legal BarSpec anchor (DEC-0135, DEC-0138). | An unmeasured daily boundary leaves venue daily bars **ungoverned**, never assumed aligned to QMF's forex 17:00-NY calendar. |
| Bar-basis reconciliation | Reconcile trendbar OHLC against explicitly-BID/ASK tick history per broker and symbol class; record the verified quote side (DEC-0135). | A failed bar-basis reconciliation refuses bar evidence. |
| Pip-formula validation | Validate `pipSize = 10^-pipPosition` against known symbols at first connection (DEC-0135). | A failed pip-formula validation refuses metadata-derived parameters. |
| Money exponent | Require the per-message `moneyDigits` exponent before decoding money (DEC-0135). | An absent money exponent refuses that message's money decode — never a default to 2. |

Measurements and verification verdicts journal as `data quality` events (DEC-0138).

### Session duties

The adapter's periodic session duties are **declared schedulable work the application's scheduler drives** — the adapter defines the work, the application runs it (DEC-0141): heartbeat (the ratified safe bound is 10 seconds, DEC-0135), token refresh, reconnect, gap replay, and verification monitors including the continuous daily-boundary monitor. **Session recovery never resubmits a command**, and command retry is prohibited — retryability rides typed refusals (DEC-0141, DEC-0137). Retry, pool, and deadline constants are do-not-default node values.

### Warm-up rider

The operator's roughly one-week warm-up/observation rider before live trading (DEC-0135) IS the soak — the operator ruled it a FULL unattended week on the demo account, live binding at its end, one attribution and one rider (DEC-0194, DEC-0212). Its machinery, sensing-only live connection, go-live gating and acceptance checklist are the "The soak week (the first-deploy warm-up rider)" section of this runbook. This runbook authorizes no live trading; the rider records the operator's stated precondition, not a grant (DEC-0041).

## Risk bindings, control actions, and paper mode

The risk contracts are ratified design, **defined-unwired**: no code exists, the composition root mediates, and implementation authorization arrives only through the factory pipeline, never from this runbook. When any step runs in production, the trigger→level→effect matrix and order-path internals stay node/risk territory, tracked in `tracker/trading-node-notes.md` (DEC-0142).

### Bind-time capability check

A binding couples one Book instance to one BMS instance on one `(VenueId, account)` command stream. The BMS is the **account-facing supervising layer** — one per account, serving many Books; a Book binds exactly one BMS at a time, dated and append-only (DEC-0143). A binding is admissible only where the venue's CT-18 declaration **and** its venue-observation profile satisfy the Book's declared required capabilities — including the account settlement currency matching the Book's `accounting_currency`, the shared-flatten signature where the account is netted, a present SQS baseline for every sensor the Book's doors read, the live-path rung baseline on this deployment's tuple, and a control-rank table the Book does not contradict — a shortfall refusing **at bind time**, never at trade time (DEC-0143, DEC-0158). A Book whose control policy contradicts its BMS's rank table is refused at bind time (DEC-0151).

### Three-layer admission

A new Book or BMS proves itself in three layers, with no trial period, probation window, or paper-performance gate (DEC-0146): Layer 1 — machine linters at registration (completeness against the declared contract format version, a unit on every parameter, exact-rational or scaled-integer values, resolvable references, worked-example arithmetic recomputed by invoking the cited producer contracts, control-rank uniqueness); Layer 2 — a technical shakedown on a demo/paper binding (connect, register a bot, execute), with a recorded live-path rung baseline on this deployment's tuple and a present baseline artifact for every sensor the Book's doors read as named prerequisites; Layer 3 — one operator signature on one assembled page carrying both proofs, the binding identity, the capability-satisfaction result, and the resolved BMS fingerprint. A Book whose admission bar holds any not-yet-ruled threshold or pending slot binds to non-live roles freely, and binding to a live account is a `policy rejection` (DEC-0146).

### Control-action vocabulary

Control actions are typed and each defined once (DEC-0150): `suspend_new` (no new entries; everything open or resting untouched), `drain` (no new entries and resting orders run to their own terminal state; nothing force-closed), `flatten` (close the scope), `resume`. The **kill switch** is the global authority that stops all new trading live and paper; the **kill line** is a per-Book capital floor whose breach automatically flattens that binding's scope and stands the Book down. `resume` is **operator-only** — escalation automates, de-escalation does not. Flatten authority is assigned — the operator always (inalienable, never removable), Book policy through pre-declared triggers, the protection authority per the node's severity policy, nobody else — and the adapter never initiates a flatten. The **exit-preservation invariant** binds: no control action, of any authority, at any scope, may block a risk-reducing act (DEC-0150).

### Paper flip and paper-epoch reset

Paper is a Book-level mode — `LIVE | PAPER` — expressed as a dated change of the Book's execution binding, minting a new **binding epoch**, never a new Book (DEC-0149). The **paper flip is an operator-ratified dated action**. The paper starting balance is a Book/family-scoped configurable UI-editable default, sized for data-collection realism, frozen at flip, and **never hand-adjusted** (DEC-0149, DEC-0157). A **reset is not an adjustment**: it mints a new **operator-signed, dated paper epoch record** with a fresh declared balance and a lineage edge to the epoch it follows; the running balance is never mutated. Paper P&L never becomes Treasury cash, never crosses the money boundary, and never buys a seat (DEC-0149).

## Secrets handling

The venue secret lifecycle is ratified as law (DEC-0136): QMF handles opaque `SecretRef` references, never values; values are injected at the composition root from the deployment environment's protected store (`systemd-creds`-class on the VPS), and only the adapter's connection manager holds `SecretValue`s in memory, through an injected `SecretStore` port. Rotation is store-before-discard with one live refresher per credential; the compromise-recovery drill is anchored on cTID re-authorization (see [OPS-INCIDENT-QMF-V1](incident-playbook.md)). The node/ops sitting has now fixed the store mechanics and key custody below; credential entry and management UI stays platform territory (DEC-0136, DEC-0197). This runbook grants no credential-bearing operation; implementation authorization arrives only through the factory pipeline.

Object-storage encryption key custody is ruled at the node's backup payload-key custody rule below (DEC-0217). The news-calendar recorder keeps provider-native identity and revisions through idempotent intake (DEC-0119); the news- and historical-provider legal archiving posture remains an open operator item, and the cTrader trendbar price basis is measured per broker at first connection under the verify-or-refuse suite (DEC-0135). No credential-bearing operation is authorized at any of these boundaries.

### The node's two-layer secret store

On the VPS the node keeps secrets in TWO layers (DEC-0197): `systemd-creds` `LoadCredentialEncrypted=`, sealed with an explicit `--with-key=host` (never the default `--with-key=auto`), delivers at service start a node key-encryption key (KEK) and the bootstrap credentials — client id and secret, the initial access and refresh tokens, the cTID account ids, and the escrowed CT-14 payload key. The node keeps ROTATED material — the refresh token dies on use, the access token lives roughly its declared lifetime — under `/var/lib/qmx/state` as AEAD ciphertext under the KEK, so rotation is ordinary unprivileged file I/O for the `qmx` service account: no root, no code change. Host-key sealing survives reboot, migration and rotation but does NOT survive VPS death, so disaster recovery rests on the escrow rule below, not on the seal (DEC-0197).

**Backup payload-key custody** is ruled, not left to a variable (DEC-0217): the CT-14 payload key that decrypts every off-host copy is generated at provisioning ON THE WORKSTATION, escrowed in Windows Credential Manager under `qmx/backup-payload-key` PLUS one operator-held offline copy, and delivered to the VPS as a bootstrap credential. It is never VPS-minted; the VPS-minted KEK protects rotated session material only.

**Rotation is keyed by credential reference, never by connection** (DEC-0197, DEC-0222): at most one refresh is in flight per credential reference, owned by the connection manager as a whole, and every session sharing that credential is a reader of the rotated access token, not a refresher; whether demo and live share one cTID credential is a declared roster fact verified at preflight. An authentication failure attributable to a rotation in flight is a retry-after-refresh condition ONLY for requests carrying no command identity (session auth, account auth, subscription, heartbeat, gap replay, read-back) and is NEVER an UNKNOWN; a `place_order`, `amend_protection`, `cancel_order`, `close_position` or `close_all` that meets an authentication failure is never retried. A failed store after rotation raises an alarm and blocks ENTRIES ONLY, while sensing, exits and protective acts continue (DEC-0197).

**Four named secret holders on the VPS, and no fifth** (DEC-0227, DEC-0197): the **connection manager** (the one in-memory holder of venue session material); the **backup unit** (the CT-14 payload key and the object-storage credentials for one run); the **observability path** (the notification-channel token); and — the declared FOURTH — the **observability STACK**, a separate zero-authority system under its own service account holding its own Grafana admin credential and any log-shipper token, delivered by its own `LoadCredentialEncrypted` line and holding nothing the node holds (DEC-0200). Each systemd unit receives only the credentials its role names; the provisioning wizard is a transient holder on the workstation only.

**Workstation provisioning is enforced, not asserted** (DEC-0197): `qmn`'s composition root refuses to compose on any host whose declared machine tuple is not the deployment roster's VPS entry, the `SecretStore` refuses to construct a venue-session holder off that host, and a tier-1 `check` proves the wizard module imports neither the connection manager nor the refresh duty — so a workstation script can never refresh a token and kill the VPS session mid-trade. After provisioning the VPS session is the ONE live refresher, and the wizard reports which `qmx/*` entries are now stale.

The **compromise-recovery drill is unchanged** — anchored on cTID re-authorization (which invalidates all outstanding refresh tokens), then application-credential reset, store replace, session restart, tested with demo credentials only; its steps are recorded in [OPS-INCIDENT-QMF-V1](incident-playbook.md) (DEC-0197).
