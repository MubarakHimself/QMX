# QMB understanding audit

Evidence reviewed from integration revision `1b451a848d897e42f6e2c7fd9f2ea86fab7295f2` using `git show integration:<path>`: `docs/AGENTS.md`, `docs/components/qmb.md`, `docs/decisions/ADR-0017-qmb-experimentation-library.md`, selected QMB source modules, and the Trading Node component specification. This is a read-only understanding audit. File presence and tests are evidence of implementation shape, not proof that the integrated runtime is installed, exercised, or production ready.

## What QMB is

QMB (`COMP-QMB`) is the application-layer experimentation/backtesting product: one importable Python distribution and the `qmb` CLI, built on six QMF packages plus QML. It is explicitly a library and CLI, never a QMF roster package, engine, kernel, permanent service, or Simulator UI (`docs/components/qmb.md`, lines 15–19; ADR-0017, “Ruling”). The CLI is the product face; the Python API is an in-process sibling for UI backends and research, and MCP is a later sibling door. The Simulator remains a separate consumer.

The design fills the previously reserved “future backtesting library” slot. ADR-0017 records the deliberate build-our-own decision: donor systems (LEAN/Jesse) supplied shapes for reverse engineering, but no donor engine code is adopted; a permanent central service is also rejected. The operator’s governing mental model is config plus logs/ledger: Book/BMS changes materialize inputs, the wind tunnel remains the same, runs are recorded, and completion yields one ledger entry. This is the correct foundation for broad experimentation across QMA and QMB: QMA may propose or request experiments, but QMB owns the reproducible experiment machinery.

## Two operating modes: pure Python versus governed orchestration

The public API door is a thin re-export of the same library surface (`qmb/src/qmb/doors/api/__init__.py`, module docstring). Direct calls return values and produce no governed evidence. The central pure primitive is `qmb.runloop.loop.run()`: it consumes event slices, a stream set, injected clock/handler, execution ports, warm-up, cancellation, limits, and an optional resolved config; it returns a `LoopOutcome` or typed refusal and writes no log or ledger (`qmb/src/qmb/runloop/loop.py`, symbols `run_slice`, `run`, `reproduce_run`, lines 687–1062 in integration source). `run_slice()` executes the pinned six subphases: frontier/stream update, scheduled position events, resting-order execution, closed-data indicator/structure update, strategy intents, then resting newly minted intents for a later slice. Forming bars are not actionable.

When a `ResolvedRunConfig` is supplied, the pure loop can mint the CT-32 performance-result fingerprint, but it still does not persist evidence. Governed evidence enters through the impure orchestrator only. `qmb/src/qmb/orchestrator/spawn.py` exposes `start_run`, `spawn_run`, `spawn_governed`, `spawn_concurrent`, `collect_run`, and `abort_run`: process-per-run isolation, cancellation, per-run limits, output envelopes, and typed aborted outcomes. The orchestrator owns operational logs, WriterId-scoped ledger fragments, and exactly one completed or aborted line per run. `qmb/src/qmb/orchestrator/study.py::stop_study` extends that invariant to a Study: stopping signals each spawned run, preserves completed lines, appends aborted lines for in-flight runs, and leaves a resumable stopped state.

Thus ordinary Python is a first-class user-facing mode for notebooks, local exploration, custom research scripts, and UI calls. It is deliberately weaker in authority: direct Python results are values, not ledgered governed evidence. The governed mode is selected by composing config, data, registry, execution ports, sinks, resource governor, and orchestrator. This split makes experimentation easy to extend without allowing an ad hoc caller to mint evidence or silently claim a result is fit for live money.

## Experimentation breadth and extensibility

QMB is substantially broader than a backtest function. The package exposes config compilation, data catalog/download/verification/gap checks/generation, execution ports for fill/slippage/cost/financing/spread, results and chart-series data, ledger operations, robustness procedures, sweeps, and optimization. The source tree contains dedicated modules under `config`, `data`, `execution`, `results`, `robustness`, `sweep`, `optimize`, `orchestrator`, and `doors`; `qmb/src/qmb/__init__.py` re-exports the public symbols.

Optimization is intentionally generation-stepped. `qmb.optimize.sampler::StudyStepper.ask()` returns an immutable next `ParameterBatch`; a second ask before `tell()` is refused for the adaptive TPE family. `tell()` requires the whole generation, making propose → barrier → condition deterministic even when trial completion order differs (`qmb/src/qmb/optimize/sampler.py`, `StudyStepper`, `trial_label`). `qmb.optimize.objective::StudyCriteria`, `StudyConstraint`, `MinTradesGate`, and `compute_winner_set` evaluate objective/constraints over ledger trial lines, preserving excluded and incomplete trials. `sensitivity::build_sensitivity_report` describes distributions, parameter slices, good-region clusters, and winner stability as canonical series data; it emits no search-quality verdict or edge claim and keeps GAP-0049 deferred.

Extensibility is ordinary Python through ports, adapters, config fragments, handlers, and library functions. A user can supply a `SliceHandler`, execution adapters, data readers, objective/constraint declarations, parameter spaces, custom report consumers, or a QML conformant bot. `qmb/src/qmb/host/adapter.py::construct_conformant_bot` and `drive_instant` show the QL-7 seam: declared-footprint evidence enters a `HostedBot`; Book, clock, and venue commands do not. This preserves user-facing Python extensibility while keeping the money path governed.

## QMA consumption and boundaries

There is an explicit QMA→QMB boundary already defined in integration. `qma.core.ports.qmb` documents the route as **Agent → QMA backtest tool → Backtesting Service → qmb door → QMB** and defines the CLI/MCP door kinds, replay-only request, recorded-evidence reference, one-job-per-ExecutionEnvironment occupancy, and a runtime `QmbDoorTransport`; it explicitly forbids importing the `qmb` package (`qmx-agents/packages/qma-core/src/qma/core/ports/qmb.py`, module docstring and symbols `QmbBacktestRequest`, `build_qmb_door_invocation`, `QmbDoorTransport`, `QMB_ROUTE`). `qma.daemon.backtest.service::BacktestingService` implements the daemon half: one Tool Registry entry, job placement/observation, transport submission, and refusal of QMB-owned scheduling, parallelism, ledger, and artifact concerns (`qmx-agents/packages/qma-daemon/src/qma/daemon/backtest/service.py`, `BacktestingService.invoke/submit/observe_outcome`).

CT-47 defines the records and contract surface: content-addressed `ExperimentSpec`, `BacktestHandle`/`StrategyHandle`, lineage and Experiment Ledger references, replay-only recorded evidence, and QMA’s candidate-only output. However, CT-47 is explicitly `defined-unwired` with `consumers: []`; this means the boundary is specified and source implementations exist in integration, while end-to-end deployment/wiring remains unverified (`docs/contracts/ct-47-qma-experiment-spec.yaml`, header, `purpose`, and invariants). The QMA service’s current transport is recording-oriented in source, so it must not be reported as proof that a live QMB process was reached.

Separately, a user or UI backend may use QMB’s in-process Python API for ordinary exploratory work, and the CLI/orchestrator remains the governed route. That standalone access does not describe QMA’s package relationship: QMA does not import QMB and does not construct or write Books, BMSs, seats, bindings, or promotion records. QMA holds ExperimentSpec references and dev-zone candidate artifacts only; a candidate touching risk/sizing/exit/protection/binding/priority fields requires the specified field-level diff before any approval request. QMA has no execution tool, including paper mode; human promotion outside QMA is the money-path transition (`docs/components/qma-core.md`, lines 25, 73; CT-47 invariants).

QMF remains the contract and primitive layer. QMB consumes QMF core, registry, data, indicators, structure, and risk contracts read-only and may not import qmf-venue. QMF risk owns Book/BMS/CT-22/23/27/28/29/32 definitions; QMF data owns rooms, splits, and journals; registry owns records and lineage. QMB uniquely owns the event-slice loop, config compiler, execution ports, sampler/validation procedures, results, and orchestrator. QML supplies bot definitions and runtime protocol; QMB hosts conformant bots at its composition root while retaining a plain-Python bridge.

Trading Node (`COMP-QMN`) is the live host and sole sanctioned importer/wirer of qmf-venue. It reuses QMB’s same loop through `run_slice`, binding live clocks and venue ports at the node root; QMB must not grow a live edge or depend on QMN (`docs/components/trading-node.md`, “The node drives QMB’s B-2 loop unforked”; ADR-0019). Node replay is diagnostic and unledgered; QMB remains the evidence source for pre-promotion governed replay runs.

## Reuse versus unresolved wiring

Reuse is clear for QMA’s research surface, UI backend, agent task execution, and broad strategy experimentation: call pure Python for fast exploratory work, then route selected candidates through compiled configs and the orchestrator for reproducible governed runs. Reuse is also clear for QMN’s run loop, QML protocol adapter, QMF risk/data/registry contracts, and CT-32/CT-13 artifacts.

Unresolved wiring should remain visible: CT-47 is defined but marked unwired, and the repository does not establish end-to-end process/transport deployment or long-running Study orchestration across QMA and QMB. QMA UI contracts and MCP exposure details remain deferred; QMB’s fidelity taxonomy/calibration content (GAP-0048), search-quality thresholds (GAP-0049), and registration gate remain open/deferred. The source tree’s APIs and tests establish intended behavior and seams, not runtime integration proof. No new architecture or contract should be invented in this audit.
