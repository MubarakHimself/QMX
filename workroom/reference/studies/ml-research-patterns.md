# ML Research Patterns — qlib, mlfinlab, QuantResearch, QuantsPlaybook

**Studied:** 2026-08-17. **Repos:** `reference/repos/qlib`, `reference/repos/mlfinlab`, `reference/repos/QuantResearch`, `reference/repos/QuantsPlaybook`, all read from the local clone (no `git log` available in any of the four — they are plain snapshots, not `.git` checkouts, so "last activity" below comes from in-repo version strings and CHANGELOG entries, not commit history).
**Cross-referenced:** `research/08-mis-ml-regime-models.md` (regime models, look-ahead trap, model registry design), `research/09-experimentation-search-overfitting.md` (DSR/PBO/MinBTL, Optuna, purgedcv), `research/00-qmf-synthesis-module-map.md` (the Ring 7/8 module map this file's findings slot into).

---

## In plain words

1. Four very different things live under "ML research prior art," and QMX needs at most 20% of any of them.
2. **qlib** (Microsoft, MIT) is the only one of the four that is an actual *framework* with a pipeline: raw data → a `Dataset` object that turns it into train/valid/test tables → a `Model` that fits and predicts → a `Recorder` that saves the prediction, the label, and the backtest report together, versioned. It is aimed at Chinese A-share equity factor investing, not forex, but the *shape* of that pipeline — and specifically how it stops a researcher from leaking future data into a training set — is worth copying almost verbatim as a mental model.
3. **mlfinlab** is a technique catalogue, not a framework: bar sampling, labeling, cross-validation, feature importance, bet sizing, backtest statistics. It is the textbook code for López de Prado's *Advances in Financial Machine Learning*. It is genuinely well-written — real triple-barrier labeling, a real purged-embargo cross-validator, real deflated-Sharpe-ratio code — but it is **fully proprietary** (a licensing agreement, not an open-source licence), and the public repo says outright it exists only so users can file bug reports, not to distribute the software. Read it, understand it, do not import it and do not vendor a single function.
4. Of mlfinlab's ~20 modules, most are built for equities with volume bars, dollar bars, and daily-close labels. Only a handful transfer cleanly to retail FX: purged cross-validation, the overfitting statistics, and the general idea of "meta-label a primary signal, then size the bet from the meta-label's probability."
5. **QuantResearch** is one person's personal notebook museum — one `.py` or `.ipynb` file per idea (hidden Markov chains, Kalman-filter pairs trading, PCA, deep-RL trading agents), MIT licensed, no shared framework, no train/test discipline visible in any file inspected. It is useful as a *reading list of techniques* and as a cautionary example of what a research lane looks like with no registry: every file is an island, nothing is comparable to anything else, and there is no way to know how many things were tried before the one that got published.
6. **QuantsPlaybook** is the most structurally interesting of the four for QMX, and it is in Chinese. It is a library of ~100 sell-side broker research reports (from Chinese brokerages — 光大证券, 华泰证券, 招商证券, 国信证券, etc.), each reproduced in its own folder as {the PDF report(s), a Jupyter notebook that replicates it, the supporting code, sometimes the data}. That one-folder-per-idea, cite-the-source, keep-the-reproduction-artifact pattern is exactly the shape QMX's component registry (file `00`, Ring 8) already independently proposed — this repo is prior art that the pattern works at scale (100+ folders) for a solo/small research operation.
7. One QuantsPlaybook folder is directly on-topic: `C-择时类/CSVC框架及熊牛指标` reproduces the exact CSCV/probability-of-backtest-overfitting paper that file `09` already covers from the primary source — corroboration, not new information.
8. The single most important structural finding: qlib's own `Dataset` class accepts **raw date-tuples** for train/valid/test segments (`"train": ("2008-01-01", "2014-12-31")`) directly in the object signature. That is precisely the anti-pattern QMX's data layer (file `02`) already ruled out — "no raw dates in the signature, only a `split_id`." Seeing a mature, widely-used framework ship the anti-pattern is a useful confirmation that the discipline QMX wants is *not* the industry default; it has to be built in on purpose.
9. qlib's leakage defence is real and worth copying exactly: a data-processing pipeline that is explicitly split into "fit this transform on the training segment only" and "apply it everywhere," with a named `fit()` step that must run before inference is possible. That is the single best transferable idea in this whole study.
10. qlib's experiment tracking is a thin wrapper around MLflow — the same 20-dependency tool file `08` already discussed and priced out as not-worth-it for a solo operator. Borrow the *shape* of qlib's `Recorder`/`RecordTemp` API (what fields it captures, how one record type depends on another), not the MLflow dependency.
11. Net verdict for the research lane: qlib supplies the cleanest **pipeline mental model** (Dataset → Model → Record, with a hard fit/predict split and an artifact-dependency chain); mlfinlab supplies a **verified reference implementation** of the statistics file `09` already specified (useful as a design-study oracle, not as code); QuantsPlaybook supplies the **registry-shaped research habit** QMX should adopt operationally; QuantResearch is mostly noise, valuable only as a "here is what happens with zero framework" warning and a source of technique names to look up properly elsewhere.

## How it is built

### qlib — Dataset → Model → Workflow → Recorder

Source root: `reference/repos/qlib/qlib/`. Licence: MIT (`reference/repos/qlib/LICENSE`).

**Data pipeline** (`qlib/data/dataset/handler.py`, `qlib/data/dataset/__init__.py`):

- `DataHandler` loads raw data via a `DataLoader` and exposes `fetch()`.
- `DataHandlerLP` ("**L**earnable **P**rocessors") is the leakage-defence core. It keeps three named views of the data, keyed by `DK_R` (raw), `DK_I` (processed for inference), `DK_L` (processed for learning) — `reference/repos/qlib/qlib/data/dataset/handler.py:52-54, 382-434`. Two processor lists, `infer_processors` and `learn_processors`, are declared separately, plus `shared_processors` that both branches receive first.
- **The load-bearing method is `fit()`** (`handler.py:513-519`): it calls `proc.fit(self._data)` for every processor in order — i.e. any processor that needs to learn parameters (a scaler's mean/std, a winsorizer's clip bounds) learns them once, from a designated segment, *before* `process_data()` is allowed to run. `process_type` (`PTYPE_I` = independent, `PTYPE_A` = append, `handler.py:425-434`) controls whether the learn-branch reuses the infer-branch's fitted state or starts fresh — this is the closed-form answer to "does my scaler for the model see the same numbers as my scaler for the report."
- `DatasetH.prepare(segments=..., col_set=..., data_key=...)` (`qlib/data/dataset/__init__.py:185-247`) is the single door a `Model` calls through. **But note finding 8 above:** `segments` in the constructor (`__init__.py:84-118`) is a plain dict of raw `("YYYY-MM-DD", "YYYY-MM-DD")` tuples — there is no split-registry indirection at all.

**Model** (`qlib/model/base.py`, 111 lines total, read in full):

```python
class Model(BaseModel):
    def fit(self, dataset: Dataset, reweighter: Reweighter): ...
    def predict(self, dataset: Dataset, segment="test") -> object: ...
class ModelFT(Model):
    def finetune(self, dataset: Dataset): ...
```

That is the entire contract. A model never sees a DataFrame directly in its public signature — it always receives a `Dataset` and a segment name, and pulls `x_train`/`y_train`/`w_train` out of it via `dataset.prepare(...)` inside `fit()`. The docstring (`base.py:34-52`) explicitly shows how to fall back to `pd.DataFrame(np.ones_like(...))` when no `weight` column exists — sample weighting is a first-class, optional input, not bolted on.

**Workflow / task templates** (`qlib/workflow/task/gen.py`): experiments are **plain dicts** ("task templates"), and a `TaskGen.generate(task) -> List[dict]` produces variations — e.g. a `RollingGen` turns one task template into N tasks, one per rolling window. `task_generator([templates], [generators])` composes multiple generators multiplicatively (`gen.py:16-50`). This is qlib's answer to walk-forward re-fitting: the *rolling* structure is a `TaskGen`, not a special-cased loop inside the backtest engine.

**Experiment tracking** (`qlib/workflow/recorder.py`, `qlib/workflow/exp.py`): `Recorder` is an abstract base ("designed similar to mlflow," `recorder.py:29`) with `start_run()`/`end_run()`, `log_params(**kwargs)`, `log_metrics(step=None, **kwargs)`, `save_objects(...)`, `load_object(name)`, and a status machine `SCHEDULED → RUNNING → FINISHED/FAILED`. The real implementation (not read in full here, but imported at the top of `recorder.py`) is `mlflow`-backed, including Azure Blob artifact storage support.

**Record dependency chain** (`qlib/workflow/record_temp.py`, 693 lines, first 220 read in full): `RecordTemp` is the base class for a *derived artifact* — `SignalRecord` (runs `model.predict(dataset)`, saves `pred.pkl` + `label.pkl`), and (by the pattern, not fully read here) `SigAnaRecord`/`PortAnaRecord` downstream of it. Two mechanisms matter:
- `depend_cls` (`record_temp.py:35-36, 104-107, 156-158`): a record can declare which other record type it depends on; `load()` and `check()` walk up that chain automatically via `class_casting`, so a `PortAnaRecord` can transparently load `pred.pkl` that a `SignalRecord` produced without either record hard-coding the other's path.
- `artifact_path` + `get_path()` (`record_temp.py:34, 39-47`): every record type owns a namespaced sub-path under the recorder's artifact store, so multiple record types can coexist under one experiment run without collision.

### mlfinlab — technique catalogue, not a framework

Source root: `reference/repos/mlfinlab/mlfinlab/` (~8,500 lines across 20 module directories, read via directory listing + targeted `grep`/`Read`). Licence: **proprietary** — `reference/repos/mlfinlab/LICENSE.txt`, described in the README as "all rights reserved," offered under "Business" / "Enterprise" tiers via `hudsonthames.org`. The README states plainly: *"This repo is public facing and exists for the sole purpose of providing users with an easy way to raise bugs, feature requests, and other issues"* — i.e. even though real, substantial source is present in this snapshot, the project's own stated intent is that this is not the distribution channel.

Module inventory (`ls mlfinlab/mlfinlab/`): `data_structures` (tick/volume/dollar bars), `labeling` (triple-barrier, fixed-time-horizon, bull/bear, excess-over-mean/median), `sample_weights`, `sampling` (sequential bootstrap), `cross_validation` (`PurgedKFold`, `pct_embargo`), `backtest_statistics` (`CampbellBacktesting`, plus `sharpe_ratio`/`probabilistic_sharpe_ratio`/`deflated_sharpe_ratio`/`minimum_track_record_length` in `statistics.py`), `bet_sizing` (`ef3m.py` — fits a mixture of two Gaussians to the primary model's scores for probabilistic bet sizing), `feature_importance` (MDI/MDA/SFI style), `microstructural_features`, `structural_breaks`, `filters` (CUSUM-style event filters), `codependence`, `networks`, `clustering`, `regression`, `ensemble`, `multi_product`, `data_generation`, `datasets`, `util`.

Two files read directly, confirming the design matches the papers file `09` already cited from primary sources:

- `mlfinlab/labeling/labeling.py:13-81` — `apply_pt_sl_on_t1`, `add_vertical_barrier`, `get_events` implement the triple-barrier method exactly as described in AFML: a profit-take barrier, a stop-loss barrier, and a vertical (time) barrier, with `min_ret` as a noise filter.
- `mlfinlab/cross_validation/cross_validation.py:40-107` — `class PurgedKFold(KFold)` takes `pct_embargo: float` directly in its constructor; this is the same purge+embargo construction file `09` §3 covers via `purgedcv`, here as the original López de Prado formulation.
- `mlfinlab/backtest_statistics/statistics.py:122-215` — `sharpe_ratio`, `probabilistic_sharpe_ratio`, `deflated_sharpe_ratio`, `minimum_track_record_length` are present as named, separate functions — direct corroboration of file `09`'s PSR/DSR/MinBTL findings from an independent, London-School-of-Economics-adjacent implementation.

### QuantResearch — a notebook museum

Source root: `reference/repos/QuantResearch/` (MIT, `LICENSE` confirms "Copyright (c) 2020 Letian Wang"). Structure: `notebooks/` (one file per statistical idea — `hidden_markov_chain.py`, `kalman_filter_linear_regression.py`, `pairs_trading_kalman_filter.py`, `mean_reversion.py`, `cointegration_pairs_trading.py`, `principal_component_analysis.ipynb`, `arima_garch.ipynb`, `gaussian_mixture_markov_switching.ipynb`), `ml/` (deep-RL trading agents: `dqn.ipynb`, `ppo.ipynb`, `a3c.ipynb`, `reinforcement_trader.py`), `backtest/bt/` (one strategy per file — `bollinger_bands.py`, `dual_thrust.py`, `turtle.py`, `r_breaker.py` — small, single-file backtest scripts, no shared engine beyond a thin `bt` wrapper).

`mean_reversion.py` (105 lines, read in full) implements a Hurst exponent estimator and a variance-ratio test as free functions — no train/test split, no class, no persisted state; it is a scratch calculation, not a pipeline stage. `hidden_markov_chain.py` was grepped for split/train-test discipline and none was found. This is consistent across the notebook set: **each file is a standalone script demonstrating a technique on one dataset, once** — there is no registry, no versioning, no artifact store, and (from what was inspected) no visible purge/embargo discipline anywhere in this repo.

### QuantsPlaybook — the report-reproduction registry pattern

Source root: `reference/repos/QuantsPlaybook/` (**no LICENSE or COPYING file found** — confirmed by directory search — licence status UNKNOWN; content is heavily Chinese, translated below). Top-level categories, from `README.md`: `A-量化基本面` (quant fundamentals), `B-因子构建类` (factor construction), `C-择时类` (market timing), `D-组合优化` (portfolio optimization), plus two shared code libraries, `hugos_toolkit/` and `SignalMaker/`.

The repeating structural pattern, verified by directory listing of `C-择时类/`: each idea gets its own folder containing (a) the original broker research-report PDF(s) — e.g. `C-VIX中国版VIX编制手册/`, `RSRS择时指标/20170501-光大证券-...RSRS...pdf`, `CSVC框架及熊牛指标/20190617-华泰证券-...基于CSCV框架的回测过拟合概率.pdf` (this is literally the CSCV/PBO paper file `09` §3 already covers first-hand) — (b) a `.ipynb` notebook that reproduces the report's method end to end, (c) a `src/` or `py/` folder with the extracted implementation, and (d) sometimes a `参考/` (references) folder and a `Data/` folder. `hugos_toolkit/` factors out the pieces every folder needs in common: `BackTestReport/` (`performance.py`, `tear.py`, `timeseries.py` — a tearsheet generator) and `BackTestTemplate/` (`backtest_engine.py`, `bt_strategy.py` — a shared Backtrader-based harness), so individual idea-folders reuse one report generator and one backtest scaffold instead of reinventing both per idea. `SignalMaker/` is a small shared library of the indicator signals used across multiple folders (`qrs.py`, `hht_signal.py`, `noise_area.py`, `vmacd_mtm.py`, `alligator_indicator_timing.py`).

The README (`reference/repos/QuantsPlaybook/README.md`, translated) states the project's purpose directly: *"Reproduce brokerage financial-engineering research reports using Python… every folder has the corresponding brokerage report and related papers; the .py files are the reproduction of the .ipynb documentation."* It lists qlib and Backtrader as its own dependencies, and cites data sources JQData and Tushare (Chinese A-share market data providers — not usable for QMX's forex focus, but irrelevant to the structural pattern being borrowed).

## Mental models worth borrowing

1. **Idea:** A dataset object splits every transform into "fit-once-on-a-designated-segment" and "apply-everywhere," with the fit step named and mandatory before inference is possible.
   **Where it lives:** `qlib/data/dataset/handler.py:382-519` (`DataHandlerLP`, `infer_processors`/`learn_processors`, `fit()`).
   **Why it matters for QMF:** This is the single cleanest structural defence against a scaler, winsorizer, or normalizer silently peeking at validation/test data — the exact leakage vector file `08` §7.4 and file `09` flag as "the leak moves into feature scaling, not the model." A property test alone (file `08` §2.3's invariant) catches leakage in a *labeller*; this pattern prevents leakage in *preprocessing*, which is a different failure mode the earlier files did not fully cover.
   **How QMF would implement it:** Give `qmf.experiment`'s dataset-preparation step (or a `qmf.data.features` transform layer, whichever ring ends up owning it) an explicit two-phase contract — `fit(split_id)` then `transform(any_segment)` — and make it a registration-time error to call `transform()` before `fit()` has run on that transform's declared fit segment. This slots directly under Ring 1/2 in file `00`'s module map, next to `qmf.data.splits`.

2. **Idea:** A model's public contract is exactly two methods, `fit(dataset, ...)` and `predict(dataset, segment)` — the model never sees a raw DataFrame in its signature, only a `Dataset` plus a segment name.
   **Where it lives:** `qlib/model/base.py:1-111` (`BaseModel`, `Model`, `ModelFT`), read in full.
   **Why it matters for QMF:** File `00` Ring 3 already specifies `qmf.models` as a registry of frozen artifacts with `input_contract`/`causality`/`fitted_through` metadata. qlib shows the runtime *interface* half of that idea working in production: because the model only ever asks the dataset for a named segment, swapping "the walk-forward validation fold" for "the live tail" is a one-line change at the call site, not a different code path. This is the same "simulator is just another implementation" principle file `00`'s novel-ideas §2 already proposes for `SimBroker` — qlib shows it applied one layer up, to models.
   **How QMF would implement it:** `qmf.models`' loader-side contract should mirror this shape: `model.predict(features, as_of=...)` where `features` comes from the same accessor whether it's backtest replay or live inference — never a bespoke "live path" that diverges from "research path" in how it assembles inputs.

3. **Idea:** Experiments are declarative task templates (plain dicts), and structural variation — especially walk-forward rolling — is produced by a separate `TaskGen` that maps one template to many concrete tasks, rather than being a special case hard-coded into the backtest loop.
   **Where it lives:** `qlib/workflow/task/gen.py:1-90` (`TaskGen`, `task_generator`, the `RollingGen` pattern it's built to support).
   **Why it matters for QMF:** File `09` §14 already establishes that `qmf.experiment` must own the search loop via Optuna's ask-and-tell so it owns the refusal point. qlib's `TaskGen` is a complementary idea at a different altitude: it separates "what varies" (the generator) from "what stays fixed" (the template), which is exactly the shape needed to generate a family of rolling-window re-fits from one `Experiment` definition without writing a bespoke loop per experiment.
   **How QMF would implement it:** A `qmf.experiment.RollingSplitGen` that takes one experiment template plus a cadence (e.g. "refit quarterly") and emits N concrete `Experiment` objects, each with its own `split_id` drawn from `qmf.data.splits` — composable with, not competing against, the split-budget ledger from file `09` §14.4.

4. **Idea:** A derived research artifact (a backtest report, a signal analysis) declares which other artifact it depends on, and can load/verify that dependency's outputs by walking the declared chain automatically, with a namespaced storage path per artifact type.
   **Where it lives:** `qlib/workflow/record_temp.py:28-210` (`RecordTemp.depend_cls`, `RecordTemp.load(parents=True)`, `RecordTemp.check(parents=True)`, `RecordTemp.get_path()`, and the concrete `SignalRecord`).
   **Why it matters for QMF:** File `00` Ring 8's registry already specifies content-addressed manifests and a `supersedes` pointer for lineage between *registered components*. qlib's `RecordTemp` chain is the same idea one level down, for the *artifacts an experiment produces* (predictions → signal analysis → portfolio analysis), and it solves the practical problem of "can I regenerate just the report without re-running the model" via `check(include_self=True)` before regenerating.
   **How QMF would implement it:** Give `qmf.experiment`'s result object a small `depends_on` graph (prediction log → overfit statistics → promotion decision) with the same load-with-fallback-to-parent behaviour, so a partially-completed experiment run can be resumed or partially regenerated instead of always re-run from scratch.

5. **Idea:** Every research idea gets one folder containing the source document, the reproduction code, and (where applicable) the data — citation and implementation live next to each other, permanently, at the scale of 100+ ideas.
   **Where it lives:** `QuantsPlaybook/C-择时类/*` (e.g. `RSRS择时指标/`, `CSVC框架及熊牛指标/`), and the pattern repeated across `A-`, `B-`, `D-`.
   **Why it matters for QMF:** File `00`'s `ComponentDef` manifest already specifies a `definition_source` field ("pointer into the research store: paper, video timestamp, chat message," file `00` line 165) as an open question (`09` OQ9). QuantsPlaybook is direct evidence that the one-folder-per-idea pattern scales to 100+ entries maintained by (effectively) one person, without a database or a service — it is filesystem discipline, not tooling. It is the strongest single piece of evidence in this whole study that QMX's `evidence_state`/`definition_source` design (file `00` novel idea §9) is operationally cheap.
   **How QMF would implement it:** Make `qmf.registry`'s on-disk layout mirror this directly — one directory per `component_id`, containing the manifest JSON, a `sources/` subfolder for the paper/screenshot/chat-log that justified the component, and the reproduction notebook or script an LLM agent (or Mubarak) used to validate it before registration.

6. **Idea:** A meta-label's probability output is converted into a bet size via a principled function (e.g. fitting a two-Gaussian mixture to the score distribution), not an ad hoc linear scaling.
   **Where it lives:** `mlfinlab/bet_sizing/ef3m.py` (design study only — proprietary licence).
   **Why it matters for QMF:** File `00`'s `qmf.book` (Ring 4) already establishes that a `Signal` carries conviction, never quantity, and that `qmf.book` alone converts conviction to size. This is a concrete worked example of *one* defensible conviction→size mapping technique, useful as a design reference for `qmf.book`'s sizing-policy catalogue — but note the input here is a classifier's probability, which only exists if QMX ever ships a genuine ML classifier (file `08`'s MIS), not for hand-authored Triggers.
   **How QMF would implement it:** If/when `qmf.mis` ships a classifier whose output feeds a Confirmation weight, `qmf.book` could offer a "probability-to-conviction" sizing policy shaped like this — as an independently-implemented QMF function, never as a dependency on or port of mlfinlab's code.

## What to avoid

1. **Raw date-tuples in a dataset's public constructor.** `qlib/data/dataset/__init__.py:107-117` — `DatasetH`'s documented example is `'segments': {'train': ("2008-01-01", "2014-12-31"), ...}`. This is a mature, widely-cited MIT framework shipping exactly the anti-pattern QMX's data layer already ruled out in file `02` ("raw dates do not exist in the signature," reaffirmed file `00` line 72). Evidence that this discipline needs deliberate enforcement — nothing in the ML-framework ecosystem defaults to it.

2. **A tracking layer bolted straight onto MLflow.** `qlib/workflow/recorder.py:1-25` imports `mlflow` at module scope and even imports `mlflow.store.artifact.azure_blob_artifact_repo` unconditionally — a cloud-storage dependency pulled in for every user regardless of whether they use Azure. File `08` §7.1 already priced MLflow's real cost for a solo operator (11.2 MB wheel, 20 core dependencies, Flask/SQLAlchemy/cryptography/matplotlib) and recommended a versioned-folder-plus-JSON-manifest instead. qlib's `Recorder` *API shape* is worth copying (finding 4 above); its *implementation* is exactly the dependency weight file `08` already said to avoid.

3. **mlfinlab is proprietary despite looking like an open-source repo on GitHub.** The README states the public repo exists "for the sole purpose of… bug reports," not distribution, and `LICENSE.txt` is a commercial licensing agreement, not an OSI licence. Yet this local snapshot contains ~8,500 lines of real, working implementation. That mismatch is itself a flag: **do not assume any public GitHub URL implies permissive terms** — read the `LICENSE` file every time, as this study's brief instructed, before treating any code as more than a reading reference. Nothing from `mlfinlab/` may be imported, vendored, or paraphrased into QMF's source tree; every finding above from mlfinlab is explicitly "design study" per the task's licence policy.

4. **A notebook museum with no registry is a real failure mode, not a hypothetical one.** QuantResearch's `notebooks/` and `ml/` directories are ~20 standalone scripts/notebooks, each demonstrating one technique once, with no shared split discipline visible in the files inspected (`mean_reversion.py`, `hidden_markov_chain.py` — no train/test separation of any kind). This is exactly the shape file `09`'s "unreadable Sharpe" warning describes: there is no way, from this repo alone, to know how many variations of the Hurst-exponent or HMM idea were tried before the version that got committed, because nothing tracks trial count. It is a legitimate *exploration*-lane pattern (file `00`'s three-tier Explore/Validate/Confirm design already scopes exactly this kind of unlimited, unreportable tinkering) but it must never be confused with a Validate- or Confirm-lane result, and QMX's registry should make that distinction structural, not a matter of the researcher remembering which lane they were in.

5. **Deep-RL trading agents as a first research investment.** `QuantResearch/ml/` devotes roughly half its content to policy-gradient/actor-critic trading agents (`dqn.ipynb`, `ppo.ipynb`, `a3c.ipynb`, `reinforcement_trader.py`) trained on a single equity (`SPY`) over a short window (`reinforcement_trader.py:9-23`, `sd='2015'` to `ed='2020'`). Per file `09`'s arithmetic, an RL agent explores its state-action space far more exhaustively than any grid or GA search — the false-strategy theorem applies with a much larger effective N. Nothing in the inspected code shows deflation, purge/embargo, or held-out evaluation. This is a caution, not a technique to adopt: an RL trading agent is one of the most search-budget-hungry things QMX could build, and file `09`'s ledger discipline would need to be airtight before one is attempted.
