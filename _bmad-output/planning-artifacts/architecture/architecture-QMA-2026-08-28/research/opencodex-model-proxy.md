## The six questions

### (1) Target mental model
A model call names an **intent, not a vendor**: the caller asks for a capability class and the system deterministically resolves it to a concrete upstream deployment + credential + wire protocol, load-balancing over a pool of equivalent deployments/accounts with health, quota, affinity, cooldown and failover — the caller never sees provider, account, or protocol. OpenCodex's own words: "one virtual model id with failover or weighted round-robin across providers"; a "local proxy that translates Codex's Responses API into whatever your provider speaks — streaming, tool calls, reasoning tokens, images, in both directions" (README, checked 2026-08-28). No LLM decides routing — it is a deterministic load balancer (transcript row 51; Constitution §2). This is exactly QMX's `ModelClass → Deployment → Credential`.

### (2) Concrete runtime / API structures (real names)
**Ingress (how clients connect):** BOTH surfaces. OpenAI-compatible endpoint at `http://127.0.0.1:10100/v1` (Responses API + Chat Completions), auto-injected into Codex as `openai_base_url` (README; issue #324). Anthropic-compatible surface for Claude Code / Claude Desktop (repo has `src/claude/`). Binds loopback with no auth by default; binding to `0.0.0.0` "requires a bearer token — the proxy refuses to start without" one (README).
**Provider record** (`config.json → providers.<id>`, live): `adapter` (`openai-responses`|`openai-chat`), `baseUrl`, `authMode` (`forward`|`oauth`|`key`), optional `codexAccountMode:"pool"`, `defaultModel`, `models[]`, `liveModels`, and a rich **per-model capability map**: `modelContextWindows{model:int}`, `modelInputModalities{model:[text,image]}`, `modelReasoningEfforts{model:[low..max]}`, `modelDefaultReasoningEfforts`, `modelReasoningEffortMap{model:{canonical→provider}}`, `noVisionModels[]`, `noReasoningModels[]`, `noTemperatureModels[]`, `noTopPModels[]`, `noPenaltyModels[]`, `parallelToolCalls`, `preserveReasoningContentModels[]`, `autoToolChoiceOnlyModels[]`.
**Combo record** (`config.json → combos.<virtualId>`, live) = a named routing policy: `strategy` (`round-robin`|`failover`), `stickyLimit:int`, `defaultEffort`, `targets:[{provider, model, weight}]`. Real: `epic-builder-workhorse` = weighted round-robin (ox-alpha-free w4, deepseek-v4-flash w3, gpt-5.6-terra w2, gpt-5.5 w2, gpt-5.6-luna w1); `epic-builder-repair` = failover (deepseek-v4-pro→gpt-5.5→gpt-5.6-terra→ox-alpha-free).
**Account pool** (top-level, live): `accountPoolStrategy:"quota"` (also `round-robin`, `fill-first` per README), `accountPoolStickyLimit:1`, `activeCodexAccountId`, `codexAccounts[]` = `{id,email,plan,isMain,logLabel,planSource,planCredentialGeneration}`. README: "new sessions … use the lowest-usage healthy account; round-robin and fill-first use their own policies … existing Codex threads normally retain affinity to the account that started them … quota re-evaluation, failover, account exclusion, affinity expiry, or 401/403 and 429 recovery can rebind them." Accounts can be given a **selection order** (last-resort account).
**Observability (live):** `routing-history.sqlite` (+wal/shm) = routing-decision history; `usage.jsonl` (7.5 MB) = usage stream; `codex-quota-cache.json` = per-account `{weeklyPercent,weeklyResetAt,shortPercent,shortResetAt,shortWindowSeconds,resetCredits}`; `config-mutation.sqlite`; `service.log`. Dashboard shows "providers, OAuth status, model selection, and a live request log with cache token counts" (README).

### (3) Failure modes it solved
1. **Quota exhaustion / 429** → quota-aware routing to lowest-usage healthy account across 5h/weekly/30d windows. 2. **Credential failure (401/403)** → fail-closed auth, account exclusion + rebind. 3. **Provider/model outage** → failover combos. 4. **Conversation incoherence** → thread/account **affinity** + `stickyLimit` so long SSH/tmux/mobile sessions don't jump mid-conversation. 5. **Protocol mismatch** → bidirectional translation Responses↔Chat↔Anthropic incl. streaming, tool calls, reasoning tokens, images. 6. **Capability mismatch** → per-model `noVision/noReasoning/modelContextWindows` maps stop unsupported payloads (issue #1043: image_url forwarded to a text-only zen model → 400 — the exact failure the maps prevent). 7. **Cross-provider reasoning-effort skew** → `modelReasoningEffortMap` normalizes canonical→provider effort. 8. **Cost** → weight free/cheap models first (ox-alpha-free w4).

### (4) What QMX should reuse conceptually
- **Virtual-id indirection** `Model→Deployment→Credential` — caller binds to a logical name, never a vendor/account (transcript rows 51,52).
- **Combo = named routing policy over a pool** (`failover` | `weighted round-robin`, sticky, ordered targets). This is precisely QMX's **ModelClass** primitive; the operator's `epic-builder-*` combos already prove the shape in production.
- **Account as a routing dimension** separate from provider, with quota-aware / round-robin / fill-first strategies and a stickyLimit — directly supports transcript row 56 (multi-account routing across paid subs + API keys).
- **Deterministic policy** (quota + health + affinity + cooldown + failover), no LLM in the loop — matches Constitution §2 and the LiteLLM row 273 primitives QMX said it would "implement… ourselves."
- **Per-model capability map as first-class data** returned to the compiler (context window, modalities, tools, reasoning efforts) — this is QMX's `ModelCapabilities` (row 55; Constitution §7).
- **authMode taxonomy** `forward|oauth|key` = the transcript's separate **Credential Broker** (row 53); OAuth refresh with expiry + `refreshGrantFingerprint` + `lastValidationStatus`.
- **Observability shape**: routing-decision history + usage stream + live request log with cache-token counts — harness-authored telemetry, separate system (Constitution §12).

### (5) What QMX should reject — INHERITED FASHION (multi-harness / multi-tenant / public)
- **The entire foreign-harness shim layer** — translating *Codex's* Responses API, injecting `openai_base_url` into someone else's app, `codexShimAutoRestore`, `ocx stop` "restores Codex to its original configuration," v1/v2 sub-agent **surface control**, Codex-Desktop catalog injection, Cursor `apply_patch` translation. QMX **owns its harness**, so it never masquerades as another product's backend. [INHERITED FASHION]
- **The `ocx-*.md` "lie to the harness" pattern** (local): agent files carry `<!-- ocx-route: … -->` and a system prompt telling the worker "your ACTUAL model is X … the proxy routes this session there regardless of what the harness displays," with a placeholder `model:"haiku"`. That is a workaround for *not* owning the caller. QMX knows the true deployment and records it honestly. [INHERITED FASHION]
- **The web dashboard as the config surface** — QMX config is a code/registry contract, not a GUI. [INHERITED FASHION]
- **Plaintext credential files** in `~/.opencodex` (`auth.json`, `codex-accounts.json` hold OAuth access/refresh tokens on disk). QMX Credential Broker must use the OS secret store (operator already keeps broker creds in Windows Credential Manager) — not home-dir JSON.
- **The ToS-evasion framing** of multi-account subscription pooling — README itself warns "Account pooling is for routing and operational resilience only; it does not guarantee protection from [provider enforcement]." QMX treats multi-account as legitimate capacity, not subscription-farming.
- **40+ built-in providers + i18n + Cursor/Grok-Build adapters** — public-breadth surface; QMX needs only its own pool (GPT/Claude frontier + DeepSeek/Qwen/GLM/Kimi/xAI/local). [INHERITED FASHION]

### (6) The QMX-owned Model Proxy contract
`ModelClassRequest → Router(RoutingPolicy over Deployment Registry) → Credential Broker`, all deterministic; the router is "just an availability-aware load balancer" (row 51).

**ModelClassRequest** `{ model_class: REASONING_HIGH|WORKHORSE_GENERAL|CODING_HIGH|FAST_CHEAP|VISION, min_context_tokens, needs:{tools,vision,reasoning_effort,parallel_tool_calls}, affinity_key (session/thread/mission), budget_hint, exclude[] }`. Harness picks the class (row 54); router picks the deployment.

**RoutingPolicy** (QMX's owned generalization of a combo) `{ strategy: failover|weighted_round_robin|quota_lowest|fill_first, sticky_limit, targets: <eligible deployments filtered by capability∧health∧quota> }`.

**Deployment record** fields (row 52 + OpenCodex evidence): `id; provider_id; upstream_model; protocol/adapter (responses|chat|anthropic|local); base_url; credential_ref (→ broker, NEVER inline); account_ref; capabilities (see below); health{state,last_ok_at,cooldown_until,consecutive_failures}; quota{window→percent_used, reset_at, healthy}; rate_limit_state; latency_p50/load; cost_in/out_per_token; weight; enabled`.

**ModelCapabilities** returned to the **Context Compiler** `{ context_window, input_modalities, supports_tools, supports_vision, reasoning_efforts+default+effort_map, temperature/top_p/penalty_support, max_output, cost }`. Compiler compiles effective context to *this* deployment's budget (Constitution §7); for RLM agents, large objects become **handles** so small-context strong models stay eligible (row 55).

**Credential Broker** `resolve(credential_ref) → {auth_mode: oauth|api_key|forward|local, secret}` with refresh/expiry/validation-status, fail-closed on 401/403, backed by **OS secret store**. Accounts are a pool dimension carrying per-account quota + affinity (row 53).

**Router telemetry** (harness-authored, separate from any ledger — Constitution §12): routing-decision record (chosen deployment+account, policy, sticky/affinity hit, failover chain, reason), usage stream, health/quota transitions.

### Can OpenCodex sit BEHIND this contract as the first implementation?
**Yes — as one opaque backing Deployment/Broker for the providers where its pooling is genuinely hard to rebuild, not as QMX's source of truth.** A QMX `Deployment` would set `base_url=http://127.0.0.1:10100/v1`, `protocol=openai-responses|chat` (or the Anthropic surface), and its `upstream_model` = an OpenCodex **combo id**, delegating failover/round-robin/quota/affinity/cooldown to OCX.
**GAINED (working today, zero build):** multi-account ChatGPT/Codex + xAI/Kimi/Gemini **OAuth pooling**, quota-aware routing (5h/weekly/30d), OAuth refresh, bidirectional protocol translation, 40+ providers, combos, live dashboard. It is literally the operator's current model plane.
**LOST / risks:** (a) **Capabilities go opaque** — OCX hides which concrete model/account served a combo and **synthesizes generic 128k/text placeholders for combo rows** (README: "their values are placeholders, not assertions"), so QMX must keep its **own** per-deployment capability map and never trust OCX's for context budgeting. (b) **Routing decisions happen inside OCX** — QMX loses deterministic control + audit (decision history is OCX's `routing-history.sqlite`, not QMX telemetry), against "infrastructure owns the state." (c) **Credential custody stays in OCX plaintext home files**, not QMX's secret-store broker. (d) It is built as a **foreign-harness shim** (Codex/Claude Code); running QMX's own runtime through it inherits the model-identity spoofing and v1/v2 surface quirks. (e) **Third-party single-maintainer npm dependency** with fast churn and an explicit account-pooling ToS disclaimer.
**Recommendation:** adopt OCX behind the `Deployment`+`Broker` contract as the FIRST implementation for exactly the subscription-pool/OAuth providers, treating each OCX combo as one Deployment annotated with a **QMX-owned** capability record; keep the RoutingPolicy layer, Capability Registry, and Credential Broker QMX-owned (LiteLLM-style primitives in-house, row 273) so OCX can later be swapped out without touching the `ModelClass` contract. Do not let `~/.opencodex/config.json` become the QMX registry.

## Open questions this reference cannot settle
- **Daemon language for the router** (TS vs Python) is unresolved in the transcript; OCX being TS/Bun is a data point, not a decision.
- Whether QMX's own harness should ever call OCX's Anthropic surface, or only its OpenAI `/v1` surface, given the foreign-harness spoofing behavior.
- Whether multi-account pooling is acceptable under each provider's ToS for QMX's single-operator use — the README explicitly disclaims this; a governance ruling is needed.
- OCX's routing decisions are not exportable as QMX telemetry today; a clean seam (or a fork that emits QMX-format decisions) is unspecified.
- The RLM "objects→handles" budgeting depends on QMX-owned capabilities; OCX cannot supply trustworthy per-call context windows for combos.
