# Cluster 6: Loop Engineering & Multi-Agent Topology

Scope: loop engineering, budgets/stop-rules/escalation as kernel-level concerns, multi-agent topology as data vs code. Read via AlphaXiv/arXiv full text (firecrawl research reader). All four papers reachable and fully read (no coverage gaps).

## 2607.00038 — Stop Hand-Holding Your Coding Agent: Engineering the Loops that Replace Step-by-Step Prompting

**Type**: Position paper + descriptive corpus study (50 real loops, hand-coded by one author). No controlled experiment, no benchmark, self-declared.

**Core mechanism (faithful)**: Defines a "loop specification" as a distinct third object — NOT an ordinary programming loop, NOT the harness's internal perceive-act-observe cycle (ReAct-style, exists by default) — but an external, bounded, reusable artifact a human hands to a harness (Claude Code, Codex). Five parts: **trigger** (person/schedule/event), **goal** (preferably verifiable), **execution** (agent calls named skills), **verification** (a 5-level ladder: L1 deterministic, L2 rule-based, L3 objective-but-fuzzy, L4 model-as-judge, L5 human — corpus shows 70% sit in L1/L2 "autonomous zone"), and a **stopping rule** that drives to a *named* terminal state (success, no-op, blocked, stalled, exhausted) — "never mistaking an error for success." State/memory persists on disk, not in conversation context (cites lost-in-the-middle). Golden rule for when a loop is even justified: "only when feedback changes the next action" — otherwise it's a scheduled one-shot, not a loop.

Design principles grounded in cited literature (not the authors' own experiments): self-correction without external feedback doesn't reliably work; generator=judge causes spontaneous reward hacking; specification gaming (editing the test instead of the code) is a documented, hard-to-remove behavior. Mitigation is always structural — separate maker from checker — never exhortative.

**Evidence quality**: Low-moderate. Descriptive coding of one public catalogue (Loop Library) by a single coder, explicitly not a random sample, no causal claims drawn. Design principles are borrowed from cited primary literature on self-correction/reward-hacking (those are stronger), applied to loops by argued analogy, not measured.

**What QMA should borrow**: The 5-part anatomy as a literal schema for a kernel-level "loop"/mind-invocation config object (trigger, goal, verification-level, terminal-states, memory-location) — the paper explicitly recommends exactly this: *"harnesses should expose trigger, verification level, architecture, terminal states and memory as first-class configuration, so that a loop's position in our taxonomy is declared rather than buried in a script."* Named terminal states (not just "stopped") prevent silently treating exhaustion/error as success. The maker/checker separation as a structural (not prompted) rule.

**What to reject and why**: Don't treat the 50-loop corpus statistics as evidence of what *works* — they only describe what practitioners currently do, with no outcome measurement attached. Don't adopt the specific verification-ladder percentages as targets.

**Kernel implications**: Argues FOR kernel-level declaration of loop control (trigger/verification/stop-state/memory as config, not code) — directly supportive of a scoped-constants style declarative loop contract. Also flags a genuine simpler-than-framework option worth noting: the "Ralph loop" (a bare shell loop replaying the same prompt with a fresh context each turn, all state in files) is held up by practitioners as the purest, most robust case — a data point that a minimal loop harness with externalized state can beat a heavier one, at least for this narrow pattern.

## 2607.01641 — When Agents Do Not Stop: Uncovering Infinite Agentic Loops in LLM Agents

**Type**: Empirical/tooling paper. IAL-Scan: static analyzer evaluated on 6,549 real LLM-agent repos.

**Core mechanism (faithful)**: Defines "Infinite Agentic Loop" (IAL) as a structural failure where an agentic feedback path (model call → tool/state update → back to model call) repeatedly reaches costly or state-growing operations **without an effective bound covering that specific path**. Key insight: the problem is essentially never "no bound exists anywhere in the framework" — LangChain has `max_iterations`, OpenAI Agents SDK has `max_turns`, LangGraph has `recursion_limit`, CrewAI has `max_iter`. The failures happen because bounds are omitted, misconfigured, disabled, or — critically — placed in the wrong scope (an inner sub-agent turn cap does not cover an outer evaluator's feedback cycle unless it structurally dominates that outer path). Builds a framework-independent Agent IR (Controllers, Invocations, StateUpdates, Bounds, ExitRecords) and an Agentic Loop Dependence Graph, finds strongly-connected components reachable from an entry point that hit costly/state-growing actions, then classifies each candidate's continuation controller as deterministic / model-controlled / tool-controlled / external-state-controlled / exception-controlled / mixed, and checks bound *coverage* (not mere bound *existence*).

**Evidence quality**: High for a tooling paper. 6,549 repos scanned, 74 flagged, 68 manually confirmed as true IALs across 47 projects = 91.9% precision. Ablation shows each pipeline stage (framework modeling, bound-coverage check, benign-loop filtering, LLM pruning) contributes distinct precision/recall value. Beats an LLM-agent (Codex) baseline and a raw-LLM baseline on both recall and cost. Of the 68 confirmed failures, 69.1% are retry-without-bound, tool-call-iteration-without-bound, or multi-agent-chat-without-turn-bound; 95.6% cause API cost exhaustion / model DoS; root cause in all 68 is the same: an unbounded model/tool/agent-controlled feedback path.

**What QMA should borrow**: The core distinction — bound *existence* vs bound *coverage of the actual feedback path* — should shape how QMA's kernel implements budgets. A per-mind or per-plugin "you can set max_turns" convenience is not sufficient; the empirical record shows developers reliably fail to scope it correctly even when the primitive is available. The kernel should be able to statically or structurally guarantee that every feedback-carrying invocation path (including nested sub-agent/plugin calls) is dominated by some enforced bound, not merely offer the option.

**What to reject and why**: The static-analysis tool itself (IAL-Scan) is not something QMA needs to build or adopt — it's a downstream auditing tool for *existing* agent codebases, not a design pattern for a new kernel. Its relevance to QMA is as evidence, not as a component to borrow.

**Kernel implications**: Strong empirical support for making budget/bound enforcement a **mandatory, kernel-level, structurally-scoped concern** rather than an author-supplied convention — this is close to a "DEMAND a kernel hook" signal. Framework-level opt-in bounds (the status quo across LangChain/AutoGen/CrewAI/OpenAI SDK) demonstrably fail in practice at scale (47 confirmed vulnerable projects) precisely because they are optional and easy to misplace. A QMA kernel that enforces bound coverage structurally (rather than trusting mind/plugin authors to add `max_iterations` correctly) would close exactly the gap this paper measures.

## 2605.14892 — Beyond Individual Intelligence: Surveying Collaboration, Failure Attribution, and Self-Evolution in LLM-based Multi-Agent Systems

**Type**: Broad survey (secondary source — synthesizes ~400 cited works). Evidence quality of the survey's own claims is moderate (organizational/taxonomic, not experimental); individual cited primary works vary in rigor and are not independently verified here.

**Core mechanism (faithful)**: Proposes the "LIFE" progression — Lay (individual agent capability: reasoning/memory/planning/tool-use), Integrate (multi-agent collaboration/orchestration topology), Find (failure attribution), Evolve (self-improvement) — as four causally linked stages, arguing attribution narrows the search space for evolution and collaborative structure determines what failures are even observable ("attribution–evolution closed loop").

*Failure attribution* taxonomy: three technical routes — data-driven (train dedicated attribution models on labeled failure trajectories, e.g. AGENTRACER, Who&When), constraint-guided, and causal-inference. Attribution answers "which agent, at what timestep, caused the failure, and how did it propagate" — formalized as a function over the full execution trajectory. A "causal lifecycle" taxonomy (per AgentFail) classifies root causes at three levels: **agent, workflow, platform**.

*Self-evolution* taxonomy — three hierarchical scopes: **Agentic** (evolves one agent: prompt/memory/parameters — e.g. Self-Refine, Reflexion, RL fine-tuning), **Systemic** (evolves the inter-agent organizational fabric: topology, team composition, shared memory — e.g. Puppeteer's RL-optimized routing, G-Designer's VGAE-decoded sparse topologies, decentralized AgentNet), and **Meta** (evolves the evolution mechanism itself). Notably, most cited self-evolution systems that touch model weights are offline/persistent (trained between runs); online, weight-free, inference-time *systemic* (topology-level) self-evolution is explicitly flagged elsewhere in this literature (and by MANTA itself, below) as comparatively underexplored.

**What QMA should borrow**: The three-level failure-root-cause taxonomy (agent/workflow/platform) is a useful lens for designing QMA's own execution-trace schema — traces should carry enough structure (per-agent, per-step, per-orchestration-layer) that attribution tooling could later be built on them without redesigning the trace format. The Agentic/Systemic/Meta self-evolution split is a clean way to scope what QMA's kernel should vs shouldn't try to make mutable at runtime (agent-level prompt/memory tuning is comparatively mature and lower-risk; topology-level runtime mutation is the newest, least-proven layer — see MANTA below).

**What to reject and why**: This is a survey, not primary evidence — don't cite its taxonomy as if it were independently validated; the aggregate claims about maturity/immaturity of subfields should be traced back to the primary papers it cites if a claim becomes load-bearing for a QMA design decision.

**Kernel implications**: Broadly complementary to a Cordis-style kernel, not a challenge to it. Reinforces treating topology as a distinct, mutable "systemic" object separate from individual-agent capability — consistent with a plugin-kernel architecture where topology is kernel-managed data. Caution worth flagging: the survey itself frames online, weight-free, topology-level self-evolution as an active but young research direction — not something with a broad, converged track record. QMA should not over-invest kernel complexity in runtime topology self-mutation as if it were a settled pattern.

## 2607.28527 — MANTA: Multi-Agent Network Topology Adaptation for Self-Evolving Multi-Agent Systems

**Type**: Empirical system paper. Evaluated on 5 benchmarks (information seeking, tool use, planning, workflow execution, math reasoning) against single-agent, static-topology multi-agent, and automated-workflow-design baselines (AFlow, ADAS, AgentSquare, MASS).

**Core mechanism (faithful)**: MANTA directly answers "is topology data or code?" — **topology is a versioned, validated JSON specification**, not code. Each agent in the spec has a structural role (coordinator/worker/verifier/debater/voter), a stage role (worker vs critic), an optional persona, allowed tools, and a context/visibility policy; agents belong to nestable "pattern groups" (singleton, star, chain, debate, voting).

Two nested layers: the *target* multi-agent system (does the task) and an *orchestration* layer of three LLM components (Topology Planner, Trace Auditor, Skill Reflector) plus **deterministic code that validates topologies, runs agents, routes messages, controls repair, and decides when to stop**. The critical design choice: the LLM Planner only *proposes* — it emits a topology or a mutation (≤3 operations: add/expand agent, rewire edge, change visibility) as JSON. Deterministic code then validates it (unique group membership, valid roles/identifiers, acyclic structure, legal group patterns, agent-budget ceiling) before any agent is ever instantiated; invalid proposals are rejected or replaced with a conservative deterministic fallback (coordinator–worker star, or a singleton). Mutation is hard-bounded: **one mutation per run, ≤3 operations**, gated behind a Trace Auditor that flags only *process* anomalies (never answer correctness — that separation is deliberate, echoing the maker/checker split in paper 2607.00038) and a Controller that decides finalize-vs-repair. Two-tier memory: a short-term playbook (this run's topology/audit history) and a long-term playbook, periodically rewritten by a Skill Reflector every 12 runs, that **only ever sees process signals, never the benchmark verdict** — a structural defense against the memory channel itself being reward-hacked.

**Evidence quality**: Solid for a single-paper system evaluation — highest average score (74.0) across 5 benchmarks, +5.8 pts over strongest baseline, best result on PlanCraft, with an ablation-style case-study section (recovers from an overloaded branch, a missing check, premature agreement, a duplicated action). Not independently replicated; single research group.

**What QMA should borrow**: This is the strongest single piece of evidence in the cluster for a Cordis-style kernel. The pattern — LLM proposes structured data, deterministic kernel code validates/applies/rejects, mutation is bounded and gated by a process-only auditor, memory is structurally denied access to the ground-truth signal it could be tempted to game — maps almost directly onto "topology as data governed by a kernel, not code the agent writes." Worth adopting near-verbatim: (1) topology/config changes as validated JSON, never as agent-authored code; (2) hard per-run mutation budgets (1 mutation, ≤3 ops) as a concrete numeric anchor, not just "some limit"; (3) an auditor role structurally forbidden from seeing the correctness signal it's meant to be independent of; (4) deterministic fallback topology when a proposal fails validation, so the system degrades to a known-safe structure instead of erroring out.

**What to reject and why**: Don't treat MANTA's specific hyperparameters (5 max initial agents, 10 max after repair, 12-run reflection batch) as universal constants — they're tuned for MANTA's benchmark suite, not derived from a general principle.

**Kernel implications**: Directly DEMANDS a kernel hook, not a simpler approach — and is explicit evidence *against* letting an LLM directly rewrite its own coordination structure. The paper's own design rejects the simpler alternative (ungated LLM-driven topology rewriting) in favor of gating every change through deterministic validation. This is the cluster's clearest confirmation that QMA's Cordis-leaning plugin-kernel direction (kernel enforces structure; LLM/plugins propose data) is the pattern the current state of the art converges on for this exact problem.

## Cluster Verdict

**Top borrowings** (ranked): (1) MANTA's propose/validate split — LLM proposes topology-as-JSON, deterministic kernel code validates/applies/rejects, hard-bounded mutation (1 mutation/run, ≤3 ops), auditor structurally blind to the correctness signal — is the single most directly transferable pattern for QMA's kernel. (2) IAL-Scan's bound-*coverage* (not bound-existence) framing should shape QMA's budget/stop-rule design: enforcement must be structural and cover the actual feedback path, not an optional per-mind convenience, because the empirical record (68 confirmed real-world failures despite frameworks already offering opt-in limits) shows authors reliably misuse or misplace optional bounds. (3) The loop-specification schema (trigger/goal/execution-via-skills/verification-ladder/named-terminal-states/on-disk-memory) from 2607.00038 is a ready-made shape for a kernel-level loop-config object, and its maker/checker separation principle reinforces MANTA's auditor design. (4) The agent/workflow/platform failure-taxonomy and Agentic/Systemic/Meta self-evolution scoping from the LIFE survey are useful organizing lenses for QMA's trace schema and for scoping what should vs shouldn't be runtime-mutable.

**Direct challenge to our direction**: None of the four papers argues for a simpler-than-kernel architecture as the *primary* recommendation — if anything MANTA is a strong pro-kernel data point. The one genuine counter-signal worth flagging honestly: the "Ralph loop" pattern praised in 2607.00038 (bare shell loop, fresh context every turn, all state externalized to files, no framework machinery) is held up by practitioners as the most robust loop pattern in their corpus — a real data point that minimal/no-framework beats heavier orchestration for at least the narrow case of single-agent iterative loops. And the LIFE survey's own framing flags that online, weight-free, *runtime topology self-mutation* (exactly what MANTA and a Cordis-kernel would enable) is still a young, thinly-populated research direction (MANTA is essentially the frontier example, not a converged consensus) — QMA should build the kernel hook for it, per MANTA's evidence, but shouldn't treat runtime topology self-evolution as a mature, low-risk feature to lean on heavily.
