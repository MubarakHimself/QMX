# QMF V1 Security Model

QMF V1 concentrates authority at explicit contract seams: humans control live promotion, backend risk semantics never originate in external adapters, middleware translates but does not decide, data stores hold evidence but no business rule, and external providers remain outside QMF control. [DEC-0009] [DEC-0041] [DEC-0059] [DEC-0065]

## Security status

The venue secret lifecycle is ratified as law (DEC-0136): QMF components handle secret **references**, never values, and the leak surfaces are mechanical to scan. The store mechanics, key custody, deployment identities, key-store locations, roles, and the privilege model that the QMF layer deferred to "the node/ops sitting" have now landed at the trading-node sitting of 2026-08-28: the two-layer secret store, the fixed `qmx` service account, the four named secret holders, the SSH-stdin provisioning wizard, and the powers-channel principal model are ratified in the trading-node sections at the foot of this document (DEC-0197, DEC-0201, DEC-0227, DEC-0202). Per-value alert thresholds stay configurable UI-editable variables and no live account is fixed here. This document grants no live access, credential use, order submission, flattening, promotion, restore, or destructive mutation authority; the design is ratified, but implementation authorization arrives only through the factory pipeline, never from these docs alone.

## Secret lifecycle (AD-26)

The venue secret lifecycle is ratified law (DEC-0136), answering GAP-0035. No secret value or secret location appears anywhere in QMF; QMF components hold **secret references, never values**.

- **References, not values.** A secret reference is an **opaque minted id** under AD-9's identity discipline: stable, never reused, and never encoding venue, broker, account, environment, or key material; any human-readable label is a separate field held outside evidence, and construction validates opacity (`invalid input` on failure). `qmf-core` ships typed `SecretRef` and `SecretValue`; a `SecretValue` never renders its value — repr, str, serialization, and logging all yield the reference id — and a **tier-1 secret-scan gate rides `poe check`** (DEC-0136).
- **Never in the open.** Secrets never appear in repositories, configuration artifacts, docs, chat, `.env` files, CLI arguments, journals, evidence, fingerprints, or logs. A missing, expired, or rejected credential is an `unavailable dependency` refusal carrying the reference id, never the value; refusal context, logs, health reports, and metric labels carry the reference id only (DEC-0136).
- **Injection at the root.** Values are injected at the composition root from the deployment environment's protected store (`systemd-creds`-class on the VPS); the store mechanics and key custody the QMF layer deferred are now ratified at the trading-node sitting as a two-layer store — a `systemd-creds encrypt --with-key=host` key-encryption key plus AEAD state under it — detailed in the trading-node sections below (DEC-0136, DEC-0197, DEC-0201).
- **Binding identity.** An account-binding record's identity is `(VenueId, AccountId, role, world)`; its secret reference is declared occurrence/display-only and excluded from `fp1` — a credential is a deployment fact, never a market fact (DEC-0136).
- **Single value-holder.** The adapter's connection manager is the single named component permitted to hold secret values in memory, for a session's lifetime, through a core-defined `SecretStore` port (read + atomic replace) injected by the root; values never cross back out — no getter, no log line, no refusal context, no health field, no metric label (DEC-0136).
- **Rotation.** A credential is a one-writer stream: exactly **one live refresher per credential** — a workstation tool never refreshes a credential a VPS session owns. Where the venue rotates refresh material on use, the new secret is stored (atomic replace) **before** the old is discarded; a failed store after rotation is an alarm **and** a command-pipe block (`unavailable dependency`, after-condition = successful store or operator re-provision) with the **sensing pipe unaffected** (DEC-0136).
- **Compromise drill.** Recovery is a documented, tested drill: cTID re-authorization (which invalidates **all** outstanding refresh tokens — the never-expiring refresh token is the crown-jewel secret, DEC-0135), application-credential reset, store replacement, and session restart; expiry and refusal paths ship as **tested behavior** (DEC-0136). See [OPS-INCIDENT-QMF-V1](../ops/incident-playbook.md) for the drill steps.
- **Testing posture.** Testing uses **demo credentials only**; factory sandboxes never hold live secrets. Credential entry and management UI is platform territory (DEC-0136).

The cTrader token facts are ratified (DEC-0135): a ~30-day access token, a never-expiring refresh token as the crown-jewel secret, and cTID re-authorization as the invalidation anchor.

## Trading-node runtime: trust boundaries (TN-3)

The trading node (COMP-QMN, package and import code name `qmn`; the operator declined to name the product, so a rename is mechanical) is the supervised runtime that executes the ratified QMF rulebook on a live account, and it draws its own trust boundaries: **three planes, two machines, one bucket** (DEC-0188). The node is one product with two modes, `paper | live`; there is no separate "live" build and no separate paper build.

- **VPS plane (Linux, always on).** One node process hosts the trading loop and the live tick/bar/depth recording, and the VPS is the **only plane that ever holds live venue credentials** (DEC-0188). The always-on **evidence tier** is a second directory tree on the same VPS — a placement and authority boundary, not a second host, not a database server, not a second writer — that hot rooms sync into one-way, watermarked, idempotent and verify-before-purge (DEC-0188). Separate scheduled units run the news-calendar recorder, the nightly backup, the nightly sample restore and the monthly full restore, each under its own `WriterId` (DEC-0188).
- **Workstation plane (Windows 11 now, Linux later).** It holds **provisioning and bootstrap material only, never rotated live session material**: the VPS session is the sole refresher and the sole holder of live session state, so a workstation tool never refreshes a credential the VPS session owns (DEC-0188, DEC-0197). Windows Credential Manager `qmx/*` is the provisioning source and the escrow home of the backup payload key. The future desktop UI reaches the node's localhost- and socket-bound doors over an **SSH tunnel** — the node is one surface inside that later UI, not a separate control path (DEC-0202).
- **Bucket.** Nightly encrypted, versioned, ciphertext-only copies, **pushed by the VPS and never by the workstation**, because a 24-hour recovery-point objective cannot depend on a laptop being awake and the bucket credential belongs where the timer runs (DEC-0188).
- **Episodic sandbox plane (factory agents).** Evidence carries `provenance = sandbox`, never merges into live evidence, and never holds live secrets (DEC-0188).
- **Two inbound crossings exist and no others** (DEC-0188): the click-gated promotion pull of registry as-of sets from the passive hub, which **refuses any artifact carrying `provenance = sandbox` at pull** (DEC-0205); and the sandbox fragment push into a **write-only inbox** over a restricted key-only SSH identity confined to `/var/lib/qmx/hub-inbox`, distinct from the operator's key and from the provisioning identity. The inbox-to-published step is the operator-signed `hub_publish` power, which **refuses `provenance = sandbox` at publish as well as at pull** (DEC-0188, DEC-0202).

**The workstation installation is provisioning-only, and enforced rather than asserted** (DEC-0197, DEC-0201, DEC-0236): the composition root **refuses to compose on any host whose declared machine tuple is not the deployment roster's VPS entry**; the `SecretStore` **refuses to construct a venue-session holder off that host**; a tier-1 check proves the provisioning-wizard module imports **neither the connection manager nor the refresh duty**; and a tier-1 check proves the packaging declares **no console-script entry point and no publishable target**. Without these, a workstation script that composed a root could refresh the token and kill the VPS session mid-trade — the boundary is a runtime refusal, not a convention.

## Trading-node privilege model (TN-16, gate ruling 12)

All node systemd units run under a **fixed `User=qmx` service account, not `DynamicUser`** — a dynamic UID cannot deterministically own the persistent trees under `/var/lib/qmx` or share them across units (DEC-0227, DEC-0201). The hardening is reconciled with the storage topology rather than asserted beside it (DEC-0201):

- **`ProtectSystem=strict` with `ReadWritePaths=/var/lib/qmx`**, every writable tree (`rooms`, `evidence`, `hub-inbox`, `hub-published`, `archive`, `state`, `staging`) pre-created and owned by `qmx`; `RuntimeDirectory` creating `/run/qmn` for the powers socket; plus `NoNewPrivileges`, `PrivateTmp`, `ProtectHome`, `LogsDirectory`, and `RestrictAddressFamilies=AF_UNIX AF_INET AF_INET6` (`AF_UNIX` is required for both the systemd notify socket and the powers socket).
- **`LoadCredentialEncrypted` per unit for that unit's credentials only**, with `systemd-creds encrypt --with-key=host` **pinned** — never the default `--with-key=auto`, which would silently bind a TPM2 where the host exposes one and reintroduce the migration fragility this design rejects (DEC-0227, DEC-0197).
- Code reaches the VPS as a **read-only clone at a pinned commit**, materialized as one immutable per-commit tree under `/opt/qmx` by the day-one bootstrap script, so the deploy identity carries no write authority over the running tree and a rollback is a symlink flip that needs no network (DEC-0201).
- The separate **observability stack is a sixth checked-in unit that is not the node's**: it runs under a **distinct non-`qmx` service account** with its own credentials and its own storage tree `/var/lib/qmx-observability`, and it holds **zero authority** — it scrapes metrics and reads a journal namespace and can act on nothing (DEC-0227, DEC-0201, DEC-0236).

| Observability stack (declared fourth) | Its own Grafana admin credential and any log-shipper auth token, delivered by its own `LoadCredentialEncrypted` line | Anything the node holds |

The provisioning wizard is carved out as a **transient workstation-only holder** for the duration of one run, so the VPS invariant above stays checkable rather than quietly false (DEC-0197).

**The store is two layers** (DEC-0197): `systemd-creds LoadCredentialEncrypted=` delivers at service start (a) a node key-encryption key (KEK) and (b) the bootstrap credentials, while the node keeps **rotated** material — the refresh token dies on use, the access token lives roughly thirty days — under `/var/lib/qmx/state` as AEAD ciphertext under the KEK, via the `cryptography` library (Apache-2.0/BSD, registered in `DEPENDENCIES.md`). Rotation is therefore ordinary unprivileged file I/O for the `qmx` account: no root, no code change. **Host-key sealing survives reboot, migration and rotation but not VPS death** — the host key is a file on the VPS disk — so disaster recovery rests on the escrow rule, not the seal (DEC-0197).

**Backup payload-key custody is ruled, not left to a variable** (DEC-0197, DEC-0217): the CT-14 payload key that decrypts every off-host copy is **generated at provisioning on the workstation**, escrowed in Windows Credential Manager under `qmx/backup-payload-key` **plus one operator-held offline copy**, and delivered to the VPS as a bootstrap credential. It is **never VPS-minted**; the VPS-minted KEK protects rotated session material only. The host-loss restore rehearsal — the `restore_drill_run` power onto a clean host holding **only** the escrowed payload key — is what measures the full disaster-recovery objective (DEC-0217).

**The provisioning wizard** is the operations toolkit's `just node-secrets-provision` recipe, a human-only step run on the laptop (DEC-0197). It reads each `qmx/*` entry and streams the value over an SSH session's **stdin** straight into `systemd-creds encrypt --with-key=host --name=<ref>` on the VPS — **never argv, never a file, never echoed, never logged**. Because writing `/etc/credstore.encrypted` needs root, provisioning runs over a **dedicated key-only SSH identity restricted to a single passwordless-sudo provisioning command**, with no interactive root login and no password anywhere, and that identity is distinct from the operator's ordinary SSH key. Token refresh is keyed by **credential reference, never by connection**: at most one refresh is in flight per credential reference and every session sharing it is a reader, not a refresher (DEC-0197).

**The compromise drill** is anchored on cTID re-authorization, which invalidates all outstanding refresh tokens, then application-credential reset, store replace and session restart; it is tested with demo credentials only, and factory sandboxes never hold live secrets (DEC-0197). See [OPS-INCIDENT-QMF-V1](../ops/incident-playbook.md) for the drill steps.

## Trading-node doors, the powers channel and audit (TN-17, gate ruling 19)

**There is no operator command line for the node** (operator ruling R1, DEC-0211): the deployment and provisioning tooling is a set of `just node-…` recipes (the operations toolkit, DevOps only, never a trading control), and every runtime act goes through one of three doors (DEC-0202). QMB's `qmb` command line stays the platform's single command-line surface; it is not the node's.

- **The Python API** — in-process; the desktop backend and the operations toolkit's scripts import it rather than shelling anywhere (DEC-0202).
- **The localhost HTTP evidence channel** — HTTP/JSON on localhost, **publish-never-act**, authority-free, refusals returned as evidence, budgeted by the `evidence_channel_budget` registry row. Its access rule is stated, not blank: **there is no authentication beyond the loopback binding**, accepted because the VPS is single-tenant and the channel cannot act; the accepted cost is that any local process (the observability stack's exporters included) can read every read-only projection (DEC-0202).
- **The powers action channel** — a **unix domain socket at `/run/qmn/powers.sock`, owned `qmx:qmxops`, mode `0660`, created by the unit's `RuntimeDirectory`**, authenticated with **`SO_PEERCRED`** (DEC-0202, DEC-0234). The peer credential is read from the transport and recorded beside the claimed signer on every powers journal record.

**Two peer principals are declared, both by uid in the resolved config artifact, and neither is the `qmx` service account** (DEC-0202, DEC-0234, DEC-0236): the **operator principal**, which may call every power; and the **ops principal**, which may call only `notify_test`, `restore_drill_run`, `config_validate`, `hub_publish` and the evidence reads. Every trading, protection, promotion, activation, settings-edit, `resurrect`, attestation and countersign power is **refused for the ops principal by the transport**, and the refusal is journaled. **Preflight refuses to boot if any systemd unit on the host declares an operator-principal uid**, so no automated unit ever runs as the operator, and a call whose peer credential is neither principal is refused outright — over an SSH tunnel that credential is the forwarded socket's sshd user (DEC-0202). This is what makes "no recipe flattens, promotes or activates" a gate rather than an assertion, and it is what makes the agent-signer refusal on the promotion path enforceable (DEC-0205).

**The honest limit is named as a residual risk: `SO_PEERCRED` proves an account, not a human** (residual risk A32, DEC-0234). Humanity beyond "no automated unit runs as the operator" is asserted by the signer, not proven. Every powers call is server-side revalidated against fresh state at click time, idempotent by artifact key, and journaled as a control action carrying the transport-read peer credential, the claimed human signer identity, and the plain-words summary that signer read — the signature attests the exact words approved (DEC-0202, DEC-0234).

## Trading-node egress and sandbox-provenance controls (TN-16, TN-3, TN-20)

**VPS hardening is default-deny in both directions** (DEC-0201): SSH is key-only with no password, alongside the separate restricted provisioning identity and the separate confined inbox-write identity; `ufw` is default-deny inbound except SSH; and outbound is a **default-deny egress allow-list** — the cTrader venue hosts, the notification and liveness-heartbeat (formerly dead-man's-switch, notification only and zero authority) endpoints (DEC-0261), the object-storage bucket, the history and news-calendar providers (Forex Factory's free weekly file is the sole V1 news-calendar source, with no paid fallback slot anywhere), the distribution index, the observability stack's container image registry (or a vendored image source — the only place containers are permitted), and NTP. **No public port ever**: the doors are localhost- and socket-bound and the desktop UI reaches them over an SSH tunnel. Unattended security upgrades run with no automatic reboot and are configured never to restart `qmn.service`, so any restart of the node is routed through the drain path (DEC-0201).

**Sandbox-provenance refusal is enforced at both inbound crossings** (DEC-0188, DEC-0205): the operator `hub_publish` power refuses any fragment carrying `provenance = sandbox` at publish, and the click-gated promotion pull refuses any artifact carrying `provenance = sandbox`, and any as-of set containing one, at pull — verifying each artifact's `fp1` against the promotion card before the seat lands. A refusal is journaled and alarmed, never skipped. This is the node's only inbound path to live authority, and no factory-sandbox artifact can traverse it.

## Trading-node V1 seat-containment limit (TN-19, GAP-0054)

V1 has **no hardened OS-level memory or security confinement** for bot seats: no restricted tokens or Job Objects on Windows, no seccomp-class filter and no `rlimit` hard cap on Linux. That confinement is **GAP-0054, deferred**. Stating the V1 limit does not close the gap (DEC-0204, DEC-0236, DEC-0260).

Admitted bot code runs in-process on the loop's only domain thread. Compensating controls, named once and still falsifiable, are:

- QL-8 static AST/import scan (`ql-8-static-scan`)
- capability starvation (hosts inject read surfaces only)
- host process isolation (stdlib process spawn of the Layer-2 runner)
- per-callback deadline (`registry:seat_callback_deadline`, cooperative `CancelToken` / `LimitProbe` at slice boundaries)
- per-seat memory ceiling (`registry:seat_memory_ceiling`, cooperative `LimitProbe`; not an OS hard cap)
- automatic quarantine whose only exit is operator-signed `seat_reinstate`
- the door-layer slice-progress watch plus supervised restart of last resort for a non-returning callback

A dynamically-evasive malicious bot is out of V1's threat model (bots are operator- or operator's-agent-authored). Do not invent a higher cap in code or prose.

## QMA — Credential Broker, principal classes, money-path barrier

The QMX agentic system (QMA) — the daemon plus the QMA SDK plus the wire contract — draws its own trust boundaries as an application-layer consumer built ON QMF, and every one is a runtime refusal rather than a convention. QMA never mints an order, a binding, a sizing decision, or a promotion; its only output into the money path is a candidate artifact a human promotes outside QMA (DEC-0324, DEC-0345).

### Principal classes on every wire connection

Every authenticated wire connection carries exactly one principal class, `operator` or `machine` (DEC-0323). The `operator` class comes only from an interactive human credential presented by a client a human is driving; workers, plugin worker halves, remote deployments, the scheduler, routines and cron, and every daemon-internal caller are `machine`, and no `machine` principal may acquire, delegate, borrow, cache, or impersonate the `operator` class — the class is recorded verbatim on every command, journal entry, and ledger entry. A closed, spine-amendment-only **human-gate command list** is the sole authority on which commands accept only an `operator` principal — admission approval, a forward-only migration confirmation, an `UNKNOWN` resolution, a `role.base` write via `role.set_base`, `model_family` assignment, `tool_adapter` writes, a live-store restore, plugin install/enable/reload, `desk.create`/`quant.create`, a Quant or Routine record write, an `ExecutionEnvironment` declaration, a `variable.set` on a registry-homed variable, and an AD-13 `human_gate` answer among them — refused from a `machine` principal with the typed refusal `OperatorPrincipalRequired` (DEC-0323). QMA mints no registry-promotion or zone-transition command at all, so there is no headless, scripted, scheduled, or agent-initiated path to any human-gate command (DEC-0323).

### The Credential Broker: scoped allowlist and egress rule

Secrets follow the platform's references-never-values law: components handle references, and the Credential Broker resolves them from an OS secret store behind a backend interface (Windows Credential Manager is the first and only v1 backend) (DEC-0323). The broker's scope is a **code-declared allowlist shipped in `qma-core`** — model and inference providers, compute and sandbox providers, corpus and knowledge sources, telemetry sinks — and **venue, broker, exchange, trading-node, and platform-registry credentials are outside QMA's namespace**, resolvable by no QMA component under any Role, Mission, plugin, or permission mode; a reference not on the allowlist returns the typed refusal `CredentialOutOfScope` naming the reference (DEC-0323). The allowlist is source code, never settings, never a plugin contribution, never a UI-editable variable, and never widened by a Mission, and the broker holds no ambient authority — exact-reference resolution only, never enumerate, search, list, or glob (DEC-0323). The **egress rule**: a resolved secret value exists only inside the model-proxy or provider-adapter egress call frame and is never stored on, attached to, or reachable from any object handed to a hook, plugin, or graph; the hook and plugin context exposes credential reference strings only, and secrets are excluded from `updated_input`, `updated_output`, and `injected_context` by a schema check (DEC-0323). The transport is loopback by default; any non-loopback bind requires TLS plus an explicit recorded operator configuration, and an unauthenticated or plaintext non-loopback bind is a hard startup refusal (DEC-0323, DEC-0304).

### Local model proxy: no QMA secret crosses in

OpenCodex sits behind the Deployment contract and deliberately NOT behind the Credential Broker; a Deployment whose implementation is a local proxy carries `auth_mode: none` on the QMA side, and **no QMA-resolved secret ever crosses into the proxy's process** — the proxy's own provider credentials are its own custody outside QMA's namespace, never read, copied, migrated, or referenced (DEC-0314, DEC-0344). The daemon permits a proxy Deployment only when it binds loopback on the daemon's host, refusing any non-loopback proxy with `NonLoopbackProxy`; a loopback proxy accepting unauthenticated connections is permitted only by the configurable `proxy.allow_unauthenticated_loopback` (default `true`, ui-editable, operator-overridable) and refused with `UnauthenticatedProxy` when that variable is `false`, and each registered proxy Deployment and the value of that setting are recorded as a startup evidence entry (DEC-0314). QMA never pools accounts itself; where pooling exists it happens inside the operator's own proxy under the operator's account terms, and QMA records the true deployment honestly on every routing decision (DEC-0314).

### The money-path reachability barrier

There is **no execution tool at any account role, "paper only" included**, and the prohibition is an enumerated **act-level deny-list** in `qma-core`, not a permission policy (DEC-0315). The prohibited acts include submitting, amending, cancelling, or replacing an order; opening, closing, reducing, or hedging a position; setting or amending protection; sizing or minting a sizing decision; creating, amending, activating, standing down, or deleting a bot-to-book binding; setting a Book mode, seat state, parameter, priority rank, or capital floor; arming or changing a kill switch or node control action; and transitioning any registry artifact between zones — `register_tool` refuses at registration with `ProhibitedMoneyPathTool`, a startup error no `check_fn`, permission policy, Role, Mission, hook, toolset, or `tool_adapter` change can lift (DEC-0315). AD-28 closes the reachability half: no agent, subagent, worker, environment, browser, or computer-use profile may reach a venue, broker, exchange, trading-node, or platform-registry control surface by any means (DEC-0327). `ExecutionEnvironment` carries a required `network` field with exactly two values, `none` and `allowlist`; venue, broker, exchange, and trading-node hosts sit on a **code-declared deny-list that no allowlist entry may name**, and the `remote_host` and `desktop` kinds may not name the trading-node VPS or any host carrying a trading credential — refused BY HOST IDENTITY, at placement or registration, never as a runtime hook deny (DEC-0327). No QMA worker image may contain, install, or import `qmf-venue`, a broker or exchange SDK, or the trading node's client, and image validation refuses one that does; the single computer-use agent runs on a profile whose browser carries no venue or broker login, cookie, or saved credential (DEC-0327). Together this is the money-path reachability barrier — nothing above a bot touches the market — and risk, sizing, and live-trading authority stay with the GitBook and trading-node corpus (DEC-0341, DEC-0324).
