# Portfolio & Risk Libraries — PyPortfolioOpt, Riskfolio-Lib, FinanceToolkit

Study date: 2026-08-17. Repos read at `reference/repos/PyPortfolioOpt`, `reference/repos/Riskfolio-Lib`, `reference/repos/FinanceToolkit`. Cross-references `research/04-portfolio-risk-sizing.md` (the prior web-research pass on this exact question) and `research/00-qmf-synthesis-module-map.md` (the proposed `qmf.book` / `qmf.bms` design).

**Headline judgment, stated up front so it isn't buried:** all three libraries are equities/multi-asset portfolio tools. None of them has a stop-loss, a lot size, a broker, a spread, a margin call, or a prop-firm rule. `research/04` already reached this verdict independently from documentation and issue trackers; reading the actual source code in this pass confirms it at the API-signature level and finds nothing that changes the recommendation: **research-only, never on QMX's live forex path.** The value here is (a) API-shape lessons for `qmf`'s own risk surface, (b) one genuinely transferable idea — hierarchical/correlation-based basket risk — and (c) FinanceToolkit's relevance to the later stocks lane, which is real but narrower than its 200+-metric surface suggests once options/derivatives content is excluded per QMX's permanent no-options-no-futures constraint.

---

## In plain words

1. These are three different tools wearing similar clothes. PyPortfolioOpt and Riskfolio-Lib both answer the question "given a bunch of stocks and history, what weight of my money should go into each one?" FinanceToolkit answers a different question: "given a stock ticker, compute me 200+ standard numbers about the company and its price."
2. All three assume you own a diversified basket of *assets you buy and hold* — stocks, ETFs, bonds. None of them knows what a stop-loss, a lot size, leverage, or a margin call is. That's not a maintenance gap; it's a different business.
3. QMX trades one instrument at a time (a forex pair) with a stop, on one broker account, sometimes under a prop firm's daily/total loss rule. That is a fundamentally different shape of problem from "split $1M across 30 stocks to maximize risk-adjusted return." So most of what these libraries do — the actual optimizers — does not transfer.
4. What does transfer is *how they organize a risk API*: a short menu of named risk measures (standard deviation, worst-case loss, max drawdown, ...) that plug into the same optimizer call, instead of one bespoke function per risk type. That's a clean pattern worth copying for QMF's own metrics module even though the optimizer itself won't be used.
5. One idea is genuinely useful beyond "just study it": these libraries build portfolios by *clustering correlated assets* rather than assuming you can predict which one will go up. If QMX ever runs two or three correlated forex pairs at once (EURUSD and GBPUSD both long, say), the same clustering math answers "how much combined risk am I actually carrying" — which is a real prop-firm-relevant question, not a nice-to-have.
6. FinanceToolkit is the most interesting of the three for QMX's *future* stocks lane, but for a narrower reason than its size suggests: it is a well-organized, well-documented wrapper around a paid data API (Financial Modeling Prep) plus yfinance, covering fundamentals, ratios, and standard technical indicators. Its options/Greeks module is irrelevant and should never be touched — QMX's stocks lane is permanently day-trading equities only, no options, no futures.
7. FinanceToolkit also ships something structurally interesting regardless of the maths: it exposes its entire calculation surface to LLM agents as an MCP tool server, generated automatically from its own Python classes. That's the same idea QMX's own `qmf.spec` module is meant to be — a single typed, discoverable surface an agent can call without touching raw code — and it's useful to see a real implementation of that pattern, even a data-analysis one rather than a trading one.
8. None of the three libraries can be put anywhere near a live order path. They solve a slow, offline, "rebalance once a week/month" problem. QMX's problem is "should this one trade happen right now, and how big." Different clock speed, different question.
9. Licence-wise, all three are safe (MIT / BSD-3-Clause) — code, not just design, can be copied or wrapped directly, which is rare in this space (most engine-shaped prior art surveyed elsewhere is GPL/LGPL/AGPL).
10. Maturity is uneven. Riskfolio-Lib is a strong one-person project with real depth but a bus factor of one. PyPortfolioOpt had a multi-year maintenance gap and an ownership transfer — its `research/04` history (issue #587) is corroborated here by nothing in the source suggesting active architectural change; it reads like a stable, slow-moving library, which is fine for the narrow thing QMX would use it for (offline research), but is a reason never to depend on it at runtime.
11. FinanceToolkit is the newest and most actively engineered of the three (clean typed controllers, an MCP server, a discovery module) — it reads like a project still being actively shaped, which is a plus for a stocks lane that won't be built for a while.
12. Bottom line for QMF's design: build `qmf.book`/`qmf.bms` from scratch per `research/04`'s recommendation (pysystemtrade + Nautilus authority split); wrap Riskfolio-Lib or PyPortfolioOpt *only* as an offline research tool for the rare cross-pair correlation study; keep FinanceToolkit on the shelf until the stocks lane actually starts, and even then use it for fundamentals/ratios/technicals only — never its options module.

## How it is built

### PyPortfolioOpt — `reference/repos/PyPortfolioOpt/pypfopt/`

A layered stack, all built on `cvxpy` (convex optimization) plus `scipy`/`numpy`:

- **Estimators, functional style.** `pypfopt/expected_returns.py` and `pypfopt/risk_models.py` are plain functions, not classes: `risk_matrix(prices, method="sample_cov", **kwargs)` dispatches to sample covariance, semicovariance, EWMA, Ledoit-Wolf/Oracle-Approximating shrinkage, or minimum-covariance-determinant, keyed by a string (`reference/repos/PyPortfolioOpt/pypfopt/risk_models.py:116`). A non-PSD matrix is auto-repaired by `fix_nonpositive_semidefinite()` (spectral or diagonal-loading method) — a real numerical-safety detail worth borrowing regardless of domain.
- **`BaseConvexOptimizer` → `EfficientFrontier`.** `pypfopt/base/_base_optimizer.py` and `pypfopt/efficient_frontier/efficient_frontier.py`. Constructor takes `expected_returns`, `cov_matrix`, `weight_bounds` (`(0,1)` long-only by default, `(-1,1)` for shorting), a `solver` name, and `solver_options`. Then you call **one method per objective**: `min_volatility()`, `max_sharpe()`, `max_quadratic_utility(risk_aversion)`, `efficient_risk(target_volatility)`, `efficient_return(target_return)` (`reference/repos/PyPortfolioOpt/pypfopt/efficient_frontier/efficient_frontier.py:17-55`). Each mutates internal cvxpy problem state — the docstring is explicit that **a new object is required per change of objective/constraint**, i.e. the optimizer is not reusable across calls, a design wrinkle worth noting for anyone tempted to wrap it in a loop.
- **Composable objectives/constraints.** `add_objective()` and `add_constraint()` accept arbitrary convex cvxpy expressions before solving — this is the one genuinely elegant part of the API: constraints are declared, not hard-coded into each method.
- **Alternative risk shapes as sibling classes**, not parameters: `efficient_cvar.py`, `efficient_cdar.py`, `efficient_semivariance.py` each re-implement the same `min_risk`/`max_sharpe`/`efficient_return` method family for a different tail-risk measure (CVaR, CDaR, semivariance) rather than parametrizing one class by a risk-measure string.
- **`HRPOpt`** (`hierarchical_portfolio.py:26`) — Hierarchical Risk Parity. `optimize(linkage_method="single")` runs `scipy.cluster.hierarchy.linkage` on a distance transform of the correlation matrix, then allocates by recursive bisection of cluster risk. **No expected-returns input at all** — it only needs a covariance/correlation structure. This is the one class in the whole survey that sidesteps the "you have to predict the mean" problem `research/04` flags as the central danger of Kelly sizing.
- **`DiscreteAllocation`** (`discrete_allocation.py:42`) — converts continuous weights + latest prices + `total_portfolio_value` into integer share counts via a greedy algorithm or an LP solve. This is PyPortfolioOpt's only concession to "real money, real lot sizes," and even it has no concept of a *minimum* lot step, margin, or a stop.
- **Black-Litterman** (`black_litterman.py`) exists as a separate module for blending market-implied returns with subjective views — irrelevant to QMX; no analogous "consensus prior" exists for FX pairs the way it does for equity market caps.

### Riskfolio-Lib — `reference/repos/Riskfolio-Lib/riskfolio/src/`

Larger and more uniform than PyPortfolioOpt — one design decision (a single risk-measure string threaded through one call) instead of PyPortfolioOpt's family of near-duplicate classes.

- **`Portfolio` class** (`Portfolio.py:56`) is a single object taking a `returns` DataFrame plus a long list of structural constraints in the constructor: `sht`/`uppersht`/`upperlng` (shorting), `budget`, `nea` (minimum effective assets, an anti-concentration control via inverse Herfindahl index), `card` (max asset count, a mixed-integer constraint), `factors`/`B` (risk-factor loadings), `alpha`/`a_sim`/`beta` (tail-risk parameters shared across all VaR-family measures).
- **One risk-measure registry, 24 entries**, declared once at module scope (`Portfolio.py:28-53`, `rmeasures = [...]`): `MV` (std-dev), `MAD`, `MSV` (semi-std-dev), `CVaR`, `EVaR`, `RLVaR` (Entropic/Relativistic VaR), `WR` (worst realization), `MDD`, `ADD`, `CDaR`, `EDaR`, `RLDaR`, `UCI` (Ulcer Index), plus range-of-drawdown variants. **The entire drawdown family — MDD, ADD, CDaR, EDaR, RLDaR, UCI — is available as a first-class convex *optimization objective*, not just a post-hoc reporting statistic.** That's the API shape worth copying (see Mental Models below).
- **`optimization(model="Classic", rm="MV", obj="Sharpe", kelly=None, rf=0, l=2, hist=True)`** (`Portfolio.py:1979`) is the single entry point for the whole mean-risk family: pick a `model` (Classic / Black-Litterman / Factor-Model / BL+Factor / Entropy-Pooling), a risk measure by string, an objective (`MinRisk`/`Utility`/`Sharpe`/`MaxRet`), and Riskfolio solves one convex program. **Note the `kelly` parameter here**: `None` (arithmetic mean), `"approx"`, or `"exact"` (log-return Kelly) — Riskfolio treats Kelly as *which expected-return estimator feeds the optimizer*, not as a bet-sizing fraction. That's a meaningfully different (and safer-looking, though still estimation-error-prone) use of the word "Kelly" than the bet-fraction sense `research/04` warns about.
- **`rp_optimization()`** (risk-parity: equalize risk contribution per asset) and **`wc_optimization()`** (worst-case, robust to uncertainty sets `Umu`/`Ucov`) are siblings of `optimization()` on the same class, same risk-measure string vocabulary.
- **`HCPortfolio`** (`HCPortfolio.py:26`, `optimization()` at line 760) — Hierarchical Clustering Portfolio: HRP/HERC-family allocation, same clustering idea as PyPortfolioOpt's `HRPOpt` but with more linkage/clustering options and the same 24-measure risk vocabulary usable as the intra-cluster allocation rule.
- **C++ acceleration** (`riskfolio/external/cppfunctions.py`, vendored Eigen 3.4.0 under `riskfolio/lib/eigen-3.4.0/`) backs some of the heavier linear algebra — a maintenance surface (native build) that a solo operator should not want to depend on for anything time-critical.

### FinanceToolkit — `reference/repos/FinanceToolkit/financetoolkit/`

Not a portfolio optimizer at all — a **fundamentals + ratios + technicals + risk + performance data toolkit**, built around one facade class and a set of thin "controller" objects, each wrapping a "model" (pure-function) module:

- **`Toolkit`** (`toolkit_controller.py:76`) is the single entry point: `Toolkit(tickers, api_key=...)` then `.ratios`, `.technicals`, `.risk`, `.performance`, `.models`, `.options`, `.portfolio`, `.economics`, `.fixedincome`, `.discovery` — each a `*_controller.py` class instantiated lazily and handed the toolkit's already-fetched historical/fundamental data (`toolkit_controller.py:14-51` shows the full import graph). This controller/model split (`ratios_controller.py` orchestrates, `profitability_model.py`/`liquidity_model.py`/`solvency_model.py`/`valuation_model.py`/`efficiency_model.py` compute) is a clean "thin dispatcher over pure calculation functions" pattern.
- **Risk module** (`risk/risk_controller.py:30`) — VaR, CVaR, EVaR, GARCH, EWMA, max drawdown, correlations. Constructor takes `historical_data`, `risk_free_rate_data`, `intraday_period`, `quarterly`, and explicit `start_date`/`end_date` — every method is date-range-scoped, not global-state.
- **Technicals module** (`technicals/technicals_controller.py:26`) — "40+ Technical Indicators" across breadth/momentum/overlap/volatility sub-models — standard TA (RSI, MACD, ADX, Bollinger, etc.), equities-and-generic-OHLCV-shaped, nothing forex-specific.
- **Options module** (`options/`: `black_scholes_model.py`, `binomial_trees_model.py`, `greeks_model.py`) — full options pricing and Greeks. **Flagged explicitly: QMX's stocks lane is permanently day-trading equities only, never futures or options — this entire module is out of scope and should never be imported, referenced, or copied**, even if the rest of the package is later wrapped.
- **Data sourcing** — `fmp_model.py` wraps the paid Financial Modeling Prep API (fundamentals, quotes, analyst estimates, ESG, earnings calendar); `yfinance_model.py` is an optional free fallback for historical price data specifically (`historical_model.py:12-19` checks for the `yfinance` package and falls back with a warning if FMP's plan doesn't cover it). **This means FinanceToolkit's fundamentals/ratios functionality has a paid-data dependency baked in** — it is not a free lunch the way TA-Lib or a pure-price-history tool is.
- **MCP server** (`mcp_server/`) — `mcp_controller.py` builds a `FastMCP` app; `inspection_controller.py`'s `ControllerInspector` and `registry_controller.py`'s `ToolRegistry` **introspect the `Toolkit`'s own controller classes at runtime and auto-generate typed MCP tools from them**, with auth (`auth_model.py`), caching (`cache_model.py`) and per-tool coercion/formatting (`coercion_model.py`, `formatting_model.py`). This is a concrete, shipped example of "reflect a typed calculation surface into an agent-callable tool registry" — the same shape as QMX's planned `qmf.spec`, just for financial-statement analysis rather than trading.
- **Portfolio module** (`portfolio/portfolio_controller.py:21`) — a *personal bookkeeping* tool: reads a CSV/Excel of your own trade history plus a YAML config mapping columns, and computes performance/cash-flow metrics against it. Not a sizing/optimization engine — closer to a tax-and-performance ledger reader. Not the same "Portfolio" concept as PyPortfolioOpt/Riskfolio-Lib's weight optimizers.

## Mental models worth borrowing

1. **One risk-measure registry, one optimizer entry point, risk measure selected by name.** Riskfolio-Lib's `rmeasures` list (`Portfolio.py:28`) plus its single `optimization(rm="MV", ...)` call means adding a new risk measure is a one-line registry addition plus one function, not a new class per measure (contrast PyPortfolioOpt's `EfficientCVaR`/`EfficientCDaR`/`EfficientSemivariance` as separate sibling classes duplicating the same method family). For QMF's `qmf.metrics` and `qmf.bms` risk-multiplier computation, a small typed enum of named risk checks feeding one evaluation function is cleaner than a class per rule and matches the `min()`-over-named-multipliers design `research/04` already recommends from pysystemtrade.

2. **The whole drawdown family as first-class, not just reported after the fact.** Both libraries treat MDD, Average Drawdown, CDaR (Conditional Drawdown at Risk), EDaR, and Ulcer Index as *optimization objectives with the same calling convention as standard deviation* (`Portfolio.py:2041-2046`; PyPortfolioOpt's `efficient_cdar.py`). QMF's own overfitting/metrics rings (`qmf.overfit`, `qmf.metrics` per `research/00`) already plan a versioned statistics contract — this confirms drawdown-family measures deserve equal billing with volatility/Sharpe in that contract, not second-class "extra chart" status.

3. **Structural constraints declared in the constructor, not scattered through method calls.** Riskfolio's `Portfolio(sht=, uppersht=, upperlng=, budget=, nea=, card=, ...)` (`Portfolio.py:56` onward) puts every hard constraint in one place, readable at a glance, before any solve happens. QMF's `Confluence`/`BookConfig` schemas (per `research/00`'s `qmf.spec`) should keep the same discipline: constraints belong in the frozen spec object, never assembled ad hoc inside a sizing function.

4. **Correlation-based clustering as a basket-risk primitive, independent of predicting direction.** `HRPOpt.optimize()` (PyPortfolioOpt) and `HCPortfolio.optimization()` (Riskfolio-Lib) allocate purely from the covariance/correlation structure — no expected-return estimate required. QMX will not use this to allocate capital across dozens of stocks, but the identical building block (a distance matrix from pairwise correlations, hierarchical clustering, recursive risk-bisection) answers a QMX-relevant question the framework doesn't yet have an owner for: **when two or three Books are concurrently long correlated FX pairs (EURUSD + GBPUSD, or a USD-basket trade), how much *combined* risk is actually being carried, and should the BMS scale one of them down because they're really one bet?** `research/04`'s open question 7 ("How Books coordinate when several are live on one account") is exactly this gap. Wrap `scipy.cluster.hierarchy` directly (BSD-licensed, PyPortfolioOpt's usage is a thin, easily-reimplemented layer over it) rather than depending on either library at runtime — but steal the algorithm shape for a `qmf.book` cross-Book correlation gate.

5. **A numerical-safety habit: auto-repair a broken covariance matrix instead of crashing.** `fix_nonpositive_semidefinite()` (`risk_models.py:57`) catches the common real-data failure mode (a covariance matrix that isn't quite valid due to missing data / too few observations) and repairs it via eigenvalue clipping, with a loud warning rather than a silent wrong answer or a hard crash. Any QMF code computing a correlation/covariance matrix for the basket-risk gate above should copy this defensive pattern.

6. **Auto-generating an LLM-agent tool surface by reflecting over typed controller classes.** FinanceToolkit's `mcp_server/inspection_controller.py` + `registry_controller.py` walk the `Toolkit`'s own controller classes and turn their public methods into typed, discoverable MCP tools automatically, rather than hand-writing a tool schema per method. This is a working precedent for QMX's `qmf.spec` design goal ("the entire surface an LLM agent sees... target: one printed page," per `research/00` Ring 8) — it demonstrates that reflection-driven tool generation from a well-typed controller layer is viable in practice, and is worth a direct look when `qmf.spec` is implemented, even though FinanceToolkit's domain (statement analysis) is unrelated to trading.

7. **Controller/model separation as a codebase-organization pattern.** Every FinanceToolkit domain (`ratios`, `technicals`, `risk`, `performance`) follows the same shape: a thin `*_controller.py` that owns state (tickers, date ranges, rounding) and dispatches to a stateless `*_model.py` of pure calculation functions. This is a plain, boring, and correct pattern for `qmf.indicators`/`qmf.structure` — keep the stateful orchestration (warm-up, replay, provenance) in one thin layer and the actual math in pure functions that are trivially unit-testable and swappable.

## What to avoid

1. **Do not put any of the three optimizers on QMX's live path.** None models a stop-loss, lot size, margin, broker fee schedule, or session — confirmed at the source level here (PyPortfolioOpt's `DiscreteAllocation` is the closest thing to "real money," and it stops at integer share counts with no lot-step or margin concept at all). This matches `research/04`'s verdict from documentation and is now confirmed by reading the actual optimizer signatures — there is no hidden sizing logic to inherit.

2. **Do not conflate Riskfolio-Lib's `kelly` parameter with a bet-sizing fraction.** In `Portfolio.optimization(kelly="exact")` (`Portfolio.py:2057-2061`), `kelly` selects *how the expected-return vector is estimated* (arithmetic vs. log-mean), not how much of the account to risk. Someone skimming the API and assuming "Riskfolio has Kelly sizing built in, safe to point a Book at it" would be wrong in a dangerous way — it's an estimator choice layered under a full-Kelly-unconstrained convex optimizer, with none of the half-Kelly capping `research/04` insists on.

3. **Do not treat PyPortfolioOpt's optimizer objects as reusable/stateful services.** The docstring itself says a new `EfficientFrontier` instance is required for any change to objectives/constraints (`efficient_frontier.py:17-22`) — the object accumulates cvxpy problem state as you call methods. Anything built as a long-running service (which QMF's runtime is) must construct a fresh instance per solve, never hold one across requests; this is an easy bug to introduce if this code were ever wrapped naively.

4. **Do not depend on FinanceToolkit's options/Greeks module at all, structurally.** It exists and is well-built (`black_scholes_model.py`, `binomial_trees_model.py`, `greeks_model.py`), but options and futures are permanently out of scope for QMX's stocks lane. Even importing `financetoolkit.options` transitively pulls in code and a mental model (implied vol, Greeks) that has no product it will ever serve — leave it un-wrapped, not merely unused.

5. **Do not assume FinanceToolkit's data is free.** Its fundamentals/ratios/discovery/economics surface is built on the paid Financial Modeling Prep API (`fmp_model.py`); only historical price data has a free `yfinance` fallback path, and that fallback is explicitly a degraded mode the code warns about (`historical_model.py:249`). Budget for an FMP subscription (or find a free-tier ceiling that's actually usable) before assuming this library gets QMX fundamentals data for nothing.

6. **Do not depend on Riskfolio-Lib's native/C++ layer for anything latency- or reliability-sensitive.** It vendors Eigen 3.4.0 and ships C++-accelerated functions (`riskfolio/external/cppfunctions.py`, `lib/eigen-3.4.0/`) — a native build dependency that adds install fragility for a solo operator, appropriate only for offline research use where a slow pure-Python fallback would be equally acceptable.

7. **Do not read "24 risk measures" or "200+ metrics" as evidence of forex/prop-firm relevance.** Every risk measure in both optimization libraries is computed from a *returns time series across assets*, i.e. it answers "how should I weight my basket," not "how much should I risk on this one trade with this one stop." The breadth is real but it is breadth along the wrong axis for QMX's actual first problem, exactly as `research/04 §3` concluded before any of this code was opened.
