# QMF V1 Security Model

QMF V1 concentrates authority at explicit contract seams: humans control live promotion, backend risk semantics never originate in external adapters, middleware translates but does not decide, data stores hold evidence but no business rule, and external providers remain outside QMF control. [DEC-0009] [DEC-0041] [DEC-0059] [DEC-0065]

## Security status

The venue secret lifecycle is ratified as law (DEC-0136): QMF components handle secret **references**, never values, and the leak surfaces are mechanical to scan. Store mechanics, key custody, deployment identities, key-store locations, roles, and alert thresholds still land at the node/ops sitting, and no live account is fixed here. This document grants no live access, credential use, order submission, flattening, promotion, restore, or destructive mutation authority; the design is ratified, but implementation authorization arrives only through the factory pipeline, never from these docs alone.

## Dependency and supply-chain trust

Dependency and licence tiers are ratified as a supply-chain control (DEC-0104): permissive licences (MIT, BSD, Apache, PSF) are freely allowed; LGPL only unmodified and separately installed; GPL and AGPL are prohibited; strategy-family libraries and platform-imposing dependencies (own event loop, runtime, or data model) are prohibited. `qmf-core` takes **zero** outside dependencies (stdlib only), which keeps the sandbox-critical core weightless and its attack surface minimal. Every dependency gets exactly one line in the workspace-root register `DEPENDENCIES.md` — name, licence, why — so no unaudited or unlicensed transitive dependency enters the build unrecorded.

## Secret lifecycle (AD-26)

The venue secret lifecycle is ratified law (DEC-0136), answering GAP-0035. No secret value or secret location appears anywhere in QMF; QMF components hold **secret references, never values**.

- **References, not values.** A secret reference is an **opaque minted id** under AD-9's identity discipline: stable, never reused, and never encoding venue, broker, account, environment, or key material; any human-readable label is a separate field held outside evidence, and construction validates opacity (`invalid input` on failure). `qmf-core` ships typed `SecretRef` and `SecretValue`; a `SecretValue` never renders its value — repr, str, serialization, and logging all yield the reference id — and a **tier-1 secret-scan gate rides `poe check`** (DEC-0136).
- **Never in the open.** Secrets never appear in repositories, configuration artifacts, docs, chat, `.env` files, CLI arguments, journals, evidence, fingerprints, or logs. A missing, expired, or rejected credential is an `unavailable dependency` refusal carrying the reference id, never the value; refusal context, logs, health reports, and metric labels carry the reference id only (DEC-0136).
- **Injection at the root.** Values are injected at the composition root from the deployment environment's protected store (`systemd-creds`-class on the VPS); store mechanics and key custody land at the node/ops sitting (DEC-0136).
- **Binding identity.** An account-binding record's identity is `(VenueId, AccountId, role, world)`; its secret reference is declared occurrence/display-only and excluded from `fp1` — a credential is a deployment fact, never a market fact (DEC-0136).
- **Single value-holder.** The adapter's connection manager is the single named component permitted to hold secret values in memory, for a session's lifetime, through a core-defined `SecretStore` port (read + atomic replace) injected by the root; values never cross back out — no getter, no log line, no refusal context, no health field, no metric label (DEC-0136).
- **Rotation.** A credential is a one-writer stream: exactly **one live refresher per credential** — a workstation tool never refreshes a credential a VPS session owns. Where the venue rotates refresh material on use, the new secret is stored (atomic replace) **before** the old is discarded; a failed store after rotation is an alarm **and** a command-pipe block (`unavailable dependency`, after-condition = successful store or operator re-provision) with the **sensing pipe unaffected** (DEC-0136).
- **Compromise drill.** Recovery is a documented, tested drill: cTID re-authorization (which invalidates **all** outstanding refresh tokens — the never-expiring refresh token is the crown-jewel secret, DEC-0135), application-credential reset, store replacement, and session restart; expiry and refusal paths ship as **tested behavior** (DEC-0136). See [OPS-INCIDENT-QMF-V1](../ops/incident-playbook.md) for the drill steps.
- **Testing posture.** Testing uses **demo credentials only**; factory sandboxes never hold live secrets. Credential entry and management UI is platform territory (DEC-0136).

The cTrader token facts are ratified (DEC-0135): a ~30-day access token, a never-expiring refresh token as the crown-jewel secret, and cTID re-authorization as the invalidation anchor.

## Audit evidence

CT-13 is the ratified journal boundary — N append streams, one per producing component under its `WriterId`, seven event types, `correlation_id` excluded from `fp1` identity (DEC-0119). On the venue path (DEC-0138), measurements and verification verdicts journal as `data quality` events and adapter-initiated state changes (suspend-new, drain, session restart, throttle engaged, reconnect) journal as `control action` events; the CT-20 cardinality law binds — exactly one journal event per recorded observation, per submission, and per outcome, and every outcome including `denied-locally` mints an observation record and a journal event (DEC-0137). Journal and evidence records carry a secret reference id only, never a secret value (DEC-0136). CT-25 is only a reserved, unwired future risk-evidence placeholder. Per-event field lists, numeric retention, and redaction rules are set after measured volume and are per-contract detail. [DEC-0048] [DEC-0119]
