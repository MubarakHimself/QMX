## 1. 2601.01885 — Agentic Memory (AgeMem): Unified LTM/STM via RL

**Core mechanism (faithful).** AgeMem exposes six memory operations as *tool calls* directly in the LLM policy's action space: `Add`/`Update`/`Delete` on long-term memory (LTM), `Retrieve`/`Summary`/`Filter` on short-term context (STM). A single policy π_θ is trained end-to-end with a **three-stage progressive curriculum** inside one rollout: Stage 1 = casual exposure to info, agent may write to LTM; Stage 2 = context reset + distractor injection, agent must filter/summarize STM; Stage 3 = the actual task, requiring coordinated retrieval + reasoning. LTM persists across all three stages; STM resets between 1→2 to force genuine retrieval rather than context leakage. Training uses a **step-wise GRPO** variant: the terminal task reward is group-normalized then *broadcast* to every earlier step in the trajectory (not discounted per-step), giving every memory decision (including Stage-1 writes) the same credit-assignment signal as the final answer. Reward is a weighted sum of task-completion (LLM-judge score), context-management quality, and memory quality, plus a penalty for overflow/redundant storage.

**Evidence quality.** Empirical, ablated (Fig. 4: Base → +LTM → +LTM/RL → +LTM/STM/RL, monotonic gains), tool-usage statistics reported (RL increases Add/Update/Filter call frequency), memory-quality scored via LLM judge against HotpotQA ground truth (MQ 0.533–0.605), token savings 3–5% vs. RAG variant. Five benchmarks, two backbones (Qwen2.5-7B, Qwen3-4B). Moderate-to-good rigor for a method paper; single-domain (QA-style) task suite, not tool-use/coding agents.

**Borrow.** The *single unified action space* for memory ops is a strong argument that memory verbs (add/update/delete/retrieve/summarize/filter) belong in the model's tool-calling surface, not a bolted-on external controller — directly reinforces a kernel-level "memory as first-class tool contract" rather than memory as an opaque service the model can't see into. The reward-shaping split (task / context / memory) is a reusable pattern for anyone building an RL-trained mind.

**Reject.** The RL training apparatus (three-stage curriculum, step-wise GRPO, broadcast advantage) is a *training methodology*, not a runtime architecture — irrelevant to QMA, which is not proposing to RL-train minds. Treat this paper as evidence for the *tool schema* only, not for how memory management gets learned.

**Kernel implications.** DEMANDS a kernel hook only in the narrow sense that the six-verb tool schema (Table 1) is a good reference contract for a `MemoryPlugin` interface. Does NOT demand anything about storage/consolidation internals — those stay swappable. Suggests kernel should standardize the *verb set* (add/update/delete/retrieve/summarize/filter) as a stable ABI so different memory plugins are interchangeable behind the same tool surface.

## 2. 2606.06448 — Agent Memory: Characterization and System Implications of Stateful Long-Horizon Workloads

**Core mechanism (faithful).** This is NOT a new memory architecture — it is the first **systems-level empirical characterization** of 10 existing agent-memory systems (BM25, embedRAG, GraphRAG, HippoRAG v2, Mem0, SimpleMem, A-Mem, Letta, MIRIX, long-context baseline) across a **4-paradigm taxonomy** (I: long-context / II: flat RAG / III: structure-augmented RAG [III.a append-only, III.b consolidating] / IV: agentic control flow) and a **7-stage execution pipeline** (ingestion → construction → storage → retrieval → prompt assembly → generation → maintenance). Built a phase-aware profiling harness (API + GPU telemetry) and ran all 10 systems on MemoryAgentBench + LongMemEval + MemoryArena on identical hardware (Stanford Marlowe cluster, H100s).

**Evidence quality.** Very high — this is the strongest evidence-quality paper in the cluster: real quantitative benchmarking, not self-reported numbers. Key measured findings: per-query serving latency spans **two orders of magnitude** across systems on identical hardware (Mem0 <0.1s vs long-context ~38s); **construction (write-path) dominates lifecycle cost**, not query-time serving — construction energy exceeds total 300-query serving energy for LLM-mediated systems, with energy-per-correct-answer differing by >47×; construction is prefill/embedding-dominated (median decode share of construction tokens = 4.6%); Paradigm IV (agentic) systems scale **super-linearly** in token cost as memory store grows (Letta diverges steeply beyond 256K tokens); per-session construction time spans **five orders of magnitude** (BM25 ~10⁻³s to MIRIX/Mem0 ~10s, tails >100s); no evaluated system prunes/forgets by default — footprint grows monotonically absent an explicit forgetting policy; construction-LLM downscaling is safe for systems without strict output contracts (Mem0, A-Mem) but MIRIX *fails completely* at small models because its pipeline depends on well-formed multi-tool-call JSON.

**Borrow.** This paper should directly shape kernel API design, independent of which memory plugin QMA ships with:
- **Kernel needs an admission-control / scheduling hook for background memory-construction work**, distinct from the inference-serving path — construction is a throughput job (batch, rate-limit, defer), not a latency-sensitive one, and routing both through the same LLM endpoint causes head-of-line blocking (Insight 3/Rec 3).
- **Kernel needs an iteration-cap / timeout hook for LLM-bounded memory phases** — "agentic control flow" paradigms have unbounded worst-case latency (LLM decides when to stop); the kernel must be able to impose external caps regardless of which memory plugin is loaded (Insight 8/Rec 10).
- **Kernel needs a freshness/staleness signal at the memory-read interface** — under async construction scheduling, agents can retrieve against memory sessions behind the ingest stream; a kernel-level "as-of" or staleness flag on retrieval results is implied (Sec 4.6).
- **Kernel (or platform ops) needs a mandatory forgetting/pruning policy hook** — every system tested accumulates unboundedly by default; this is a missing primitive across the entire ecosystem, not something any one plugin solves (Insight 7/Rec 9).
- Construction-vs-query cost tradeoff is paradigm-dependent and not visible to accuracy-only evaluation — reinforces that memory backend choice should be a swappable, workload-matched *plugin decision*, not baked into the kernel.

**Reject.** Nothing to reject — it's a measurement study, not a design proposal. The one caution: results are English-text, single-node; multi-agent/distributed consistency and multimodal memory are explicitly flagged as open (unmeasured) by the authors — don't over-generalize kernel design for distributed memory from this paper alone.

**Kernel implications — the strongest in this cluster.** This paper is the best evidence that memory is a *systems* problem requiring kernel-level scheduling/admission primitives (background construction lanes, iteration caps, staleness metadata, pruning mandates) that sit **above** any specific memory algorithm. The actual storage/retrieval algorithm (Mem0-style consolidation vs. graph vs. flat RAG) stays a swappable plugin — the taxonomy itself proves no single algorithm dominates on the construction/serve/accuracy frontier, so the kernel must not hard-wire one paradigm in.

## 3. 2607.23809 — ACM: Agentic Context Management for Long Horizon Tasks

**Core mechanism (faithful).** Exactly two tools, both operating on the *working context only* (not a separate long-term store, despite the "memory" framing): `manage_context` compresses prior turns into a summary AND writes the raw discarded messages to an external file on disk (so compression is **lossless** — nothing is thrown away, just moved out of the active window); `query_memory(summary_id, query)` lets the agent re-read the archived raw messages behind a specific summary on demand via a querier LLM. Critically, **both tools are agent-initiated** (the model decides when to call them, not an external threshold monitor like the "Summary Agent" baseline). A **teacher-guided dual-constraint SFT pipeline** trains a 9B model to learn correct *timing*: one constraint injects `manage_context`/`query_memory` calls into failed no-tool rollouts where compression would have helped; the other constraint replaces premature/unnecessary compression calls in tool-equipped rollouts with better actions (search deeper, commit to an answer). Training is on-policy distillation (KL to teacher top-K token distribution), not RL.

**Evidence quality.** Solid empirical results with real held-out benchmarks: BrowseComp-Plus, DeepSearchQA, SWE-Bench Verified. ACM (untrained, tools-only) already beats ReAct/Summary-Agent/ACE baselines; post-training gives 27%/16%/8% relative gains respectively; peak token usage cut ~20%; near-matches a 40×-larger frontier model on BrowseComp-Plus. Important negative/honest result: **GPT-5.5 given the same tools rarely uses them without training** — tool availability alone doesn't induce good timing behavior. Also honestly reports that a 4B model never reaches the regime where context management matters (collapses to 2-turn trajectories) — context management is a property of long rollouts, not small models.

**Borrow.** The lossless-compression pattern (summarize-and-archive rather than summarize-and-discard, with an addressable pointer back to raw content) is directly reusable as a kernel-level context-management primitive — cheap, general, and doesn't require any learned memory architecture underneath. The clean two-verb tool contract (`manage_context`, `query_memory`) is a minimal reference ABI.

**Reject.** The finding that agent-initiated timing must be *trained* (not just made available) is a caution against assuming a kernel can simply expose the tools and get good behavior "for free" from any backbone mind — the kernel exposing the hook is necessary but not sufficient; the mind (or its scaffolding/prompting) still needs deliberate design to use it well. Don't treat "give the agent the tool" as a complete solution.

**Kernel implications.** ACM's mechanism is a strong candidate for a **kernel-level short-term-context management primitive** (working-context compaction with lossless archive-and-retrieve), distinct from and simpler than a full long-term memory subsystem. It suggests QMA's kernel should offer a *minimal, standardized* context-editing tool pair as a base capability (not a plugin), with richer long-term memory (semantic/episodic/procedural stores, consolidation policies) layered as swappable plugins on top. This is a SIMPLER approach than a full Cordis-style plugin kernel for the specific sub-problem of context-window pressure — it argues for a small built-in primitive rather than requiring every memory plugin to reinvent context compaction.

## 4. 2606.06787 — AdMem: Advanced Memory for Task-solving Agents

**Core mechanism (faithful).** A **multi-agent** architecture (actor / critic / long-term-memory agent, running in parallel threads) with a bi-level split: short-term memory (STM) is a **stack-based** context-compaction scheme borrowed from program execution — sub-goals push/pop a stack frame, turns outside the current sub-goal are summarized and popped, letting the agent "resume" higher-level objectives after finishing a sub-task (this is architecturally distinct from ACM's flat compress-and-archive). Long-term memory (LTM) splits into semantic (facts), episodic (event summaries), and procedural (decision-making guidance) stores. The **critic agent** is the interesting piece: the actor states an *expected outcome* before acting; the critic later compares actual vs. expected outcome, assigns a binary reward, and writes a procedural-memory entry with reflection. Retrieval scoring for procedural memory uses a lightweight **Bayesian bandit model**: each memory entry has a latent effectiveness parameter v_m ∈ [0,1], updated via EM from a noisy-OR reward model over which retrieved memories plausibly caused success — memories are retrieved by score v_m · cosine-similarity(context, memory-context), and entries with retrieval frequency below ε are pruned; entries retrieved-together-or-not-together above 1-ε are merged.

**Evidence quality.** Weaker than papers 2 and 3: evaluated on AgentBoard (embodied AI, text games, web research, tool calling) as a single life-long streaming run, one LLM backbone (Claude Haiku 4.5), baselines limited to ReAct and AWM (explicitly *not* compared against Mem0/MemGPT/MIRIX because those target QA retrieval, not interactive tool-use — a reasonable but narrowing scoping choice). Reports an honest negative finding: naive procedural memory (just replaying past successes, no reward filtering) **can harm performance** when transferred info causes confusion rather than help — this is exactly the "failure cases" gap AdMem claims to fix. Ablation shows LTM alone "burns in" with early performance degradation before it helps; only combined with the critic/reward mechanism does it net-improve.

**Borrow.** The expectation-vs-outcome critic pattern for procedural memory is a genuinely useful mechanism absent from AgeMem/ACM/systems-characterization — it's a principled way to generate a reward signal for procedural memory *without* requiring an environment-native reward, applicable directly to QMA minds operating in reward-sparse environments. The stack-based STM (mirroring call-stack semantics for sub-goal scoping) is a cleaner mental model for context management in planning-heavy minds than flat summarization. The bandit-based retrieval-effectiveness scoring is a lightweight, principled alternative to pure semantic-similarity retrieval.

**Reject.** The multi-agent (actor/critic/memory-agent) architecture as a *mandatory* runtime shape is expensive (worst case: 2× latency, 3× LLM calls per step) and is a design choice, not a proven necessity — the paper doesn't ablate against a single-agent-with-tool-calls version equivalent to AgeMem's approach, so it's unclear the multi-agent split earns its cost over a unified tool-based policy. Treat the "three-agent" framing as one implementation choice, not evidence that a kernel must support multi-agent memory management.

**Kernel implications.** Suggests a plugin, not a kernel hook: the critic/expectation-outcome pattern, the stack-based STM, and the bandit retrieval scorer are all naturally implementable as one coherent memory-plugin design, callable through a standard tool interface — nothing here demands new kernel primitives beyond what AgeMem/ACM already imply (a tool-callable memory surface, async background writes). The one thing worth flagging for kernel designers: if minds are expected to state *expected outcomes* before acting (for later critique), the kernel's action-logging/event schema should have a first-class slot for "predicted outcome" alongside actual observation — this is a small but real schema implication, not a control-flow one.

## 5. 2607.16621 — MSCE: From Memory to Skills, Evidence-Grounded Co-Evolution Governance

**Core mechanism (faithful) — the paper most relevant to "promotion-gate."** A **training-free**, three-level memory hierarchy plus a governed promotion path to callable skills:
- **L1 trace memory**: grounded per-step tuples (state, action, observation, self-reflection, value V). Stores *normalized* evidence (truncated/redacted text, capped tool I/O) — not unbounded raw logs — for storage/privacy bounding.
- **L2 policy memory**: procedures induced from **cross-episode** recurring trace patterns (requires evidence from ≥ n_min=2 distinct episodes, matched via embedding similarity + structured signature — domain tags, tool types, normalized error signatures). Each policy tracks a **gain** G = value-weighted mean of traces linked to the policy minus a shrinkage-adjusted mean of traces not linked to it — a heuristic (explicitly *not causal*) utility estimate.
- **L3 environmental cognition**: declarative facts about the *environment* (not the task) abstracted when multiple active L2 policies share a domain context — e.g., repeated file-editing policies induce a "this repo's structure" cognition. Provides parameters/priors to instantiate skills without overriding their procedure.
- **Skill promotion (the promotion-gate)**: an L2 policy becomes an eligible skill only when it passes **two gates**: (1) positive-gain gate, G(policy) > θ_G (θ_G = 0 in their hyperparameters — i.e., must beat the without-policy baseline at all); (2) **stability gate** — recent evidence must still fit the *current* trigger/procedure/boundary rather than requiring a rewrite. A crystallization LLM call drafts the skill (steps, params, decision guidance) constrained to a tool whitelist observed in evidence; a **deterministic verifier** checks schema validity, evidence-grounding (cited evidence IDs must be in the support set), and coverage (no invented commands) — drafts failing any check are discarded, never exposed as callable.
- **Post-promotion lifecycle**: skills carry a smoothed reliability score η = (n_pass+1)/(n_trials+2) (Beta-prior smoothing); η rises on success, falls on failure/user-rejection; low-η skills go probationary → archived (θ_η^active=0.6, θ_η^archive=0.2 in their config); user rejection can **shrink the applicability boundary** rather than just lowering reliability; if the *source* L2 policy gets substantially rewritten, the skill is **rebuilt from fresh evidence**, not patched in place.
- **Value signal**: "reflection-weighted value backfilling" — sparse terminal reward R_i is propagated backward through steps via V(f_t) = α·R_i + (1-α)·γ·V(f_{t+1}), where α is an LLM-estimated per-step "reflection quality/faithfulness" weight (faithful, concrete, causally-informative reflections get high α; empty/tautological ones get α≈0). This lets locally-informative steps anchor closer to the true reward while uninformative steps mostly inherit from later steps' backfilled value.

**Evidence quality.** Solid ablations (Table 3): removing skill crystallization causes the single largest degradation among component ablations (Pass@1 down 6–11.5 pts, cost up in every domain); flat memory (no hierarchy at all) is far worse than any structured ablation (Pass@1 down 15–19 pts). Tested on EvoAgentBench (5 domains: IR, Math, SE, Code, Knowledge-Work) and LoCoMo (dialogue memory). Reports a genuine lifelong-learning curve (p0→p100 accumulated experience) showing monotonic Pass@1 gains *and* falling per-task cost at scale — a "learning by using" effect. Caveat honestly stated by the authors themselves: gain/reliability scores are "heuristic governance signals... not causal credit-assignment estimates" — they support ranking/filtering, not a guarantee that a promoted skill *causes* success.

**Borrow.** This is the cluster's most directly useful paper for "verified experience becomes governed capability." The two-gate promotion pattern (positive-gain + stability, both computed from evidence-linked traces, verified by a deterministic non-LLM checker before exposure) is close to a reference design for QMA's promotion-gate concept: memory → policy → skill, with hard verification (schema + evidence-grounding + no-invented-commands) as a non-negotiable final check regardless of how confident the LLM crystallizer is. The reliability lifecycle (probation → active → archive, shrinkable boundary on rejection, rebuild-not-patch on source drift) is a complete, concrete state machine worth adopting close to verbatim.

**Reject.** The "training-free" framing is somewhat oversold — while the *base LLM* isn't fine-tuned, the system depends on multiple prompted LLM operators (reflection scoring, policy induction, L3 abstraction, reward quantification, skill drafting) that add real latency/cost and are "sensitive to model and prompt choices" (authors' own limitation). This is not free — it trades gradient-based training cost for inference-time LLM-call cost, which the systems-characterization paper (#2) would flag as exactly the "construction dominates lifecycle cost" pattern. Don't adopt the "training-free ⇒ cheap" framing without also budgeting the crystallization/reflection LLM calls as construction cost.

**Kernel implications — DEMANDS a kernel hook, and this is the one direct challenge to a pure-plugin memory stance.** Unlike AdMem (plugin-shaped) and ACM (small built-in primitive), MSCE's promotion-gate genuinely wants something closer to a **kernel-level capability registry**: skills, once promoted, become *callable objects with a standardized interface, lifecycle state, reliability score, and evidence anchors* — this is structurally identical to what a kernel's plugin-registration/capability system needs to do for any capability (deterministic verification before activation, reliability-gated exposure, boundary-scoped applicability, revocation on drift). If QMA's kernel already has a plugin-loading/capability-registration mechanism, the promotion-gate is arguably *the same mechanism* applied to LLM-synthesized procedures instead of human-authored code — meaning the kernel should expose its capability-registration API to the memory subsystem rather than the memory subsystem inventing a parallel one. This is the strongest argument in the cluster for a named kernel interface: **"propose-verify-register-revoke" as a first-class kernel primitive**, with memory-driven skill promotion as one caller among several (human-authored plugins being another).

## Cluster Verdict

**Top borrowings (ranked):**
1. **MSCE's two-gate promotion + verify + reliability-lifecycle state machine** — best template for "verified experience becomes governed capability"; reuse near-verbatim.
2. **Systems-characterization paper's operational demands** — background-construction admission control, LLM-bounded iteration caps, staleness metadata on retrieval, mandatory pruning policy — these are kernel-shaped requirements independent of which memory algorithm ships.
3. **ACM's lossless compress-and-archive pattern** — minimal, general, good candidate for a small built-in context-management primitive rather than a full plugin.
4. **AgeMem's six-verb tool schema** (add/update/delete/retrieve/summary/filter) as a reference ABI for memory tool-calling surfaces.
5. **AdMem's expectation-vs-outcome critic pattern** for generating procedural-memory reward signal without an environment-native reward — useful plugin-level technique.

**Kernel hook vs. plugin split, synthesized:** Memory *algorithms* (what AgeMem, AdMem, and most systems in paper #2's taxonomy implement) should stay swappable plugins — no evidence any single paradigm dominates, and workload-fit varies (paper #2's construction/serve/accuracy frontier). But three things want to be **kernel-level, not plugin-level**: (a) scheduling/admission-control for background memory-construction work, distinct from inference serving (paper #2); (b) a minimal built-in context-compaction primitive (ACM-style, lossless archive+retrieve) so every mind gets basic context-pressure relief without needing a full memory plugin; (c) a general **propose→verify→register→revoke capability-promotion primitive** (MSCE-style) that memory-driven skill crystallization can call into rather than reinventing — and which should probably be the *same* mechanism used for human-authored plugin registration, not a parallel one.

**Direct challenge to Cordis-leaning kernel direction:** MSCE is the one paper here that pushes back on "memory as pure plugin" — it implies the kernel needs an opinion about capability lifecycle (verification, reliability gating, revocation) that spans both LLM-synthesized skills and conventionally-authored plugins. If QMA's kernel currently treats "plugin registration" and "agent memory" as separate subsystems, this cluster's evidence says they should share one registration/verification primitive. This is worth flagging prominently rather than smoothing over: it argues for *more* kernel surface area than a minimal Cordis-plugin-kernel might currently assume, specifically around capability governance — not memory storage itself.
