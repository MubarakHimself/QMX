# QMA understanding audit (integration revision)

This is a bounded reading audit of the ratified QMA contracts and the corresponding source at integration revision `1b451a848d897e42f6e2c7fd9f2ea86fab7295f2`. It describes responsibilities and integration questions; the presence of source files or tests is not treated as runtime readiness.

## Plain-language explanation

QMA (QuantMind Agents) is the agentic operating layer around QMX’s quantitative work. It gives agents durable identities and work context, turns a goal into a governed mission and task graph, selects permitted tools and compute environments, routes model calls, records evidence and ledgers, and lets work continue across sessions or remote workers. QMA is three packages: `qma-core` defines the vocabulary and ports, `qma-daemon` is the single runtime and writer, and `qma-wire` is the versioned client/worker protocol (`docs/components/qma-core.md:15-19`, `docs/components/qma-daemon.md:15-19`, `docs/decisions/ADR-0020-qma-agentic-system.md:39-50`).

This adds substantially more than chat. The ontology is Desk → Role → Quant → Agent → Subagent, with Mission → Task and Session/Worker context (`docs/components/qma-core.md:51-55`). The daemon owns deterministic mission compilation, graph dispatch, hooks, ledgers, mailboxes, model/credential routing, compute placement, artifact admission, scheduling and telemetry (`docs/components/qma-daemon.md:21-25`). Agents propose transitions and artifacts; gates, leases, typed refusals and operator-principal checks keep proposals from silently becoming authority.

## What each layer owns

`qma-core` is definitions-only and depends only on `qmf-core`; it runs and writes nothing. Its public responsibilities are the ontology, seven runtime ports (MemoryProvider, ModelDeployment, ExecutionEnvironment, KnowledgeSource, ToolAdapter, ComputeProvider and ContextCompiler), plugin contribution types, typed refusal variants, handles and closed vocabularies (`docs/components/qma-core.md:17,21-25,57-69`). The integration source reflects this boundary: `qmx-agents/packages/qma-core/src/qma/core/__init__.py` describes a definitions-only SDK, while `src/qma/core/control/primitives.py` keeps Graph Template, Loop and Skill distinct. A Skill is reusable procedure/knowledge and may invoke a Loop; it is not itself a Loop or capability grant.

`qma-daemon` is the runtime composition root. `src/qma/daemon/taskgraph/compiler.py` contains the deterministic `MissionCompiler`, converting a `CompileRequest` into one `MissionRecord` and initial `TaskGraph`; it does not ask an LLM to compile. `src/qma/daemon/taskgraph/dispatcher.py` grants dispatch leases and asks `ComputeRouter` for environment leases, so agents declare requirements but do not choose hosts or vendors. The daemon’s stores and services cover the journal, Task/Quant/Experiment ledgers, hooks, plugin loader, context, memory/knowledge adapters, model proxy, tools, environments, scheduler and telemetry (`docs/components/qma-daemon.md:23,51-100`).

`qma-wire` is the sole cross-boundary contract. It carries versioned JSON-RPC commands/events over WebSocket and queries over HTTP GET, with `initialize`, `producer_id` + `id` deduplication, scoped replay and durable remote outboxes (`docs/components/qma-wire.md:27-40,59-70`). `src/qma/wire/envelope.py` validates the ordered `scope_path` and canonical envelope. `src/qma/wire/host_request.py` makes the RLM kernel’s host calls ordinary wire commands/queries, each mapped to exactly one daemon primitive and its `before_*` hook; unknown verbs return `UnknownHostRequest`. This is how a remote or containerized worker reaches QMA without a private shortcut.

## Relation to QMB, QML, QMF and nodes

QMB remains the experimentation/backtesting product. QMA reaches it through one runtime `qmb` door and does not import the QMB package. `qma/core/ports/qmb.py` states the route as agent → QMA backtest tool → Backtesting Service → `qmb` door → QMB, with replay-only requests; `qma/daemon/backtest/service.py` records the invocation and holds no scheduler, parallelism or durable backtest state. QMB owns its run ledger, parallelism and artifact contract. This preserves the user’s broad experimentation intent while keeping orchestration separate from the experiment implementation.

QML is the plain-Python bot-authoring library. Its governed bot has a declaration plus ordinary Python logic; QML’s conformance gate is a ticket into governed evidence/Book seats, not a replacement language or agent runtime (`docs/components/qml.md:17-25,50-62`). QMA can reference and coordinate QML artifacts, but does not redefine Bot, Book, BMS or risk authority. The QMF libraries remain the shared foundation for exact money/time, fingerprints, registry records, risk contracts and typed refusals. QMA’s documented registry/risk edges are explicitly read-and-calculate and default-deny; it never imports `qmf-venue` (`docs/components/qma-core.md:71-73`).

The trading node is a separate money-path application. QMA may produce candidate artifacts for human promotion, but no QMA tool, worker or environment may reach venue/broker/trading-node controls (`docs/decisions/ADR-0020-qma-agentic-system.md:49-50,59-63`). Node and QMA therefore integrate through reviewed artifacts and evidence, not an agent execution shortcut.

## Extensibility and remote coordination

The extension model is explicit rather than ambient: plugins register tools, adapters, hooks, skills, graph templates, deployments, toolsets and worker templates through `PluginContext`; singleton cardinalities and qualified IDs prevent collisions (`docs/components/qma-core.md:57-65`). Ordinary Python remains a first-class authoring path in QML, while QMA plugins add capabilities through typed ports and `qma-wire` schemas. This supports user-facing extensibility without randomly connecting libraries: each edge and contribution point has a named owner, scope and refusal behavior.

Confirmed coordination choices are workstation-default daemon, Docker workers, remote sides dialing out, durable outbox/replay, Task Graph synchronization rather than group chat, and RLM host calls through wire (`docs/components/qma-daemon.md:17-19; docs/components/qma-wire.md:41-65; docs/decisions/ADR-0020-qma-agentic-system.md:44-46`). Open questions remain deliberately visible: UI presentation/extension SDK beyond the stub (`GAP-0081`), external agent-to-agent transport (`GAP-0079`), remote compute/vendor choices, Windows VPS desktop provisioning (`GAP-0070`), memory backend and knowledge indexing (`GAP-0072–0073`), graph engine choice (`GAP-0086`), context compaction (`GAP-0090`) and several QMA deferred rows. These are integration unknowns, not invitations to invent a new architecture.

The practical distinction is: QMA supplies durable, governed agent coordination and evidence; QMB supplies experiments; QML supplies bot declarations and plain Python logic; QMF supplies shared quantitative contracts; the node owns market execution. The split makes broad strategy experimentation possible while preserving user-facing Python extensibility and authority boundaries.
