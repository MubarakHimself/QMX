# QMX - Epic Breakdown

## Overview

This document provides the epic and story breakdown for the **QMX agentic
system (QMA)** increment — the daemon, the QMA SDK (QuantMind Agents) and the
wire contract — decomposing the ratified QMA corpus (`docs/components/qma-*`,
CT-40..CT-51, ADR-0020, SCN-0013/0014, the QMA registry rows and
FEAT-0040..FEAT-0046) and the QMA architecture spine (AD-1..AD-29, FINAL
2026-08-29) into implementable stories for the factory lanes.

The Phase-1 epics file (`epics.md`, Epics 1–23, FR-001..FR-050) stays
untouched and is not superseded: this is a separate increment with its own
requirement ladder. **Epic numbering starts at Epic 40**, a reserved block so
QMA epics never collide with Phase-1's 1–23 or with the later trading-node
epics.

Requirement prefixes carry the Q marker because these requirements derive from
the **ratified docs corpus and the QMA spine, not from PRD §5**: the PRD names
QMA as a phase on its own track and carries no V1 FRs for it (PRD §2, §6).
Rules carried forward from the Phase-1 file: each FR's cited artifact is the
epic boundary and the source of its acceptance criteria; FR granularity is
deliberately coarser than epic granularity — never size a lane by counting FRs.

Ratification fixes the architecture only. Nothing in this document grants
implementation, credential, order, promotion, live-money or destructive
authority; that arrives only through the factory pipeline (ADR-0020; DEC-0329).

## Requirements Inventory

### Functional Requirements

**A. qma-core definitions (FEAT-0040)**

- FR-Q01: The QMA packages are exactly `qma-core` (definitions only, depends only on `qmf-core`), `qma-daemon` (the only process that runs anything and the sole writer) and `qma-wire` (the only cross-boundary contract package), with `qma-ui-contract` present only as a deferred stub; the Python namespace is `qma.*` and no blanket `qmx.` prefix exists anywhere. (qma-core.md §Identity; AD-1; ADR-0020)
- FR-Q02: `qma-core` defines the seven runtime ports — MemoryProvider, ModelDeployment, ExecutionEnvironment, KnowledgeSource, ToolAdapter, ComputeProvider, ContextCompiler — each declaring a cardinality, every singleton declaring an explicit scope key (MemoryProvider per `desk`, KnowledgeSource per `source_id`, ExecutionEnvironment per `kind`, ComputeProvider per `kind`, ContextCompiler per daemon as a replaceable default binding) and every multi point keyed by its fully-qualified `<plugin_id>:<local_id>`; the eight multi points are `tool`, `tool_adapter`, `hook`, `skill`, `graph_template`, `model_deployment`, `toolset`, `worker_template`; there is no `ui_view` point and a contribution point with no `qma-wire` schema may not be registered. (CT-42; AD-1)
- FR-Q03: `qma-core` defines the plugin contribution surface in a `plugins/` package beside `ports/` — `PluginManifest`, the `PluginContext` protocol carrying the cardinality-typed registration methods that each return a disposer, `HookEvent`, `HookResult`, the closed handle-kind vocabulary and the `credential_ref` string type — which the daemon implements, so a plugin imports its contribution types from `qma-core` and never from `qma-daemon`. (CT-42; AD-1)
- FR-Q04: `qma-core` mints no parallel base for anything `qmf-core` already defines: refusals are variants of the `qmf-core` typed-refusal base, ids and `correlation_id` are `qmf-core` types, `fp1` is imported and never re-derived, money and time follow the parent's exact types, and content addressing has exactly one construction — `fp1` over canonical JSON, with a tree digest as `fp1` over a canonical manifest of per-file `fp1` values. (CT-04, CT-05; AD-3)
- FR-Q05: Every QMA refusal variant is defined once in `qma-core` and returned (never raised) at a public boundary: `NoMemoryProvider`, `NoEnvironment`, `SlugUnavailable`, `CursorScopeMismatch`, `NoEligibleReviewer`, `NoEligibleDeployment`, `NonLoopbackProxy`, `UnauthenticatedProxy`, `ProhibitedMoneyPathTool`, `UnknownHostRequest`, `ProvenanceShapeMismatch`, `StaleSnapshot`, `OperatorPrincipalRequired`, `CredentialOutOfScope`, plus the store-version refusal naming the store and both schema versions. (qma-core.md §QMA refusal variants; CT-04; AD-3)
- FR-Q06: The ontology chain is Desk → Role → Quant → Agent → Subagent with Session as the run container and Worker as an addressable execution slot that is not an ontology object; the work vocabulary is Goal → Mission → Task; `ActorId` is `quant:<desk_slug>/<quant_slug>` over the five fixed `desk_slug` values `research`, `trading`, `dev`, `analysis`, `pm`, minted only by `desk.create` and `quant.create` from an `operator` principal, opaque to every consumer, never reused, tombstoned on retirement, and refused with `SlugUnavailable` on any case-folding collision; Profile is presentation only and never daemon state. (qma-core.md §Ontology; AD-7)
- FR-Q07: `qma-core` enumerates, default-deny, the permitted read-and-calculate surfaces of the `qma-daemon → qmf-registry` and `qma-daemon → qmf-risk` edges — value types, typed refusals and pure calculation surfaces, plus the single write of a content-addressed dev-zone candidate artifact — so a surface not listed is not callable; QMA constructs, writes, amends or deletes no binding, Book, BMS, seat, control-action, exit, protection, priority-rank or promotion record, calls no zone-transition surface, and `qmf-venue` is importable by no QMA package, worker or plugin. (AD-2; SCN-0014 Branch B; ADR-0020)
- FR-Q08: Every closed-and-addable vocabulary is declared exhaustively in `qma-core` and extended only in the AD that owns it: the 23 hook verbs plus the two phase-less controls, the six `HookResult` decisions, the six handle kinds, the seven `JobHandle` states, the eight Task and Mission states, the seven `MessageKind` values, the five `DeliveryState` values, the four `ModelClass` values, the four routing policies, the two principal classes, the seven memory `validation_state` values, the ten node kinds, the six ExecutionEnvironment kinds and two `network` values, the nine RefinementProposal edit kinds, the eight variable scopes, the `host_request` verb set, and the three closed verbs admit / apply / promote. (qma-core.md §Closed vocabularies; AD-1, AD-10, AD-12..AD-26)
- FR-Q09: `qma-core` declares the six-rung capability ladder and the act-level money-path deny-list constants beside it as code — not settings, not a plugin contribution, not a UI-editable variable — for the daemon to apply at registration. (AD-16; DEC-0315; SCN-0014)
- FR-Q10: The three closed verbs name three distinct acts and are never interchanged: a memory candidate is **admitted**, a RefinementProposal is **applied** out of the staging store, and only a registered artifact is **promoted** into the live zone by a human outside QMA; `promote` and `promotion` never appear for memory or refinement. (AD-18, AD-22, AD-25; DEC-0345)

**B. qma-wire (FEAT-0041)**

- FR-Q11: Every wire message carries the wire envelope `v`, `type`, `id`, `producer_id`, `correlation_id`, `scope_path`, an optional `seq` and `payload`, with JSON canonical per `fp1`; `scope_path` is an ordered array of `kind` plus `id` segments in the fixed order desk, quant, mission, task, session, agent, subagent with every existing ancestor present and prefix-matching filters; `seq` is always the per-scope projection index of the scope named last, and `journal_seq` never appears on the wire and is opaque to clients. (CT-40; AD-5)
- FR-Q12: The wire carries exactly three message families — commands that mutate and are acked immediately with side effects settling asynchronously, queries that read durable state over HTTP GET, and a durable event stream — under which snapshots are authoritative, progress events explicitly are not, closing a client never stops an agent, and an overnight agent need not know a client exists. (CT-40; AD-5; SCN-0013)
- FR-Q13: Transport is JSON-RPC 2.0 over WebSocket for commands and events with HTTP GET for queries, opened by an MCP-style `initialize` handshake that negotiates a semver `protocolVersion` plus capabilities and assigns the connection its `producer_id`, and every command, query and event family is described by JSON Schema. (CT-40; AD-5; stack.md §QMA application stack)
- FR-Q14: `qma-wire` is the sole compatibility authority: evolution is additive-only within a major, unknown types and fields are ignored by older clients, and a deprecation lives `registry:wire.deprecation_minors` minors before it drops. (CT-40; AD-5)
- FR-Q15: `wire.attach(scope, since_seq)` and `wire.detach` are client state only — attachment never changes an actor's identity and never stops a run; session replay is `wire.attach(since_seq=0)`, read-only over that scope's durable stream; a cursor is valid only for the scope that issued it and a cross-scope cursor is refused with `CursorScopeMismatch`, never silently re-based. (CT-40; AD-5)
- FR-Q16: Every wire command is idempotent on the pair `producer_id` plus `id` behind a dedup cursor of window `registry:wire.dedup_window`; `correlation_id` has exactly three minting origins (an originating operator command, a scheduled trigger, a daemon-internal lifecycle act) and is copied verbatim downstream, never regenerated, derived or truncated; a record without one is refused at the gate except an evidence append, which is recorded under a daemon-minted lifecycle id annotated `correlation_missing`. (CT-40; AD-5; L39)
- FR-Q17: The daemon binds loopback by default; any non-loopback bind requires TLS (`wss://` plus HTTPS for queries) **and** an explicit recorded operator configuration; every client authenticates with a Credential-Broker-resolved credential before protocol bytes; an unauthenticated bind or a plaintext non-loopback bind is a hard startup refusal, never a warning. (CT-40; AD-5, AD-24)
- FR-Q18: A remote worker or deployed Quant dials **out** to its daemon and the daemon never dials in, so the daemon's own listener is the single inbound port; a remote or partitioned worker holds a durable, ordered, fsynced local outbox bounded by `registry:wire.remote_outbox_depth` and `registry:wire.remote_spool_bytes` that replays in order on reconnect against the daemon's dedup pair, blocks the dispatch of new work rather than discarding a pending evidence append, discards telemetry before evidence, and marks its Task's ledger `unknown_tail` at the last acked `id` when the environment is lost. (CT-40; AD-5, AD-6)
- FR-Q19: The `host_request` bridge is a `qma-wire` message family and never a second channel: every host call the RLM kernel makes is a wire command or query issued under the Task's `scope_path` and `correlation_id`, its verb set is closed-and-addable, every verb maps to exactly one daemon-owned primitive and runs that primitive's `before_*` hook, an unmapped verb returns `UnknownHostRequest`, and an async spawn returns a `JobHandle` under the `registry:rlm.depth_cap` depth cap. (CT-40; AD-14)
- FR-Q20: Every authenticated connection carries exactly one principal class, `operator` or `machine`, recorded verbatim on every command, journal entry and ledger entry; the closed human-gate command list — admission approval, forward-only migration confirmation, UNKNOWN resolution, every retention trim outside the two daemon-job trims, plugin install/enable/reload, `desk.create` and `quant.create`, a `role.base` write via `role.set_base`, `model_family` assignment, `tool_adapter` writes, a restore of the live store, a Routine catch-up, reading or answering an `approval_request` in the operator approval queue, a `desk.moved` change, a Quant record write including its `WakePolicy`, a Routine record write, an `ExecutionEnvironment` declaration write, a Mission `approval_route` write, a `variable.set` on a `registry`-homed variable, and a `human_gate` answer — is accepted only from an `operator` principal and refused from a `machine` principal with `OperatorPrincipalRequired`. (CT-40; AD-24)
- FR-Q21: The wire vocabulary is the packet's 26-noun seed as a closed-and-addable registry — 9 commands, 7 queries and 10 `noun.verb` events — with new families added only in `qma-wire`; wire events are `noun.verb` while hook events are `before_<verb>` / `after_<verb>` and are not wire families. (CT-40; qma-wire.md §The 26-noun seed vocabulary; AD-5)

**C. qma-daemon substrate (FEAT-0042)**

- FR-Q22: The daemon is a single Python 3.14 asyncio process — the only process that runs anything and the sole writer of the event journal, the SQLite store and the artifact store — persisting JSONL append journals plus SQLite in WAL mode behind `qmf-data` sinks with DuckDB holding rebuildable fold views only; it opens SQLite on exactly one connection in one thread with every checkpoint on that connection, asserts `sqlite3.sqlite_version` at startup as evidence, and a read-only fold process may open those files read-only on the daemon's host and never checkpoints. (CT-13; AD-4, AD-6)
- FR-Q23: A single append-only journal with a global monotonic `journal_seq` is the only durable append target for daemon-owned events and the single total order in the system; the store list is closed — journal-derived projections (per-scope event streams, mailboxes and delivery state, the operator approval queue, Task Graph state, Session and Agent records, desk ledger views, the ledger quarantine stream, and the sixteen-member definition store) plus five declared independent stores (the three ledgers, the artifact store, the telemetry store, the staging store, and an admitted MemoryProvider's own store) — and a store not on that list may not be created. (qma-daemon.md §One journal, one writer, one clock; AD-6, AD-8)
- FR-Q24: Every append to a declared evidence store also emits a journal event naming the store and carrying the record's `fp1`, with the telemetry store the one exemption; the announcement's `journal_seq` is the ordering key in every cross-store fold and equal instants are disposed by ascending `journal_seq`, never by timestamp. (AD-6, AD-23)
- FR-Q25: Every durable record carries `occurred_at` and `recorded_at` as int64 UTC nanoseconds from `qmf-core`'s clock plus its announcement `journal_seq` where the announcement law binds; the v1 folds are exactly the enumerated set and each declares its fold contract (stream, ordering key, knowledge-time bound, equal-instant disposition), a new fold being a spine amendment; no component reads host local time, no worker timestamps its own evidence, every wall-clock policy carries an explicit IANA zone resolved at evaluation time, and every duration policy is a span from a recorded UTC instant. (AD-6)
- FR-Q26: Ownership and lifetime are fixed across the eight store classes — journal, ledger, memory, knowledge, artifacts, context, telemetry, staging — with one named writer, one crossing rule and one retention rule each; the definition store takes agent edits only as RefinementProposals, with exactly one closed exception: a mission-scoped, template-validated observe-or-deny hook registered through `before_hook_register` and disposed with its Mission. (AD-8, AD-11, AD-22)
- FR-Q27: The Task Graph is deterministic persisted daemon state and the only place work state lives; a Task is transcript-independent, carrying intent, inputs, refs, acceptance criteria and its Task Ledger; a Mission is the executable organizational contract owned by exactly one Quant with an optional `approval_route` (an `ActorId` or the reserved `operator` route, refused at compile time if it names a non-existent Quant); the Mission Compiler is deterministic daemon code that turns a Goal plus an optional Graph Template into a Mission record and its initial Task Graph, emitting a decomposition Task whose Agent acts as Mission Director; a deterministic scheduler and dispatcher decide where, when, who and dependencies and grant the `dispatch_lease` and `environment_lease`. (AD-12; SCN-0013)
- FR-Q28: Task and Mission state is the closed vocabulary `pending`, `ready`, `running`, `blocked`, `unknown`, `done`, `failed`, `cancelled` with terminal states exactly `done`, `failed`, `cancelled`; the daemon refuses any proposed terminal transition of a dispatched Task not evidenced by a terminal `JobHandle`, a never-dispatched Task may reach only `cancelled`, a Mission's terminal state is computed from its Tasks, a Task whose handle is `unknown` may enter only `unknown` and holds both leases until an explicit recorded resolution, and an LLM may propose a transition but can never author a terminal outcome. (AD-12; L35)
- FR-Q29: Three control primitives stand — Graph Template (authored, plugin-contributed, versioned, stateless), Loop (a node kind whose `stopping_condition`, `budget` and `escalation` are runtime-owned) and Skill (Skill ≠ Loop) — over the ten node kinds of which only `task`, `agent` and `loop` emit Tasks; a `loop` node emits exactly one Task per iteration with deterministic Task ids from task-graph id, node id, iteration and `retry_index`; back-edges are rejected at registration; a template is never mutated by a run; there is no Mission Template registry in v1 and `qma-daemon` ships no `graph_template` of its own. (AD-13; qma-daemon.md §Control primitives and node kinds)
- FR-Q30: Hooks are the single enforcement and control surface: the closed-and-addable v1 registry is a `before_` and an `after_` event for each of the twenty-three daemon-owned verbs plus exactly the two phase-less blocking controls `agent_stop` and `review_required`; every new daemon-owned primitive ships both a `before_<verb>` gate and an `after_<verb>` event; and an agent-reachable write into any daemon-owned store passes a `before_*` hook without exception. (CT-41; AD-10; DEC-0339)
- FR-Q31: The phase law governs what each event may return — only `before_*` events and the two controls may return `deny`, `ask` or `defer`; `block_stop` is legal only on the two controls; `allow` rides `updated_input` on `before_tool` and `updated_output` on `after_tool` only; `injected_context` is `before_*` only and reaches the Context Compiler, never the ledger; `ledger_entry` and `verifier_ref` are `before_task_complete` and `review_required` only — with the six decisions resolving under the total precedence `block_stop > deny > defer > ask > allow > observe`, parallel hooks most-restrictive-wins, and any illegal decision or field refused **at registration**. (CT-41; AD-10)
- FR-Q32: Hooks fail closed — a timeout resolves to `deny` with reason `hook_timeout` plus a telemetry record — with exactly three carve-outs: `before_ledger_append` is a validating gate whose timeout resolves to `allow` (entry recorded and annotated) and whose explicit `deny` writes the entry to the quarantine stream with its reason and never discards it; an `agent_stop` timeout resolves to `observe`; and every `after_*` timeout resolves to `observe`. No permission policy, precedence resolution or permissive mode may produce a `deny` on a well-formed evidence append from the holder of the relevant lease. (CT-41; AD-10; L39)
- FR-Q33: `ask` suspends the invocation and emits exactly one `approval_request` into the Mission's `approval_route` target or the owning Quant's mailbox, carrying `registry:mission.ask_timeout` and an `on_timeout` of `deny` or `escalate`; `escalate` re-emits once and restarts the timeout once, a second expiry resolving to `deny` with reason `ask_escalation_exhausted`; an `autonomous` session resolves `ask` to `deny` with reason `no_interactive_authority` unless the route's final hop is the reserved `operator` value; `defer` parks the work durably, releases the `environment_lease`, retains the `dispatch_lease` and re-runs the full hook chain on resume; an unresolved `ask` or `defer` never holds an `environment_lease`. (CT-41, CT-48; AD-10, AD-12)
- FR-Q34: A hook's source (desk, role, mission or plugin) bounds the events it can ever receive, the bound is applied before the matcher, and a registration whose matcher could resolve outside its bound is refused at registration; every hook is a deterministic Python callable or subprocess with no prompt-type and no agent-type handlers; `before_task_complete` and `review_required` are required gates running a deterministic verifier script rather than an LLM judging itself, with ReviewPolicy enforcing `author_family != reviewer_family` against the optional `model_family` and returning `NoEligibleReviewer` when none qualifies. (CT-41; AD-10, AD-15)
- FR-Q35: An Agent may author a hook only from an approved template, only scoped to its Mission and only as an observe-or-deny hook, under six mechanical constraints: template schema-validated at registration; permission set the intersection with the Mission's own and refused (never silently narrowed) if it names a permission the Mission lacks; a registration record exposed through a named `qma-wire` query and folded under the Mission's scope; a journal entry carrying the `correlation_id`, the registration itself passing `before_hook_register`; the disposer pushed onto the Mission's exit stack; and no privilege escalation — it may register nothing, may not raise its source above `mission`, and never becomes a durable hook except through the admission gate. (CT-41; AD-11)
- FR-Q36: Every number any QMA subsystem mints is a row in a machine-readable variable registry shipped in v1 declaring name, owning subsystem, scope (of the eight closed values), type, units, default, `ui-editable` or `uneditable`, and a `home` of either `registry` or a named owning record type; a `registry`-homed value is set only by an `operator`-principal `variable.set` recording a `variable.set` journal event, a record-homed value only by that record's own operator-principal write command, and a `variable.set` naming an `uneditable` or record-homed variable is refused; there is no `variable` edit kind, so no agent, hook, Role or Mission may ever set one. (docs/registry/variables.yaml; AD-26; L38)
- FR-Q37: Journal, SQLite, ledger, task-graph, mailbox, staging and artifact-store migrations run the parent's five steps verbatim — preflight → backup first → dry-run → migrate → verify — with a documented restore path and never an in-place mutation of the only copy; the journal and SQLite store each stamp a `store_schema_version` and the daemon refuses to open an unknown version, never reading a newer store optimistically and never silently upgrading one; backup covers the seven daemon-owned durable stores as nightly encrypted versioned off-machine copies, a sample-restore test and a full-restore rehearsal each run on their registered cadence into an isolated scratch location recording verified results as evidence, and a restore of the live store is a recorded `operator`-principal act, never a background job. (AD-27; L18; qma-daemon.md §Daemon store lifecycle)

**D. Model proxy, Tool Registry, permissions and the reachability barrier (FEAT-0043 — the first milestone lands here)**

- FR-Q38: Every model call resolves through the deterministic chain ModelClass → Deployment → Credential Broker, never an LLM: `ModelClass` has exactly the four values `REASONING_HIGH`, `WORKHORSE_GENERAL`, `CODING_HIGH`, `FAST_CHEAP`; selection is two-stage and never crosses a class boundary (the class selects the pool, then `needs` flags plus `min_context_tokens` are the sole eligibility filter); an empty filtered pool returns `NoEligibleDeployment` naming the class and the unmet constraint; the router load-balances under `failover`, `weighted_round_robin`, `quota_lowest` or `fill_first` and returns `ModelCapabilities` to the Context Compiler; the harness picks the class and an agent never names a vendor. (CT-45; AD-15)
- FR-Q39: Every Deployment record carries an optional, operator-assigned `model_family` — unset at registration, never defaulted and never synthesized, independent of `ModelClass` — assigned only by an `operator`-principal command; a plugin manifest that declares one is refused at load naming the plugin id and the field; a deployment whose family is unassigned stays routable but ineligible for every ReviewPolicy comparison. (CT-45; AD-15)
- FR-Q40: OpenCodex is the first `ModelDeployment` implementation, sitting behind the Deployment contract and deliberately not behind the Credential Broker; a local-proxy Deployment carries `auth_mode: none` so no QMA-resolved secret value crosses into its process and its own provider credentials stay outside QMA's namespace; the daemon permits a proxy Deployment only when it binds loopback on the daemon's host, verified at registration, refusing `NonLoopbackProxy` otherwise and `UnauthenticatedProxy` when `registry:proxy.allow_unauthenticated_loopback` is false; at every startup it records an evidence entry naming each registered proxy Deployment and that setting; QMA never pools accounts and records the true deployment honestly on every routing decision. (CT-45; AD-15; DEC-0344; SCN-0013)
- FR-Q41: One Tool Registry spans native, CLI, plugin, MCP-adapter, browser, computer-use and backtest tools with everything resolving through it — MCP is an adapter inside the registry configured per desk and role by `tool_adapter` records whose desk-and-role binding is written only by an `operator`-principal command; every entry carries a `check_fn` availability preflight excluding an unrunnable tool before its schema reaches the model; toolsets are versioned definition-store records listing fully-qualified tool ids; a Role grants a toolset, a Mission narrows and never widens it, and a Subagent inherits no more than its parent and is blocked from delegation and memory-write tools at the leaf; the capability ladder has six rungs and the lowest capable one wins. (qma-daemon.md §Tool Registry; AD-16; P-10)
- FR-Q42: There is no execution tool at any account role, "paper only" included, and the prohibition is an enumerated act-level deny-list — submit/amend/cancel/replace an order; open/close/reduce/hedge a position; set or amend protection; size, re-size or mint a sizing decision; create/amend/activate/stand down/delete a bot-to-book binding; set a Book mode, seat state, Book or BMS parameter, priority rank or capital floor; arm/disarm/change a kill switch or node control action; transition any registry artifact between zones — refused at registration with `ProhibitedMoneyPathTool` naming the plugin id, the tool id and the matched act, evaluated before `check_fn`, applied to every entry regardless of kind, refusing an MCP server advertising a prohibited tool **whole**, and liftable by no `check_fn`, permission policy, Role, Mission, hook, toolset or `tool_adapter` change because the deny-list is code. (SCN-0014; AD-16; DEC-0341; L36)
- FR-Q43: The effective capability set is computed once by the daemon at Agent spawn as an ordered narrowing — `role.base` the ceiling, narrowed by `role.overlay`, then Mission, then parent — where every step after `role.base` may only remove; an appended skill is knowledge and never a capability grant; an overlay entry naming a tool or toolset outside `role.base`'s grant is refused at application rather than silently dropped; the result is recorded verbatim on the Agent record and never recomputed for a running Agent. (AD-16, AD-22)

**F. Ledgers, Agent Bus, scheduler, memory, knowledge, admission gate and telemetry (FEAT-0045)**

- FR-Q57: The Task Ledger is owned by the Task — one per Task for its whole life across every Agent that ever holds it, persisted in the daemon store through the wire so it survives the worker — with append rights following a single `dispatch_lease`; every entry carries `attempt_no`, `authored_by` (an agent ref plus the owning Quant's `ActorId`, or `daemon`) and the model deployment used; a change of the Agent holding the lease is a daemon-authored `reassigned` entry incrementing `attempt_no`, while a resume from `defer` retains the lease, writes no `reassigned` entry and leaves `attempt_no` unchanged. - FR-Q58: `before_ledger_append` is a validating gate that refuses only a schema-invalid entry or one authored outside the relevant lease, with exactly two exempt authors (the daemon for `reassigned` and `unknown_tail`, and a `ledger_entry` returned by `before_task_complete` or `review_required` recorded with `authored_by: daemon` plus the returning hook's registry id), both still schema-validated; a task-completion transition requires a structured append (what was done, what changed, evidence and artifact refs, unresolved issues, next recommendation) or **the completion** is refused while the entry is still written and never discarded. (CT-51; AD-9; L39)
- FR-Q59: The Quant Ledger is a desk lead Quant's own work ledger with a declared entry schema, appended only through `before_ledger_append` by an Agent of that Quant holding the `quant_ledger_lease` which the daemon grants to at most one Agent at a time, opened only while the Quant carries its desk's lead flag and retained if the flag moves; the Experiment Ledger is one per Experiment appended by the Agent holding the registering Task's `dispatch_lease`; and Research, Trading, Development, Analysis and PM ledgers are read-time **views** over those three stores with a declared fold contract, never stores. - FR-Q62: A Routine is a durable, Quant-owned scheduled trigger carrying an id, the owning `ActorId`, a cron expression or interval with an explicit IANA zone, the Goal it supplies to the Mission Compiler, the fully-qualified `graph_template` id the Compiler expands, an enable flag and a max-concurrent cap — declarative daemon state, never agent-authored, UI-editable; firing is deterministic and never an LLM decision, minting a fresh `correlation_id`, firing `before_routine_fire` and `after_routine_fire`, and instantiating with no authority an operator command lacks as a `machine` principal that can answer no human gate; missed fires while the daemon is down are recorded, not replayed, and catch-up is an explicit operator action. (CT-49; AD-29)
- FR-Q63: Unattended continuation is a v1 obligation: a Task is not complete until the deterministic verifier passes, and `agent_stop` returning `block_stop` returns the Agent to the next ready Task in its Mission's Task Graph rather than ending the run; max consecutive continuations, the budget ceiling and the escalation target are registered configurables, and an Agent that exhausts its budget escalates to its Quant's mailbox and stops, never inventing work to fill the remainder. (CT-49; AD-29)
- FR-Q64: QMA builds no memory engine in-house: memory enters through the `MemoryProvider` port (one binding per desk) with `propose`, `admit`, `recall` (token-budgeted, not result-count), `get`, `list`, `history`, `supersede`, `invalidate`, `expire`, `scopes`, `reflect` optional and off, and **no** `promote` operation; a MemoryCandidate carries provenance, supporting artifacts, `admission_confidence`, scope, proposer, occurrence time and supersession over the seven `validation_state` values; `admission_confidence` is a scalar the daemon's admission gate computes deterministically and a `propose` call carrying it is refused; until a provider is bound `recall` returns `NoMemoryProvider` and candidates stage as RefinementProposals carrying exactly one `memory` edit; once bound, admission is the deterministic gate alone through `before_memory_write`; and the no-database-server rule binds QMA's own stores and never a provider's internal storage behind a QMA-owned port. (CT-43; AD-18; DEC-0342)

(CT-44; AD-19; DEC-0343)

(AD-23; AD-8; qma-daemon.md §Telemetry)

**G. Plugin loader and the five desk plugin packs (FEAT-0046)**

### Epic 46: A Quant that works while nobody is watching — ledgers, mailboxes, Routines and unattended continuation (Wave 7, H)
After this epic a Quant keeps working overnight and leaves an account of it. The Task Ledger belongs to the Task for its whole life across every Agent that ever holds it, appended only by the holder of the `dispatch_lease` through a validating gate that refuses a schema-invalid entry or one authored outside the relevant lease and quarantines rather than discards, with reassignment a daemon-authored entry and a completion transition refused unless its structured append is written; a desk lead Quant keeps its own Quant Ledger under the `quant_ledger_lease`, every Experiment its Experiment Ledger, and the five desk ledgers are read-time views with declared fold contracts and never stores. Each Quant owns one durable Mailbox in the daemon's own store with at-least-once delivery, idempotent dedup, a per-actor ack cursor and dead-lettering, `approval_request` the single human-approval channel every gate raises, and a `WakePolicy` whose quiet hours suppress wakes only — never delivery, never a Routine firing, never an approval reply. A Routine is a durable Quant-owned scheduled trigger firing deterministically with a fresh `correlation_id` and no authority an operator command lacks, and unattended continuation is an obligation: a Task is not complete until its deterministic verifier passes, `agent_stop` returning `block_stop` returns the Agent to the next ready Task in its Mission's Task Graph, and an Agent that exhausts its registered budget escalates to its Quant's mailbox and stops rather than inventing work. ### Epic 47: What a Quant knows and how it is allowed to change — memory, knowledge, the staging store and telemetry (Wave 7, M)
After this epic a Quant can learn without anything agent-produced becoming runtime state by itself. ### Epic 48: Five desks, five plugin packs — the reversible extension surface (Wave 8, M)
After this epic the system extends without being re-opened. A `PluginManifest` declares id, version, supported `qma_api` range, desk, dependencies, contributions, permissions, entrypoint, migrations and rollback mode; activation registers every contribution through a scoped context honouring the declared cardinality, each registration returning a disposer pushed onto a per-plugin exit stack so unload closes the scope LIFO and every contribution disappears together, with reload an explicit command and no file watcher. Data is the half LIFO cannot undo, so every migration declares a `down` or the manifest declares `rollback: forward_only`, migrations run the five-step order inside a daemon-held transaction preceded by a recorded journal checkpoint, and a forward-only upgrade takes a recorded `operator` confirmation. A failed load fails that command with a typed refusal, disposes that plugin's scope and leaves the running daemon, every `dispatch_lease` and `environment_lease` it holds and every running Task untouched. The five desk packs — `research-corpus`, `analysis-backtest`, `dev-factory`, `trading-readonly`, `pm-coordination` — then contribute tools, tool adapters, hooks, skills, Graph Templates, model deployments, toolsets, worker templates and singleton port bindings through the same core-defined surface, and face the act-level deny-list, the reachability boundary and the effective capability set like any other contribution.
