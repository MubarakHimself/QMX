# Focused adversarial recheck — AD-23..AD-31 and CONTRACTS

Scope was limited to the requested packet files. OD-01 remains closed; QMA AD-17 JobHandle vocabulary is treated as parent law. Findings are concrete desk-fix blockers, not approval.

## Findings

| ID | Citation | Counterexample / gap | Required desk fix |
|---|---|---|---|
| AD-C-01 | ARCHITECTURE-SPINE.md:238 | AD-25 says `unknown-blocked` is “terminal for this attempt until operator reconcile”, while the ordered machine immediately permits `unknown-blocked → predecessor-acked`. It is unclear whether reconciliation is a new attempt or a transition of the same record. | Define reconcile command/result and whether it creates a new epoch/attempt; make terminality and allowed transition graph consistent. |
| AD-C-02 | ARCHITECTURE-SPINE.md:238; CONTRACTS.md:333-353 | Fencing is keyed by `(account, venue, role)` but the deployment payload omits `role`; two roles can therefore serialize under an identity the persisted record cannot represent. | Add role to the deployment contract and uniqueness/fencing key; reject missing role. |
| AD-C-03 | CONTRACTS.md:299-313 | “Exactly one logical successor effect” is asserted, but no unique constraint/idempotency key is defined for `(task_graph, successor, eligibility_revision)` or for outbox rows. A crash after invoke-before-ack can create duplicate rows/effects. | Specify durable uniqueness and the receiver-side effect ledger keyed by logical invocation; define ack/retry atomicity. |
| AD-C-04 | ARCHITECTURE-SPINE.md:244; CONTRACTS.md:315-331 | Join state has no join input/output identity, edge/node identity, or revision. A retried/late partition from an older join can be accepted into a newer join with the same `partition_id`. | Bind join state to task graph/node/edge and join revision; reject stale partition reports. |
| AD-C-05 | ARCHITECTURE-SPINE.md:250; CONTRACTS.md:398-415 | Checkpoint manifest hashes/fences stores but has no checkpoint generation or per-store restore outcome. A restore can mix owners from different checkpoints while each hash is locally valid. | Add manifest generation, atomic membership/commit marker, and explicit per-owner outcome; quarantine mixed generations before QMA projection restore. |
| AD-C-06 | ARCHITECTURE-SPINE.md:256; CONTRACTS.md:251-274 | AD-28 names gap/duplicate/late events and loss evidence, but the subscription payload has no fields carrying gap ranges, duplicate/late disposition, heartbeat status, or loss evidence. Consumers cannot prove “no silent loss.” | Add typed gap/duplicate/late records, heartbeat/lease timestamps, and evidence reference to the contract. |
| AD-C-07 | ARCHITECTURE-SPINE.md:256; CONTRACTS.md:251-274 | Cutover is declared atomic at a watermark, but there is no producer acknowledgement/barrier or rule for a missing watermark event. Replay and live can overlap or leave a hole during provider restart. | Define barrier handshake, inclusive/exclusive watermark semantics, and refusal/recovery for missing or conflicting watermark. |
| AD-C-08 | ARCHITECTURE-SPINE.md:262; CONTRACTS.md:140-160 | CAS mutation and change-request both use revisions, but no command-id retention/uniqueness scope or expiry is specified. A reused `command_id` across sessions or after retention can be treated as `duplicate` with the wrong prior result. | Scope command IDs to product session and define durable retention/expiry plus collision refusal. |
| AD-C-09 | ARCHITECTURE-SPINE.md:262; CONTRACTS.md:140-160 | Change request includes `context_revision` and base hashes, but `request_hash` is not defined as a hash over canonical payload (nor does it bind patch ordering/app-instance version). Equivalent/reordered patches can produce different requests or tamper undetected. | Define canonical serialization and exact hash preimage, including target/app/version/patch and source context. |
| AD-C-10 | ARCHITECTURE-SPINE.md:268; CONTRACTS.md:276-293 | AD-2 requires pack `contributes` entries `{point, local_id}` that expand to ContributionHit; the manifest example uses opaque strings (`"tool:inspect"`, `"graph_template:daily-brief"`). Pin/invoke cannot deterministically derive the required qualified identity. | Replace manifest entries with the normative object shape and define expansion/validation before roster publication. |
| AD-C-11 | ARCHITECTURE-SPINE.md:268; CONTRACTS.md:276-293 | Lifecycle has `validated → enabled` but no explicit validation result/schema, migration transaction boundary, or uninstall state precondition. A failed migration can publish a new availability revision while old roster remains active. | Add validation/migration evidence and atomic state/availability-revision ordering; define uninstall dependency and in-flight pin behavior as transitions. |
| AD-C-12 | ARCHITECTURE-SPINE.md:232; CONTRACTS.md:38-59,118-138 | GrantRecord has `expires_at`/`revoked_at`, but InvocationEnvelope has no grant snapshot revision or mint-time validity evidence. Revocation/expiry racing an in-flight external call is therefore unspecified. | Define grant evaluation point, snapshot/revocation semantics, and result when grant expires/revokes during execution. |
| AD-C-13 | ARCHITECTURE-SPINE.md:226; CONTRACTS.md:355-392 | AD-23 requires ATC Command to bind AD-25 owner epoch and admission to check health/grants/paper readiness; AlternativeRunConfig example omits owner epoch and health/grant evidence and permits `venue_touching:false` with `paper_complete:false` without a typed admission result. | Add required owner epoch, grant/health attestations, and an explicit admission verdict with refusal reasons. |
| AD-C-14 | ARCHITECTURE-SPINE.md:274; CONTRACTS.md:162-227 | AD-31 requires coverage, schema/roles, freshness, provenance, entitlement, licensing, revision, and output completeness. The recipe example lacks explicit coverage, schema/roles, provenance object, freshness policy, and a concrete completeness enum; `completeness:"required"` is not an output completeness value. | Make the example schema-complete and distinguish required policy from observed output completeness (`complete|partial|missing|expired` or a defined recipe-specific enum). |
