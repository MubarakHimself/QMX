## In plain words

Jesse is a crypto backtesting/live-trading framework where you write one Python class per strategy and answer a handful of yes/no questions: *should I enter now? what do I buy, where's my stop, where's my take-profit?* You never write a backtest loop — the same class runs candle-by-candle whether it's replaying history or watching a live feed, so "does it work in backtest" and "does it work live" are answered by the same code path, not two separate implementations that can drift apart.

Under the hood, Jesse always simulates in one-minute steps and builds every larger timeframe (5m, 1h, 4h...) by aggregating those minutes forward in time, never backward — which is the honest, no-lookahead way to replay a market. It stores candles as plain numpy arrays in a growable in-memory buffer, not a database or a dataframe, so a multi-year backtest runs in seconds. Optimizing a strategy's parameters is a wrapper around Optuna (a standard hyperparameter search library) running many parallel backtests and scoring each one on a held-out test slice. Before you even bother backtesting a new entry idea, Jesse can run a statistical test asking "does this entry rule beat random entries on the same data?" and refuses to let an AI agent proceed past that question if the answer is no.

Most recently, Jesse's creator has built an MCP server — a way for an AI coding agent (like Claude) to drive the whole framework through a fixed set of tools (write strategy, run backtest, run Monte Carlo, check significance) instead of writing arbitrary code. That MCP layer ships with a written "agent constitution" (`agent_rules.md`) full of hard rules: never fabricate a result, never work around a broken tool by hand-editing config, never skip the mandatory Monte-Carlo / significance checks, always surface the dashboard link. This is close to the exact problem QMX is trying to solve for LLM-authored strategies, and it is worth studying line by line — not for the crypto-specific code, but for the shape of the constraints.

The one big caveat: this repo is Jesse's core — the actual live-exchange connectivity lives in a separate, not-included repo (`jesse-live`). What's here is backtest, optimize, paper-trading (`Sandbox`), and research tooling, all built assuming a crypto spot/futures exchange (funding rate, liquidation price, base/quote asset). Forex concepts (pips, lots, swap/rollover, a cTrader-shaped broker) do not exist anywhere in this codebase.

## How it is built

### Module map (as found, not aspirational)

| Area | Path | What it does |
|---|---|---|
| Strategy base class | `jesse/strategies/Strategy.py` (1874 lines) | The entire authoring surface: lifecycle hooks, order state (`buy`/`sell`/`stop_loss`/`take_profit`), position/account properties, chart hooks, ML feature capture, DNA/hyperparameter hooks. One large `ABC` subclassed by every user strategy. |
| Backtest engine | `jesse/modes/backtest_mode.py` (1523 lines) | The minute-by-minute simulation loop (`_step_simulator`) and a vectorized "skip empty time" fast path (`_skip_simulator`), candle aggregation, order fill simulation, liquidation checks, progress reporting. |
| Candle storage | `jesse/store/state_candles.py`, `jesse/libs/DynamicNumpyArray` | Per `exchange-symbol-timeframe` growable numpy buffer (`DynamicNumpyArray`), preallocated in `bucket_size` chunks; candles are 6-column float arrays `[timestamp, open, close, high, low, volume]`. No ORM, no DataFrame on the hot path. |
| Indicators | `jesse/indicators/*.py` (~170+ files) | One pure function per indicator, e.g. `sma(candles, period, source_type, sequential)`. `sequential=False` returns only the latest scalar via a dedicated fast Rust kernel (`sma_last_rust`), avoiding computing the full series just to read its last element; `sequential=True` returns the full array for charting. Typed with `@overload` trios so editors resolve the return type from the literal `sequential` value. |
| Performance layer | `jesse_rust` (external package, `jesse-rust==1.2.0` in `requirements.txt`) | SMA/candle-aggregation/jump-fix kernels are implemented in Rust and called from Python (`from jesse_rust import sma as sma_rust`, `candle_from_one_minutes`, `fix_jumped_candles`). Hot loops are hoisted out of Python entirely rather than "optimized in place". |
| Position & risk | `jesse/models/Position.py`, `jesse/utils.py` | `Position` is a plain stateful object with computed properties (`pnl`, `roi`, `liquidation_price`, `bankruptcy_price`) branching on live-vs-sim and spot-vs-futures. Sizing (`risk_to_qty`, `size_to_qty`, `kelly_criterion`) lives in `jesse/utils.py` as advisory helper functions the strategy calls itself — there is no separate mandatory sizing/risk gate the framework imposes. |
| Order lifecycle | `jesse/models/Order.py`, `jesse/services/broker.py`, `jesse/services/order_service.py` | `Broker` exposes `buy_at_market/buy_at/start_profit_at/reduce_position_at`; `Strategy._submit_buy_orders` picks MARKET vs LIMIT vs STOP purely from comparing the requested price to the current price — the user never names an order type. |
| Optimize mode | `jesse/modes/optimize_mode/Optimize.py`, `.../fitness.py` | Optuna for the search algorithm, Ray for parallel trial execution (`@ray.remote def ray_evaluate_trial`). `fitness.py` runs each trial's hyperparameters on a training slice, computes a normalized composite score (log-scaled trade count × normalized target ratio — Sharpe/Calmar/Sortino/Omega/Serenity/"smart" variants, selectable), rejects hp sets with ≤5 trades or a negative ratio, then separately reports (not gates on) testing-slice metrics. |
| Robustness modes | `jesse/modes/significance_test_mode/`, `jesse/modes/monte_carlo_mode/`, `jesse/candle_pipelines/*` | Two first-class product modes, not scripts: **Rule Significance Testing** (does this entry rule beat random entries on the same candles — returns a p-value) and **Monte Carlo** (re-run the strategy over N synthetic candle paths — moving-block bootstrap / Gaussian-noise / Gaussian-resampler pipelines — and separately over N reshuffled trade sequences). Both run via Ray for parallelism. |
| Agent/MCP layer | `jesse/mcp/` (server, tools, resources, `agent_rules.md`, `usage_limits.py`) | A native MCP server exposing typed tools (`create_strategy`, `run_backtest`, `run_monte_carlo`, `create_significance_test_draft`, `list_indicators`, `get_indicator_details`, `import_candles`, ...) plus markdown "resources" the agent is told to consult (`jesse://strategy`, `jesse://position_risk`, `jesse://backtest_management`, ...) and a written rules doc governing agent behavior (see Mental Models). |
| Project/dashboard shell | `jesse/controllers/*.py`, `jesse/routes/`, `jesse/models/*Session.py` | FastAPI controllers per concern (backtest, optimization, monte_carlo, significance_test, live, exchange, ai_model) backed by Peewee ORM models per "session" — the dashboard is a thin HTTP+websocket layer over the same engine functions a script or the MCP server would call directly (`jesse/research/backtest.py` exposes the equivalent programmatic entry point). |

### Event flow — the "one loop, two speeds" backtest engine

`backtest_mode._step_simulator` (`jesse/modes/backtest_mode.py:536`) is the reference loop:

1. For each simulated minute `i` in `range(length)`:
   - Advance `store.app.time`.
   - For each traded pair, append/generate that minute's 1m candle (`candle_service.add_candle`), applying a jumped-candle fix (`fix_jumped_candles_rust`) so a gapped exchange feed doesn't corrupt indicators.
   - Roll that 1m candle up into every larger configured timeframe the moment enough minutes have accumulated (`i_next % count == 0`), via `generate_candle_from_one_minutes` — never by looking ahead.
   - For every route whose timeframe just closed a bar, call `strategy._execute()` — this is the **only** place a strategy's logic runs.
   - Feed any pending MARKET orders through `execute_simulated_market_orders()`.
2. There is a second engine, `_skip_simulator` (fast/vectorized mode), which advances in `candles_step`-minute jumps (the GCD-like minimum meaningful step across all routes' timeframes) when no order needs sub-step resolution, and only refines to per-minute granularity around actual price touches. Both engines are required to produce **bit-identical** results — the code comments in `backtest_mode.py:597-671` are explicit about preserving that equivalence bar-for-bar when adding the numpy-buffer "prefill" optimization.
3. Inside `Strategy._execute()` (`jesse/strategies/Strategy.py:1308`): `before()` → `_check()` → `after()` → (`update_chart()` if not live) → clear per-bar caches → `self.index += 1`. `_check()` (`Strategy.py:1061`) is the actual state machine: cancel stale entries if `should_cancel_entry()`, update trailing/managed exits if a position is open, simulate any pending market fills, then — only if flat and not already trying to enter — evaluate `should_short()`/`should_long()` and dispatch to `_execute_short()`/`_execute_long()`, which call the user's `go_long`/`go_short`, validate `self.buy`/`self.stop_loss`/`self.take_profit`, run `filters()`, and only then submit orders through `Broker`.
4. Live trading (in the separate `jesse-live` repo, not present here) is documented as calling the exact same `Strategy._execute()`/`_check()` path, with `jh.is_live()` branches inside `_check` only for exchange-round-trip waits (`sleep`, WS-confirmation polling) — the strategy logic itself has no live/backtest fork.

### Key types

- `Strategy` (`jesse/strategies/Strategy.py`) — abstract base; user overrides `should_long`, `go_long`, optionally `should_short`/`go_short`, `filters`, `hyperparameters`, `dna`, `on_open_position`, `on_close_position`, `update_position`, `before`/`after`, `terminate`. Order intent is expressed only as `(qty, price)` tuples assigned to `self.buy`/`self.sell`/`self.stop_loss`/`self.take_profit` — order **type** (market/limit/stop) is inferred by the framework from price vs. current price, never chosen by the user.
- `Position` (`jesse/models/Position.py`) — computed-property object (`pnl`, `roi`, `liquidation_price`, `bankruptcy_price`, `type` ∈ {long, short, close}) that branches on `jh.is_live()` and `exchange_type` (spot vs futures) internally, so the strategy reads one consistent interface regardless of mode.
- `Order` (`jesse/models/Order.py`) — framework-owned; user never constructs one directly, only requests intent via the tuple attributes above.
- Candle array — a raw `np.ndarray` of shape `(N, 6)`; there is no `Candle` class on the hot path, just a documented column layout.
- `Route` (`jesse/models/Route.py`, `jesse/routes/__init__.py`) — the `(exchange, symbol, timeframe, strategy)` binding that both backtest and live read from the same `RouterClass`.

## Mental models worth borrowing

1. **One authored loop, replayed at two speeds, byte-identical.** *Where:* `backtest_mode._step_simulator` vs `_skip_simulator` (`jesse/modes/backtest_mode.py:536` and `:1048`), and the comment block at `:597-671` explaining exactly which invariants must hold for the fast path to stay bit-exact with the slow one. *Why it matters for QMF:* this is the concrete existence-proof for "no central backtest engine, backtest is just a replay" — Jesse runs a fast vectorized skip-mode for research iteration speed and a strict step mode for correctness, and they *test that both produce the same numbers*, rather than trusting the fast mode by assertion. *How QMF would implement it:* build `qmf.sim`'s driver the same way — a reference step-by-step replay as the source of truth, and an optional accelerated replay validated in CI against the reference on the same fixture data, never shipped without that equivalence test.

2. **Order type is inferred, never chosen.** *Where:* `Strategy._submit_buy_orders` (`Strategy.py:653`) — price ≈ current → MARKET, price beyond current → STOP, price behind current → LIMIT; codified again in `agent_rules.md`: "Never hand-pick market/limit/stop." *Why it matters for QMF:* this is a smaller, sharper version of QMX's own "Trigger never says quantity" rule — collapsing a whole class of order-type mistakes an LLM agent could make into something the type system/interpreter decides instead. *How QMF would implement it:* extend the existing `Signal` design so a Confluence's exit similarly never asks the agent to name an order type — only a target price and urgency; `qmf.broker` maps that to the concrete order the venue needs, exactly as Jesse's `Broker` does today.

3. **A mandatory statistical gate *before* a full strategy gets built, not after.** *Where:* `jesse/modes/significance_test_mode/`, and its usage contract in `jesse/mcp/agent_rules.md` (§"RULE SIGNIFICANCE TESTING") — p<0.05 proceed, 0.05–0.10 flag as inconclusive and ask, p>0.10 is a **HARD STOP**, and the rule fires automatically whenever an agent proposes a new entry rule, not only on request. *Why it matters for QMF:* this is the closest thing found anywhere in the sweep to `qmf.experiment`'s "refuse when the evidence is spent" idea, already shipped as a product feature with an enforced decision table an agent cannot silently skip. *How QMF would implement it:* wire an equivalent "beats a random-entry baseline on this split" check as a hard precondition inside `qmf.registry`'s promotion from `proposed → measured` — refuse to spend split budget on a confluence whose trigger hasn't cleared this bar, using the same three-tier verdict language (confirmed / borderline / hard stop) so a non-technical operator reads the same three words every time.

4. **Two distinct Monte Carlo questions, kept explicitly separate.** *Where:* `jesse/candle_pipelines/*` (moving-block bootstrap, Gaussian noise, Gaussian resampler) feeding `monte_carlo_mode`, documented in `agent_rules.md` (§"MONTE CARLO SIMULATION"). Candles-MC perturbs the *price path* and re-runs the full strategy (answers "is this overfit to this exact history?", compares `original` vs `median`/`best_5`/`worst_5`); trades-MC only reshuffles the *order* of already-realized trades (answers "how bad could the drawdown path have been?", and is explicitly documented as carrying zero information about overfitting since win rate/return are invariant to trade order). *Why it matters for QMF:* the sweep's overfitting research (`09`) treats robustness testing as one big grey area; Jesse shows a working operator-facing decomposition into two cheap, separately-interpretable checks, with the interpretation table (`original > best_5` → overfit; `original ≈ median` → good; `original < median` → conservative/good) written once and reused. *How QMF would implement it:* `qmf.overfit` should ship the same two-question split — a candle-perturbation Monte Carlo as the primary overfitting signal (feeding `qmf.experiment`'s refusal logic) and a trade-reorder Monte Carlo strictly scoped to drawdown-path risk for `qmf.bms`'s prop-firm ratchet checks — and the operator-facing verdict table should be this literal three-way (overfit / good / conservative), not a raw p-value.

5. **An explicit, versioned "agent constitution" shipped alongside the tool surface, not left to prompt engineering.** *Where:* `jesse/mcp/agent_rules.md` (used as the system prompt / rules doc for any agent driving Jesse via MCP) plus `jesse/mcp/usage_limits.py`'s daily credit meter with a documented **fail-open** policy ("if the plan cannot be determined... we ALLOW the run and log a warning — we never block a legit user because our own metering plumbing is down"). *Why it matters for QMF:* QMX's whole premise is LLM agents authoring strategies through a constrained surface; Jesse has already had to solve the exact problems that implies — agents fabricating results, agents working around a broken tool by editing config directly, agents asking "should I keep checking?" instead of just polling, agents skipping a mandatory validation step. Every one of those failure modes is named and closed with a specific, testable rule in the document. *How QMF would implement it:* write `qmf.spec`'s companion rules doc the same way — one markdown file, one rule per known failure mode, each traceable to an incident or an anticipated one, shipped as a first-class artifact next to the typed schemas rather than folded into a system prompt nobody versions.

6. **Fast-path scalar kernels are separate from the array kernels, not `array[-1]`.** *Where:* `jesse/indicators/sma.py` — `sequential=False` calls a dedicated `sma_last_rust` kernel that runs the same recurrence without allocating the full output array, rather than computing `sma(..., sequential=True)[-1]`. *Why it matters for QMF:* live trading and the step-mode backtest both need "what's the indicator's value right now" on every single bar; computing the full historical series every time to read one number is the kind of quadratic-in-disguise mistake that only shows up as "the VPS is slow" months later. *How QMF would implement it:* `qmf.indicators`' `Indicator` protocol should specify `peek()` (latest value) as a genuinely separate code path from `replay()` (full series) for any indicator where the two are asymptotically different to compute, not merely a documented convenience wrapper.

7. **Position is one object with mode-branching computed properties, not a type per exchange-mode.** *Where:* `jesse/models/Position.py` — `liquidation_price`, `pnl`, `leverage`, `mode` all branch internally on `jh.is_live()` / `exchange_type` / `mode` (cross vs isolated) so the strategy author reads `self.position.pnl` once and it means the right thing everywhere. *Why it matters for QMF:* QMX's own `InstrumentSpec` is already designed as "a nullable superset covering forex CFD and crypto perp" (per the synthesis doc) — Jesse's `Position` is a smaller, working instance of exactly that pattern: one object, several optional axes, computed rather than duplicated per axis combination. *How QMF would implement it:* keep `qmf.model.Position` as a single class with properties that branch on the instrument's declared axes (margined vs cash, live vs sim) rather than spawning `SpotPosition`/`FuturesPosition`/`ForexPosition` subclasses that would each need independent bugfixing.

## What to avoid

- **Sizing is advisory, not enforced — there is no mandatory risk gate.** `jesse/utils.py`'s `risk_to_qty`/`size_to_qty`/`kelly_criterion` are plain functions a strategy *may* call; nothing in `Strategy._execute_long`/`_execute_short` (`Strategy.py:611-722`) requires it, and `agent_rules.md` compensates for this gap entirely in prose ("Never use fixed quantities — use available sizing utilities") rather than in the type system. A strategy can still do `self.buy = 1000000, price` and the framework's only backstop is the exchange-level `InsufficientMargin` exception at fill time. This is the opposite of QMX's Ring 4 design (`qmf.book` sizes, `qmf.bms` can veto, the strategy is structurally incapable of naming a size). Copy Jesse's *ergonomics* (the sizing helper functions), not its *enforcement model* — QMX's `Signal` must stay quantity-less by construction, not by convention.
- **Crypto-shaped core, not a clean venue abstraction.** `Position.liquidation_price`, `funding_rate`, `mark_price`, `bankruptcy_price`, and `exchange_type ∈ {spot, futures}` are baked directly into the core `Position` model (`jesse/models/Position.py:216-252`), not pushed behind a swappable `VenueModel`. There is no pip/lot/swap/rollover concept anywhere in the codebase. Porting Jesse's core to forex-over-cTrader would mean editing these core files, not writing an adapter — confirming the synthesis doc's finding (`01`, `05`) that no existing framework has a cTrader-ready venue abstraction. QMX's `qmf.venue_model` split (venue-specific behaviour as data/config, not scattered `if exchange_type ==` branches in the domain model) is the right call and should not be weakened to match Jesse's shape.
- **Live trading is not in this repo at all.** `AGENTS.md` states plainly: "jesse-live depends on this — Changes here affect live trading" and lists `jesse-live` as a separate related repository. This clone contains only `jesse/exchanges/sandbox/Sandbox.py` (the backtest/paper-trading simulator) — no real exchange connectivity, no reconciliation logic, no rate-limit handling to study. Any claim about "how Jesse talks to a live exchange" cannot be verified from this codebase; treat it as an open gap, not a solved problem to copy from.
- **One 1874-line `Strategy` class carries order management, ML feature capture, six chart-hook variants, and DNA/hyperparameter plumbing together.** (`jesse/strategies/Strategy.py`.) It reads pleasantly for the author because every hook lives in one predictable place, but it is a single god-object from a maintainer's-eye view — a change to chart rendering sits in the same file and same review surface as a change to order validation. QMX's ringed module map (Level/Trigger/Confirmation/Exit as separate typed concepts, ML feature capture as its own concern) is a deliberate improvement on this; don't let "it should feel like Jesse to write" pull the *implementation* back into one file the way Jesse's is.
- **The optimizer's train/test split is real but shallow.** `fitness.py` (`jesse/modes/optimize_mode/fitness.py:23-110`) does run every candidate hyperparameter set on a held-out testing slice and reports its metrics — but the *fitness score* that drives the search is computed on the training slice only, and the testing-slice metrics are informational, not a second gate. There is no CSCV/PBO-style combinatorial purge, no `effective_n_trials` accounting, no split-budget ledger — the exact gap the synthesis doc's research on overfitting (`09`) already flagged as scarce and unbuilt anywhere in the sweep. Jesse's significance-test and Monte Carlo modes (mental models 3–4 above) partially compensate for this in practice, but QMF should not assume Optimize mode's own scoring is already overfitting-safe.
- **Infra footprint is heavier than a solo operator needs.** `requirements.txt` pulls in Postgres (`psycopg2-binary`), Redis (`redis`, `aioredis`), Ray, FastAPI/uvicorn/websockets, and Peewee — a real multi-process, pub/sub-driven service stack built for a hosted multi-user dashboard product, not a single VPS running one operator's strategies. QMX's two-lockfile plan (a lean trading lockfile vs. a heavier analysis lockfile, per the synthesis doc) is the right correction; Jesse's dependency list is a reason to keep that split, not a reason to relax it.
