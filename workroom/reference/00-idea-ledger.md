**How to read a row.** *Idea* is the one-line claim. *Source* is the repo and the file that proves it exists, with the study section that read it. *What we borrow* is the mental model — the shape, never the code, unless the licence column says otherwise. *Why it matters* is the QMX-specific consequence. *How QMF implements it* is the concrete landing spot in the module map. Rows are numbered 1–113 and grouped by QMF ring; a number is stable, so "ledger #57" is a citable thing. Negative lessons ("do not do this") are rows too — the borrow is the refusal.

## What the whole study concluded, in ten lines

1. Eight code studies covering roughly twenty-five repositories, plus two decision briefs. **Not one repo has a cTrader adapter, a prop-firm rule engine, or an honest market-structure library** — the three things QMX most needs are unbuilt everywhere, now confirmed for the fourth time.
2. The strongest architectural finding, confirmed four independent ways, is that **the backtest is a wiring of one kernel, never a second program**. Nautilus reduces the whole mechanism to a 155-line clock factory with no `if backtest:` anywhere in the kernel; lumibot, Jesse and rqalpha each ship their own version of it.
3. And it comes with a **third wiring nobody planned for**: live prices with simulated fills ("sandbox" / Paper mode), built from the same matching engine. That is a prop-firm challenge dry-run at zero risk, and it is nearly free.
4. The backtest itself is **small** — rqalpha's whole simulator is under 700 lines; QMF's honest path is ~1,500 lines across five modules. The kernel underneath it is the expensive part (13,000–19,000 lines plus a comparable volume of tests), and the **fill model is the whole ballgame**, with no reference implementation anywhere for retail forex.
5. The single strongest artifact found is Nautilus's **canonical result document** — a versioned, key-sorted, identity-normalised JSON projection of a run, BLAKE3-digested, that refuses non-canonical bytes and reports the *first differing field* between two runs. An agent can lie in a sentence; it cannot make the lie survive a re-run.
6. The cheapest integrity mechanism is older and simpler: zipline's `window_safe` shows a correctness property can **compose automatically and be refused at graph construction, before any data is loaded**. A run that never happens cannot be fabricated.
7. backtrader — dead since 2023 — supplies the best single idea in the classic engines: **warm-up is computed automatically up the tree and enforced by dispatching to a different method**, so a strategy is structurally incapable of trading on a half-warm indicator. An LLM composing five components will never get this right by hand.
8. Nautilus's most valuable paragraph for a prop-firm operator is about uncertainty: every failed order command is `NotSent`, `VenueRejected` or `Ambiguous`, and **an `Ambiguous` outcome may never emit a terminal event**. Converting a timeout into "rejected" is how an account ends up with a position the system believes does not exist.
9. Licences sort the field cleanly and unhelpfully: the engines that are legally clean and mature are built for the wrong asset class; the ones closest to QMX are copyleft-blocked, mid-rewrite, or non-commercial. **D1 still needs amending** — LGPL does not say what `research/00` A.1 claims it says.
10. Net effect on the plan: **nothing overturns the module map.** One decision needs amending (D1), one needs a ruling (stored vs derived bar resolutions), one must be fixed *before any code* (the fidelity taxonomy, because it enters every stored result key), and the rest of this file is the borrow list.

## Contradictions with the earlier web research

Four live disagreements with `research/00`–`research/10`, plus one tension inside the studies, plus two rev1 items now formally retired and two dangling citations to fix. Each names the file and the claim.

**C1 — The LGPL posture. `research/00-qmf-synthesis-module-map.md` line 211 (Decide-next A.1) is wrong.**
It states that assuming QMX may be sold *"rules out NautilusTrader (LGPL)"*, and line 214 repeats *"plus LGPL"* as a reason to build. `reference/01-kernel-verdict.md` §(b) and `reference/studies/nautilus-trader.md` §"Licence & maturity" both read the licence text directly: LGPL-3.0 permits linking from a proprietary, sellable application, and §0 explicitly treats *"Defining a subclass of a class defined by the Library"* as a mode of *using* an interface. The obligations attach to modifying and redistributing the library itself — and in Nautilus v2, "modifying" means forking Rust. **D1 needs amending** to: Apache-2.0 / MIT / BSD / NCSA freely; **LGPL permitted for unmodified, separately-installed dependencies with notice** (a normal `pip install` satisfies the relink requirement); AGPL, GPL, Commons Clause and non-OSI custom licences excluded. *Status: both verdicts now agree — rev1's note about `02` still calling Nautilus "blocked by D1" is resolved; `02` §6.2 rev2 now records the objection as timing and shape, not licence.*

**C2 — Whether coarser bars are stored or derived. `research/02-data-foundation.md` lines 301–302 plans to store them.**
It specifies *"Ticks: `symbol / year / month`"* and *"Bars M1 and coarser: `symbol / year` (or single-file for H1+)"* — multiple materialised resolutions. `reference/studies/jesse.md` §In-plain-words 2 and §Module map document a production system that persists **only** 1-minute candles and aggregates every larger timeframe forward through one Rust kernel shared by backtest and live, precisely so a 4h strategy is guaranteed to see the same 4h bars in both. Storing N resolutions creates N caches that can drift from each other and from live. **Still open, still needs a ruling:** store-and-verify, or derive-only with an optional materialised cache checked against the derivation in CI. This is ledger #11.

**C3 — The order of the overfitting machinery. `research/09-experimentation-search-overfitting.md` line 25 names the smallest recommended stack as Optuna + `arch` + QMF-owned code for the four closed-form numbers.**
Candle-perturbation Monte Carlo does not appear in that stack at all. `reference/studies/jesse.md` §MM4 documents it as a shipped product feature with an operator-readable percentile verdict requiring no closed-form derivation, and `reference/02-backtesting-verdict.md` §5.3 then makes it the mechanism for the decay bands *and* the primary overfitting signal. This is a sequencing disagreement rather than a substantive one — both end up inside `qmf.overfit` — but `research/09` does not contemplate shipping the cheap resampling check first, and the build order matters. See ledger #80.

**C4 — Silent parameter dropping. `reference/studies/platform-patterns.md` §MM2 recommends OpenBB's warn-and-drop; `research/00` line 159 requires refusal.**
The study lists `Query.filter_extra_params()` (`core/openbb_core/app/query.py:36`) as a mental model worth borrowing — an unsupported parameter is dropped with a `UserWarning` rather than raising. `research/00`'s `input_contract` specification is explicit that *"Binding is refused on mismatch"*. Both are right in their own scope and the ledger splits them (#14): warn-and-drop is acceptable in ingest, where vendors genuinely differ; on the agent path a `UserWarning` is invisible and the agent receives partially-wrong results it cannot detect, so bind-time is a hard error. **Recorded so the study's recommendation is not adopted wholesale.**

**C5 — A tension inside the studies, not with the research: is one `is_backtesting` flag a pattern or a leak?**
`reference/studies/bot-frameworks.md` §MM4 lists lumibot's `IS_BACKTESTING_BROKER` — one class attribute checked at 15+ sites inside `brokers/broker.py` — as a **mental model worth borrowing** ("one boolean, one place, instead of parallel code paths"). `reference/01-kernel-verdict.md` §"strongest counter" cites the identical fact as evidence that backtest≡live **erodes under maintenance pressure**, and `research/00`'s A3 position is that the simulator is just another adapter with no such flag at all. Both readings are defensible and the resolution is a boundary, not a verdict: the flag may exist **below** the venue port (locking, log volume, telemetry cadence — concerns that legitimately know they are simulated), the list must be short and written down, and it may never be visible to strategy or component code. The conformance suite (#39) is what turns erosion into a CI failure rather than a discovery.
