# Kernel Implications — what 40+ papers say about the QMA kernel

**Inputs:** the nine cluster files in this folder (C1 harness core, C2 reversibility, C3 memory, C4 skills, C5 tools, C6 loops/multi-agent, C7 RLM/context, C8 eval/provenance/safety, C9 self-improvement), `research/qma-extensibility-dossier.md`, and `kernel-contract-draft.md` (DRAFT v0, read in full; collisions flagged inline and collected in §5).

**Stance:** every paper judged on its own merits. The AlphaXiv chat was a pointer, not an authority. Findings that cut against the Cordis-leaning direction are stated at full strength and placed before the supporting ones inside each section where they conflict.

---

## PLAIN SUMMARY — for the operator, no jargon

Read this and you have the decision. The rest is the working.

**What the research agrees on.** Wrapping a model in a well-built harness is worth a lot — the same model scores 13.6 percentage points differently on average across harnesses on one benchmark, and up to 41 points on another. So the layer we are designing is real and matters. That is the good news and it is not in dispute.

**What the research does not agree with.** It does *not* say that a bigger, cleverer harness wins. One paper's section heading is literally "scaffold complexity does not predict effectiveness": a hundred-line scaffold that leaves the model alone beat a much more elaborate one on the same model. A survey of 70 real agent projects found that plugin architectures are a **10% minority pattern** — the ordinary majority just keeps a plain list of tools — and that projects adopt formal plugin boundaries when they want to be a **platform other people build on**, not because it makes their agent better. That is the sharpest thing in this whole corpus for us: **a plugin kernel is a bet on other people contributing, not a performance decision.** If QMA is a one-operator system, that bet is unpaid complexity. If QMA is meant to be a platform, the bet is legitimate — but it should be named as an ecosystem investment, out loud, not as a capability one.

**The hardest single result against us — corrected on re-read.** The best-evidenced self-improvement system in the corpus (tested on a full 89-task benchmark, verified to transfer to other benchmarks and other model families) got everything we want — swappable parts, checkpointing, rollback, attribution, safe self-modification — out of remarkably little. Our first pass reported that substrate as "a folder layout, a program that reads it, git, and read-only file permissions — no plugin kernel at all." A re-read of the paper's own appendix showed that last half-sentence was **wrong, and the error ran in the anti-kernel direction**: the system also carries a declarative typed component manifest (components registered in a yaml with import paths and binding resolution), one lifecycle hook wrapping model calls, and an auto-injected recall sub-agent — a **thin kernel**, not bare files (full retraction in c9-self-improvement.md §3e). Three other independent groups landed nearby. The corrected challenge to us: before we build more kernel, the contract has to say plainly what it buys that *folder + git + chmod + a loader + a typed component manifest with binding resolution and one model-call hook* does not.

**The honest reconciliation, and it is the most useful sentence in this document.** The anti-kernel evidence and the pro-kernel evidence are about **two different problems**, and they do not actually contradict each other:

- **Improving a harness overnight, in batches, where restarting is fine.** Files and git win. A kernel adds nothing. Every paper that measured this converged there.
- **Changing a live system while minds are running inside it** — swapping a model provider without dropping a session, giving each profile its own private instances, forking a running sandbox, spawning a child mind with an inherited spending limit, letting the UI reconfigure things safely. *Here* the machinery earns its place, and the papers that build this kind of thing all build something kernel-shaped.

So the kernel is justified by **live operation and isolation**, not by self-improvement. The draft contract currently sells the undo ledger partly on the self-improvement story (Part A, item 5). That justification is the weak one and should be rewritten to the strong one, or the first serious reviewer will knock it over.

**Three things the papers say we must build that the draft currently pushes outside the kernel.** (1) A **spending and step ledger the kernel enforces** — one study scanned 6,549 real agent projects and found 68 confirmed runaway-loop failures across 47 of them, *all* in frameworks that already offered optional limits; optional limits reliably get misplaced. (2) **One trace format everybody writes into** — the survey of this area says the reason nobody can trust agent systems is precisely that each part invents its own logging. (3) A **checkpoint between "the agent decided to act" and "the action happened"** that cannot be skipped, even when no policy plugin is installed. All three are currently listed in the draft as things the kernel does *not* own.

**One thing the papers say we may be building at the wrong seam.** If we expose our plugins to the model as one-call-at-a-time JSON tool schemas, that has a measured ceiling: a frontier model starts silently dropping calls somewhere past 70 parallel ones, and performance degrades once many tool schemas are in the window. The alternative — hand the model typed function stubs and let it write one script that we run once in a sandbox — matched or beat JSON on 11 of 14 models tested and got *better*, not worse, when flooded with 128 schemas. That is a fork in the road the draft does not currently contemplate.

**Bottom line.** Build a *thin* kernel — a loader, declared dependencies with real substitution, isolation, an enforced budget/checkpoint layer, one trace format, and a sandbox with a real filesystem — and keep everything else outside it. Defer the dynamic plugin marketplace until there is a second contributor. And before spending more on kernel machinery, beat the embarrassingly simple baseline: a coding agent with a folder, `grep`, and Python took state-of-the-art on 4 of 5 long-context benchmarks at about a fifth of the cost of the fancy method.

## 1. CONFIRMATIONS — where the literature independently supports a Cordis-style plugin kernel

Ordered by evidence strength. Each item names what is confirmed and, precisely, *which* property — several papers endorse a narrower thing than "plugin kernel."

**1.1 — The two properties a measured plugin kernel is actually credited with are substitutability and observability, and only those.**
HarnessX (2606.14249) *is* a Cordis-shaped kernel: typed hooks, slot singletons, processor pipelines, evolution loop. Its §6.4 ablation replaced the sophisticated four-stage evolver with a single-agent one at the same model/budget: **86.4% vs 87.4%, inside one standard error**, at ~14% more tokens. The authors' own conclusion: gains "derive primarily from HarnessX's infrastructure (typed components enabling isolation, structured traces enabling diagnosis) rather than the evolver's internal architecture." That is a direct, self-damaging endorsement of exactly two kernel properties — **type-safe substitutability** (draft K6: identity-keyed provider swap) and **structured traces** (draft B.9 obligation 2, `fiber.effects()`). It is not an endorsement of orchestration depth, taxonomy breadth, or hook richness.

**1.2 — Model config and harness config as disjoint, independently substitutable objects.**
HarnessX's `H = (M, C)`, combined as `agent = model_config.agentic(harness_config)`: "An agent is a processor pipeline bound to a model, both independently substitutable." This is QMA's provider-unbiased requirement expressed as a type, and it is exactly the draft's `ctx.llm` seam + `Entry.name` one-row swap (B.10). Independently arrived at.

**1.3 — Shared infrastructure is singleton and plugins depend on it but do not own it.**
HarnessX's P/S split — "P implements all per-step behavior; S houses the shared infrastructure that processors depend on but do not own"; slots (tool registry, tracer, workspace, sandbox provider) are singletons, processor state is instance-private. This is Cordis's service-vs-plugin split derived independently from a different starting point. It is the sharpest kernel-boundary rule in the corpus and it validates draft B.4.

**1.4 — LLM proposes structured data; deterministic kernel code validates, applies, or rejects.**
MANTA (2607.28527) is the cluster-6 winner and the clearest pro-kernel result in the corpus. Topology is a **versioned, validated JSON specification, never agent-authored code**. Deterministic code validates it (unique group membership, valid roles, acyclicity, legal patterns, agent-budget ceiling) *before any agent is instantiated*; invalid proposals are rejected or replaced with a conservative deterministic fallback. Mutation is hard-bounded (**one mutation per run, ≤3 operations**), gated by an auditor that sees only *process* signals and is structurally denied the correctness verdict. Result: highest average across 5 benchmarks, +5.8 over the strongest baseline. This maps almost verbatim onto draft B.7 — declarative entry tree, per-field dispatch, transactional update with rollback, deterministic reconciliation — and it explicitly rejects the simpler alternative (ungated LLM rewriting its own structure).

**1.5 — Bounds must be enforced structurally, not offered optionally.**
IAL-Scan (2607.01641) scanned **6,549 real agent repos**, flagged 74, manually confirmed **68 true infinite-loop failures across 47 projects (91.9% precision)**. The finding that matters: bounds almost always *exist* in the framework (LangChain `max_iterations`, OpenAI SDK `max_turns`, LangGraph `recursion_limit`, CrewAI `max_iter`) and fail anyway because they are omitted, disabled, or **placed in a scope that does not dominate the actual feedback path**. 95.6% of confirmed failures caused API cost exhaustion / model DoS. Conclusion: bound *coverage*, not bound *existence*, and it must be the kernel's job because authors demonstrably misplace it. → **Confirms a kernel-enforced budget layer. Collides with draft B.8, which puts budgets outside the kernel.**

**1.6 — A non-bypassable checkpoint between "action proposed" and "action executed."**
JANUS (2607.19913) shows a *predictive* pre-action guard beats reactive step-level guards by +15.9pp average protection while *also* completing +5.1pp more benign tasks (i.e. not winning by over-blocking); ablating anticipation raises attack success 0.072→0.148. The transferable part is the **hook shape**, not the model. Independently corroborated from a completely different literature: the critical-systems survey (2607.18548) names "**an unverified boundary between reasoning and action**" as a failure mode shared by all four industrial domains it examined (power, autonomous vehicles, HPC, telecom). Draft B.6's `<x>/pre-execute` waterfall is the right shape — **but a waterfall is bypassable by omission** (see §5, collision C1).

**1.7 — The enforcement layer must sit outside anything the agent can edit.**
Weng (Lil'Log, 4 Jul 2026 — a blog post, not a paper; weigh accordingly): "if a program is allowed to edit the OS system, abstraction boundaries are broken. The editable surface needs to be properly designed and **the permission control and security layers need to live outside this loop**." AHE (2604.25850) implements exactly this and it is what blocks the reward-hacking shortcuts: runs directory, tracer, verifier and model configuration are read-only; the seed prompt is non-deletable — "these restrictions block the shortcuts an unconstrained self-modifier would take, such as disabling the verifier, swapping the model, or raising the reasoning budget." The self-improvement survey (2607.13104) states the same as its one concrete governance requirement. → Confirms draft K9 as the *right kind* of mechanism (declaration-gated access as capability mediation), and confirms that the enforced boundary must be at load time, not prompt discipline.

**1.8 — Declared capability sets, knowable before a component runs.**
Draft B.2 property 2 ("the complete capability set of any plugin — including one an agent just wrote — is knowable before it runs, and therefore reviewable and approvable at load time") is independently the right idea. Code as Agent Harness (2605.18747) reaches it from the security side with a three-tier permission model (read-only / sandbox-edit / full-access with mandatory HITL on the last) — **and sharpens it**: "permissions should depend not only on tool identity, but also on **arguments, environment state, data sensitivity, and expected side effects**. The same command may be safe in a disposable sandbox but unsafe in a production repository." Confirms the mechanism, widens the scope tuple.

**1.9 — Isolation realms (draft OPEN-10) are independently confirmed three times over.**
HarnessX: **variant isolation beat a single global config both on accuracy (87.4% vs 49.5% final) and on cost (107.8M vs 143.7M tokens)** — the shared config degraded catastrophically because every edit perturbed everything. ACID-Agent (2608.13900): removing failed-step isolation alone costs **11.7%** of task score. AgentFactory (2603.18000): per-task workspace isolation is what keeps in-progress mutation from corrupting the shared library. → **Ship isolation realms in v1.** This is the best-supported single item in the draft's open register.

**1.10 — Live structural change genuinely needs privileged, kernel-level plumbing.**
Shepherd (2605.10913): atomic copy-on-write fork of *both* filesystem/process state and effect stream, measured at 134–143ms (2–3% of an agent turn, ~5× faster than `docker commit`), enforced at the **native syscall jail layer** (macOS Seatbelt, Linux Landlock). No application-level scaffolding can fake that. RAH (2606.13643): a spawn primitive callable *from inside sandbox code*, instantiating a full child mind with its own tool grant and workspace, carrying a depth counter and an inherited budget — "cannot live in a plugin. It is the kernel." The recursion theory paper (2603.02112) proves the sharpest version: a suspendable, offloadable **context stack** exceeds what *any* single-context strategy (including optimal summarisation) can do, and summarisation is provably optimal among single-context methods. Confirms the sandbox/computer seam and a kernel-level spawn primitive.

**1.11 — "The kernel owns no domain concept" (draft K14) is the corpus's most-validated law, by accident.**
Four harness papers produce **four mutually incompatible decompositions**: Gu's `(R,M,C,S,O,G)`; Guo et al.'s `⟨I_obs,C,L,I_act,S,V⟩`; Hu Wei's five empirical dimensions; HarnessX's nine. The non-convergence *is* the finding — there is no canonical taxonomy yet. A kernel that enshrines one in its type system will be wrong. Keep the **seams** (hooks, slots, permission scopes, keys) stable and let the taxonomy churn above them. K14 is correct and should be defended hard.

**1.12 — The kernel/adapter boundary in 2606.20683 §8.3, converged on by three other papers.**
> "A general substrate plus domain-specific adapters. The substrate provides logging, isolation, permission control, persistence, cost accounting, standardized tool access, and auditability. Adapters define observations, actions, verifiers, memory policies, and retry, rollback, stopping, or escalation rules."

Seven kernel services, and nothing else; orchestration topology, memory policy, verifier choice and stopping rules live in adapters. This is the most defensible boundary in the corpus. **Note it does not match the draft's boundary** — the draft pushes permission control, persistence and cost accounting *out* of the kernel (B.8). See §5, collisions C1–C3.

**1.13 — One registration primitive, reused rather than duplicated.**
MSCE (2607.16621) builds a memory→policy→skill promotion path whose final step is structurally identical to plugin registration: deterministic verification before activation, reliability-gated exposure, boundary-scoped applicability, revocation on drift. Its own conclusion is that this should be **the same mechanism** the kernel uses for human-authored plugins, not a parallel one. That is an argument for the kernel's registration path being valuable *and* for it carrying more surface than the draft currently allows (see §5, C8).

## 2. CONTRADICTIONS AND SIMPLER WAYS — stated at full strength

Nothing in this section is softened. Where a finding has a legitimate limitation, the limitation is stated too, but never used to blunt the claim.

**2.1 — Plugin architectures are a 10% minority pattern, and adoption tracks market ambition, not capability.**
Hu Wei (2604.18071), cross-sectional study of **70 public agent projects**. Tool systems: **explicit registry 34.3%**, MCP-first 14.3%, minimalist 11.4%, **plugin ecosystem 10.0%**, decorator 10.0%. Registry + MCP + decorator = 58.6%. The co-occurrence that matters (support 0.62, lift 2.8): formalized registration boundaries "are rarely adopted in isolation. They usually appear in projects that present themselves as reusable platforms, developer-facing CLIs, or broader orchestration substrates." The plugin architecture appears in the **"Enterprise Full-Featured" bundle — 10.0% of the corpus and the heaviest governance/infrastructure cost in it.** The author explicitly says the patterns "are not maturity levels or quality tiers."

Read plainly: **a plugin kernel is a bet on third-party contribution.** If QMA does not intend a third-party mind/plugin distribution channel, it is unpaid complexity. If it does, the cost is real and should be budgeted as an ecosystem investment. The draft's acceptance property (A.4) is a *development-cost* argument, which is legitimate — but it is not the argument this data supports, and the contract should say which one it is making.

*Limitations, stated:* single author, non-institutional email, no chance-corrected inter-rater agreement, composite scores (4.62, 4.1, 2.1…) with no published rubric — use the rank orderings and the marginal distributions, not the numbers. One corpus row (`claude-code-src`) is coded from a "source-visible leaked snapshot," which is a provenance problem for anyone citing it. None of that touches the marginal distributions above, which are the load-bearing part.

**2.2 — "Scaffold complexity does not predict effectiveness." That is a literal section heading, and the numbers are inside the same paper that proves harnesses matter.**
2606.20683. On Claude Opus 4/4.5 SWE-bench Verified: **mini-SWE-agent — a ~100-line scaffold that "leaves most orchestration to the model" — scores 76.8%, beating SWE-agent+tools at 73.2%**, and trails the full OpenHands+CodeAct runtime by **0.8pt**. Agentless, a *non-agentic fixed pipeline*, beat interactive SWE-agent on GPT-4o by **15.6pt** (38.8% vs 23.2%). Proprietary vendor scaffolds beat the best open scaffolds by only **2–4%**. Meanwhile the same paper's Terminal-Bench 2.0 analysis (75 submissions, 32,604 trial records, 48 strictly matched) finds a **median within-model spread of 13.6pt across harnesses, with 14 of 20 models varying ≥10%**, and WebArena spans up to 41.5pt.

So: the harness matters enormously, *and* layers are not what makes it matter. "Compatibility is an empirical property of the model–harness pair rather than an implementation detail." And the cost dimension a kernel must respect: Meta-Harness on Opus 4.6 buys 76.4% with a **755.0K** median input context per trial; Terminus 2 gets 62.9% on **79.4K**. Nearly 10× the context for 13.5pt. **A kernel that assembles maximal context is not free.**

**2.3 — The best-evidenced self-improvement system in the corpus needs only a THIN kernel (claim corrected on re-read), and four independent groups converged on a minimal substrate.**
AHE (2604.25850): Terminal-Bench 2, **all 89 tasks**, k≥2 rollouts, official pass@1 convention, ~32 hours. **69.7% → 77.0% over ten iterations**, beating three human-designed harnesses (OpenCode 47.2, Terminus-2 62.9, Codex 71.9) and two self-evolving baselines from the same seed (ACE 68.9, TF-GRPO 72.3). Transfer *tested, not assumed*: the frozen harness tops SWE-bench-verified at 12% fewer tokens and gains +2.3 to +10.1pp across five alternate bases including three other model families.

Its substrate, corrected on re-read of the paper's Appendix B (fidelity defect retracted in c9-self-improvement.md §3e — the first-pass claim "no plugin registry, no lifecycle hooks" was false and overstated the anti-kernel case): **named component types as files at fixed mount points, git (one logical edit = one commit → "file-level diffs and rollback granularity for free", iterations are git tags), OS read-only permissions on the tracer/verifier/model-config — plus a declarative typed plugin registry (`code_agent.yaml` lists with `import:`/`binding:` paths resolved at load), one lifecycle hook (`wrap_model_call`), and an auto-injected `RecallSubAgent`.** A thin kernel, not "folder + git + chmod." Still: no capability negotiation, no reversible-action runtime. Meta-Harness stores each candidate as a filesystem directory of source + scores + trajectories. MCE stores a context function as a directory containing `skill.md`. AutoDesign (2608.13560) checkpoints a repository. Continual Harness (2605.09998) mutates four stores **through ordinary tool calls** (`define_agent`, `run_code`, `process_memory`) — no privileged mutation path at all — and from a bare minimal harness recovers most of the gap to a hand-engineered expert harness, Pareto-dominating the baseline on Gemini 3.1 Pro (100% of milestones at $130 median vs 98% at $215).

**The contract must state what a kernel buys that `directory layout + git + chmod + a loader + a declarative typed component manifest with binding resolution and one model-call hook` does not.** The honest answer, which the evidence supports, is in the plain summary: live reconfiguration without restart, per-profile isolation, and enforced budgets across a spawn tree. It is *not* self-improvement.

**2.4 — "Everything reversible" is the wrong primitive. "Nothing applied until promoted" is cheaper and stronger, and it is what the systems that worked actually used.**
AutoDesign's rollback is **don't promote** — the candidate is run on train+dev and the incumbent is simply retained; zero cost, zero machinery, because nothing was ever applied. AHE's rollback is `git revert` on a path. The self-improvement survey's answer to "how are changes rolled back" is **"keep versions"** — `Σ_{t+1} = IMPROVE_Σ(Σ_{1:t}; S_t)`, an update over the *history*. Reversibility of **actions** and versioning of **configuration** are different problems, and this literature only ever needed the latter.

**This is a direct challenge to the draft's Part A framing of the undo ledger** (A.2 item 5: "why a self-improving harness can rewrite one of its own capabilities without dying"). Every self-improving system in the corpus rewrote its capabilities by restarting, and that was fine. Cordis's inverses buy something real but different — *live* swap while sessions, sandboxes and streams are open. Rewrite the justification to the case it actually wins.

**2.5 — Clean plugin composition is empirically false, and no kernel feature can rescue it.**
AHE ablation on Terminal-Bench 2: memory-only **75.3%**, tool-only **73.0%**, middleware-only **71.9%**, **prompt-only 67.4% — a 2.3pp regression below the 69.7% seed** — and full AHE **77.0%**. The three positive single-component gains sum to **+11.1pp**; together they deliver **+7.3pp**. On the Hard split, **memory-only (63.3%) exceeds full AHE (53.3%).** Cause: memory, middleware and prompt all push toward the same closure-style verification, so stacking them spends turns on redundant re-checks.

Components that were **file-level orthogonal by construction** still interfered behaviourally. Cordis's confluence theorem (Thm 73) guarantees the settled **state** equals the statically-assembled state; it says nothing about behavioural additivity, and nothing can. **The contract needs an explicit non-claim on this**, plus a requirement for interaction-aware evaluation of component *sets* rather than per-plugin validation (§5, C5).

**2.6 — Elaborate composition machinery is the scar tissue of missing formal state.**
Code as Agent Harness §4.4: "**Topology complexity inversely correlates with harness-state formality.**" L2MAC, which has "the clearest formal harness substrate (a persistent file store with explicit context scheduling), uses a **simple sequential chain** with sophisticated state management. By contrast, implicit-state systems like EvoMAC and SEW develop elaborate adaptive topologies (dynamic DAGs, workflow mutation, agent pool scaling)… topology complexity is partially a **symptom**." And: "**Context management is the tax of implicit shared state.**" And: "the reliance on implicit state representations is the technical root of system brittleness rather than a scalability convenience."

Applied to us: **if QMA's kernel budget goes into plugin composition, hook ordering and orchestration rather than a formal, queryable, versioned state substrate, this predicts QMA will later grow exactly the orchestration complexity the kernel was supposed to prevent.** The high-leverage kernel investment is read/write sets, declared assumptions, provenance, belief-vs-ground-truth divergence — not composition.

**2.7 — If the plugin surface reaches the model as one-call-at-a-time JSON schemas, that seam has a measured ceiling.**
The Bitter Lesson of Tool Calling (2608.06370), 14 models across 20 months of releases, deterministic scorer, matched LLM-call counts: **programmatic tool calling (typed Python stubs, one script, one sandboxed execution) matches or exceeds JSON dispatch on 11/14 models.** Its advantage *grows with chain length* (**18.8pp absolute at ≥12 hops**, because JSON pays one inference turn per hop). **JSON has a hard structural fan-out ceiling** — Claude Sonnet 5 starts silently dropping calls between N=70 and N=72, while PTC holds 100% enumeration accuracy through N=100. Under context flooding with 128 schemas including decoys, **JSON degrades 2.3% on average while PTC improves 5.5%.** RAH confirms the mechanism independently: JSON spawning is capped by the provider's per-turn parallel-tool-call budget, code-execution spawning is not. The RLM authors state the position outright: "We want to move away from the JSON tool-calling standard for both sub-agents and generic tool calls."

*Limits, stated:* PTC carries ~1.5× fixed input-token overhead on non-fan-out tasks (crossover ≈ N=26 calls) and fails outright on three older models via one specific `\n`-escaping codegen bug — viability tracks model *generation*, not vendor. So keep JSON dispatch as a fallback; do not make it the default.

**Note the scope of this challenge precisely:** Cordis's plugin seam is a *Python service seam*, not a JSON schema, so this does not indict the kernel. It indicts **draft B.6's per-call tool pipeline** (`tools/pre-execute` → guards → `tools/execute` → `tools/post-execute` per invocation), which assumes one-call-at-a-time mediation. Under code-execution-first, the kernel mediates once per script and per-call policy must live inside the generated stubs. That is a genuine architectural fork the draft does not contemplate (§5, C6).

**2.8 — Model choice moves outcomes ~1.8× more than harness choice, and harness rankings do not hold across models.**
HarnessOpt-Bench (2608.06301), 111 scored runs, held-out test partition evaluated once: optimizer model choice moves gain **0.142 average swing vs harness choice 0.079**, and native (model-specific) harnesses show **no consistent advantage** over a shared harness (11 wins vs 9 of 20 pairs). Harness ranking does not transfer across models. Caveat the paper itself flags: on GAIA, the one task with a genuinely varied harness axis, native-harness advantage was large but concentrated in specific pairs — so this is an average-case finding, not a uniform one. Still: **do not over-invest kernel complexity on the theory that harness sophistication is the dominant lever.**

**2.9 — Self-improvement is net-harmful below a capability floor, and QMA is deliberately provider-unbiased.**
Continual Harness on **Gemini 3.1 Flash-Lite: every variant underperforms the minimal baseline** (3–13% of milestones vs 20%) at equal or higher cost. STOP degraded on GPT-3.5 and Mixtral. Lin et al. (2605.30621, via Weng) disentangle two axes: harness-**authoring** capability is flat from ~9B up to Opus 4.6, while harness-**benefit** capability is **non-monotonic, with middle-tier models benefiting most**. → Self-improvement must ship as an **opt-in capability with a declared floor and a measured off-switch**, never as a default kernel service. Otherwise it degrades exactly the cheap-model deployments provider-unbiasedness exists to serve.

**2.10 — Even the best evidence *for* self-evolving kernels is soft, and its own predicted pathologies all fired.**
HarnessX's headline **+14.5% average (up to +44.0%)** carries the authors' own disqualifier: "**No held-out evaluation.** All reported gains are measured on the same task set used for evolution. Since we report **peak** accuracy and evaluate on the adaptation set itself, the numbers carry both selection bias and potential overfitting." SWE-bench runs use a **55-task subsample**. And all three predicted pathologies actually occurred: global-strategy GAIA/GPT-5.4 **Δ = 0.0 over 15 rounds** with a **−24.3pt peak-to-final collapse** (verified to exceed the per-round binomial CI — catastrophic forgetting); SWE-bench 63.6% → 50.9%; τ³-Bench Telecom **−14.0% in a single round** from five consecutive same-type edits accumulating sub-threshold coupling **that the per-edit acceptance gate structurally could not see**. Their own verdict on the theory: "a design checklist rather than a predictive theory."

**2.11 — The system cannot see its own blast radius. Containment must be structural, never predictive.**
AHE's self-attribution study: fix-prediction precision **33.7%** / recall 51.4% (≈5× random). **Regression-prediction precision 11.8% / recall 11.1% against random baselines of 5.6% / 5.4%** — barely above noise. "The agent can justify why an edit should help, but it cannot reliably name the tasks the same edit is about to break." → Any QMA hook that asks a self-improving mind to declare what its change might break returns near-noise. Use those declarations to **measure the loop's calibration**, never as a safety input. (This one cuts *for* the draft: declared write scopes and read-only boundaries are exactly the structural answer.)

**2.12 — A meaningful share of "transactional agent reliability" needs no kernel at all.**
ACID-Agent (2608.13900) on KramaBench (104 tasks): **+10.6% over Claude Code on the same backbone**, beating Claude Code even on a *larger* backbone, with run-to-run variance dropping from ±30.9 to ±18.6. Its guarantees come **entirely from orchestration-level scaffolding** — retry loops, an append-only logical workspace, and a small local confidence-divergence classifier. No OS-level sandboxing, no copy-on-write forking, no kernel hooks. The key ablation: removing **failed-step isolation alone costs 11.7%**. → Split two problems the Shepherd framing tends to conflate: **(a) undoing real-world side effects** (genuinely needs kernel-level fork/rollback) versus **(b) keeping failed attempts out of a mind's context and memory** (a pure harness-level discipline, worth ~12% by itself, shippable long before any kernel sandbox substrate exists). Do not let the kernel case for (a) route (b) through the kernel too.

**2.13 — Accountability without any kernel provenance primitive is demonstrably possible at low stakes.**
AppLooper (2608.14093) builds candidate-bound evidence chains, role-separated agents and an inviolable human release gate on **stock Claude Code**, with no bespoke kernel primitive: role prompts plus an orchestration layer that binds every finding, test result and approval to an immutable candidate version, auto-invalidating approvals when the candidate changes. *But:* it has **no quantitative evaluation whatsoever**, and its role boundaries are **convention-enforced** (an LLM that violates its role prompt would not be caught by anything described). Honest reading: **stakes-dependent, not settled.** Where consequences are recoverable and a human inspects before anything real happens, light orchestration suffices; where actions are irreversible or inputs are adversarial, prompt-level convention is precisely what fails.

**2.14 — Before paying for any of this, beat the embarrassingly simple baseline.**
Cao et al. (2603.20432): write the corpus to a **directory tree of `.txt` files**, hand an off-the-shelf coding agent the path plus the query, impose **no constraints**. Result: **SOTA on 4 of 5 benchmarks, +17.3% average over published SOTA**, across 188K to **three trillion** tokens. On Oolong-Synthetic it beats RLM 71.75 vs 64.38 at **$0.194 vs $0.920 — 4.7× cheaper and more accurate**. Two sub-findings with direct design consequences: **folder layout is worth ~6 points** over the same content in one JSON file (89.0 vs 83.0), and **adding a BM25 retriever dropped the score 89.0 → 82.0** ("naively providing retrieval tools may degrade performance… without suppressing agents' native exploration"). And the critique lands: "RLMs impose a uniform recursive decomposition strategy regardless of task structure."

**The single cheapest high-value thing QMA can build is a sandbox with a real filesystem, shell, and code execution.** Everything else should have to beat it.

**2.15 — Bare-model recursion is the weakest rung, and recursion may not be the causal ingredient at all.**
On Oolong-Synthetic with the backbone held fixed at GPT-5: **RLM 64.38% < plain coding agent 71.75% < recursive agent harness 81.36%**. Inside the RLM paper's own tables, wrapping GPT-5.2 in RLM cut **MATH from 26.0 → 5.6 and CS from 40.4 → 11.0**. An independent reproduction found Kimi K2 collapsing **86.6% → 60.0%** when forced into the scaffold, with latency going 3.6s → 89.3s → 344.5s across depths 0/1/2. Apple's SRLM (2603.15653), the best-controlled comparison in the cluster (equal wall-clock budget), gets **+22% over RLM with no recursion and no self-query at all**, concluding "recursion is not the primary driver of RLM's performance." λ-RLM (2603.20105), nine base models / 36 comparisons, **wins 29/36 against standard RLM with 3.3–4.1× latency reduction and formal termination proofs**, by replacing free-form model-authored code with a fixed typed combinator library.

→ **Do not make a free-form model-authored loop the kernel's default control flow.** LCM's framing is the right one: RLM gives the model **GOTO**; structured operators give bounded control flow with termination guarantees. Their own conclusion is the design to adopt: default to structured operators, retain free-form recursion as the escape hatch behind them.

**2.16 — Skill libraries that grow without matching routing investment make agents worse.**
Demystifying Agent Skills (2608.14036) — the most methodologically rigorous paper in cluster 4 (8,135 normalized trial records, 528 matched triples, taxonomy validated at **κ=0.952** against human coding). Skills work as **procedural anchors** (65.7% of success cases) not knowledge injection (4.5%). But: **`skill_guidance_misapplied_or_ignored` appears in 10.0% of skill-arm trajectories vs 0.8% raw — a 12–25× increase.** Skills introduce a failure mode that does not exist without them. And as pool size grows 5 → 100, **actual-use retrieval precision collapses 29.6% → 3.3%**. Skills do not fix reasoning or verification failures at all (`algorithmic_logic_error` persists at 7.4–11.0% across *all three* arms). → Any skill registry must treat **retrieval-precision decay and misapplication rate as first-class monitored constraints**, with an active-pool cap, and must validate net benefit **at the current pool size**, not at creation time against a small benchmark.

**2.17 — A single trained text file beat every registry-and-evolution-engine competitor on a bounded domain.**
SkillOpt (2605.23904), the strongest empirical matrix in cluster 4: **6 benchmarks × 7 models × 3 harnesses = 52 cells, best-or-tied on all 52**, +23.5pp for GPT-5.5 in direct chat, and a Codex-trained skill transferring to Claude Code at **+59.7pp**. It has **no runtime registry, no retrieval, no routing machinery** — one offline-optimized 300–2,000-token document swapped in via a thin adapter, zero extra inference cost at deployment. → For any narrow, well-verified sub-task, a **trainable skill slot per mind** is the higher-leverage first increment. Reach for registry machinery only when a mind genuinely needs multiple composable retrieved skills.

**2.18 — "Python backend" buys no architectural argument in either direction.**
Advanced subagent patterns by implementation language: Rust 57%, Go 43%, **Python 42%**, TypeScript 40%. Language "constrains implementation style more directly than it constrains high-level harness architecture." Neither side of the kernel debate can appeal to it.

Each item states the mechanism, the evidence, and whether it belongs in the kernel or above it. Items marked **[COLLISION]** conflict with `kernel-contract-draft.md` B.8's "what the kernel does not own" list.

### 3.1 Memory interfaces

### 3.2 Skill / tool registries with promotion gates

- **One `propose → verify → register → revoke` primitive**, shared by LLM-synthesized skills and human-authored plugins rather than duplicated. Verification is **deterministic and non-LLM**: schema validity, evidence-grounding (every cited evidence ID must be in the support set), and coverage (no invented commands). Drafts failing any check are discarded and **never exposed as callable**. — MSCE. **[COLLISION with B.8: "promotion gates are plugin policy, not kernel law"]** — the *thresholds* are policy; the *primitive* wants to be the kernel's registration path.
- **Two promotion gates:** positive-gain (must beat the without-policy baseline) **and** stability (recent evidence must still fit the current trigger/procedure/boundary rather than requiring a rewrite). — MSCE.
- **Post-promotion reliability lifecycle** as a concrete state machine, adoptable near-verbatim: η = (n_pass+1)/(n_trials+2) Beta-smoothed; probation → active → archive (θ_active 0.6, θ_archive 0.2); **user rejection shrinks the applicability boundary** rather than only lowering reliability; if the source policy is substantially rewritten the skill is **rebuilt from fresh evidence, not patched**. — MSCE.
- **Default promotion gate = bounded edits + held-out selection split + rejected-edit buffer**, with strict-improvement acceptance and an epoch-wise slow update into a protected field that fast edits cannot overwrite. — SkillOpt (best-validated, 52/52 cells). Reserve the heavier **information-isolated verifier + opaque-pass/fail-bit oracle** protocol for domains with deterministic ground truth — it is the strongest anti-gaming mechanism in the corpus (removing the surrogate verifier drops pass rate 30pp) but needs an automatic oracle. — CoEvoSkills.
- **Live re-execution of old vs new version on matched tasks** before deploy, not just a static held-out score; day/night batch cadence. — SkillClaw (whose own validation log shows the conservatism: ~4 candidates over 6 nights, **1 accepted**).
- **add / merge / drop as atomic auditable registry operations** from day one, rule-based first, learned later. CODESKILL shows bank size **stabilises** rather than growing unboundedly once merge/drop dominate — the mechanism Demystifying's decay finding implies is necessary. — CODESKILL.
- **Retrieval-precision decay as a monitored, first-class constraint**: active-pool cap per context, routing investment proportional to library size, explicit misapplication monitoring using the 12-mode taxonomy. — Demystifying.
- **Shadow-mode execution path as a kernel primitive**: run the candidate in parallel with production, log discrepancies, **no side effects**, human review before promotion. Production-validated over >5,000 live alarms. — 2607.08010.
- **Build-time / offline tool-compilation phase decoupled from the runtime model**, grounded in a recorded **execution trace** (real calls against the live interface plus a graded verdict), with a mandatory **test–repair loop** against held-out labelled cases before entering the versioned registry. Ablations: removing repair −9.6pp, removing the trace −5.2pp. — 2607.08010.
- **Mandatory fallback from a compiled tool back to a general sandboxed sub-agent** on `no_data` or throw; uniform tool signature with an explicit failure mode. — 2607.08010.
- **Spec quality, not codegen, is the residual bottleneck.** At the 94.5% pass@1 ceiling, remaining errors traced almost entirely to **SOP specification ambiguity**; clarifying the spec pushed a run to 99.9%. Invest tooling in edge-case capture, not in more codegen loops. — 2607.08010.
- **Self-describing portable artifact format** — plain inspectable code plus a standardized companion doc — validated by cross-framework reuse with zero code-level integration. Borrow the format; **reject its promotion gate** (a single self-judging LLM, no held-out set, no reviewer). — AgentFactory.
- **A behaviour-aligned skill router, not a semantic one** — retrieval conditioned on the query plus the agent's behavioural signature, trained on LLM-synthesised positives and hard negatives (Recall@1 0.60, Recall@10 0.90 in-paper) — the cluster's **only mechanism for the retrieval-precision decay problem** Demystifying measures but does not treat. Integrated late: this paper was silently dropped from the first research pass (correction of record in c4-skills.md). — Memento-Skills (2603.18743).
- **Utility-threshold escalation `patch → discover` with a minimum-sample floor** — a per-skill Beta-style success rate decides when to stop patching a skill and rebuild it from a fundamentally different approach, preventing the library from accumulating individually-dying skills. Two stated limits: precision is never measured as a first-class outcome, and Memento's own GAIA transfer failure cautions against treating the router as a solved problem. Consequence for the kernel: the skill-registry contract must expose **retrieval-precision decay and misapplication as first-class monitored signals**, not leave them to plugin discretion. — Memento-Skills (2603.18743).

### 3.3 Provenance and tracing

- **One canonical trace/provenance schema the kernel owns, with a mandatory emission contract for every subsystem** (tools, memory, retrieval, inter-agent messaging). Canonical entity types (claims, evidence units, tool observations, memory items, environment states, agent messages) and canonical relations (SUPPORT / CONTRADICT / DEPEND-ON / UPDATE / INVALIDATE, per W3C PROV-DM). The survey's diagnosis of the field's central blocker: "**Few provide interoperable schemas that jointly represent reasoning steps, retrieval, tool calls, tool outputs, memory operations, inter-agent messages, intermediate claims, final answers, and external state changes.**" If provenance is per-plugin and opt-in, QMA reproduces exactly the fragmentation identified as the industry-wide obstacle. — 2606.04990, corroborated independently by 2607.18548 Open Challenge D ("build provenance standards before regulators do"). **[COLLISION with B.8: persistence/replay is a plugin on a separate bus]** — reconcilable: kernel owns schema + emission obligation, plugin owns the store.
- **Taint as a first-class field on every context handle**, and the kernel must **refuse to bind tainted content into a sandbox with host-process access or unrestricted egress**. Isolation level is *derived from input taint*, not chosen by the caller. Concretely urgent: the RLM reference implementation's default sandbox runs `exec` **in the host process** — for a web-reading research mind that is a live prompt-injection-to-code-execution path. — C7 §10, non-negotiable before any web-reading mind ships.
- **Trajectory tree recorder** matching the execution tree — run config plus every iteration and sub-call, hierarchical and reconstructable. Required for both debugging and audit. — ROMA, RLM, AHE.
- **Traces as a navigable file environment with layered distillation** (per-task root-cause report → benchmark overview → raw trace on demand). Progressive disclosure is simultaneously a token-budget mechanism and an agent-ergonomics mechanism. — AHE.
- **Mandatory run-record contract**: model version, harness identity, tool privileges, retry and timeout policy, execution environment, token/API usage, trace and verifier metadata. "A benchmark score is interpretable only together with the runtime configuration that produced it." — 2606.20683.
- **Evidence bundles on every accepted action**: checks run, assumptions preserved, untested regions, remaining risks. And: **every verifier declares what it verifies, what it cannot verify, and what confidence it provides.** A verifier that does not declare its own scope is a liability. — 2605.18747.
- **Version-bound accountability** (cheap, general): bind every finding, test result and approval to an immutable candidate id; **approval auto-invalidates when the candidate changes**, forcing re-inspection rather than letting stale sign-off carry forward. — AppLooper.
- **Trace structure sufficient for later failure attribution** at three levels — agent / workflow / platform — so attribution tooling can be built without redesigning the format. — 2605.14892.
- **Two-bus split** (live ephemeral coordination bus + durable append-only replayable log, bridged by exactly one live emit, with surface-vs-log-only row tagging and a replace-range operation so compaction shadows history without rewriting it). Strongly confirmed: the durable bus is where the canonical provenance schema lives. — DSH convention + 2606.04990 + Weng.

### 3.4 Budgets and stop rules

- **Bound *coverage*, not bound *existence*.** The kernel must structurally guarantee that every feedback-carrying invocation path — including nested sub-agent and plugin calls — is dominated by an enforced bound. An opt-in `max_turns` per mind is demonstrably insufficient: 68 confirmed real-world failures across 47 projects, in frameworks that all already offered the primitive. — IAL-Scan. **[COLLISION with B.8: budgets outside the kernel]**
- **Budget ledger inherited down the spawn tree and decremented**: depth (**default 1**), fan-out, max concurrent sub-calls, tokens, spend, wall-clock, plus a **no-progress detector**. A plugin cannot bound its own runaway — *the loop is the runaway*. Evidence: latency 3.6s → 89.3s → 344.5s across depth 0/1/2, one trace at 1223.6s; a prompt change causing "thousands of LM subcalls for basic tasks"; the RLM authors' own unsolved "exploding sub-call costs"; and the diagnosis that lands hardest — "**the REPL architecture inherently lacks a stopping mechanism for an over-anxious agent.**" — C7 §5, §12.
- **Kernel-owned completion contract** — a typed return with a schema, **not** string tags. RLM's `FINAL()` / `FINAL_VAR()` were malformed in **16% and 13%** of root turns respectively, requiring a programmatic patcher; the authors say it "should be avoided altogether in the future." — C7.
- **Named terminal states** — success, no-op, blocked, stalled, exhausted — so exhaustion or error is never silently treated as success. — 2607.00038.
- **Loop guards as kernel constants**: max_steps, action deduplication by `hash(tool, args)` over a sliding window, progress-stall detection, and the escalation predicate `escalate ⟺ p_success < τ_conf ∨ action ∈ A_irreversible ∨ cost > B_auto`. — 2606.24937.
- **Pre-flight token counting as a kernel invariant.** The **Silent Truncation Trap**: many APIs silently drop tokens from the *middle or beginning* of an over-long input **with no error signal**. The kernel is the only layer that can prevent it. Context budget `C ≥ S + M + T + H + R` with per-mind shares (defensible defaults 0.10 / 0.20 / 0.10 / 0.50 / 0.10) is exactly what scoped constants are for. — 2606.24937.
- **Non-bypassable pre-action checkpoint.** A synchronous decision point must exist in the kernel's execution loop between "action proposed" and "action executed" that a guard can occupy — *a plugin cannot retroactively insert a checkpoint the loop did not leave room for.* The guard's judgment (model, policy, strictness) stays pluggable. **Hook point = kernel constant; guard policy = plugin.** — JANUS, corroborated cross-domain by 2607.18548.
- **Verification-governed termination, not confidence-governed.** "Termination should likewise be governed by verification rather than by model confidence." The kernel acts as a **cybernetic governor** over deterministic sensors (linters, parsers, compilers, type checkers, tests, static analyzers, runtime monitors, CI) rather than forwarding error strings to the model. — 2605.18747.
- **Engage-gate before expensive strategies.** Cheap triage decides *whether* to recurse/expand at all — without it, RLM is a net negative on the majority of traffic; RLM-JB proposes the same shape for its ~3× processing cost. — C7 B9/B19.
- **Permission scope over `(tool, arguments, environment state, data sensitivity, expected side effects)`**, not tool identity alone. Three tiers: read-only / sandbox-edit / full-access with **mandatory HITL on the last**. — 2605.18747 §3.4.3, §5.2.5. This validates "scoped constants" as a concept and widens the scope tuple beyond what `isolate`/`intercept` currently address.
- **Autonomy spectrum as shared vocabulary for bounded authority**: advisory → human-in-the-loop → human-on-the-loop → human-in-command → autonomous, declared per task/domain rather than each deployment inventing its own permission language. — 2607.18548.

### 3.5 Self-improvement: measure / mutate / validate / rollback

Answering the three structural questions directly, from the systems that worked:

**What is measured.** Not scalars — **trajectories**. AHE distils k traces per task into per-task root-cause reports plus a benchmark overview, retaining raw traces for verification. AutoDesign mines full trajectories with parallel subagents for *recurrent* failure patterns. Continual Harness scans a sliding trajectory window for named failure signatures. **Outcome scores decide promotion; process evidence drives proposal.** A QMA that emits only success/failure metrics cannot host any of these loops. Also required alongside outcome metrics: trajectory quality, memory hygiene, context efficiency, communication fidelity, verification cost.

**What is mutable.** Convergent across all four systems: **prompt, tool description, tool implementation, skills, sub-agents, memory, and control/orchestration logic** — declared as *named, loosely-coupled, file-backed component types, one failure class per type*. **Immutable in every system that took safety seriously: the tracer, the verifier/evaluator, model selection and reasoning budget, the gate, and the audit record.** Note the finding that reshapes where effort goes: gains localise to **tools, middleware and long-term memory, not the system prompt** — prompt-only evolution *regressed* the seed by 2.3pp, and "factual harness structure transfers across tasks and models whereas prose-level strategy does not."

**How changes are validated / applied / rolled back.** The spread is itself the finding: AHE — git commit per logical edit, falsifiable prediction manifest, next-round attribution, file-granularity revert, iterations as git tags. AutoDesign — candidate run on train+dev, promote iff train improves and dev does not decline, **rejection = retain incumbent (rollback is free because nothing was applied)**. Continual Harness — applied immediately, never validated, never rolled back, and it produced the corpus's one documented catastrophic regression (newly authored sub-agents overtaking inherited ones around step 213 and driving the milestone staircase *below the minimal baseline*).

Concrete hooks demanded:

- **A loader** that mounts declared component types into a running mind. *(The one irreducible kernel piece from cluster 9.)*
- **An enforced read-only boundary** around tracer, evaluator/verifier, model configuration, gate and audit ledger — **enforced at load time, not by prompt discipline**.
- **Scoped visibility between agent roles at *record* scope**: held-out results never enter the artifact the proposer reads — not merely hidden from one prompt. Cheapest and most transferable idea in cluster 9. — AutoDesign.
- **Declared write scopes** as the containment mechanism; **never predictive blast-radius declarations** (§2.11).
- **One intervention per iteration** as attribution discipline, plus an **append-only ledger carrying rejected directions forward** so the proposer does not re-propose them.
- **Falsifiable prediction manifest** per edit (expected fixes *and* at-risk regressions), intersected next round with observed deltas — used to **measure calibration**, not to gate.
- **Deterministic acceptance gate** (reject any change regressing a previously-passing case) **plus a cap on consecutive same-type edits**, because per-edit gating structurally cannot see accumulated sub-threshold coupling (τ³-Bench −14.0% in one round).
- **Variant isolation over one global config** (§1.9) — more effective *and* cheaper.
- **Robustness to random state perturbations before commit** — required by the self-improvement survey and implemented by **nobody** in the corpus. A cheap differentiator.
- **Off switch + declared capability floor** (§2.9), non-negotiable for a provider-unbiased SDK.
- **Evolution is a build-time activity, not a runtime one**: "At deployment, the evolved harness is a static artifact requiring no meta-agent inference."
- **Interaction-aware evaluation of component sets**, not per-plugin validation (§2.5).
- **Mutation through the ordinary tool-call channel**, not a privileged kernel path — the simpler design, and it worked. Plus **CRUD with stable identity per store** and observable component lifetimes, plus a **reuse prior / deprecation policy** for newly authored components whose task signature is already covered by an inherited one (Continual Harness's own proposed fix for its worst failure).
- **Skill = a named, serialized, reusable instance of the update operator**, with object-level vs meta-level scope and an "installer" form. Substrate-agnostic by construction, which fits provider-unbiasedness exactly. — 2607.13104.
- **A mind *is* a Σ.** `A_t = (θ_t, Σ_t)` with `Σ = (p, m, T, g)` — prompts, memory, tools, and **control logic including safety constraints** — separated from the ephemeral run state `X_t` (KV caches, intermediate plans) which is discarded at task boundaries and is explicitly *not* part of the agent's identity. This is the cleanest available definition of "deployable semi-profile." — 2607.13104.

### 3.6 RLM-style loop swapping

The direct answer: **RLM as published is a plugin, and a shallow one** — `rlm.completion(prompt, model)` is a drop-in for `llm.completion(prompt, model)`, and the reference library already ships swappable sandboxes (local/ipython/docker/modal/prime/daytona/e2b) and swappable providers. If QMA has a model-provider seam, RLM slots in with zero core changes. **But four things it needs are not available at that seam:**

| # | Kernel primitive | Why a plugin cannot own it |
|---|---|---|
| **K-a** | **Reentrancy** — sandbox code must call *back into* the kernel to start a model call or a child mind, accounted to the same run | The sandbox is by construction isolated from the host; a host-side proxy must bridge access back in |
| **K-b** | **Budget ledger** (§3.4) — inherited down the tree and decremented | A plugin cannot bound its own runaway; the loop *is* the runaway |
| **K-c** | **Context stack** — `call`/`return` with isolated frames, suspendable, offloadable to storage, restorable | Formally proven to exceed what any single-context strategy can achieve; requires owning frame lifecycle and storage. Gives checkpointing and resumability for a long-running mind as a side effect |
| **K-d** | **Taint-scoped isolation** (§3.3) | A plugin choosing its own isolation level is not a control |

Plus three design rules the kernel must express:

- **One spawn primitive, two capability grants.** `spawn(prompt, model, tools=[], workspace=None)` = a bare sub-model call; `spawn(prompt, model, tools=[fs, shell, web], workspace=fresh)` = a full child mind. **The grant, not the call site, is what differs.** This is the most important design decision in cluster 7, because the ladder on a fixed backbone is 64.38 (bare-model recursion) → 71.75 (plain coding agent) → **81.36 (full-harness recursive unit)**. Make the recursive unit a **mind**, not a model call.
- **`ContextRef` — inputs by reference, never by value**: `{id, type, total_length, chunk_boundaries, accessor, taint}`. Materialisation is an explicit, budgeted operation. **Five independent derivations** — RLM's REPL variable, Cao's filesystem, LCM's immutable store with lossless pointers, Chained RLM's artifact workspace, ROMA's typed artifact signatures. This is the finding of cluster 7 and it is bigger than RLM.
- **Engine-managed operator library as the default path, free-form recursion as the escape hatch behind it.** `SPLIT / PEEK / MAP / FILTER / REDUCE / CONCAT / CROSS` (λ-RLM) ≡ `llm_map` / `agentic_map` with `input_path`, `prompt`, `output_schema`, `concurrency` (LCM). Two papers converging on the same ~seven operators from opposite directions (theory and production) is a strong signal. Deterministic, terminating, cost-predictable.

Also: **ROMA's typed input/output signatures are the better plugin seam than either a JSON tool schema or an untyped module** — swappable while type-compatible, keeping the verifiability of schemas and the expressivity of code. That is convergent with the draft's key-object decision (OPEN-04) and is an independent argument for it.

CODESKILL's add/merge/drop atomic ops and task-level-vs-event-driven granularity split. Demystifying's 12-mode taxonomy as registry telemetry. SkillClaw's maintenance-prompt discipline (**attribute the failure to skill / agent-runtime / environment *before* editing; never delete correct environment facts because the agent failed to use them**). Watch the survey's named open problem: **asymmetric revision** — the field is far better at adding skills than at safely rewriting or retiring them. And the supply-chain risk: **PoisonedSkills** shows third-party skill docs can hide malicious logic the agent later executes as trusted guidance.

**Memory.** Everything in §3.1, plus: AdMem's **expectation-vs-outcome critic** for generating a procedural-memory reward signal without an environment-native reward, its stack-based STM for sub-goal scoping, and its bandit-based retrieval-effectiveness scoring. LCM's **append-only immutable store with lossless pointers and summaries as a DAG over it** — nothing is destroyed, compaction is a view, and it is the only design in the corpus that makes an agent's history auditable after the fact. Cao's finding that **corpus layout is a first-class design decision** (folder hierarchy 89.0 vs single file 83.0) and that **retrieval-by-default is a measured regression** (89.0 → 82.0 with BM25) — default a research mind to *no retriever* and make it earn one. Chained RLM's **fresh-root checkpoint boundaries with plain-text artifact handoff** (summary + blackboard + artifacts, no host-parsed schema) as the antidote to trajectory staleness — with the kernel enforcing the read-before-finalise contract they left open.

**Loops / orchestration.** The 5-part loop specification as a literal config object (trigger, goal, execution-via-skills, verification level, named terminal states, on-disk memory) — the paper explicitly recommends exposing exactly these as first-class configuration "so that a loop's position in our taxonomy is declared rather than buried in a script." Maker–checker separation as a **structural** rule, never exhortative ("a model grading its own output is analogous to a student marking their own exam"). MANTA's bounded mutation (1 per run, ≤3 ops) and process-only auditor structurally blind to the correctness signal. ROMA's four-role node contract (Atomizer / Planner / Executor / Aggregator) and **type-specialised executors with per-type model selection** (`search` / `think` / `write` / `code`), making cost control a routing decision. Task-pressure profiling (horizon × environment × autonomy) as the configuration mechanism, with §6.3's domain-independent rules as scoped-constant policies. **External state is mandatory, complexity is optional**: "A loop without external state is a loop with amnesia… The state mechanism need not be complex — a markdown file committed to git after each iteration is often sufficient — but it must exist." And keep the anti-patterns named in QMA's own docs: *loopmaxxing*, *comprehension debt*, *reward hacking* (test deletion, metric gaming, specification narrowing, output masking).

**Eval / provenance / safety.** Everything in §3.3, plus HarnessOpt-Bench's **trusted execution boundary as infrastructure separable from optimizable content** (sandbox isolation, per-scope budget/allow-list enforcement at a gateway, mandatory candidate versioning) and its evaluation *method* — held-out test partition + normalized gain over seed, because visible-best-score is systematically optimistic. The ten-stage workflow decomposition as a checklist of where hooks must exist, notably naming **validation** and **monitoring/re-evaluation** as distinct stages between planning/tool-use and audit.

**Self-improvement.** Everything in §3.5. Sequence: build the **substrate** (typed components, structured traces, read-only boundaries, record-scope firewall) and **defer the evolver**. Three of three predicted pathologies fired in a well-instrumented system with a deterministic gate and a frontier meta-agent; QMA does not have the telemetry maturity to survive that yet. Harness–model co-evolution is closed to us entirely — it requires joint control of model training, and QMA is provider-unbiased by design.

**UI.** No paper evidence bears on one-kernel-vs-two. Everything relevant comes from the dossier. **Say so honestly in the ratified contract rather than implying research support.** The one transferable finding: sub-agent and plugin output must land in **files, logs and status records, not transient context** — "if subagent outputs only live in a transient chat context, they quickly become obsolete and hidden."

**Constants.** Validated as a concept and widened in scope: permission constants scoped over `(tool, args, environment, data class)`; the recursion envelope (`max_depth` default 1, `max_fanout`, `max_concurrent_subcalls`, token/spend/wall-clock budgets, no-progress detector) inherited and decremented — cluster 7 calls this "the cluster's best argument that scoped constants were the right call"; context budget shares `α/β/γ/δ/ε`; isolation and audit enums; loop guards and the escalation predicate; MANTA's mutation bounds; MSCE's reliability thresholds; the self-improvement capability floor. **Do not hard-code the value-density weights** — the source paper calls them "a family of deployment-specific utilities rather than a fixed metric."

## 6. OPEN QUESTIONS for the kernel ratification conversation with Mubarak

Ordered by cost-to-change-later. The first four are the ones only you can settle; the rest have a draft position but need your call.

1. **Is QMA a platform or a private system?** This is *the* question, and everything else moves with it. The evidence says a plugin architecture is a bet on third-party contribution (plugin ecosystems = 10% of 70 projects, and their adoption correlates with platform ambition at lift 2.8). If there will never be a second contributor, the honest justification for the kernel is **live reconfiguration + isolation + your "everything via the UI" requirement** — which is a real justification, just a different one. Name it out loud in the ratified contract.

2. **Does the kernel enforce budgets and the pre-action checkpoint, or not?** (Collisions C1, C2.) The draft currently says no; the evidence says optional bounds fail at scale and a checkpoint a plugin can omit is not a checkpoint. Enforcing them is a real widening of the kernel's remit and it must be a deliberate decision, not a drift.

3. **What is the primary tool-calling convention: per-call JSON dispatch, or compile-to-typed-stubs and execute one script in a sandbox?** (C6.) This decides the shape of the entire tool pipeline, the permission layer and the fan-out ceiling. It is not reversible after the pipeline ships.

4. **What does the emission table say, resource by resource?** (OPEN-07 / C9.) For an in-flight model stream whose provider is unloading; a running sandbox or subprocess; a file written into your workspace; a message already shown to you; a tool call already dispatched to a third party — for each: abort / drain / orphan / compensate, and reversible / compensable / irreversible. This is the sentence the whole safety story rests on.

5. **What must a QMA kernel buy that `folder + git + chmod + a loader + a typed component manifest with one model-call hook` does not?** (C13.) Write the answer into the contract as a paragraph — the best-evidenced system in the corpus needed only that thin substrate (baseline corrected upward on re-read, see §2.3), and any serious reviewer will ask.

6. **Is self-improvement in scope for v1 at all, and at what capability floor?** The evidence says it is net-*harmful* below a threshold, that QMA's provider-unbiasedness guarantees it will run below that threshold on cheap models, and that "evolution is a build-time activity." Draft position: build the substrate (traces, typed components, read-only boundaries, record-scope firewall), **defer the evolver**, ship it opt-in with a declared floor and an off switch.

7. **Where does the formal state substrate live, and does it get kernel budget before composition machinery does?** (§2.6.) "Topology complexity is a symptom" and "context management is the tax of implicit shared state" together predict that if we fund composition instead of queryable state, we grow the complexity the kernel was meant to prevent.

8. **Do skill promotion and plugin registration share one primitive?** (C8.) MSCE says they are structurally the same operation. Sharing it means more kernel surface than B.8 currently allows; not sharing it means two governance systems that will drift.

9. **What is the bound on model-authored plugins?** (OPEN-08 / C7.) Quota on live dynamic plugins per mind, depth limit on plugins-that-define-plugins, and a loud recorded refusal at the ceiling. Draft position: this is a **ship-blocker** for the self-modification tools, not an open item.

10. **Does the kernel carry a `taint` field and derive isolation level from it?** (§3.3.) A web-reading mind that writes and executes code is a live injection-to-execution path, and the field's own reference implementation ships a default sandbox that runs `exec` in the host process. Draft position: yes, non-negotiable before any web-reading mind ships.

11. **Does the kernel own the canonical trace schema, with the store as a plugin?** (C3.) Draft position: yes — schema and emission obligation in the kernel, store and retention on the durable bus.

12. **Do event keys carry declared permitted modifications, validated after every invocation?** (C14.) Cheap now, effectively impossible to retrofit once third-party plugins depend on current hook behaviour.

13. **What is the second acceptance test?** (C13.) Proposal: "the kernel must beat `sandbox + filesystem + shell + code-exec + git` on at least one real QMA task before further kernel investment is authorised" — a falsifiable gate rather than an aspiration.

14. **Do we adopt `Σ = (p, m, T, g)` as the definition of a mind?** Prompts, memory, tools, and control logic **including safety constraints**, separated from the ephemeral run state discarded at task boundaries. It is the cleanest definition of a "deployable semi-profile" in the corpus and it is substrate-agnostic by construction. If yes, it should shape serialization, portability and versioning before any of those are built.
