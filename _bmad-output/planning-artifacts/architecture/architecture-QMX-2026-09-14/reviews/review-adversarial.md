# Adversary review — workbench spine

## Method

For each local AD I built **two conforming units one level down** — the epics a connect-wave factory lane would actually spawn (QMB results/CLI, QMA door/persistence, QML generation, Library query, What-if, procedures, notebooks) — and asked whether both can obey every written Rule, plus every inherited parent Rule, and still be unable to assemble. Only pairs where **both readings are literal** are reported. Deferred rows count when v1 must already pick a shape. Every finding ends with paste-ready Rule text.

Parent spines bind read-only (QMF AD-1..41, QMB B-1..B-15, QML QL-1..QL-10, TN-1..TN-25, QMA AD-1..AD-29, CONNECT AD-1..AD-5). A local AD that forces a parent-container fork is a hole, not a license.

## Verdict

**Return for amendment — do not freeze connect-wave epics.** Intent is tight: no sixth application, three lanes, generation ≠ search, two analysis methods, no QMA-paper, no cloned databank store. The AD set fails at the joints those epics would implement. Four load-bearing joints let two conforming units ship incompatible products: the analysis artifact has no kind/owner/identity (and AD-5 contradicts itself on rescale vs `starting_capital`); `lane` has no stamper and ExperimentSpec/CT-32/ungoverned values are three identities for one experiment; AD-9's "invoke QMB library functions" collides with AD-2's "never import qmb", yielding two job-state writers; candidate identity has three homes and generation has two mint paths despite AD-4 claiming ownership is decided. Two more highs poison evidence labels forever (claim-class vs B-4 role vs AD-12 evidence class) and the dual-ledger/`CT-07` write. Connect-wave (door, Library projections, named analysis, CLI coverage) is exactly the work that will fork if these stay open.

Pairs that could **not** be made to diverge (closures that hold): a sixth application package; a generator inside QMB's tunnel; QMA-paper / an execution tool; a QuantDataManager clone store; a copied-row databank table; QMA `import qmb` inside the daemon or `analysis-backtest` plugin; treating node-paper as research-paper if the builder stays on AD-7's three names. Those are not the problem. The problem is the named objects the spine introduces without a home.

## CRITICAL

### C-1 — AD-5 × AD-3 × AD-14 × AD-1: the analysis artifact has no kind, no owner, no identity, and AD-5 names two opposite methods for the same rescale

**Unit A — What-if / QMB results epic.** Reads the capability map ("What-if lives in QMB results") and B-1 ("every capability exists once, in the library"). Ships `qmb.analysis.project` as a library function that writes a **new CT-32** with `analysis_method=projection` and AD-15 `claim-class=projection`. Path-dependent What-if is `spawn_governed` of a new resolved config; that CT-32 carries `analysis_method=path-dependent`. Equity rescale that changes displayed `starting_capital` is projection because AD-5's projection clause is "read-time filter/**rescale** of a cited CT-29/CT-32 stream". Saved output lives in the run directory beside the source CT-32 (not a new store — AD-1).

**Unit B — What-if / QMA query epic.** Reads AD-3 (Library is a projection over fp1 kinds), AD-14 (saved views cite fingerprints and predicates, **not duplicated payloads**), and QMA AD-14 (`BacktestHandle` / `TradeLogHandle` are the Analysis-desk read path). Ships What-if as a QMA query over a cited CT-32: the analysis "artifact" is a **saved view** in daemon sqlite (Experiment Ledger note + predicate JSON). No new CT-32, because CT-32 is parent-owned by COMP-QMF-RISK (QMF AD-41) and does not have `analysis_method` or AD-15 `claim-class` fields. `starting_capital` change is **path-dependent** because AD-5's path-dependent clause lists `starting_capital` and B-3 makes it the binding's virtual-ledger seed. Rescale of an equity series that implies a different seed is refused as projection (AD-6: "trade-list rescaling posing as Book simulation").

Both obey every AD. What diverges:

- **Shape.** A's published What-if is a CT-32 sibling (second performance-result for one run). B's is a predicate document. A Library query (AD-3) returns a result in A and a view in B.
- **Owner.** COMP-QMB vs COMP-QMA-DAEMON. B-1 door parity then forces A's function onto CLI/API/MCP; B never appears on `qmb` doors at all.
- **Parent fork.** A mutates CT-32's schema (lane/method/claim-class) without a QMF amendment. B does not. The two artifacts cannot join.
- **Numbers.** Same trade list, new starting capital: A rescales equity in-place (projection); B re-runs the tunnel (path-dependent). Different CT-29 streams, different fingerprints, both honestly labelled.
- **Store.** A's run-dir files vs B's sqlite vs a third unit stuffing views into `qmf-registry` as a new kind (AD-3's list does not include one; AD-1 forbids a store beside registry/data). AD-14 requires saved views to exist and forbids copied payloads; it never names a home.

AD-13's "quality surfaces are projections" mints a second, unrelated `projection` noun over CT-13/`gap_check`. A third unit stamps those as AD-5 analysis artifacts; a fourth does not. Same hole, data epic.

**Tightened Rule (replace AD-5; add a sentence to AD-3 and AD-14).**

> **AD-5.** Exactly two methods. **Projection** is a COMP-QMB library function (`analysis.project`) over one cited CT-32 and its CT-29 stream. Output is a **saved view**, not a CT-32: identity is `fp1` of the canonical JSON `{method: projection, source_ct32, source_ct29, predicate, as_of}`. The view stores the predicate and cites, never a copied trade list or rescaled measure set. Publishing appends that `fp1` to the QMA Experiment Ledger when a coordinated experiment exists; otherwise the function returns the view value and writes no ledger (AD-2 ungoverned). Claim-class is always `projection`; it is never admission evidence. **Path-dependent** is a new QMB run through the tunnel (new resolved run-config: Book/BMS fragments, fill/cost/financing ports, `starting_capital`). Its canonical artifact **is** the new CT-32. `analysis_method` and `lane` are **not** CT-32 fields (CT-32 stays parent-shaped). They live on the QMB ledger line (governed) and/or the Experiment Ledger entry (coordinated) as metadata citing the CT-32 by `_ref`.
>
> Changes to `starting_capital`, Book/BMS fragments, or execution ports are always path-dependent. Read-time filter of hours/days/max-trades, and display-only equity rescale that does **not** change the binding seed, are projection. Combining two bots' equity/trade streams into a synthetic portfolio is neither method — refused here; F07 stays deferred. `analysis.project` / `analysis.rerun` exist once in the QMB library; doors wrap them (B-1). QMA queries may **call** those functions and persist refs; they may not reimplement the filter.
>
> **AD-3 addendum.** Saved views and analysis publications are not registry kinds. They do not appear on the shared-object list as a new fp1 kind. Library search returns them only as query hits citing the source kind's `fp1`.
>
> **AD-14 addendum.** A saved view's home is: QMB-returned value (ungoverned); QMB run-dir sidecar citing `fp1` (governed, no new store); Experiment Ledger entry citing the same `fp1` (coordinated). Not `qmf-registry`, not a new sqlite table, not QMA staging.

### C-2 — AD-2 × AD-8 × B-10: `lane` has no stamper; ExperimentSpec, CT-32, and returned values are three identities for one experiment

**Unit A — QMB orchestrator / CLI epic.** AD-2: governed = QMB orchestrator, one ledger line, CT-32. Structural seed: `DOOR → ORC`. The orchestrator cannot see QMA, so every orchestrator-written ledger line and CT-32 is `lane=governed`. Ungoverned `qmb.run()` returns a CT-32 value and writes a sidecar JSON with `lane=ungoverned` because "stamped on every experiment artifact" and the return value **is** the artifact (B-10: every run emits one CT-32). Coordinated is QMA's problem: ExperimentSpec records `lane=coordinated` separately. Join is optional.

**Unit B — QMA door / ExperimentSpec epic.** Capability map: "Experiment identity = ExperimentSpec + Experiment Ledger". AD-3 lists CT-47 ExperimentSpec as a shared Library object. AD-8 binds persistence of ExperimentSpec through the daemon. B registers an ExperimentSpec for **every** experiment including notebook `import qmb` (identity must exist for the Library). It passes `--lane=coordinated` (or `ungoverned`) into the CLI because the stamp must land on the CT-32 the UI will show. QMB accepts a caller-declared lane (AD-2 says UI and agents **select** a lane). Ungoverned notebooks that never talk to QMA are identity-less and do not appear in Library search.

Both obey. What diverges:

- **One coordinated backtest, two lanes.** A's CT-32/ledger say `governed`; B's ExperimentSpec says `coordinated`. A Library filter `lane=coordinated` is empty against A and full against B.
- **Caller-declared vs derived.** B's flag lets a notebook stamp `coordinated` without QMA (a fourth door in practice). A's hardcode makes the CT-47 door indistinguishable from `qmb backtest` in QMB evidence.
- **Ungoverned identity.** A manufactures an artifact (contradicts "writes no ledger" if the sidecar is durable; if it is not durable, Library cannot cite it). B omits ungoverned work from the shared Library (contradicts AD-3 if the user expects one identity).
- **CT-47 schema.** ExperimentSpec fields are `code_ref`, `resolved_config_ref`, `data_ref`, `environment_ref`, seed, harness, cost, lineage, ledger ref — **no `lane`**. B extends CT-47. A does not. Two ExperimentSpec shapes.
- **Who is "the experiment"?** A: the CT-32 fingerprint (B-10, B-3 run id). B: the ExperimentSpec `fp1` (CT-47). AD-3 lists both as shared objects with no primary key. UI tabs (AD-3 "UX over those fingerprints") bind to different ids.

Inherited QMA AD-6 already says QMB's run ledger is reached by `_ref` and never merged. AD-2's stamp law does not say which side of that `_ref` carries `lane`.

**Tightened Rule (replace AD-2's stamp sentence; add identity law).**

> Exactly three lanes, selected by **which door is called**, never by a flag on a payload:
> 1. **ungoverned** — `qmb.run()` / ordinary Python / `import qml` on a controlled-room host. Returns values. Writes no QMB ledger line, no CT-32 registry record, no ExperimentSpec. It is not a Library object. Graduation to governed evidence is an explicit later orchestrator spawn (L33).
> 2. **governed** — QMB orchestrator spawn **not** placed by the CT-47 door (CLI/API `spawn_governed`, including path-dependent `analysis.rerun`). One QMB ledger line, one CT-32. No ExperimentSpec.
> 3. **coordinated** — QMA Backtesting Service places at most one `qmb` CLI/MCP invocation per ExecutionEnvironment and never `import qmb`. Requires a registered ExperimentSpec. The QMB ledger line and CT-32 of the spawned run are the evidence (`_ref` from the Experiment Ledger). QMA does not copy them.
>
> `lane` is **derived** from the door and is recorded only on: the QMB ledger line (`governed` for every orchestrator spawn, including those placed by QMA — it names the evidence class of that line) and the Experiment Ledger entry (`coordinated` when QMA placed it). CT-32 is not extended. ExperimentSpec exists only in the coordinated lane. UI/agents select a lane by calling `run` / `spawn_governed` / QMA backtest tool; a fourth call path is a spine amendment.

### C-3 — AD-9 × AD-2 × AD-8 × AD-10: procedure steps "invoke QMB library functions" while coordinated QMA "never import qmb" — two invocation paths, two occupancy counts, two cancel writers

**Unit A — procedures / Graph Template epic.** AD-9: "steps invoke existing QMB library functions (backtest, optimize, sweep, robustness, data)". A QMA worker ExecutionEnvironment (AD-11 allows `import qmb` on a controlled-room host; AD-28 denies `qmf-venue`, not `qmb`) **imports qmb** and calls `robustness.run_trade_shuffle`, `data.gap_check`, `analysis.project` in-process. The daemon itself does not import qmb, so AD-2's "QMA … never import qmb" holds of the daemon package. Occupancy "one `qmb` job per environment" applies to the CT-47 **backtest** door only (AD-8 / parent QMA AD-17). Data and analysis steps do not take a JobHandle. Cancel is the worker process. QMB orchestrator lifetime is those in-process calls.

**Unit B — procedures / CT-47 door epic.** AD-2 coordinated: QMA places at most one `qmb` job per env and never `import qmb`. Plugins already must not import qmb. Every AD-9 step is a CLI invocation through the single door (`qmb backtest|optimize|sweep|robustness|data|analysis …`). Occupancy counts **every** such invocation. A Custom-Project-shaped template cannot overlap `data.download` with a sweep on the same env. Job state is QMA `JobHandle` (AD-10 continuation, parent AD-17). Cancel is `JobHandle.cancel` mapped to QMB abort. A sweep's child processes are internal to the one CLI job (AD-8 "QMB keeps intra-node parallelism").

Both obey. What diverges:

- **Mutation path.** A's robustness run never appears as a JobHandle and is invisible to laptop-off continuation (AD-10). B's is a durable job. Same Graph Template, two continuation stories.
- **Occupancy.** A runs analysis.project in-process during an in-flight backtest. B refuses the second `qmb` invocation. One template deadlocks on B and sails on A.
- **Import law.** A's worker image contains `qmb` (and therefore the tunnel). B's worker image does not; only the door-spawned CLI process does. Two images, both "QMA ExecutionEnvironment".
- **Cancel.** Tab-close cancels nothing (AD-10). What does? A: nothing unless the worker dies. B: JobHandle. A third unit binds UI Stop to `qmb abort` (B-5 cancel token) without QMA, leaving JobHandle `running` and ledger `aborted`. Two terminal states for one job.
- **"qmb job".** CLI parent vs each B-5 child vs JobHandle vs Experiment Ledger entry. AD-8 says both "one job per environment" and "QMB keeps intra-node parallelism" without defining job.

**Tightened Rule (replace AD-9's invoke sentence; pin occupancy and cancel on AD-8/AD-10).**

> **AD-9.** Reusable procedures are QMA Graph Templates, Skills, and operator Routines. QMB does not grow a task graph. A step that names a QMB capability (backtest, optimize, sweep, robustness, data, `analysis.project`, `analysis.rerun`) is **placed through the CT-47 `qmb` door as one CLI/MCP invocation**. The daemon, every plugin, and every QMA worker image never `import qmb`. The CLI process is QMB; in-process library calls from QMA are a spine amendment. Composition stays non-linear: any step in the intent set may be the first door placement. SQ Custom Projects remain a donor shape, not a clone.
>
> One Graph Template instantiation is one Mission. Each door step that changes resolved-config is an ExperimentSpec successor (`create_successor` + CT-07 `branches-from`); the procedure is not itself an ExperimentSpec.
>
> **AD-8 occupancy.** One `qmb` invocation per ExecutionEnvironment. QMB's process-per-run children inside that invocation are not additional QMA jobs and do not consume occupancy. Data/analysis/robustness CLI invocations **are** `qmb` jobs and do consume occupancy.
>
> **AD-10 cancel.** Coordinated cancel authority is `JobHandle.cancel` only; the door maps it to QMB abort and the QMB ledger writes `aborted`. Governed-without-QMA cancel is QMB abort only. Ungoverned cancel is process death and writes nothing. UI tab-close remains a no-op. No other writer may set a terminal JobHandle or ledger state.

### C-4 — AD-3 × AD-4 × AD-6 × AD-14: three homes for "candidate", two mint paths for one generated bot

**Unit A — generation / QML epic.** AD-4: generation authors new CT-33/CT-34 and/or logic-source via QML; "QML authors; registry owns; QMB runs". A uses `mint_bot_definition` + host CT-06 envelope (QL composition-root, already the parent pattern). Identity is the CT-33 `fp1`. QMA `StrategyHandle` is a display alias over that fingerprint (AD-3 "display aliases are UX"). Book/BMS variants (AD-6) are likewise full CT-22/CT-27 documents written into the registry `dev` zone by the same composition root. QMA staging is unused for bots (parent QMA AD-22: RefinementProposal pipeline never reaches `qmf-registry`).

**Unit B — generation / QMA StrategyHandle epic.** AD-4: "QMA holds `StrategyHandle` / lineage". Parent QMA AD-14: `StrategyHandle` **creates** content-addressed candidates in the `dev` zone. AD-6: QMA emits `money_path_relevant` candidates with a field-level diff. B has QMA assemble CT-33 JSON from producer templates (QML templates already exist; placeholder-fill is the open question, not forbidden) and `StrategyHandle.create(candidate)`. Identity is the handle id plus QMA `origin` field; registry `fp1` appears at create. Book variants are **diffs only** (AD-6 "field-level diff"); the full CT-22 is reconstructed at read time. AD-14 candidate-set query also reads QMA staging (the AD literally says "QMA staging / `dev`-zone candidates"), so a RefinementProposal for a skill and a CT-33 candidate appear in one databank.

Both obey. What diverges:

- **Two owners of one bot.** A's Library key is CT-33 `fp1`. B's is `StrategyHandle`. Same bytes, two records, the thing AD-3 exists to prevent ("one bot/result existing as three records").
- **Write path.** QML host mint vs QMA candidate write. Parent QMA AD-2 allows only the candidate write through `qmf-registry` and forbids constructing a Book; AD-6 requires a CT-22 candidate. A reads the forbid and refuses agent-authored Book candidates (human fills qmf-risk, QMA holds a handle). B reads AD-6 and writes Book-shaped JSON to `dev`. One unit cannot consume the other's Book variant.
- **Full document vs patch.** A's CT-22 candidate is a complete fingerprinted definition. B's is a diff against a parent `fp1`. Replay (AD-6 "QMB governed replay citing that fingerprint") has nothing to cite in B until someone materializes the document; A cites immediately.
- **Staging vs dev zone.** AD-3 and AD-14 treat them as one bag. Parent QMA AD-22: staging is RefinementProposals (`prompt|memory|skill|…`), never bots/Books, and never reaches registry. A databank query that unions them is a type error in A and a feature in B.
- **AD-4's "ownership is no longer undecided"** decides the *noun* owner (QML) and not the *write* owner. The open-question row ("placeholder-fill vs Python-logic synthesis") lets both units ship as "generation". Search vs generation then collapses: B's template-fill is parameter-adjacent work QMA should not do; A's logic synthesis never happens in connect-wave, so B becomes the de facto generator.

**Tightened Rule (replace AD-3's object list, AD-4 write path, AD-6 candidate, AD-14 sources).**

> **AD-3.** Shared Library objects are exactly these existing kinds, cited by `fp1`: CT-33 bot, CT-34 confluence, strategy-family (CT-06 metadata kind), CT-22 Book, CT-27 BMS, CT-28 binding, CT-12 split, CT-10 observation, CT-32 result, CT-47 ExperimentSpec (coordinated only). Logic source-manifests are cited from CT-33, not a separate Library kind. **Not** Library objects: QMA staging/RefinementProposals, JobHandles, Graph Templates, Skills, Routines, saved views, analysis publications, derived datasets (those have homes below). Work-environment tabs and display aliases are UX over those fingerprints. STRATS is a KnowledgeSource corpus (QMA AD-19); it does not write registry kinds.
>
> **AD-4 write path.** Search varies declared CT-33 parameters (QMB optimize/sweep, B-8) and writes trial ledger lines citing the **same** bot `fp1`. Generation, if built, authors new CT-33/CT-34 content and/or logic-source **bytes via QML**. The QML/host composition root mints the CT-06 envelope. QMA `StrategyHandle` may only (1) reference an already-fingerprinted registry record and (2) register those bytes as a `dev`-zone candidate with a QMA `origin` field and a CT-07 predecessor edge. QMA never assembles CT-33/CT-34 JSON, never mints mechanism nouns, never fills RandomCondition slots. Placeholder-fill vs logic synthesis is a later QML increment; neither ships as a QMA step.
>
> **AD-6.** A proposed Book/BMS version is a **complete** new fingerprinted CT-22/CT-27 document in the registry `dev` zone (not a patch record). QMA may emit it only as a `money_path_relevant` candidate whose `approval_request` carries the field-level diff against the predecessor; QMA never fills an unset money-path field. Shape owner remains QMF Risk; mint remains the composition-root pattern (same as CT-33). Path-dependent evaluation is a QMB governed (or coordinated) replay citing that fingerprint.
>
> **AD-14.** Retain/filter/rank is a read-time view over (1) QMB ledger lines, (2) registry as-of sets including `dev`-zone candidates of Library kinds, (3) coordinated Experiment Ledger refs. It does **not** read QMA staging. `sweep.rank` is this view; it publishes no copied-row artifact.

### H-2 — AD-15 vs B-4 role vs B-7 claim class vs AD-12 evidence class: four stamps, one English word "confirmation"

**Unit A — results labelling epic.** Treats AD-15 `claim-class` as the single field on CT-32/analysis artifacts. Extends B-4's closed role enum with `projection | robustness | infra-stress`. A robustness MC ledgers `role=robustness`. A confirmation backtest ledgers `claim-class=confirmation` and drops AD-12 evidence class (`confirmed|unconfirmed|provisional`) as a synonym.

**Unit B — parent-preserving epic.** Keeps B-4 role ∈ `{confirmation, trial, replicate, aborted}` on every QMB ledger line. Keeps B-7 claim class as a distinct label field (robustness-only / infra-stress on procedure runs). Keeps AD-12 evidence class on CT-32. AD-15 `claim-class` exists only on **published analysis** (projection views and path-dependent wraps). A robustness MC is `role=replicate` + B-7 claim class `robustness` and has no AD-15 field unless someone publishes it.

Both conform: AD-15 says "every published analysis"; B-4 says every orchestrator line carries a discriminated run role; B-7 says claim class is distinct from world; CT-32 already carries evidence class. UI filter "confirmation" matches A's robustness-excluding set, B's B-4 role set, or AD-12 `confirmed` — three different populations. A parent-illegal CT-32 lands in A.

**Tightened Rule (replace AD-15).**

> Do not extend CT-32 or B-4. Mapping is total:
> | Object | B-4 role (ledger line) | B-7 / AD-15 claim-class | AD-12 evidence class |
> | --- | --- | --- | --- |
> | Governed/coordinated confirmation run | `confirmation` | (absent; not an analysis) | as AD-12 |
> | Optimize trial / sweep combo | `trial` | (absent) | as AD-12 |
> | MC / WF replicate | `replicate` | `robustness` or `infra-stress` on the procedure label (B-7, B-14) | as AD-12 |
> | Aborted | `aborted` | (absent) | as AD-12 |
> | Projection saved view | none (not a run) | `projection` | inherit source world; never `confirmed` |
> | Path-dependent re-run | B-4 role of **that** run | stamp AD-15 only if published as analysis; still not admission evidence unless `role=confirmation` |
>
> Confirmation evidence remains B-4 `role=confirmation` only. L20 stands. Replay-world verdicts still cannot gate live money. "Published analysis" = a saved view or an Experiment Ledger `analysis.published` entry, not every CT-32.
