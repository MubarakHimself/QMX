# Bot Frameworks — lumibot, qtpylib, and a QuantLib skim

**Scope of this study:** `reference/repos/lumibot` (deep), `reference/repos/qtpylib` (deep, with a focus on why it went stale), `reference/repos/QuantLib` (structure/concepts skim only — C++, huge). Written for the QMF minimal-core design session; complements `research/00-qmf-synthesis-module-map.md`, which already proposes "the simulator is just another `BrokerAdapter`" as QMF's own architecture (Ring 5/6, Novel idea #2). This study exists to check that claim against a framework that actually ships it at scale (lumibot) and one that never separated the two at all (qtpylib) — and to note what, if anything, QMF needs from the bond-market machinery in QuantLib.

---

## In plain words

Lumibot is a currently-and-heavily maintained (commits as recent as August 2026) trading framework built around one strong idea: a strategy is just a handful of named methods — "before the market opens," "on each trading iteration," "when an order fills" — and the framework decides when to call them, whether the clock is real or simulated. The exact same strategy class runs against a live broker or against a backtest driver without being rewritten, because both the broker and the clock are swappable parts behind one shared interface. That is the single most useful thing in this repo for QMF: proof, at production scale with a real commercial user base, that "no separate backtest engine, just another broker/clock pair" actually works and stays maintainable for years.

qtpylib is the cautionary tale. It is the same idea half-built: it does have a live/backtest switch and an indicator/broker split, but the strategy class directly *inherits* from the broker class, so a strategy and its venue are welded together in one Python class hierarchy — you cannot test a strategy without also standing up a broker connection, live or fake. Worse, it needs two extra always-on services just to run at all: a MySQL server for trade logging and a ZeroMQ message bus between the data-recording process and the trading process. Its only supported venue is Interactive Brokers, reached through two now-unmaintained community wrapper libraries the project never controlled. When those broke, or IB changed its API, qtpylib had no path forward — and its last release was November 2019. It is a clean example of what happens when a solo project's plumbing (message bus, database server, SMS gateway, bundled web app) outweighs its actual trading logic: the parts hardest to keep patched turn out to be the parts least related to the edge.

QuantLib is a different animal entirely — a 25-year-old C++ library for pricing bonds, swaps and derivatives, not a trading bot. It is included here only because two of its idioms recur in every serious quant codebase: a **Calendar** (which named holiday/business-day rule applies to a venue) and a **DayCounter** (which named year-fraction convention — Actual/360, Actual/365, 30/360 — applies to an interest calculation), both looked up by name rather than hand-coded as date arithmetic. QMF needs a thin version of both for forex swap/rollover math and session gating, and nothing else QuantLib offers — the rest (yield curve bootstrapping, exotic option pricing, the whole `Handle<T>` observer-pattern machinery for relinking market quotes) is out of scope for a solo forex/crypto operator and would be wildly disproportionate to adopt.

## How it is built

### lumibot

**Licence: GPL-3.0** (`reference/repos/lumibot/LICENSE`). Design-study only per the standing licence policy — nothing here should be copied verbatim into QMF.

Module layout (`reference/repos/lumibot/lumibot/`):

- `traders/trader.py` — the process entry point. `Trader.run_all()` refuses to mix backtest and live strategies in one run (`is_backtest_broker != self.backtest` raises), starts one `StrategyExecutor` thread per strategy, joins them, and re-raises any exception the thread captured (`lumibot/traders/trader.py:155-172, 224-231, 422-431`).
- `strategies/strategy_executor.py` — a `Thread` subclass that owns the per-strategy control loop; it wraps the user's `on_trading_iteration` in an "append locals" decorator for debugger-friendly tracebacks (`strategy_executor.py:126-202`), and gates iteration logging/locals-capture behind `IS_BACKTESTING_BROKER` so a million-iteration backtest doesn't drown in per-tick logs (`strategy_executor.py:185-202`).
- `strategies/session_manager.py` — the actual live/backtest switch. `SessionManager(ABC)` defines `should_continue_session()`, `advance_time()`, `execute_trading_cycle()`, `wait_for_next_cycle()`, `run_session()` (`session_manager.py:33-124`). `BacktestingSession` and `LiveTradingSession` are two full implementations of that same interface (`session_manager.py:131-330`) — one steps a simulated clock forward in fixed increments, the other sleeps a real wall clock and waits on real market-open/close boundaries. Nothing in the strategy or executor code needs to know which one it's driving.
- `strategies/strategy.py` — the ~5,900-line surface a strategy author actually touches. The entire authoring contract is a fixed set of lifecycle hooks the framework calls: `before_market_opens`, `before_starting_trading`, `on_trading_iteration`, `before_market_closes`, `after_market_closes`, `on_abrupt_closing`, `on_new_order`, `on_canceled_order`, `on_partially_filled_order`, `on_filled_order`, plus `trace_stats` for per-iteration telemetry (`strategy.py:5286-5680`). A strategy never owns a loop; it only fills in named callbacks.
- `brokers/broker.py` — `class Broker(ABC)` with `IS_BACKTESTING_BROKER = False` as a class attribute (`broker.py:173-175`), and roughly a dozen `@abstractmethod` hooks any concrete broker must implement: `_submit_order`, `_modify_order`, `cancel_order`, `_get_balances_at_broker`, `_get_stream_object`/`_register_stream_events`/`_run_stream`, `_pull_positions`/`_pull_position`, `_parse_broker_order`/`_pull_broker_order` (`broker.py:893-1040`). `IS_BACKTESTING_BROKER` is then checked at 15+ call sites throughout the same file to gate backtest-only behaviour (locking strategy, trade-log retention, rate limiting, telemetry — e.g. `broker.py:469, 477, 501, 553, 735, 1104, 1272, 1352, 1496, 1527, 1564, 1663, 2030, 3005, 3282, 3338`) — one boolean, one place, instead of parallel code paths.
- `backtesting/backtesting_broker.py` — a 5,008-line concrete `Broker` subclass with `IS_BACKTESTING_BROKER = True` that implements the exact same abstract hooks a live broker does, sourcing fills from historical bars instead of a venue connection. Fourteen other files in `backtesting/` (`alpaca_backtesting.py`, `polygon_backtesting.py`, `databento_backtesting_polars.py`, etc.) are thin data-source variants layered on top of this one broker.
- `data_sources/` — one file per vendor (Alpaca, IBKR REST, Schwab, Tradier, Polygon, Yahoo, DataBento, ccxt…), each implementing a common `DataSource` interface (`data_sources/data_source.py`, 1,253 lines) so `get_historical_prices` and similar calls are vendor-blind from the strategy's point of view.
- `entities/` — `Order` (1,578 lines — order types, legs, statuses), `Asset` (911 lines — the venue-neutral instrument description), `Position`, `Bar`/`Bars`, `Quote`, `TradingFee`/`TradingSlippage` as explicit typed models a strategy manipulates instead of vendor dicts.
- Lazy-import shell: `lumibot/_lazy_imports.py` provides `LazyLogger`, `LazyModule`, `lazy_class`, used at the top of `brokers/broker.py:11` and `strategies/strategy_executor.py:9` to defer importing pandas, `pandas_market_calendars`, `dateutil`, etc. until actually touched. This keeps the always-on trading process's import graph — and by extension its dependency surface — thinner than a strategy that pulls in the full analysis stack.

Event flow, end to end: `Trader.run_all()` → one `StrategyExecutor` thread per strategy → a `SessionManager` (backtest or live) drives `advance_time()`/`execute_trading_cycle()` → the cycle calls the strategy's lifecycle hooks in order → any order placed goes through the `Broker` ABC → either a real venue adapter or `BacktestingBroker` fills it against historical bars → fills come back through `on_filled_order`/`on_partially_filled_order` → `Position`/`Order` entities are updated → `trace_stats` records the per-iteration snapshot used for the tearsheet.

**Maturity note beyond the licence:** `reference/repos/lumibot/CLAUDE.md` (the repo's own AI-agent operating instructions, read in full before writing this section) documents a live commercial operation around this code — version-branch discipline (`version/X.Y.Z`), a deploy pipeline (`BotSpot`/`Lumiwealth`), and a standing **"RULE #1 — NEVER FABRICATE BACKTEST DATA"** born from real incidents: missing bars must come back empty, never interpolated or carry-forwarded, because a backtest built on fabricated data produces fabricated P&L. The same document records a fixed bug where a corporate-action adjustment function was applied 26+ times per backtest because it had no idempotency guard, and the fix was a marker column (`_split_adjusted`) so the transform refuses to re-apply. `CHANGELOG.md:1-10` shows a deploy dated 2026-08-05, nine days before this study's date — this project is not abandoned, it is under active, disciplined, multi-agent development.

### qtpylib

**Licence: Apache-2.0** (`reference/repos/qtpylib/LICENSE.txt`), despite `setup.py:31` still saying `license='LGPL'` — a small internal inconsistency, itself a maintenance smell. Apache-2.0 means code reuse would be legally fine; it is skipped here anyway because the design is the cautionary example, not something to adopt.

Module layout (`reference/repos/qtpylib/qtpylib/`):

- `algo.py` — `class Algo(Broker)` (`algo.py:59`). The strategy base class **inherits from** the broker class rather than holding one by composition. A strategy author subclasses `Algo` and implements four abstract hooks: `on_start`, `on_tick(instrument)`, `on_bar(instrument)`, `on_orderbook(instrument)` (`algo.py:416-491`). Because `Algo` *is a* `Broker`, there is no way to unit-test strategy logic without also instantiating (or fully mocking) a live/paper IB connection, and no way to point the same strategy class at a second venue without rewriting the inheritance chain.
- `broker.py` — `class Broker()` (not an ABC) wraps `ezibpy`/`ibpy2` to talk to Interactive Brokers' TWS/Gateway socket API, and separately opens a `pymysql` connection to log trades (`broker.py:37, 61, 180-182`).
- `blotter.py` — a **separate long-running process**, not a library call. It imports `zmq` and `pymysql` (`blotter.py:38,42-43`), subscribes to IB's tick stream via ezIBpy, republishes every tick/bar over a ZeroMQ PUB socket on a configurable port (default topic `_qtpylib_<name>_`, `blotter.py:123,162-163`), and writes every tick/bar into a MySQL database (`blotter.py:704-729`) using a hand-rolled thread pool decorator (`asynctools.multitasking`, `blotter.py:75, 403, 470, 518, 592, 608`). The `Algo` process is a separate OS process that subscribes to this ZeroMQ feed.
- `talib_indicators.py` / `indicators.py` — thin TA-Lib wrappers and pandas-based indicator helpers, unremarkable.
- `_webapp/` — a bundled Flask dashboard shipped inside the library itself.
- `sms.py` — Twilio and Nexmo integrations for trade alerts (`requirements.txt`: `nexmo>=1.2.0`, `twilio>=6.0.0`).
- `requirements.txt` pins `ibpy2>=0.8.0` and `ezibpy>=1.12.66` — two third-party, non-Interactive-Brokers-maintained wrappers around IB's legacy TWS socket API. Both had already gone quiet years before qtpylib's own last release.
- Minimum supported Python is 3.4 (`algo.py:43-44`) — a version whose own end-of-life predates qtpylib's last commit by years.
- `CHANGELOG.rst:1-9` — last entry is `1.5.84`, dated **November 10, 2019**. No activity since.

Event flow: `Blotter` process (own MySQL connection, own ZeroMQ publisher) ↔ `Algo` process (subscribes via ZeroMQ, buffers ticks/bars into pandas windows, calls the user's `on_tick`/`on_bar`, and — because `Algo` inherits `Broker` — places orders by calling its own inherited broker methods directly against the same IB connection the Blotter also opened).

### QuantLib (skim only — C++, structure and concepts)

**Licence: BSD-3-Clause (QuantLib License)** — permissive, but this is a ~25-year-old, extremely large (`ql/` contains hundreds of files across `time/`, `cashflows/`, `pricingengines/`, `termstructures/`, `experimental/`, etc.) fixed-income/derivatives pricing library, not a trading bot framework, and C++ rather than Python. Two idioms are worth naming, everything else is out of scope:

- **`Calendar`** (`ql/time/calendar.hpp`) — a named business-day/holiday rule per country or exchange, looked up by name, with dozens of concrete calendars shipped under `ql/time/calendars/` (Argentina, Australia, Brazil, China, and so on). Business-day *conventions* (how to roll a date that lands on a holiday) are a separate, composable enum (`ql/time/businessdayconvention.hpp`).
- **`DayCounter`** (`ql/time/daycounter.hpp`, concrete implementations under `ql/time/daycounters/`: `Actual360`, `Actual365Fixed`, `Actual366`, `ActualActual`, `Thirty360`, `Business252`, …) — a named convention for turning a date range into a year-fraction, used everywhere an interest amount is computed.
- **`Quote` / `Handle<T>`** (`ql/quote.hpp`, `ql/handle.hpp`) — `Quote` is a purely virtual "current market observable" (`value()`, `isValid()`); `Handle<T>` is a relinkable smart pointer so a pricing object can hold a reference to "whatever the current EUR/USD spot quote is" and have every downstream calculation update automatically when that quote is relinked to a new source, without rebuilding the dependent objects (`quote.hpp:38-48`).

**What QMF needs from this world:** a Calendar-and-DayCounter *pattern*, not QuantLib's code or its scope. Forex swap/rollover and crypto funding math need a named day-count convention (typically ACT/365 or ACT/360 depending on venue) and a named trading-session calendar per venue, both resolved by ID rather than hardcoded as inline date arithmetic — a few dozen lines, not a dependency. The `Handle<T>` relinking pattern is elegant but solves a problem (many pricing objects sharing one live-updating market quote inside a single pricing run) that QMF's event-driven, single-clock architecture doesn't have; it is not worth adopting.

## Mental models worth borrowing

1. **One `Broker` interface, and the simulator is just implementation #2.** `lumibot/brokers/broker.py:893-1040` defines the abstract contract (`_submit_order`, `_pull_positions`, `_parse_broker_order`, streaming hooks, balance queries); `lumibot/backtesting/backtesting_broker.py` is a 5,008-line concrete subclass of the *same* ABC. Every other broker (Alpaca, IBKR, Tradier, Schwab…) implements the identical contract. This is lumibot at production scale proving the exact claim QMF's own synthesis doc already commits to (`qmf.sim.SimBroker` as an ordinary `BrokerAdapter`) — worth citing as validation, not a new idea, when the design session revisits that decision.

2. **A swappable "session driver" behind one ABC decides how time advances, not the strategy.** `lumibot/strategies/session_manager.py:33-330` — `SessionManager(ABC)` with `should_continue_session()`/`advance_time()`/`execute_trading_cycle()`/`wait_for_next_cycle()`, and two concrete drivers (`BacktestingSession`, `LiveTradingSession`). This is a clean, separately-named object for exactly what QMF's `qmf.runtime` kernel needs to inject: a `Clock`/`Session` that the kernel calls without caring whether ticks are simulated or real.

3. **Typed lifecycle hooks are the entire strategy authoring surface — never a loop the strategy owns.** `lumibot/strategies/strategy.py:5286-5680` — `before_market_opens`, `on_trading_iteration`, `on_filled_order`, etc. are the only things a strategy author writes; the framework owns all control flow and calls them at defined points. This is precisely the shape QMF wants for LLM-agent-authored strategies (`qmf.spec`, Ring 8): a small, fixed, named vocabulary of callbacks/typed slots, never free-form code that owns `while True`.

4. **One boolean flag, checked in one class, gates every backtest-only behaviour — never a parallel code path.** `IS_BACKTESTING_BROKER` is a class attribute on `Broker` (`broker.py:175`) referenced at 15+ sites in the same file (locking strategy, rate limiting, log retention, telemetry cadence). The alternative — a `if backtest: ... else: ...` branch duplicated across strategy code, or a separately-maintained "fast" strategy class for backtests — is exactly the kind of drift that breaks backtest/live parity. QMF should thread one `is_simulated` signal through `qmf.broker`/`qmf.runtime` and resist letting strategy code ever see it.

5. **Lazy-import the heavy stuff so the always-on process stays thin.** `lumibot/_lazy_imports.py` (`LazyLogger`, `LazyModule`, `lazy_class`) defers importing pandas, `pandas_market_calendars`, etc. until a code path actually needs them, used from the top of `brokers/broker.py` and `strategies/strategy_executor.py`. This is a concrete implementation technique for QMX's own two-lockfile plan (`00-qmf-synthesis-module-map.md` Novel idea #7): `qmf.broker.ctrader` and `qmf.runtime` can defer-import anything outside the trading lockfile so a VPS process never silently pulls in the analysis stack.

6. **Stamp a transform so it refuses to re-apply itself.** Documented in `reference/repos/lumibot/CLAUDE.md` under "ThetaData Split Adjustment (FIXED)": a corporate-action adjustment function was being called 26+ times per backtest with no idempotency check, silently compounding the correction; the fix was a marker column (`_split_adjusted`) checked at the top of the function. This is the same discipline QMF already wants for provenance and confluence registration (`00-qmf-synthesis-module-map.md`'s content-hash/append-only registry) — apply it one level lower, to any data-mutating pipeline step, not just to registered components.

7. **Calendar and day-count convention as named, swappable objects — never inline date arithmetic.** `QuantLib/ql/time/calendar.hpp` + `ql/time/daycounters/*.hpp` (`Actual360`, `Actual365Fixed`, `Thirty360`, `Business252`, …), each looked up by name rather than computed ad hoc. QMF's forex swap/rollover and crypto funding math (the "financing as a P&L line item" idea already in the synthesis doc) needs exactly this in miniature: `qmf.venue_model` carries a `day_count_convention` and a `calendar_id` as data, resolved through a handful of named functions — not a QuantLib dependency, just its naming discipline.

## What to avoid

- **Do not let the strategy class inherit from the broker class.** qtpylib's `class Algo(Broker)` (`qtpylib/algo.py:59`) welds strategy logic and venue connectivity into one inheritance chain. The direct consequence: a strategy cannot be unit-tested without a broker connection (real or fully mocked), and cannot be pointed at a second venue without rewriting the class hierarchy. QMF already avoids this by design (`Strategy` composes a `Broker`, never extends one) — this is confirmation to hold that line, not a new decision.

- **Do not depend on someone else's unofficial wrapper around a vendor API you don't control.** `qtpylib/requirements.txt` pins `ibpy2>=0.8.0` and `ezibpy>=1.12.66`, two third-party wrappers around Interactive Brokers' legacy TWS socket protocol, both effectively unmaintained. When IB's API moved or the wrapper broke, qtpylib had no path forward because the actual protocol knowledge lived in someone else's stale project, not in qtpylib's own code. This is the exact reasoning QMF's synthesis doc already applies to cTrader (`05` — "Do **not** build on `ctrader-open-api`... vendor ~400 lines asyncio over vendored `.proto`") — qtpylib is the concrete failure case that argument is protecting against.

- **Do not require standing infrastructure (a database server, a message bus) just to log a trade.** `qtpylib/blotter.py` needs a running MySQL server (`pymysql`, `blotter.py:38-114`) and a ZeroMQ pub/sub link between two separate OS processes (`blotter.py:38, 123, 162-163`) before a single strategy can run. For a solo operator this is two extra always-on services to provision, monitor, and recover when they fail — with the failure mode being silent (a strategy that stops recording because MySQL is full or the zmq port is taken gives no obvious signal tied to the cause). QMF's plan (SQLite-WAL live inbox, Parquet lake, no database server — `00-qmf-synthesis-module-map.md` Ring 1) is the right call, and this is direct evidence for why.

- **Do not bundle orthogonal, third-party-API-dependent features (SMS alerts, a web dashboard) into the trading library itself.** qtpylib ships a Flask app (`qtpylib/_webapp/`) and Twilio/Nexmo SMS integration (`qtpylib/sms.py`) inside the core package. Every one of those dependencies is a thing that can break for reasons that have nothing to do with trading logic, and every one of them needs to be kept patched by the same one person maintaining the strategies. Surface area unrelated to the edge is exactly what a solo maintainer runs out of time for first — qtpylib's SMS/web/DB layers were very likely dead weight well before the trading logic itself stopped being useful.

- **Do not let a data pipeline step silently re-apply itself or fabricate missing values.** Both failure modes are documented from lumibot's own operating history (`reference/repos/lumibot/CLAUDE.md`): a corporate-action adjustment applied 26+ times per backtest because it had no idempotency guard, and a standing top-of-file rule ("RULE #1 — NEVER FABRICATE BACKTEST DATA") that exists because someone, at some point, was tempted to forward-fill or interpolate missing bars to keep a strategy running. Missing data must surface as missing; a correction must be able to prove it has already been applied.

- **Do not let a licence marker rot.** `qtpylib/setup.py:31` still declares `license='LGPL'` while `LICENSE.txt` is actually Apache-2.0 — a small, easily-overlooked inconsistency that is nonetheless the kind of thing that accumulates in an unmaintained repo. Worth a note only because QMF's own registry/manifest design (component semver, licence, `evidence_state`) should make this class of drift structurally impossible rather than trusting a human to keep two files in sync.
