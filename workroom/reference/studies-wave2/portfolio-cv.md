# Portfolio CV — skfolio and riskkit

**Scope:** two repos, one mature and one unvetted. `skfolio`: read narrowly for its cross-validation-native optimizer design (`BaseOptimization` as an sklearn estimator, `WalkForward`/`CombinatorialPurgedCV` as first-class splitters, `cross_val_predict` as the fold-stitching driver) as a reference for how `qmf.book` sizing logic could expose a fit/predict seam to `qmf.experiment`. `riskkit`: read in full — it is small enough — for how it factors position sizing, drawdown control, a composable stop engine, correlation limits and exposure caps, cross-checked against QMF's planned `qmf.book` (sizes) / `qmf.bms` (gates) split. Read-only throughout: no code executed, no package installed from either clone.

---

## In plain words

1. `skfolio` is a real, mature, BSD-3-Clause portfolio-optimization library built directly on scikit-learn's estimator API — every optimizer is a `BaseOptimization(BaseEstimator, ABC)` with `fit(X, y)` and `predict(X) -> Portfolio | Population`, so anything scikit-learn already does (pipelines, grid search, cloning) works on a portfolio strategy for free.
2. Its most exportable idea is that **walk-forward is not a loop you write, it is an object you pass in.** `WalkForward` and `CombinatorialPurgedCV` are `sklearn`-compatible cross-validator classes; a single generic driver, `cross_val_predict(estimator, X, cv=...)`, fits on each train fold and predicts on each test fold, then stitches the resulting portfolios into one `MultiPeriodPortfolio` (or a `Population` of them, for the multi-path combinatorial case).
3. The driver also solves a real, subtle problem cleanly: when a fold-to-fold estimator needs its previous weights (because of transaction costs or a turnover cap), it declares this with one estimator property, `needs_previous_weights`, and the driver switches from parallel to sequential fold execution and threads `previous_weights` through automatically. Nobody has to remember to do this by hand per experiment.
4. `skfolio`'s `BaseOptimization` also ships a `fallback` chain (try estimator A, then B, then "keep previous weights") and a `raise_on_failure=False` mode that turns a failed fit into a typed `FailedPortfolio` object instead of an exception — a "never leave the caller without a typed answer" discipline worth noting on its own.
5. `riskkit` is the opposite kind of artifact: ~1,900 lines across seven core modules (sizing, drawdown, stops, correlation, session, validator, manager), zero runtime dependencies, MIT-licensed, written by one person over about six weeks (first PyPI release 2026-06-19, latest changelog entry 2026-07-02), 2 GitHub stars, 0 forks, no external contributors.
6. Despite the thin external track record, the code itself is unusually disciplined for a solo, days-old repo: full type hints, docstrings on every public symbol, a changelog that documents a real bug it found and fixed in itself (an inverted-stop trade that silently passed validation in 0.4.1, fixed in 0.4.2 with two new named checks), and property-based tests (Hypothesis) asserting the anti-martingale invariant and the exposure caps hold under randomized fill sequences.
7. `riskkit`'s six components map onto QMF's Book/BMS split reasonably well at the component level (`PositionSizer` ≈ Book's sizing core, `PreTradeValidator` ≈ BMS's typed-reason gate, `SessionManager`/`CorrelationGuard` ≈ BMS's cadence and correlation rules) but the *façade*, `RiskManager.evaluate()`, deliberately blends sizing and gating into one call and one return object — the opposite of QMF's committed design, where Book and BMS are separate objects read by separate hats.
8. One design choice in `riskkit` is a genuine anti-pattern by QMF's own stated rule: `PositionSizer` accepts a `confluence_score` and uses it to *increase* size 1.5–2×. QMF's module map explicitly forbids a signal from ever expressing quantity — this is exactly the loophole that rule exists to close, because a component's own self-reported conviction should never be allowed to buy itself a bigger position.
9. `riskkit`'s `DrawdownManager` has no persistence: peak equity, tier, and the weekly-loss window are all in-process instance attributes with no reconciliation against a broker at startup. QMF's `qmf.bms` explicitly requires durable state reconciled at startup — this is the clearest place `riskkit`'s scope stops short of what QMF needs, not because the idea is wrong but because it was never asked to survive a restart.
10. Net: `skfolio` earns a **borrow-the-shape, not-the-code** verdict (BSD lets QMX use it directly too, but its cvxpy/pandas/plotly weight makes it a research-environment-only dependency, not something the trading VPS should ever import); `riskkit` earns a **read the design, verify everything, copy nothing verbatim** verdict — good architecture instincts from someone learning the same lessons QMX already learned independently, wrapped in code with real but modest quality signals and zero track record.

## Findings per repo

### skfolio

**Licence:** BSD 3-Clause, confirmed at `reference/repos/skfolio/LICENSE` and restated in every module's header (e.g. `reference/repos/skfolio/src/skfolio/model_selection/_walk_forward.py:1-9`, `reference/repos/skfolio/src/skfolio/optimization/_base.py:1-13`). Safe for QMX to depend on or read code from directly, no copyleft obligation — this was already the wave-1 verdict per `catalog-maps.md`'s shortlist note ("skfolio" listed among repos already deep-dived in files `01`–`10`), and nothing here changes it.

- **The estimator contract.** `BaseOptimization` (`reference/repos/skfolio/src/skfolio/optimization/_base.py:39-124`) is an abstract `sklearn.base.BaseEstimator` requiring only `fit(X, y=None)`; it supplies `predict`, `score`, `fit_predict`, and a `needs_previous_weights` property for free. `fit` is automatically wrapped at subclass-definition time (`__init_subclass__`, lines 127-163) to add a fallback chain and typed failure capture (`error_`, `fallback_chain_`) without every subclass having to remember to implement that machinery itself — a "the base class enforces the contract, subclasses cannot opt out" pattern.
- **`predict` never returns a bare array.** It returns a `Portfolio` (1D weights) or a `Population` of `Portfolio` (2D weights), and when `weights_ is None` after a non-raising failure, a typed `FailedPortfolio` carrying the `optimization_error` string (`_base.py:341-370`). No naked float, no silent `NaN` array — every outcome is a typed object a caller can branch on.
- **Walk-forward as a first-class, declarative splitter.** `WalkForward` (`reference/repos/skfolio/src/skfolio/model_selection/_walk_forward.py:25-354`) takes `train_size`, `test_size`, an optional calendar `freq` (so "rebalance monthly on the third Friday, train on the last 6 months" is one constructor call), `expand_train` (rolling vs. expanding window), and — the one line that matters most for QMX — `purged_size`, with a docstring (lines 118-143) that spells out exactly the same execution-timing-latency argument QMX's own provenance discipline already encodes: `purged_size=0` assumes same-period execution is safe; `purged_size>=1` is required whenever observation-to-execution latency is non-negligible. This is `skfolio` independently arriving at the same "you must declare, not assume, your execution lag" rule QMF's `Provenance` type exists to enforce.
- **Combinatorial purged CV for multi-path validation.** `CombinatorialPurgedCV` (`reference/repos/skfolio/src/skfolio/model_selection/_combinatorial.py:50-120`) generates every valid combination of held-out fold groups (with purging and embargo), producing many independent out-of-sample *paths* rather than one — directly the same lineage as `purgedcv`, which the module map's Ring 7 (`qmf.overfit`) already names as a CI oracle. Its presence here as a first-class `sklearn`-compatible splitter (not a bolt-on function) is the transferable idea, not the code.
- **The fold-stitching driver.** `cross_val_predict` (`reference/repos/skfolio/src/skfolio/model_selection/_validation.py:39-137+`) is generic over any `BaseOptimization | Pipeline` and any splitter (`WalkForward`, `CombinatorialPurgedCV`, `MultipleRandomizedCV`, or a plain `int`/iterable). It fits per training fold, predicts per test fold, and assembles either one `MultiPeriodPortfolio` (single-path CV) or a `Population` of them (multi-path CV) — the researcher never writes the fold loop by hand, and the same call works whether the strategy is a single optimizer or a whole `Pipeline`.
- **Quality verdict: mature, well-governed, safe to study closely, not to embed on the trading path.** Real CI (`codecov.yml`, `.pre-commit-config.yaml`), a 38KB `CHANGELOG.md` spanning many releases, a security policy (`SECURITY.md`), a Zenodo DOI, and commercial backing (`skfoliolabs.com`) all point to a genuinely maintained project — this is not a catalog mirage. But its dependency footprint (`cvxpy-base`, `clarabel`, `pandas`, `plotly`, `scikit-learn` per `reference/repos/skfolio/README.rst:99-112`) is squarely research-environment-only by QMF's own two-lockfile rule (module map, Novel Idea 7) — none of it belongs on the Linux trading VPS. The right use of `skfolio` for QMF is exactly what this assignment asked for: read the estimator/CV/driver *shapes*, do not import the package into `qmf.book`.

### riskkit

**Licence:** MIT, confirmed at `reference/repos/riskkit/LICENSE` ("Copyright (c) 2026 Hasib"). Fully compatible with QMX's "assume it will be sold or served over a network" policy; no obligation beyond attribution.

**Maintenance / track record (checked live, since this is the unvetted find the assignment flagged):** GitHub shows 2 stars, 0 forks, 0 watchers, 32 commits, 0 open issues, a real CI badge and a published PyPI package (`riskkit-quant`). The `CHANGELOG.md` (`reference/repos/riskkit/CHANGELOG.md:1-119`) dates the first release `0.1.0` to 2026-06-19 and the latest, `0.4.2`, to 2026-07-02 — roughly six weeks of solo development, ending about six weeks before this study. This matches the wave-1 catalog's flag ("days-old, single-author, possible self-promotion") on the numbers; it does not match it on code discipline, discussed below.

- **What's actually in the box, read in full.** Seven core modules, no third-party runtime dependency: `sizing.py` (263 lines — `PositionSizer`, `kelly_fraction`, `volatility_target_size`, `inverse_vol_weights`), `drawdown.py` (171 lines — `DrawdownManager`, a 5-tier ladder plus a rolling weekly-loss pause), `stops.py` (228 lines — `StopEngine`/`StopStack`, 9 stop kinds, tighten-only), `correlation.py` (119 lines — `CorrelationGuard`, static + dynamic groups), `session.py` (173 lines — `SessionManager`, daily caps/cooldowns/tilt), `validator.py` (211 lines — `PreTradeValidator`, ~18 named checks), and `manager.py` (619 lines — the `RiskManager`/`RiskConfig`/`TradeIntent`/`RiskDecision` façade that wires the other six together). Confirmed via `wc -l` and direct reads of all seven files.
- **Real, dated bug discovery-and-fix — a genuine maturity signal for a young repo.** `CHANGELOG.md:6-19` documents that in version 0.4.1, `RiskManager.evaluate()` on a long position whose `stop_price > entry_price` (an inverted, backwards stop) returned `ok=True` with a "plausible-looking" R:R, because the sizer computed risk as `abs(entry - stop)` and the validator never checked stop *side*. Version 0.4.2 adds two named checks, `stop_on_protective_side` and `target_on_profit_side` (`reference/repos/riskkit/src/riskkit/validator.py:177-186`), closing it. This is exactly the kind of self-caught, then-fixed, then-tested defect that distinguishes "someone actually used this and it broke" from "someone wrote this and never ran it" — a small positive signal despite the low star count.
- **Property-based tests exist and target the right invariants.** `CHANGELOG.md:50-55` (v0.4.0) and the presence of `tests/test_properties.py` describe Hypothesis tests asserting: a position never exceeds its notional/risk caps; size never increases after losses or deeper drawdown (the anti-martingale property); the per-sector exposure cap holds across randomized fill sequences; and the three standalone sizers stay within their documented bounds. This is a stronger test discipline than most single-author, six-week-old repos carry, and it targets exactly the properties a risk-sizing library should prove, not just "does it run."
- **The Book/BMS cross-check.** `PositionSizer.size()` (`reference/repos/riskkit/src/riskkit/sizing.py:135-188`) is a pure function: risk-per-unit from the stop distance, scaled by an ATR-ratio volatility factor, an optional half-Kelly ceiling, a reduction-ladder multiplier (losing streaks, drawdown, daily loss, a low-confluence penalty), clamped to `[min_risk, max_risk]`, and hard-capped by `max_notional_pct` — this is squarely `qmf.book` territory (money math, continuous multiplier, named binding constraint via `multipliers_applied`). `PreTradeValidator.validate()` (`reference/repos/riskkit/src/riskkit/validator.py:107-211`) is squarely `qmf.bms` territory: ~18 independent named checks (market quality, sizing, risk limits, signal quality, timing), each returning a `CheckResult(name, ok, details)`, combined into one `ValidationResult(passed, failures, ...)` — this is a real, working instance of "typed denial reasons from one mandatory gate," missing only an enum (it uses string names) and durable cross-restart state.
- **Where the factoring differs from QMF's design, and why it matters.** `RiskManager.evaluate()` (`reference/repos/riskkit/src/riskkit/manager.py:437-582`) computes the size (via `PositionSizer`, with the drawdown multiplier folded in) *and* runs the validator *and* returns one `RiskDecision` object carrying both `units` and `ok`/`reasons` from a single call. Sizing and gating share one method, one call site, one return type. QMF's design keeps them structurally separate — Book is read identically by the PM and by the researcher inside a fitness function; BMS is read identically by the trader live and by the researcher as a hard disqualifier (module map, Ring 4 and "PM ≡ Researcher, through the ledger"). `riskkit`'s blend is *convenient* for a single-actor bot with one call site, but it would be an *accident* to copy into QMF: QMF's researcher needs to invoke the BMS gate alone, without re-running Book's sizing math, to test "would this confluence have passed prop-firm rules on this split" as a pure yes/no. `riskkit` cannot do that split cleanly today — sizing and gating are welded together in the façade (though the underlying components, read individually, could).
- **One genuine wisdom nugget worth keeping, separate from the welding above.** `RiskManager.__init__` (`manager.py:334-370`) deliberately derives the validator's thresholds (`max_total_exposure_pct`, `max_daily_trades`, `max_daily_loss_pct`, `min_seconds_between_trades`) from the same `RiskConfig` fields that also seed the sizer and session manager, with a comment explaining why: "so the two enforcers never silently disagree on the same threshold." That specific failure mode — two components each holding their own copy of what should be one number, silently drifting apart — is real and worth guarding against in QMF too. The fix `riskkit` chose (constructor-time kwarg merging inside one Python object) is not the fix QMF should copy; QMF already has the structurally correct answer for this same problem — one manifest/schema that both Book and BMS read (module map's `qmf.registry`) — so the underlying concern transfers, the implementation does not.
- **The anti-pattern: signal quality buying its own size.** `SizingInputs.confluence_score` (`reference/repos/riskkit/src/riskkit/sizing.py:45`) feeds `_reduction_multiplier` (`sizing.py:96-131`), where a score `>= high_conviction_score` (default 85) multiplies size by `high_conviction_size_mult` (default 1.5, up to 2.0 in the aggressive preset). In `RiskManager.evaluate()`, this `confluence_score` defaults to the trade's own self-reported `score` (`manager.py:469-472`) when no separate value is supplied — so in the common case, a strategy's own conviction rating directly inflates its position size. QMF's module map states the opposing rule explicitly and for a specific reason: "`Signal` carries no quantity. An agent that cannot express 'buy 5 lots' cannot blow the account through sizing" (module map, Level/Trigger/Confirmation/Exit section). If an LLM-authored `Confirmation` component could ever influence its own reported score, `riskkit`'s wiring would let it buy itself a bigger position — the exact failure mode QMF's typed-`Signal`-carries-no-quantity rule exists to close.
- **The durability gap.** `DrawdownManager` (`reference/repos/riskkit/src/riskkit/drawdown.py:51-171`) and `SessionManager` (`reference/repos/riskkit/src/riskkit/session.py:39-173`) hold all state — peak equity, current tier, the weekly-loss window, today's trade/loss counts, the cooldown timer — as plain Python instance attributes. There is no persistence layer anywhere in the seven core modules (confirmed by reading all of them: no file I/O, no database handle, no serialization of manager state). A process restart silently resets every counter to zero — the drawdown tier, the daily trade count, the cooldown, all forgotten. QMF's `qmf.bms` explicitly requires "durable state reconciled against the broker at startup" (module map, Ring 4) precisely because this class of bug (a restart quietly re-arming a halted account) is a real prop-firm-account killer, not a hypothetical.
- **Quality verdict: better than the "days-old, unvetted, possible self-promotion" framing alone would suggest, but genuinely unproven.** The code itself — type hints throughout (`py.typed` marker present), docstrings on every public class and function, a changelog that admits and fixes a real bug with a dated entry, property-based tests targeting the right invariants, zero runtime dependencies, adapters kept strictly optional (only `riskkit.adapters.*` import third-party frameworks; the core seven modules import nothing beyond the standard library, confirmed via `grep` across `src/riskkit/*.py`) — reflects real engineering discipline for a solo six-week project. But "2 stars, 0 forks, 0 external contributors, six weeks old" means zero independent verification exists: no one else has read this code critically, no real account has traded against it (the README's own disclaimer says as much: "Test everything on paper first"), and the self-promotion risk the wave-1 catalog flagged cannot be ruled out just because the code reads well — a well-written repo is exactly what a plausible self-promotion attempt would look like too. Treat every numeric threshold and every design choice here as a hypothesis to re-derive, not a fact to trust, and never import the package — read it, and rebuild the two or three genuinely good ideas (below) in QMF's own typed, durable, hat-separated shape.

## What to avoid

- **Importing either package.** Neither licence forbids it (BSD-3 and MIT both permit direct use), but the assignment's own instruction stands regardless of licence: mental models only, no code transplantation. `skfolio`'s dependency weight (`cvxpy-base`, `plotly`, full `pandas`) also disqualifies it from the trading-VPS lockfile even if QMX did decide to depend on it for research.
- **Letting a signal's own conviction score buy it a bigger position.** `riskkit.PositionSizer`'s `confluence_score`-driven high-conviction multiplier (`sizing.py:123-129`, wired from the trade's own `score` by default in `manager.py:469-472`) is precisely the loophole QMF's "`Signal` carries no quantity" rule exists to close. Do not let any QMF `Confirmation` or `Trigger` weight feed a size multiplier directly — conviction may only ever influence *which* confluence gets budget in `qmf.experiment`'s search, never the position size `qmf.book` computes for an already-registered confluence.
- **Treating a monolithic risk façade as a template for QMF's Book/BMS boundary.** `RiskManager.evaluate()` deliberately does sizing and gating in one call — good ergonomics for a single-actor bot, wrong shape for QMF, where the researcher must be able to run the BMS gate alone (as a hard disqualifier inside a fitness function, per the module map's `09§14.6`) without re-running Book's money math every time.
- **Trusting in-memory-only risk state.** `riskkit`'s `DrawdownManager`/`SessionManager` reset every counter on process restart — no persistence, no reconciliation. Copying this shape into `qmf.bms` (which explicitly requires durable, broker-reconciled state at startup) would silently re-arm a halted prop-firm account after every crash or redeploy — exactly the failure mode a solo, six-week-old repo would have no way to have discovered yet.
- **Reading `riskkit`'s two-star, zero-fork status as proof of anything either way.** It is neither evidence the code is bad (it reads cleanly, has real tests, and documents a genuine self-caught bug) nor evidence it is trustworthy (no one else has used it against a real account, and a well-written README is exactly what a plausible self-promotion repo would also have). The only sound conclusion from the numbers alone is "unverified" — treat every default threshold (tier percentages, `high_conviction_size_mult`, the Kelly fraction cap) as an unsourced guess to re-derive from QMX's own data, not a number to copy.
- **Assuming `skfolio`'s BSD licence and polish mean it was built for QMX's constraints.** It optimizes multi-asset portfolios for asset managers; its `Portfolio`/`Population`/CV machinery has no concept of a broker, a spread, a prop-firm rule, or a single-instrument forex position — same gap the module map already found across the entire portfolio-optimization space (`04`). The transferable part is strictly the fit/predict/CV-driver *shape*, not its investment-universe assumptions.
