# ADR-0019: The trading node — a supervised composition-root runtime over a pure rulebook

Date: 2026-08-29. Status: accepted — the trading-node spine TN-1..TN-25 is FINAL (2026-08-28), ratified by operator delegation plus four direct rulings (DEC-0259). This ADR records the design decision the documentation-factory increment absorbed into `docs/`; implementation authorization arrives only through the factory pipeline, never from this record.

## Context

The trading node is the Phase-2 QMX application: the live-and-paper composition root on the Trading VPS that runs Book and BMS runtime, hosts QML seats, drives the cTrader order path over `qmf-venue`, records live market data, carries the MIS seam, and exposes the operator doors — while QMF (the foundation), QMB (the experimentation library and `qmb` CLI, ADR-0017), and QML (the bot-authoring library, ADR-0018) are already designed and built at `integration@ef9bb25` (DEC-0186, DEC-0259). The ground-truth inventory of that commit is the parts-bin: 154 capabilities the node needs, of which 78 exist as-is, 24 need a live adapter, and 52 are missing — an effort-weighted 45–60% already in hand, so the node is an assembly-and-wiring application over a mostly-built substrate, not a new framework (DEC-0186, DEC-0259).

The requirement body is the PRD's Phase-2 node doctrine (§6), carried there to ratify at node planning; every mined item — startup and recovery ordering, explained-drift stand-down, stand-down-alive, the always-on evidence tier — is ratified by adoption, each tied to the TN rule that adopts it (DEC-0238). Two constraints frame the whole design: nothing QMX is published to any index (DEC-0186), and the node inherits QMF AD-1..AD-41, QMB B-1..B-15 and QML QL-1..QL-10 read-only — a local decision that contradicts an inherited invariant is a conflict to surface, never an override (DEC-0259). The node spine is therefore a **child spine** of `architecture-QMX-2026-08-19`, and its paradigm is a supervised composition-root runtime over a pure rulebook (DEC-0259).

## Options considered

1. **A runtime inside `qmf-venue`.** Rejected. `COMP-QMF-VENUE` is the venue transport and the CT-18..CT-21 venue contracts — an edge module nothing imports — and at `ef9bb25` it exposes no `VenuePort`, `OrderPort` or `VenueAdapter` seam to host a runtime behind (DEC-0228). Making the transport module own the trading loop, secrets, scheduling and real money inverts its charter, and amending `qmf-venue` to realize that seam is a parent amendment, never a child's call — recorded not-applied (DEC-0242).
2. **A runtime inside `qmf-risk`.** Rejected. `COMP-QMF-RISK` is a definitions boundary forbidden from running anything: the node runs the ratified AD-33..AD-41 / CT-29..CT-32 protection set **verbatim** and mints values, never rules (DEC-0193). A definitions module cannot carry a composition root, a slice loop, or the venue edge.
3. **A mode of QMB.** Rejected. `COMP-QMB` is the experimentation host — it consumes bots, publishes results, never benches, promotes or binds, and never imports `qmf-venue` (ADR-0017; DEC-0190). The node reuses QMB's B-2 event-slice loop *unforked* through `run_slice`, but the node — not QMB — is the composition root that binds a live frontier clock, live venue sessions, and real money; QMB's world stays `replay` (DEC-0190). Folding live trading into QMB would break the door/library fence that keeps the host from owning what it hosts.
4. **A container-first service.** Rejected. NFR-10 forbids a container requirement and requires one canonical checkout with no database server that one person can deploy and repair; the node is a plain systemd service on Ubuntu 24.04 LTS, and containers appear only in the separate observability stack (DEC-0201, DEC-0212).
5. **A node with its own operator command line or typed operator door.** Rejected by operator ruling R1: the trading node ships no operator command line and no typed operator door of its own (DEC-0211). `qmb` remains the platform's single command-line surface (DEC-0185 Ruling C), unchallenged, and the memlog's earlier "`qmn` command" / "Door 2" text is superseded history, never presented as current (DEC-0186).
6. **A `qmf-venue`-realized `VenueClientPort` versus a node-realized one.** The node mints its own `qmn.venue.VenueClientPort` over the CT-19/CT-20 shapes because `qmf-venue` exposes no port seam to inject (DEC-0228). Realizing the seam **inside** `qmf-venue` is the alternative — recorded as a candidate AD-28 parent annotation, not applied by this increment, because it is a parent amendment (DEC-0242).

## Decision

The trading node is a **supervised composition-root runtime over a pure rulebook** — hexagonal at application scale — and is a new component, `COMP-QMN` (code name `qmn`; the operator declined to rule the product name, recording "that question is not for this layer", and a rename is mechanical) (DEC-0186, DEC-0259).

- **One product, two modes `paper | live`.** Never "a paper node", never a separate "live node". Paper is a Book-level mode routed to the paired demo account, and the node is a top-level uv-workspace member alongside `qmb/` and `qml/`, an application layer built ON QMF exactly as QMB and QML are — never a `qmf.*` roster package and never a framework (DEC-0186, DEC-0194).
- **The only impure shell.** One long-lived systemd-supervised process composes the pure QMF/QMB/QML parts at boot — compose, fingerprint (`composition_fp`), seal — and owns everything the libraries refuse to own: ambient time, async (venue edge and doors only), scheduling, secrets, and real money; below the root nothing is impure and above it nothing is a rule (DEC-0187, DEC-0189, DEC-0190).
- **No operator command line — three doors and an operations toolkit.** The control surface is the desktop UI over the node's doors: the in-process Python API, the localhost HTTP evidence read channel (publish-never-act, per-read provenance fields), and the unix-socket powers action channel authenticated by `SO_PEERCRED` against two declared principals (DEC-0202, DEC-0211, DEC-0234). Deployment and provisioning are an **operations toolkit** of `just node-…` recipes — DevOps tooling, never a trading control: no recipe places, cancels, amends, flattens, promotes or activates anything, and the restriction is enforced by the transport (the ops principal is refused every trading, protection, promotion, activation, settings, `resurrect`, attestation and countersign power), not by recipe text (DEC-0186, DEC-0202).
- **A plain systemd service; a separate zero-authority observability stack.** The node runs as `qmn.service` (Type=notify, raw sd_notify over a stdlib `AF_UNIX` datagram socket, no container) on Ubuntu 24.04 LTS (DEC-0189, DEC-0201). Observability is a **separate** Prometheus/Grafana/Loki-class system under `qmn/deploy/observability/`, under its own non-`qmx` account with its own storage budget, and is the only place containers are permitted; it is a zero-authority consumer of the node's exported signals and the node runs and passes with it absent (DEC-0200, DEC-0201, DEC-0212).
- **The sole sanctioned `qmf-venue` wirer, through `qmn.venue`.** The node's composition root is the one place `qmf-venue` is imported and wired (AD-28 requires a composition root to construct the adapter); the writable boundary of that sanction is the `qmn.venue` subpackage, and every other `qmn` module receives `VenueClientPort` and CT-19/CT-20 shapes only, with the L30 default-deny lint written against that boundary (DEC-0186, DEC-0241). `qmb` and `qml` keep their `qmf-venue` ban.
- **One delegated impurity, named once.** `qmf-venue`'s `ConnectionManager` holds the venue socket, the venue session and the single in-memory venue secret value on the loop the node injects, under the injected `Clock` and `SecretStore`; the QMF async-conformance test is amended to exempt `qmf.venue.connection` **by name** in the same increment as the cTrader transport. If the parent refuses the exemption, the transport increment lands in `qmn.venue.ctrader` instead, and the epics may not choose between the two (DEC-0187, DEC-0196, DEC-0243).

## Architecture-preflight verdict

**new `COMP-QMN`** — the inventory was read and every reuse candidate is named and refused by ID:

- **`COMP-QMF-VENUE`** is the venue transport and the CT-18..CT-21 contracts, never a runtime; it exposes no injectable port seam at `ef9bb25` and nothing may import a runtime into it — the node mints `qmn.venue.VenueClientPort` over it instead, and the one delegated impurity lives in its `ConnectionManager` under a named async exemption (DEC-0228, DEC-0243).
- **`COMP-QMF-RISK`** is a definitions-only rulebook boundary forbidden from running anything; the node runs its AD-33..AD-41 / CT-29..CT-32 set verbatim and mints only values (DEC-0193).
- **`COMP-QMB`** is the replay-world experimentation host, barred from `qmf-venue`, that publishes and never binds; the node reuses its B-2 loop unforked but is itself the live composition root (DEC-0190).
- **`COMP-QML`** is the bot **author**, never the host; the node hosts QL-7 seats, and QML builds before the node (DEC-0204).
- **`COMP-QMF-DATA`** owns the seven room-roles and the journal — rooms, not runs; the node adds an eighth room role (`sealed-archive`) as a recorded parent annotation and instantiates rooms per world, but does not become a data layer (DEC-0188, DEC-0253).

**What shrinks: nothing.** No existing component's authority is reduced. Every parent touch is an annotation applied exactly as the spine's "Parent annotations and mints" section records it — `applied` (the L30 `qmn.venue` boundary DEC-0241, the async exemption DEC-0243, the CT-20 read-back mapping rows DEC-0247, the Records↔CT-13 projection bridge DEC-0246, the CT-30 predicate declarations DEC-0250, the CT-24/CT-28 usage DEC-0251, the CT-14 backup-key custody DEC-0252, the `sealed-archive` role DEC-0253, `value_status_required` DEC-0254, the `kill_line_capital_floor` = `loss_floor` one-name record DEC-0255, the registry mint table DEC-0256, the four reconciliation verdicts DEC-0258), `recorded-not-applied` (VenueClientPort realized inside `qmf-venue` DEC-0242, the CT-20 lifecycle-stop UNKNOWN trigger DEC-0248), or `proposed` (the PRD §3 allow-list widening DEC-0257). The `SessionTopology` connection-count relaxation is a CODE item of the same `qmf-venue` increment that carries the transport, and the soak cannot start without it (DEC-0244); the stale `qmf-venue` README correction is documentation-only and changes no code (DEC-0245).

**Dead list honored.** DEC-0084's central backtesting service stays dead — the node revives no central service; the passive file-sync hub is dumb storage under B-15, not a service (DEC-0188). The memlog's pre-ruling `qmn` command surface is **not** a dead ledger decision; it is superseded text, replaced by the no-command-line ruling and never presented as current (DEC-0186, DEC-0211).

## Consequences

- **Registry mints.** Every row of the spine's registry mint table lands in `docs/registry/variables.yaml` as `configurable: true`, unit-kinded, owner-scoped, carrying evidence values only and a blank-effect tag from the three-way partition `blocks-boot | blocks-role-live | blocks-soak` (DEC-0256, DEC-0193). `kill_line_capital_floor` is recorded as the canonical registry key and AD-40's `loss_floor` — one variable, one name (DEC-0255).
- **Value-status mint.** `docs/registry/variables.yaml` gains a new schema field `value_status_required`; the per-value `value-status ∈ blank | provisional-evidence | ratified` lives on the resolved config artifact and is countersigned through the powers channel with an evidence citation. A `provisional-evidence` value gating live money blocks `role = live` exactly as a blank does (DEC-0254, DEC-0231).
- **A proposed PRD §3 widening, cheap veto.** The ratified notification allow-list gains a silent-degradation class ("the node has stopped accepting entries or cannot persist evidence for a reason that is not a KSA escalation"), an external dead-man's switch, and a liveness digest — surfaced by the sitting as a PRD amendment and ratified by this increment by default, overturnable in one line (DEC-0257, DEC-0233).
- **Deferred rows.** Eight questions are carried and none blocks V1 — seven `deferred` (GAP-0050 through GAP-0056) plus one non-blocking `open` cheap-veto item (GAP-0057): the KSA matrix cell VALUES (GAP-0050, a pre-soak operator ratification through the settings surface), MIS labeler training and shadow rollout (GAP-0051), hot-apply settings (GAP-0052), the agent/MCP door (GAP-0053), hardened OS confinement for seats (GAP-0054), a second VPS for the evidence tier (GAP-0055), fill simulation in replay (GAP-0056), and per-bot post-promotion warm-up (GAP-0057). The last is the recorded answer to the operator's post-promotion warm-up recollection: the inherited admission row stands (no probation, no paper-performance gate), and the only warm-up the corpus carries is the deploy-level soak week (DEC-0194, DEC-0213).
- **Human-only acts.** Promotion (a signed AD-18 card) and activation are two separate human acts through the powers channel; `resurrect` from node stand-down, the countersign that flips a `provisional-evidence` value, and every operator-signed protective command are human-only, and no automated unit ever runs under an operator principal (preflight asserts it) (DEC-0205, DEC-0213, DEC-0211). Nothing in these docs grants implementation, credential, order, promotion, live-money, or destructive authority.
- **Cheap-veto register.** The sitting's assumption register A1–A47 (A1/A10/A17/A26 ruled, A8 retired) is surfaced in the changelog so the operator can overturn any without-operator call in one line; this ADR points there rather than restating the register (DEC-0259, DEC-0260).

## Operator rulings 2026-08-28

Four calls were put to the operator and ruled; each is applied above. The wording below is quoted only where the transcript scan verified it.

- **R1 — no operator command line.** "there is nothing like commands or anything"; killing, status, resolving a stuck order and promotion are UI actions over the node's doors, running "the same setting or the same logic behind even the agentic system", because the control surface is "a user interface on the desktop application as per the overall architecture". The priority is plain: "first, make the trading node work. Make sure it can execute." The node is one surface inside the desktop UI, and the operator declined to rule the product name — "that question is not for this layer" (DEC-0211).
- **R2 — the soak is one full unattended week.** "two days to a week… I think a week is enough and sufficient." The soak IS the ratified first-deploy warm-up week, run unattended on the demo account with the live binding taken at its end and the TN-23 acceptance checklist unchanged; the operator named a Prometheus/Grafana/Loki-class stack and made tracking through the week mandatory as his own requirement, delivered by the separate zero-authority observability stack (DEC-0212, DEC-0200).
- **R3 — promotion is a click, activation is a second act.** "two separate acts." Promotion rests on backtest evidence the operator has already reviewed, so the precondition battery runs silently server-side against fresh state; activation is the separate second act that starts the binding, and the agentic system's own pre-promotion paper period is outside this layer (DEC-0213, DEC-0205).
- **R4 — no paid news, ever.** "I will not pay for news." Forex Factory's free weekly file is the sole V1 news-calendar source (`COMP-CALENDAR-FEED`); no paid fallback slot exists anywhere, `news_calendar_refresh_cadence` is minted configurable, and a failed refresh fails entries closed. The later fallback is a second free source or an agent-scraped JSON in the same CT-15 intake shape (DEC-0214, DEC-0198).

Also ruled the same round and applied: the desktop UI **will** exist and the node is designed with it in mind; MIS models do not exist and must be trained (training a named follow-on, the shadow-lane seam explicit V1 node work); extensibility is registry-plus-config-plus-a-restart, never code; alpha decay stays at AD-41 primitives (DEC-0215).

## Veto round follow-up (2026-08-30)

The record above is the design as accepted on 2026-08-29 and stays immutable; this note records the operator's direct veto-round rulings of 2026-08-30 that refine it, closing the cheap-veto surface DEC-0259 attached (DEC-0261).

- **Bot journey and no per-bot warm-up (GAP-0057 answered).** A bot's backtesting, iteration and paper trading happen BEFORE promotion and OUTSIDE the node — in QMB and the research lanes — so by promotion the bot is known ready for live capital and everything on the node (bot, Book, BMS) carries the operator's approval to touch money. There is no per-bot warm-up, probation, ramp or paper lane on the node; the node's only paper semantics are the first-deployment demo-account soak week and the BMS/Book protective demotion that routes-to-paper after a drawdown or bench event (DEC-0261).
- **Next-day activation.** A bot promoted or activated during a trading day does not trade until the next trading day — activation takes effect at the next day boundary of the account-scoped day-boundary calendar the node already uses for its accounting period (TN-25) — and no manual override exists (DEC-0261).
- **Alert widening settled (narrows the proposed PRD §3 widening bullet above).** The silent-degradation class is accepted; the daily liveness digest is REJECTED, the desktop UI streaming liveness later; and the external switch is KEPT and renamed the **liveness heartbeat** — an outbound alive-ping from the node to an off-VPS free-tier watcher that is notification only, holds zero authority, and can never stop entries, close positions or touch the node. The three monitoring surfaces are declared disjoint: the liveness heartbeat answers "is the box alive" from outside; the separate Prometheus/Grafana/Loki-class stack is the engineers' logs-and-metrics view on the box; and the desktop UI's later connectivity-and-latency panel reads the node's own `/health` states and `qmn_` latency figures through the evidence channel — none replaces another and none holds authority (DEC-0261).
- **Costs and placement.** The Backblaze B2 default stands and the observability stack stays on the same VPS; the VPS is the operator's own procurement, and its minimum spec is what the node's own benchmark measures in the soak's first hours — the recorded procurement starting point (Ubuntu 24.04, about 4 vCPU, 8 GB RAM, about 100 GB SSD shared with the stack, sited near the broker's cTrader server) is engineering evidence and never a ratified value. The single-machine placement variant — the node co-located with the agentic system on one box — is deferred as GAP-0058, a roster placement change plus lifting the V1 VPS-only refusal and never a second product (DEC-0261). *Superseded in the second exchange, below: the variant is in scope and GAP-0058 is open (DEC-0262).*
- **MIS training (GAP-0051).** The plan stands as GAP-0051 records it; the training-plus-shadow-rollout epic runs OFFLINE — the operator's machine, a factory sandbox, or rented compute hours, the operator's call at epic time — MAY run in parallel on its own branch because it touches no node code until the shadow lane consumes a candidate, and its first story is research-first because the corpus names no models (DEC-0261).

The same day's second exchange refined two of the rulings above; the record and the bullets above stay as written (DEC-0262):

- **Two placement variants in scope; self-setup a requirement (GAP-0058 reopened).** The single-machine placement variant deferred in the costs-and-placement bullet is now IN SCOPE by direct operator ruling: the node co-located with the agentic system on one box as one installed QMX application a non-technical operator can set up out of the box, its backend setting itself up (installing its own dependencies, provisioning its own stores), the desktop UI later fronting an installation page or walkthrough over that self-setup, and Docker permitted wherever that variant needs it while the ratified VPS variant keeps its no-container posture (DEC-0262). It is ONE product with a second placement and never a fork: the roster's machine identity names the box and the V1 VPS-only refusal is re-scoped to refuse to compose off the machine the roster names; GAP-0058 flips deferred → open, its design — supervision without systemd, the secret store without systemd-creds host-key sealing, the powers channel without a unix socket and `SO_PEERCRED`, the observability stack's placement, and the self-setup installer — owed to a one-shot architecture increment ruled before the variant's epic while the VPS epics proceed now and are never blocked by it (DEC-0262).
- **MIS training is the last node epic, with a ratified labeler catalog (refines the MIS bullet above).** MIS training is the LAST epic under the trading node, run OFFLINE as a script the operator executes on his own machine over a few hours with data window and seed recorded and the artifact registered (DEC-0262). Its starting inventory is the labeler catalog the corpus already ratifies: six rule-based labelers (identity, spread-state, gap-event, feed-state, SQS, degraded-sensors), one fitted (`liquidity_stress_v1`, a CPU quantile fit), and one trained (`regime_classifier_v1`) that carries no ratified model family, hyperparameters, label-generation method or training location — the design story — while the recovered candidates Kronos, HMM, BOCPD and MS-GARCH carry no authority without fresh ratification, replacing the earlier increment's "the corpus names no models" note (DEC-0262).
