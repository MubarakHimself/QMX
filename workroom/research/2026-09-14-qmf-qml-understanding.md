# QMF/QML understanding for QMX planning

Read-only review of `docs/AGENTS.md`, the dependency manifest and component/contract docs, plus selected implementation files at the `integration` revision (`1b451a848d897e42f6e2c7fd9f2ea86fab7295f2`, 2026-09-04). This is an evidence map for later research prompts; it does not redesign canonical docs or claim runtime readiness.

## Toolbox versus application

The governing boundary is explicit: QMF V1 is a reusable Python toolbox, not a trading application; loops, scheduling, orchestration and product UI stay outside QMF (`docs/AGENTS.md:47`, `docs/AGENTS.md:123`). Its public roster is five libraries plus Venue and Risk modules, with internal data seams kept distinct (`docs/AGENTS.md:49`). The dependency manifest substantiates this: `qmf-core` has no dependencies; `qmf-registry` depends on core and data; `qmf-data` depends on core and the data store; indicators and structure depend on core; Venue and Risk remain core-only in the roster (`docs/architecture/dependencies.yaml:2-97`). Risk contracts are described as `defined-unwired`, and their wiring belongs at an application composition root (`docs/architecture/dependencies.yaml:87-97`).

This makes QMF the typed substrate: exact money/time/instrument values, fingerprints, refusals, producer/structure contracts, registry records, data rooms/splits/journals, and risk/Book/BMS contract shapes. It does not itself decide how a user explores hypotheses, runs a study, coordinates workers, or sees a screen. Those are application/product concerns.

QMB is the broad experimentation surface. The manifest calls it “experimentation/backtesting library + qmb CLI,” an application-layer product built on QMF, with dependencies on core, registry, data, indicators, structure and risk (`docs/architecture/dependencies.yaml:99-125`). QMB is the first sanctioned composition root for wiring defined-unwired risk contracts in `world = replay`; its outputs are CT-32 result artifacts and CT-13 journal streams (`docs/architecture/dependencies.yaml:112-125`). The integration source confirms breadth beyond a narrow runner: `qmb/src/qmb/optimize/space.py:1-29` defines identity-bearing optimization spaces over one CT-33 parameter schema; `qmb/src/qmb/orchestrator/spawn.py:1-9` owns process isolation, limits and cancellation; and the package tree includes data, execution, results, optimization and orchestrator modules. Thus QMA should be considered alongside QMB for experimentation coordination, while preserving ordinary Python and avoiding a preselected single architecture.

## QML declaration and logic

QML is a separate application-layer bot-authoring library, not a QMF roster package, framework, engine or CLI. The documented dependency is QMF core, registry and risk, never Venue (`docs/architecture/dependencies.yaml:127-160`; `docs/components/qml.md:15-20`). Its surface is intentionally thin: author-side types/helpers for CT-33 Bot definitions and CT-34 confluences, a bot runtime protocol, and a conformance gate (`docs/components/qml.md:15-20`).

A governed bot has exactly two artifacts: a structured CT-33 declaration and a versioned plain-Python logic distribution (`docs/components/qml.md:24-29`). The `.qml` DSL is not revived in V1. Plain Python remains first-class: an unregistered bot can run in QMB or research lanes without QML imports; conformance is the ticket to governed evidence and Book seats, not tunnel entry (`docs/components/qml.md:24-29`). The integration implementation matches this division. `qml/src/qml/__init__.py:1-10` describes the pure `import qml` distribution and identity via CT-33 content plus a logic source-manifest. `qml/src/qml/declaration/bot.py:1-8` says QML returns fingerprintable content while the host composition root stamps the registry envelope. `qml/src/qml/protocol/factory.py:1-7` shows host-driven construction from declaration, assignment and injected read surfaces; no Book, clock or venue command surface is injected.

QML therefore declares *what* a bot consumes and its governed parameter/footprint identity, while arbitrary Python defines *when/how* conditions are evaluated. CT-34 legs carry roles (`level | trigger | confirmation | filter`) and producer bindings; condition semantics remain in Python (`docs/contracts/ct-34-confluence.yaml`, purpose/invariants). The conformance gate is technical, not performance validation; registration and evidence citation are separate from ordinary execution (`docs/components/qml.md:24-29`).

## Shared identity, data and Book/BMS semantics

Shared identity lives in QMF’s fingerprint/registry contracts. `qmf-registry` owns every registry kind, including CT-33 and CT-34, even though QML authors their content (`docs/components/qmf-registry.md:39-48`). Records have kind-specific bodies plus common writer/sequence/envelope facts; semantic content determines `fp1`, while occurrence facts are excluded (`docs/components/qmf-registry.md:48`). This is why a changed bot declaration, producer, parameter default or logic source creates a new identity, while a seat rebinding does not.

Data semantics live in `qmf-data`: journals are read-time projections over writer-scoped streams, with explicit entity identity and role-scoped namespaces (`docs/components/qmf-data.md:103-107`). QMB reads split-governed research rooms and does not fetch providers inside a run; acquisition is a separate step (`docs/components/qmf-data.md:153-157`). This is the evidence foundation for experimentation, not merely a storage implementation.

Book/BMS authority lives in QMF Risk contracts. CT-22 is the Book definition; CT-27 is the BMS definition. The BMS is the account-facing supervising layer: one BMS instance per account can serve many Books, each Book binds exactly one BMS, and a Bot binds exactly one Book (`docs/AGENTS.md:23`; `docs/contracts/ct-27-bms-definition.yaml`, invariants). Templates are configuration artifacts: every variable has exact units/value, `ui-editable | uneditable`, and versioning; UI edits mint new versions (`docs/AGENTS.md:23`; `docs/contracts/ct-22-book-charter.yaml`). QML may author CT-22/CT-23 v2 semantics, but Risk owns the shapes (`docs/components/qml.md`, Interfaces). Bot logic never sizes or owns the full-loss price; Book resolves those meanings.

## Extensibility levels and readiness

The current design supports several distinct extension levels: (1) user-editable/versioned Book/BMS and bot declaration parameters; (2) reusable producer/confluence composition; (3) plain-Python bot logic distributions; (4) QMA/QMB host orchestration, tools and studies; and (5) future UI views/tools. These are different authorities. A new UI extension SDK is explicitly deferred in QMA (`docs/AGENTS.md:29`), while QMA’s daemon/wire/core designs provide agent ports and plugin contribution surfaces; that does not prove a UI plugin system exists.

The practical planning implication is to ask, for each proposed capability, whether it is a QMF contract/tool, a QMB or QMA application capability, a QML declaration/logic concern, a Risk-owned Book/BMS rule, or a future UI composition. Do not randomly connect packages or assume a new feature means a new database, world or architecture. The source and contracts are substantial, but many are explicitly `defined-unwired`, and the integration revision’s source presence is not evidence that the current checkout is wired, packaged, or production-ready. Implementation authorization remains factory-pipeline-only (`docs/AGENTS.md:123`).
