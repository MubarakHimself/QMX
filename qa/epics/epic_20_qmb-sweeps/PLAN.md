## 3. Risk gates and priority assertions

The epic-specific centre of gravity. A multi-route sweep's entire trustworthiness rests on **no combination being silently lost, no two combinations being confused, one frozen registry state governing them all, and nothing in the batch or its ranking ever claiming or gating edge.** One confirmed defect already breaches the first of these.

**R-004 — distinct semantic inputs ⇒ distinct `fp1`; no silent drop or overwrite (the confirmed defect, and the epic's defining risk).**
CT-05 (DEC-0108) fixes the law: the fp1 recipe makes *equal value imply equal fingerprint by construction*, and — its contrapositive on the write path — an **idempotent re-write (same hash, byte-identical content) is accepted silently, but a true collision (same hash, differing identity bytes) is refused and alarmed, never overwritten.** B-3 makes each combo's resolved-config `fp1` the **run-id root and the ledger key**; B-12 makes each combination **one isolated fully-labeled run with its own ledger line.** If two semantically-distinct combinations collapse to the same key — a truncated/lossy `fp1`, a `param-hash` with a collision, a dict/output-dir/ledger-key keyed on a lossy digest, or an as-of-set write-back that overwrites rather than refuses — then **one combo is silently dropped or overwritten by the other, and the sweep's evidence is incomplete without any refusal.**
**Confirmed advisory finding F-20-01:** the sweep drops combinations on an fp1 collision. **Covered by T20-302** (two distinct combos → two distinct fp1 run-ids; the true-collision path refuses-and-alarms, never overwrites) and pinned by **T20-PIN-01** — the pin drives two semantically-distinct combinations that the current source collapses, and asserts (a) distinct fp1 run-ids, (b) no silent drop/overwrite, (c) a genuine collision REFUSES-and-alarms per CT-05. **This pin is expected to FAIL against current source; the failure IS the finding (F-20-01), recorded — never worked around by editing source or weakening the assertion.** It **interlocks with R-010**: a dropped combo manifests as a *missing* ledger line, so the audit cross-checks **combinations-admitted == ledger-lines-written** (T20-314) as an independent detector of the same root cause, and with **T20-320** (the read-side sibling — a lost combo must never silently vanish from the ranking either).

**R-010 — exactly one ledger line per sweep run (per combo): never zero, never two.**
B-4 / B-12: the orchestrator appends **exactly ONE** ledger line per combination on completion *or* abort — a dead/cancelled process still yields an `aborted` line with refusal context, **never silently absent** — carrying the AD-12 label, the CT-32 fingerprint, the raw AD-40 measures, and the sweep coordinates. Zero lines = a dropped combo (the F-20-01 symptom); two lines = a double-count that poisons the read-time ranking fold.
**Covered by T20-314** (combos-in == ledger-lines-out; each line carries the full payload and the `{sweep_id, instrument, BarSpec, param-hash}` coordinates), reinforced by **T20-315** (an aborted/refused combo still writes its one line and the batch continues) and **T20-312** (each combo = exactly one resolved run-config whose fp1 is the run id). Because F-20-01 is real, **T20-314 is a co-detector expected to surface the same defect from the ledger-count angle** — recorded under the same finding, not invented as a second one.

**SC-11 / B-15 — one registry as-of, frozen at admission for every combination (the batch-determinism firewall).**
A sweep resolves exactly ONE as-of at batch admission through the single read port, frozen for every combination and stamped into every label; after admission fragments resolve by explicit `fp1`, never `name@latest`; a superseded ref is a stale-evidence refusal, not a silent bind of either version. If this leaks, two combos silently resolve different Book/BMS/bot versions mid-flight and the sweep is unreproducible.
**Covered by T20-307** (exactly one as-of via the single port, no second cache), **T20-308** (frozen for the whole batch; a mid-batch fresher state changes nothing; same Book → identical `fp1`), **T20-310** (superseded ref → stale-evidence refusal, no invented severity), **T20-309/T20-311** (resolve-by-fingerprint; verbatim `registry_as_of` on every combo).

**L20 / SC-06 / SC-07 — the ladder and its ranking never masquerade as edge; nothing gates money while GAP-0048/0049 are open.**
Structurally P0 across Stories 20.3–20.4: every fill carries the `optimistic` taint and no combo emits a verdict-bearing edge claim (world from provenance, never live); cross-run ranking **publishes and never acts** — no money-gating composite score, no promotion, no binding, no unbiased pass/fail verdict; and no threshold is invented (the comparison value is a configurable).
**Covered by T20-316** (world-from-provenance + optimistic taint + no edge claim), **T20-319** (ranking publishes-never-acts; taint/world carried forward; no verdict), **T20-318** (no invented threshold), and **T20-320** (a refused combo is neither dropped nor coerced to a favourable/zero score that could bias a ranking).

**OPEN OPERATOR-RULING ITEM (flagged here, recorded UNPROVEN in §7.7) — the sweep-combo ledger role.**
B-12 gives each sweep combination a ledger line but assigns it **no role**; B-4 names `role = trial`/`replicate` for optimize trials, MC/significance replicates, and walk-forward train windows, and `role = confirmation` for Book-declared-adapter confirmation runs, but is **silent on a plain multi-route sweep combo.** Whether a sweep combo ledgers as a `trial` (never bar-eligible) or could be a `confirmation` (bar-eligible under the Book-declared adapter set) is **not settled by this epic's ACs or the ratified spine — it is an open operator-ruling item.** The plan asserts only the **structural** role-discriminant + confirmation-only-fold property (T20-323) and **does not invent the answer.** Escalate to the operator; until ruled, any test asserting a specific role for a sweep combo would be testing an unratified value.

### 4.3 Contract / acceptance conformance (L3) — the T3 band, one test per P0/P1 AC

**Story 20.1 — axis declaration, Cartesian expansion, pre-flight run count**

- **T20-301** *(L3, B-12/spec R9-R13)* — expansion of a declaration `instruments[]` × `timeframes[]` (BarSpec list) × `parameters{name: values[]}` produces the **full Cartesian product**, exactly one run spec per combination, in a **deterministic declaration-order enumeration** (two expansions of the same declaration yield the same ordered list); and a **1×1×1 declaration expands to a single run spec** identical in shape to a directly-created single run. *(20.1 AC1)* **P1**
- **T20-302** *(L3, R-004, CT-05/DEC-0108)* — over a declaration whose combinations are **semantically distinct**, every combination's resolved-config **`fp1` is distinct**; **no combination is dropped or overwritten** (`len(distinct fp1) == pre-flight count`); and a **true fp1 collision** (constructed same-hash / differing-identity-bytes) is **REFUSED and ALARMED** on the write/keying path — **never silently overwritten** (an idempotent byte-identical re-write is accepted silently, the collision is not). *(20.1/20.3, CT-05 collision invariant)* **P0 — R-004**
- **T20-303** *(L3, FR-038/B-4)* — the **pre-flight run count equals the product of the axis lengths** and is returned **before any process is spawned**; the count call **spawns no process, writes no ledger line, and admits no batch** (assert the injected spawn/ledger/admission sinks are never touched) — a pure inspection. *(20.1 AC2)* **P0**
